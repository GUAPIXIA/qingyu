## 1. 架构与技术债

### 1.1 IPC 契约常量护栏（高价值，改动中等）

**现状**：channel 字符串在 `preload.ts` / `electron/ipc/*.ts` / `electron/services/ai.ts` 三处硬编码，无共享常量；`shared/ipc-api.ts` 只约束了渲染进程侧类型，主进程 `ipcMain.handle` 的 channel 不经过任何编译期校验——拼写错误只有在运行时静默失效。

**证据**：`electron/preload.ts:32-51`（ai 事件订阅）、`electron/main.ts` 中 18 个 `registerXxxIPC`、`electron/services/ai.ts:159`（`safeSend(webContents, 'ai:chunk', ...)`）。

**方案**：
1. 在 `shared/` 新建 `ipc-channels.ts`，导出全部 channel 常量（`export const IPC = { aiChunk: 'ai:chunk', ... } as const`）；
2. preload、ipc 注册、safeSend 三处改用常量；
3. 类型层面用 `as const` + 模板字面量类型，让 `safeSend`/`ipcMain.handle` 的 channel 参数在编译期可校验。

**影响面**：约 130 处字符串替换，机械但量大；需全量测试兜底。
**工作量**：1-2 天。**风险**：低（纯替换）。

### 1.2 错误处理三机制统一（中价值，改动中等）

**现状**：三种错误处理风格并存——① `main.ts` 全局包装 `ipcMain.handle`（统一 catch+日志），② `utils/safeHandle.ts` 再包装一层（25+ channel 异常记两次日志），③ 部分 handler 内部自行 try/catch 返回错误对象。日志重复、行为不一。

**证据**：`electron/main.ts:170-184`、`electron/utils/safeHandle.ts:19-29`、`electron/ipc/*.ts` 中混合风格。

**方案**：
1. 二选一：保留 `safeHandle` 并让 `main.ts` 的全局包装跳过已被 safeHandle 包裹的 channel（加标记），或统一收敛到 `safeHandle`；
2. 错误对象约定：IPC 响应统一 `{ ok: true, data } | { ok: false, error }`（或维持抛错+全局 catch），渲染进程 `window.api` 包装层统一解包；
3. `friendlyError` 映射集中管理。

**工作量**：1 天。**风险**：中（涉及渲染进程调用方约定，需同步改 preload 包装）。

### 1.3 单聊/群聊双轨合并（评估完成：暂缓合并，先共享增量）

**现状**：`useChatStore` 与 `useGroupChatStore` + `streamController` + `groupStreamController` 大量逻辑复制（消息发送、流式处理、上下文构建、记忆压缩），累计 2000+ 行重复。

**评估结论（2026-08-06）**：已抽取共享 `streamAIResponse`（单聊）与 `groupStreamController`（群聊）各自的流式管线；差异点（消息路由、speaker 选择、轮询策略、批次保存）占比约 40%，完全合并需 3-5 天且核心路径风险高。**建议**：合并为「流式会话引擎」前，先做**增量共享**——把双方相同的部分（上下文构建、正则清洗、记忆压缩触发）逐个收敛到共享模块（`chatContext` 已部分完成），以低风险方式逐步减少复制；完整合并作为独立排期的重构项。

**工作量**：增量共享 1-2 天（低风险）/ 完整合并 3-5 天（高风险，需集成测试）。

### 1.4 数据迁移双轨（低优先，改动小）

**现状**：settings 迁移有两套实现——主进程 `storage.ts` 的 `migrateData`（读文件时迁移）与渲染进程 `useSettingsStore` 内部迁移逻辑，行为可能分叉。

**证据**：`electron/services/storage.ts`（`migrateData`）、`src/store/useSettingsStore.ts`（loadSettings 内迁移）。

**方案**：统一到主进程 `migrateData`（单一事实源），渲染进程删除自建迁移；migration 版本号收口到 shared 常量。

**工作量**：0.5 天。**风险**：低。

### 1.5 validatedPaths 只增不删（低优先，改动小）

**现状**：`electron/ipc/file.ts:24` 的 `validatedPaths` Set 只 add 不 delete，长时间运行累积对话框选择过的路径（含已删除文件）。

**方案**：每次 `font:save`/`file:readImageBase64` 成功后 delete；或在应用退出时清空（内存数据，泄漏量级很小）。

**工作量**：0.5 小时。**风险**：无。

### 1.6 注册器散落（低优先，改动小）

**现状**：`registerAIIPC` 定义在 `services/ai.ts`（而非 `ipc/`），`app:checkVersion` 挂在公告模块；`main.ts` 手动列举 18 个注册器，新增容易漏。

**方案**：ipc 目录统一放注册器；main.ts 用目录扫描或显式清单 + 启动时校验（注册数不匹配报错）。

**工作量**：0.5 天。**风险**：低。

### 1.7 巨型文件拆分（部分完成，继续推进）

**现状**：`MessageBubble.tsx` 约 36KB、`useChatStore.ts` 约 40KB、`ChatPage.tsx` 较大——单文件职责过多，维护成本高。

**已做（2026-08-06）**：`useChatStore` 三个生成类方法（regenerate/continue/swipe，233 行）提取至 `src/store/chatGeneration.ts`（set/get 闭包模式），store 从 1017 行降至约 784 行。

**后续**：`MessageBubble` 的操作栏（用户/AI 两处）与气泡状态（流式/翻译/编辑）交织，提取需精确复制 JSX，建议专项拆分（先提取操作栏组件，再提取编辑表单）；`ChatPage` 可拆消息列表/输入区。

**工作量**：1-2 天/文件。**风险**：低（有测试兜底）。

### 1.8 主进程 strict ✅（已核实）

`tsconfig.electron.json:9` 与 `tsconfig.json` 的 `strict` 均为 `true`，无需改动。

## 2. 打包体积

### 2.1 已完成项 ✅（v0.11.17）

- `sourcemap: 'hidden' → false`：dist 从约 7MB → 1.25MB（不再产出 5MB+ .map）
- `react-dev-locator` 仅 dev 注入
- 14 个非首屏页面路由懒加载：主包 ~2MB 单 bundle → 865KB + 14 个按需 chunk（5.9~88.6KB/页）

### 2.2 tiktoken 冗余（中价值，需验证）

**现状**：`tiktoken`（约 15-18MB 安装体积）被用于 token 计数；`shared/types.ts` 中 `countMessagesTokens` 是主进程能力。若实际只在 `countTokens`/`embedding` 路径使用，且对计数精度要求不苛刻，可替换为 `gpt-tokenizer`（纯 JS，<1MB）或服务端计数降级。

**注意**：替换前需对比计数误差对 context 裁剪的影响（低估会超 context 上限）。属**实验性优化**，需基准测试。

**工作量**：1 天 + 验证。**风险**：中（行为变化）。

### 2.3 electron 产物瘦身（中价值，改动小）

**现状**：`electron-build.mjs` 打包 asar 时直接包含 `node_modules`（含 devDependencies？需确认 prune 配置）；可检查 asar 内容，确认 `node_modules/.pnpm` 缓存、测试文件、`__tests__` 未被带入。

**方案**：`electron-builder` 的 `files` 白名单 + `asarUnpack` 精准控制；构建前 `npm prune --production`（或 pnpm deploy）。

**工作量**：0.5 天。**风险**：低（打包配置）。

### 2.4 manualChunks 细分（低优先）

主包 865KB 中 tiktoken/语法高亮等大依赖可进一步拆 vendor chunk 提升缓存命中。收益边际（本地 file:// 加载无网络），可选。

## 3. 群聊性能

### 3.1 已完成项 ✅（v0.11.17）

- 轮询循环不再每 2s 全量保存群组文件（`currentSpeakerIndex` 纯运行时化）

### 3.2 saveMessage 批量写入（高价值，改动中）

**现状**：群聊流式（及自由发言拆分 `splitAndSaveMessages`）对每条消息单独调用 `window.api.group.saveMessage` → 主进程 `appendFileSync` 逐条写 + 每轮 `writeMessages` 全量重写 sessions。一次回复 3-5 条消息 = 3-5 次 IPC + 文件写。

**证据**：`src/store/groupStreamController.ts:967,983`（`savePromises.push`）、`electron/ipc/group.ts`（saveMessage）。

**方案**：新增 `group:saveMessagesBatch`（一次 IPC 批量追加 + 一次 sessions 更新），`splitAndSaveMessages` 与流式收尾改用批量接口；单聊的 `saveMessage` 同理可加 `chat:saveMessagesBatch`。

**工作量**：0.5-1 天。**风险**：低（新增接口，不动旧接口）。

### 3.3 GroupChatPage 选择器订阅（中价值，改动小）

**现状**：与 ChatPage 修复前同款问题——`GroupChatPage` 全量订阅 `useGroupChatStore`，群聊流式时整页重渲染；群聊还有 2s 轮询驱动的状态更新。

**方案**：复用 ChatPage 的拆分模式（每字段一个选择器调用）；成员栏/消息列表用 `React.memo`。

**工作量**：0.5 天。**风险**：低。

### 3.4 群聊轮询间隔可配置下限（低优先）

`speakerInterval || 2000` 无下限校验，用户可配 0 → 忙轮询。加 `Math.max(500, ...)`。

**工作量**：5 分钟。**风险**：无。

## 4. server 路由测试落地

### 4.1 现状与根因

`server/app/__tests__/announcements.test.js`、`version.test.js` 等使用 `describe.skipIf(!expressAvailable)` —— **express 不在 pnpm workspace 依赖中**，测试在本地与 CI 全部静默跳过（CI 假绿），server 路由覆盖率为 0%。

**证据**：`server/app/__tests__/announcements.test.js:17-20`、`pnpm-workspace.yaml`（仅 src/electron）。

### 4.2 方案 A：workspace 纳入 server（推荐）

1. `pnpm-workspace.yaml` 增加 `server` 包；
2. `server/package.json` 声明 express/cors/jsonwebtoken/bcryptjs 等依赖（与主 package.json 去重或独立）；
3. `vitest.config.ts` 的 include 已含 `server/**/*.test.js`，测试自动跑起来；
4. 验证：本地 `vitest run server` 通过 → CI 自然生效。

**影响**：让现有 4 个测试文件（announcements/auth.middleware/auth.route/sanitize/version）真正执行；为 server 后续改动提供回归网。
**工作量**：0.5-1 天。**风险**：低（依赖声明 + workspace 配置，不影响主应用运行）。

### 4.3 方案 B：仅测试期安装（备选）

CI 在 test job 前 `pnpm add -D express ... --filter root` 或 `npm i --no-save`——治标不治本（本地仍跳过）。不推荐。
