# 轻语安卓端完善路线图

> 编制日期：2026-08-19 · 二次核验：2026-08-20（全仓扫描：`酒馆 0.11.28→0.12.0` / `android 0.1.5 build 6` / `server`）  
> 代码基线：Android `0.1.5`（build 6，`gradle/libs.versions.toml` 权威）· PC `0.11.28` 已冻结  
> 适用范围：`android/` 安卓伴侣端及其依赖的 `酒馆/electron/bridge/` PC 桥接层 · 关联：`酒馆/docs/PC端0.12版本实施方案.md` / `PC端0.12版本任务清单.md` / `android/README.md`

> **二次核验结论（2026-08-20 全量扫描）**：本文 P0 六项经 `android/app/src` 实码抽检全部命中，仍为 0.1.4 阻塞项；0.1.5 已部分收口（WS token 改 Header、心跳回归、Fake 签名补齐），但 `scheduleFlush 覆盖 / sending 永久卡死 / 导航丢 memberNames / retry 丢 replyToId / usesCleartextTraffic / 明文 DataStore` 仍必现。本次更新仅收敛漂移与排期，不推翻原 P0 判定。

## 1. 结论

当前安卓端已经具备比较完整的伴侣端骨架，不需要推倒重做。扫码/手动配对、多 PC 管理、会话与角色、单聊、图片、TTS、Markdown、快捷设置、长记忆、群聊、公告和用量页均已有代码实现。

下一阶段建议将目标从“继续堆功能”切换为“做出一个能长期日用的稳定版本”：

1. 先恢复绿色工程基线，修复流式输出、群聊状态和导航数据丢失等真实闭环问题。
2. 再提升弱网、后台、进程被杀后的可靠性，让消息做到可追踪、可恢复、不重复。
3. 随后补齐安全、通知、草稿、分享、搜索和自适应布局等移动端能力。
4. 最后再考虑公网中继、语音输入、桌面小组件等增量功能。

建议将近期里程碑定义为 `0.1.4 稳定性版`，而不是继续以“大功能版”为目标。

> **与全仓协同（新增）**：PC `0.12.0` 正以 `ChatOrchestrator + TaskStore(requestId幂等) + EventLog(sequence)` 统一双链路。安卓的 `持久化发件箱 + sequence 补拉` 是其镜像；0.1.4 必须先把 `流式/发件箱/切换 PC 串台` 修通，否则 PC M3 真机联调（`V12-09-5 同一 fixture 在 v1/v2 下一致`）无法通过。0.1.4 是 PC 0.12 的前置门禁。

## 3. P0：`0.1.4` 稳定性版必须先完成

### 3.1 恢复绿色构建

现状（二次核验）：

- `ChatRepository` 的记忆和上下文接口新增了 `characterId` 参数，`ChatViewModelTest.kt` 的 Fake 在 0.1.5 已补齐，但新增 `getSessionMemory` 后需再次同步。
- `lintDebug` 在 `ExoPlayerTtsPlayer.kt` 仍报 4 个 `UnsafeOptInUsageError`（`import androidx.media3.exoplayer.ExoPlayer` 无 OptIn）。
- Lint 还报告 Locale、备份规则、扫码页方向限制、Compose Modifier 顺序、单色图标等问题。

建议：

- 修正全部 Fake/测试夹具，禁止通过删除测试或加全局 Lint baseline 掩盖新增错误。
- 对 Media3 用法做局部 `@OptIn(UnstableApi::class)`，并为播放失败、401、断网补测试。
- 收敛现有 10 个 Warning；确需保留的规则逐条写明原因。
- 建立统一命令：`testDebugUnitTest + lintDebug + assembleDebug`，任何一项失败都不可发布。

验收标准：三个命令在干净环境中全部通过。

### 3.2 修复流式文本跨批次覆盖

位置：`ui/chat/ChatViewModel.kt:513 scheduleFlush()`。

当前每 100ms 将 `chunkBuffer: LinkedHashMap<requestId,StringBuilder>` 清空，然后用本批 `snapshot` 直接替换 `Streaming.Generating(requestId, text)`。当一次回复经历多次 flush 时，界面只保留最新一批增量，而不是完整累积内容（`handleEvent:474 getOrPut` 仅缓冲，未累加展示）。

建议把流式状态设计为明确的 request 状态机：

```text
Idle -> Sending -> Streaming(accumulatedText) -> Completed
                                      \-> Failed(retryable)
```

每次 flush 应 `accumulated += snapshot` 后再写入 `Generating`；`done/error/stop` 必须清理对应 `requestId` 缓冲，不能影响其他请求。建议先为“3 次 flush 累加”写失败单测，再修。

验收标准：构造至少 3 次、每次间隔超过 100ms 的 chunk，最终流式文本和 `done` 消息内容完整一致。

### 3.3 修复群聊发送后永久“发送中”

位置：`ui/groups/GroupChatViewModel.kt:60 send()`。

成功分支将 `sending` 设为 `true` 后调用 `load()`，但 `load()` 没有恢复 `sending=false`（`_ui.copy(loading=false)` 仅清 loading）。首次成功发送后输入区永久 `sending=true` 且不能再次发送。

同时，`groupAiReply()` 的失败被外层 `runCatching` 吞掉，用户无法判断是用户消息发送失败、AI 生成失败，还是刷新失败。

建议：

- 在 `finally` 中保证 `sending=false`（或 `load()` 内同步复位）。
- 将“用户消息落盘”和“AI 回复生成”拆成两个可见状态（`sending` vs `generating`）。
- 保留失败原因并提供“重试 AI 回复”，不要重复发送用户消息。

验收标准：连续发送两轮成功；AI 回复失败时用户消息不重复，并能单独重试 AI。

### 3.4 修复群聊成员名称在导航中丢失

位置：`ui/navigation/CompanionNavHost.kt:113` + `Routes.kt:46`。

`GroupsScreen` 已将 `memberNames: Map<String,String>` 传给导航回调，但 `Routes.groupChat(groupId,groupName,sessionId)` 签名无此参数，目标页固定以空 Map 构造 `GroupChatViewModel`，因此群聊消息中的角色名退化为 `characterId.take(6)`，@提及候选也为空。

建议不要把整张 Map 塞入字符串路由。目标页应依据 `groupId` 从 Repository/ViewModel 重新加载群组与角色，再构造成员映射；这样也能应对成员在页面存活期间发生变化。

验收标准：冷启动、返回重进、进程恢复后三种路径均显示正确角色名和提及候选。

### 3.5 修复弱网重试语义丢失

位置：`model/ChatTimeline.kt:14 PendingMessage` + `ui/chat/ChatViewModel.kt:331 retryPending()`。

当前 `PendingMessage` 只保存 `requestId/content/timestamp/failed/images`，没有保存 `replyToId`。`doSend` 时虽传入 `replyTarget?.id`，但 `retryPending` 固定以 `replyToId=null` 重发 `repository.sendMessage(..., null, pending.images)`，引用语义丢失。

建议把待发消息作为完整命令持久化（为 4.1 Outbox 做准备）：

```text
requestId + sessionId + content + images + replyToId + createdAt + retryCount + state
```

验收标准：引用回复在断网、重连、进程重启后的重试中仍指向原消息。

### 3.6 对齐版本、README 和真实能力

目前仍存在文档漂移（二次核验）：

- `gradle/libs.versions.toml` 已升至 `0.1.5/6`，`android/README.md` 顶部仍写“当前版本 0.1.1（build 2）”。
- README 的待办仍称群聊依赖桥接端点，但 `electron/bridge/routes.ts:1191-1450` 已实现 58 个路由中的群聊全量（建群/加人/会话/消息/TTS）。
- 早期的 `docs/安卓端功能缺失分析.md` 中，快捷设置、长记忆、AI 续写/润色、清空对话等多项“缺失”已经落地，但未归档。

建议把本路线图作为新的执行基线，并在每次版本发布时由同一发布任务同步：`libs.versions.toml` → `android/README.md` → `android/CHANGELOG.md` → `酒馆/README.md` 顶栏版本 + 协议 `apiVersion`。

## 4. P1：可靠性与安全

### 4.1 持久化发件箱（拆为 B1，两步走）

当前待发送/失败消息只存在 `ChatViewModel.pending` 内存中，App 被系统回收、切换会话或崩溃后会丢失；图片以 base64 长期驻留 Compose state。

**B1-1（0.1.4 必做，1-2d）**：先补 `replyToId` 内存修复（3.5），打通引用重试。

**B1-2（0.1.4-0.1.5，1w）**：再迁 Room `outbox` 表，由 Repository 统一维护：

- `queued`：等待网络；
- `sending`：已提交请求；
- `awaiting_ai`：用户消息已落盘，等待 AI；
- `completed`：收到 done；
- `failed`：保留错误和重试次数。

依靠 `requestId` 幂等（对齐 PC `TaskStore` 的 `findByRequestId`），恢复连接后安全续传。图片先落临时文件（`ImageUtils` 已有压缩逻辑），不要把大尺寸 base64 长期放在 Compose state 或数据库字符串中。

> 与 PC 0.12 对齐：PC `TaskStore: queued->preparing->streaming->finalizing->completed` + `EventLog(sequence)` 即安卓的镜像；两端同用 `requestId + sequence` 补拉语义。

### 4.2 生命周期感知与后台策略

当前页面普遍使用 `collectAsState()`，建议改为 `collectAsStateWithLifecycle()`，避免页面进入后台后仍无必要地收集和重组。

同时明确产品策略：

- 前台：保持 WS，正常流式接收；
- 短时后台：允许连接继续一段时间；
- 长时后台：主动断开，由系统通知或回到前台后恢复；
- 生成中的任务：在通知中展示“生成中/已完成/失败”，可点击回到对应会话。

不要用永久前台服务维持空闲 WebSocket；仅在用户明确发起且尚未完成的长任务中考虑短期使用。

### 4.3 连接安全分级（0.1.5 已修一半，剩余放 B2）

**已修复（0.1.5 CHANGELOG 验证）**：WS token 改 Header `Authorization: Bearer`、公网强制 HTTPS/WSS、应用层心跳 `CONNECTION_HEARTBEAT->PONG`。

**仍未收口**：`AndroidManifest.xml: usesCleartextTraffic=true` 全局明文、REST 仍允许 `http://` 回退、token 明文 JSON 存 `DataStoreConnectionStore: companion_connections`、`Room cached_messages` 含聊天明文。

建议按两种模式设计：

| 模式 | 用途 | 安全策略 |
| --- | --- | --- |
| 局域网模式 | 同 Wi-Fi 或 Tailscale/ZeroTier | 明确标注“局域网连接”；限制可访问主机和重定向；WS 已改 Header |
| 远程安全模式 | 公网域名/自建中继 | 强制 HTTPS/WSS；证书校验；禁止明文回退；关闭 `usesCleartextTraffic` |

其他建议（B2）：

- token 使用 Android Keystore 包装密钥后加密落盘。
- Room 中包含聊天明文，可提供“应用锁/生物识别”和“离开后台后隐藏最近任务预览”。
- 真正的服务器公钥指纹与当前随机 UUID 设备标识分开命名，避免形成错误的信任感。
- Release 禁止固定 `debugLog=true`，敏感 URL、query、token 和消息正文不得进入日志。

### 4.4 网络错误统一建模

当前部分 Repository 方法用 Boolean 或 null 吞掉异常，例如快捷回复、群聊 AI 回复和版本请求。建议统一为领域错误：

```text
Unauthorized / IncompatibleVersion / Offline / Timeout /
ServerRejected(code, message) / ParseError / Unknown
```

UI 再根据错误决定“重新配对、升级 PC、重试、离线查看或报告问题”，避免所有失败都变成泛化提示。

### 4.5 API 契约自动校验（先做 Fixture，再做 capabilities）

Kotlin DTO 与 TypeScript 桥接响应目前靠人工对齐，测试 Fake 的签名漂移已经证明该方式容易失效。

**优先级调整（二次核验新增）**：先做最止血的 `Fixture 驱动 Contract Test`，再做能力协商：

1. PC `electron/bridge/routes.ts` 固定响应 JSON → Android `model/ApiDtos.kt` 反序列化测试（含新增/缺失字段兼容）；
2. WS `WsEnvelope/WsEvents.AI_CHUNK etc.` fixture 双端共用；
3. `apiVersion` 先冻结为 `1`，待 PC `shared/chat-core/capabilities.ts` 冻结后再升级为 `capabilities: [group_ai, memory_v2, tts_range]`。

能力探测比“API v1 全有或全无”更适合当前快速演进阶段，但不应阻塞 0.1.4 的 Fixture 测试。

### 4.6 媒体与重连补充（二次核验新增）

- **图片**：补 `FileProvider + 压缩 + EXIF 清理`，大图先写临时文件再发，避免 `MessageImages` OOM；`NetworkModule.wsUrlOf` 对公网禁止 `http` 回退。
- **WS 重连**：`WsClientImpl: H-17/M-32` 已修切换 PC 串台与线程可见性，需补“多 PC 列表 + 指数退避上限 30s”的并发测试。

## 5. P1：移动端体验

### 5.1 启动与导航

- 已有有效连接时直接进入会话列表，连接失败再显示可恢复状态，不必每次以配对页为起点。
- 保存最近打开的会话，支持冷启动恢复。
- 使用 SavedStateHandle 保存输入、弹窗和分页游标等关键状态。
- 统一路由参数编码；角色名、群聊名等展示数据不应成为数据源。

### 5.2 草稿、分享与搜索

建议优先补三项高频能力：

1. 每会话草稿自动保存，发送后清除。
2. 单条消息分享、复制为纯文本/Markdown；整段会话导出并调用系统 Share Sheet。
3. 会话、角色和消息搜索；先做端侧已缓存数据，再扩展 PC 全量搜索接口。

### 5.3 通知

通知应围绕用户发起的任务，而不是做泛化推送：

- AI 回复完成；
- 长记忆总结完成/失败；
- 连接失效，需要重新配对；
- PC 端出现需要手机确认的安全事件。

Android 13+ 动态申请通知权限，并提供通知总开关、内容隐藏和免打扰策略。

### 5.4 自适应布局与输入体验（0.1.4 仅修阻塞项）

当前部分布局使用固定宽度，例如消息气泡最大 `312dp`，群聊输入框仅占 `60%`。在小屏、平板、横屏和大字体下容易出现空间浪费或拥挤。

**0.1.4 仅修**：输入框被键盘遮挡（IME Insets）、`312dp` 在小屏溢出两项；**双栏/窗口尺寸类/回到底部按钮** 放 C 阶段。

建议（C 阶段）：

- 手机使用单栏，平板使用“会话列表 + 对话”双栏。
- 宽度基于窗口尺寸类和可用空间计算，不绑定单个 dp 常量。
- 输入框支持键盘发送、换行策略、附件预览和失败图片重选。
- 流式时提供“回到底部”按钮；用户上滑阅读历史后不要强制抢滚动位置。

### 5.5 无障碍与资源化（C 阶段）

目前 `strings.xml` 基本只有应用名，大量中文文案硬编码在 Compose 中。

**0.1.4 不做全量资源化**，仅保证新增文案走 `strings.xml`；存量硬编码放 C 阶段统一迁移：

- 将用户可见文本迁移到 string resources，为简繁体或英文留出空间。
- 检查 contentDescription、TalkBack 顺序、触控目标最小尺寸、颜色对比度。
- 支持系统字体缩放到 200%，同时测试大字体下的底部面板和输入栏。
- 补 adaptive icon 的 monochrome 资源和 Android 12+ 数据提取规则。

## 6. P2：功能增强

完成稳定性和安全基线后，再按真实用户反馈选择以下能力：

| 功能 | 价值 | 前置条件 |
| --- | --- | --- |
| 语音输入 | 移动端高频，实施成本较低 | 权限与隐私说明 |
| 拍照发送 | 比仅相册选图更符合手机使用 | FileProvider、图片压缩与 EXIF 清理 |
| 对话分支 | 高级用户价值高 | PC 桥接层分支 API（已具备 `branchSession`） |
| 上下文预览 | 便于调试世界书/记忆/预设 | 上下文只读 API、敏感信息脱敏 |
| 群聊 @角色与手动点名 | 提升群聊可控性 | 成员映射和 group AI 状态先稳定（依赖 3.4） |
| 角色/会话置顶与筛选 | 数据量增加后价值明显 | PC 与 Android 排序语义统一 |
| 公网中继 | 跨网络体验最佳 | 端到端安全、账号体系、运维成本评估 |
| 桌面小组件/快捷方式 | 快速进入常用角色 | 核心稳定后再做 |

不建议近期在安卓端内置本地大模型推理。项目当前定位是 PC 伴侣端，过早加入本地推理会显著增加模型管理、存储、功耗、兼容性和隐私支持成本。

## 7. 工程化建议

### 7.1 测试金字塔

建议按风险而不是按文件数量补测试：

**JVM 单元测试**

- 流式 chunk 跨多次 flush 的完整累积（先写失败用例）；
- done/error/stop 乱序与重复事件；
- pending 引用回复重试（含 `replyToId`）；
- 群聊发送状态复位和 AI 单独重试；
- DTO 兼容新增/缺失字段；
- Room 裁剪、孤儿清理和 outbox 恢复。

**Compose/UI 测试**

- 未配对 → 配对 → 会话列表 → 发消息的主路径；
- 401 重新配对；
- 断网离线缓存；
- 大字体、深浅主题、横屏；
- 权限拒绝后的扫码、通知、相册行为。

**PC/Android 契约测试**

- 用桥接层 fixture 驱动 Android DTO（优先）；
- 用固定事件序列验证 REST 落盘与 WS 完成事件的一致性；
- 每个 capability 至少一个成功和一个不支持用例（待 PC capabilities 冻结）。

### 7.2 CI/CD

最低流水线建议：

```text
PR: testDebugUnitTest -> lintDebug -> assembleDebug
Tag: clean -> test -> lint -> assembleRelease/bundleRelease -> 签名 -> 生成校验值 -> 发布
```

Release 还应开启 R8/资源压缩，维护 ProGuard 规则，使用独立签名密钥和安全的 CI Secret。版本号、更新日志、APK/AAB、SHA-256 校验值应由同一发布任务生成，减少手工漂移。`0.1.5→0.1.6` 起建议开启 `isMinifyEnabled=true` 并补充 `proguard-rules.pro`。

### 7.3 架构演进

当前手动 `AppContainer` 对 1.2 万行规模仍可接受，不必为了“现代化”立即引入 Hilt 或大规模多模块重构。

更值得先做的是：

- 将网络 DTO、数据库实体、领域模型继续分离；
- 将每项操作的状态和错误集中在 ViewModel/Reducer 中；
- Repository 不再用 Boolean/null 吞异常；
- 网络客户端按连接复用（`ConnectionManagerImpl.cachedApi` 已做），并为切换 PC、登出和进程恢复写并发测试；
- 当功能继续增长时，再拆为 `core-network`、`core-data`、`feature-chat`、`feature-group`。
