## 三、详细方案

### 1️⃣ 上下文溢出压缩（P0）

**现状问题**
- `buildContext` 按 token 预算从最新往回装历史，**超预算的旧消息直接丢弃**，长对话（尤其 1M 上下文外的更早部分）前期内容完全丢失
- 用户无感知：不知道哪些内容被裁掉了

**目标**
- 当历史裁剪不可避免时，先用 AI 把"将被丢弃的旧消息"压缩成摘要（数百 token），替换原始消息参与上下文
- 与周期性的长记忆摘要互补：记忆是"定期快照"，压缩是"边界兜底"，两者不冲突

**方案设计**
```
buildContext 历史裁剪流程改造：
1. 预算计算 → 从最新往回装，发现装不下（存在被丢弃消息）
2. 检查会话是否已有"压缩摘要"（session.compressedSummary，新字段）
3. 若有 → 直接注入（0 成本）；若无 → 标记"需要压缩"（不阻塞本轮生成）
4. 本轮生成完成后（或空闲时），异步对"将丢弃的最早 N 条"发起压缩调用
5. 压缩结果存 session.compressedSummary，下次构建上下文时注入
```

**关键点**
- 压缩是**异步 + 延迟**的：不阻塞当前请求（第一轮先丢弃，压缩完成后轮生效）
- 提示词复用 `parseMemoryResult` 的结构化输出（【摘要】+【事实】），但不写回 `memoryFacts`（避免与长记忆双写冲突），独立字段 `compressedSummary` + `compressedRange`（记录压缩覆盖的消息时间范围，避免重复压缩）
- 注入位置：system 末尾，与【对话历史摘要】并列但标注【早期对话压缩摘要】
- 预算：复用 `fitMemoryBudget`（摘要占 ≤ 400 token）
- 开关：Settings 加 `contextCompression.enabled`（默认开），可设置压缩触发阈值（如"历史裁剪量 > 2000 token 时才压缩"）

**涉及文件**
- `shared/types.ts`（ChatSession.compressedSummary / compressedRange + Settings 配置）
- `src/store/useChatStore.ts`（buildContext 注入 + 压缩调度）、`src/store/useGroupChatStore.ts`（群聊同步）
- `electron/ipc/chat.ts`（updateSession 已支持通用字段，无需新增 IPC）
- `src/utils/memory.ts`（复用解析）

**验收**
- 长对话跨 200 轮：早期消息被压缩为摘要注入，且关键人物/地点仍可被模型回忆
- 压缩只执行一次（compressedRange 防重复），修改历史后缓存失效重建
- 关闭开关后行为回退为"直接裁剪"

**工作量**：中（2~3 小时）

### 2️⃣ 记忆事实向量检索注入（P0）

**现状问题**
- `memoryFacts` 全量注入（上限 30 条），会话越久事实越多，与当前话题无关的事实长期占用预算（每次最多 800 token 预算里被无关事实挤占）
- 1.4 的嵌入服务（Ollama/OpenAI）已就绪但只用于世界书

**目标**
- 按当前对话语义，只注入相关事实（topK 3~5 条）

**方案设计**
```
1. 事实向量化：triggerMemorySummary 保存 memoryFacts 后，批量嵌入并存 session.factsVectors（JSON：事实文本 → 向量）
2. 构建上下文前：对"扫描文本"（同 1.4 语义扫描的文本）嵌入，余弦 topK(3)
3. 注入仅命中的事实（【关键事实】段只含相关项）；未启用嵌入服务时回退全量注入
```

**关键点**
- 复用 `electron/services/embedding.ts` + `vectorStore` 的存储模式（按会话存向量）
- 事实变更（重新总结）时向量需重建——用 `memoryUpdatedAt` 作缓存失效键
- 与 1.4 的语义触发共用同一嵌入配置（Settings.semanticTrigger），不新增配置面

**涉及文件**
- `electron/ipc/embedding.ts`（新增 sessionFact 相关 IPC 或复用 semanticSearch 改造）
- `src/store/useChatStore.ts` / `useGroupChatStore.ts`（注入前检索）
- `src/utils/memory.ts`（工具）

**验收**
- 100 条事实中，"询问角色伤势"时只注入伤势相关事实
- 嵌入服务不可用时行为与现状一致（全量注入）

**工作量**：中（3 小时）

### 3️⃣ 上下文上限预警（P1）

**现状问题**
- 历史塞满预算后静默裁剪，用户不知道"对话已经很长、即将丢内容"

**目标**
- token 用量达到阈值时，在聊天区顶部/快捷设置显示预警条，附"立即总结 / 清理历史"操作

**方案设计**
```
- buildContext 返回 usedTokens/budgetBase 的比值（store 缓存 lastContextUsage）
- 聊天页轮询或流式完成时检查：≥ 85% 显示琥珀色预警条，≥ 100% 红色
- 预警条操作：一键触发长记忆总结、一键清理历史（clearChat）、打开快捷设置
```

**涉及文件**
- `src/store/useChatStore.ts`（缓存用量）、`src/pages/ChatPage.tsx`（预警条）、`ContextViewer.tsx`（已有用量展示，可复用样式）

**验收**：长对话中预警条出现时机与预期一致，操作可直达

**工作量**：小（0.5~1 小时）

---

### 4️⃣ 会话标题自动生成（P1）

**现状问题**
- 新会话标题为"新对话 N"，多会话时难以区分

**目标**
- 会话产生 ≥ 4 条消息后，用 AI 生成 ≤ 20 字标题并持久化

**方案设计**
```
- 触发：sendMessage 后检测（title 以"新对话"开头 且 消息数 ≥ 4 且 未生成过）
- 复用流式 AI 调用（参考 handleAiTranslate 模式），system 提示："为以下对话生成 2~8 字中文标题，只输出标题"
- 成功 → renameSession 持久化；失败静默，不重试
- 开关：Settings.autoTitle（默认开）
```

**涉及文件**
- `src/store/useChatStore.ts`、`src/components/chat/ChatHeader.tsx`（显示已有，无需改）

**验收**：新会话第 4 条消息后标题自动更新

**工作量**：小（1 小时）

### 5️⃣ 单聊引用回复（P1）

**现状问题**
- 群聊已有 `replyToId` 引用，单聊没有；长对话中"回复上一条"需要手动复制内容

**目标**
- 单聊消息 hover 出现"引用"按钮 → 输入框上方显示引用条（同群聊交互）→ 发送时消息携带 `replyToId`

**方案设计**
- `Message` 增加 `replyToId?`；发送链路透传；`MessageBubble` 显示被引用消息摘要（点击跳转）
- 上下文构建时引用内容不额外注入（消息本身可见），仅 UI 层展示
- 复用群聊 `GroupChatInput` 的引用条交互样式

**涉及文件**
- `shared/types.ts`、`MessageBubble.tsx`、`ChatInput.tsx`、`ChatPage.tsx`、`electron/ipc/chat.ts`（saveMessage 已透传全字段）

**验收**：引用后发送，气泡内可看到被引用内容摘要并可点击定位

**工作量**：中（2 小时）

### 6️⃣ 生成中实时 token / 成本估算（P2）

**现状问题**
- 生成时看不到消耗，只有完成后 usage 统计

**目标**
- 流式中显示：已接收 token（累计）+ 预估本轮总消耗（system+历史已精确计数，输出按当前速率外推）

**方案设计**
- 复用 `countMessagesTokens`（已有 IPC）精确计算 prompt 侧；输出侧按 `accumulated.length / 平均字符每 token` 估算
- 显示位置：流式状态区（发送按钮旁），完成后定格为最终 usage

**涉及文件**
- `src/components/chat/ChatInput.tsx` 或 `MessageBubble.tsx` 流式区、`useChatStore`（暴露累计）

**验收**：流式中数字实时增长，完成后与 usage 记录一致

**工作量**：小（1 小时）

### 7️⃣ 消息全文搜索（P2）

**现状问题**
- 长对话/多会话无法搜索"某角色说过什么"

**目标**
- 单聊：当前会话内全文搜索（高亮定位）；群聊：同
- 进阶（可选）：跨会话搜索（扫描 chats/*.jsonl）

**方案设计**
- 会话内：渲染层对已加载 messages 做过滤（含正则高亮），无需 IPC
- 跨会话：主进程 `chat:searchMessages(characterId, query)`，流式读 jsonl 匹配（复用 `countLines` 的分块读取思路）

**涉及文件**
- `src/pages/ChatPage.tsx`（搜索栏）、`electron/ipc/chat.ts`（跨会话）、`MessageBubble`（高亮）

**验收**：输入关键词即时过滤定位；跨会话搜索返回命中列表

**工作量**：中（2~3 小时，先做会话内）

**涉及文件**
- `src/components/chat/MessageBubble.tsx`

**验收**：3 个候选可一次对比选择

**工作量**：小（1 小时）

### 9️⃣ 自动朗读（P3）

**现状问题**
- TTS 需手动点击朗读

**目标**
- 设置开关：AI 回复完成后自动朗读（仅最新回复），手动停止后本轮不再自动播

**方案设计**
- 复用现有 `tts.speak`，流式 done 后触发；开启"自动朗读"且当前无播放时朗读

**涉及文件**
- `useChatStore`（done 回调）、`Settings`（autoTTS 开关）、`src/components/chat/MessageBubble.tsx`（播放状态）

**验收**：开关开启后回复自动朗读，可手动打断

**工作量**：小（0.5~1 小时）

### 🔟 剧情线索追踪面板（P3，探索性）

**现状问题**
- 记忆事实是纯文本，无法快速回顾"谁/在哪/目标/约定"

**目标**
- 基于 memoryFacts 构建结构化"剧情档案"面板：按类别（人物/地点/目标/物品/约定）分组展示，点击事实跳转到相关消息

**方案设计**
- 记忆总结时要求模型输出**分类事实**（扩展【事实】格式：`[人物] 妹妹叫小美`）
- `parseMemoryResult` 解析类别 → 会话存档 `memoryFactsStructured`
- 面板 UI：ChatHeader 或侧栏入口，折叠展示各分类
- 需要分类训练提示词，模型输出稳定性需验证（P3 原因）

**涉及文件**
- `src/utils/memory.ts`、`triggerMemorySummary` 提示词、新面板组件

**验收**：100 轮对话后，面板能正确展示主要人物/地点并跳转

**工作量**：大（半天+），先验证提示词稳定性

## 五、风险与注意事项

1. **压缩与长记忆双写冲突**：压缩摘要走独立字段（compressedSummary），与 memoryFacts 分开，避免两套摘要互相覆盖
2. **向量注入的回退**：嵌入服务不可用 / 未配置时，事实注入必须回退全量，不破坏现有功能
3. **自动标题/压缩的 AI 调用成本**：均加"仅一次"语义（compressedRange、titleGenerated 标志），避免重复消耗
4. **数据兼容**：新增字段（compressedSummary / replyToId / titleGenerated 等）全部 optional，旧会话/旧消息读取时兜底
5. **1M 上下文下的差异**：压缩在 1M 下触发时机晚（历史极长才满），但 128K 等小上下文模型受益最大；阈值按 maxContext 比例计算
