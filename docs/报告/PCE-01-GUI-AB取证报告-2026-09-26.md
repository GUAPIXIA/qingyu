### 2.3 解读（不得美化）

1. **相对 5% 门禁在亚毫秒写路径上无法用 journal 达成**——A 基线 0.4–0.7 ms，journal 固定开销约 7–18 ms。与领域层结论一致，GUI 主路径未摊薄。
2. **消息发送/编辑在 10k 会话上约 18 ms**：`fileTransaction` 对 append 也要 **整文件读入旧备份 + 整文件哈希**，成本随会话增大。这是当前实现的真实产品代价。
3. **打开 10k 会话 +88%**：B 侧 journal 恢复/元数据可能参与；绝对值 30 ms 尚可接受，但相对门禁未过。
4. **冷启动 +7.75%**：过 8% 观察线，未过 5% 发布门禁。

**门禁判定：写路径与冷启动相对阈值均未过 → PCE-01 保持未签字。**  
可选处置（需产品/架构决策，不得静默）：
- 继续优化 journal append（增量哈希、跳过整文件 old 备份、批量 fsync），目标把固定开销压到 ≤2 ms；或
- 书面改为「绝对增量门禁」（例如每次写 ≤8 ms、冷启动 ≤+50 ms），并更新总方案 §3.4。

## 3. 本轮抓到的 P0（已修）

**现象**：B 臂 `openSession` 异常为 0.1 ms（A 为 24 ms）——文件只剩 1 条消息。

**根因**：`electron/domain/pcRepository.ts` 的 `toStagedWrites` 丢弃 `DomainFileWrite.append`：

```ts
// 修复前
return files.map((f) => ({ path: f.path, content: f.content }))
```

`appendMessage` 传入 `append: true` 的 JSONL 追加，在 journal 路径被当成 **整文件写**，把 10k 历史覆盖成单条新消息。**开启同步域后发消息会丢历史。**

**修复**：
1. `DomainFileWrite` 增加 `append?: boolean`。
2. `toStagedWrites` 透传 `append: f.append === true`。
3. 回归测试：`phase2.repository.test.ts` 新增 2 例（三行 JSONL 追加不丢行 + journal 计数）。

**验证**：修复后 openSession 恢复 16–31 ms；全量 `electron/domain` 68/68 + sync golden 全绿。
