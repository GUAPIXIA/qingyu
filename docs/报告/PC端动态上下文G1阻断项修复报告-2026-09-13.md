## 1. 背景：G1 实测出的两个可修复缺陷

| 编号 | 现象（G1 实测） | 根因 |
|---|---|---|
| D1 | 用户直接看到"模型未返回任何内容"，**没有任何恢复** | 适配器"零输出防御"以**抛错**结束；主进程发 `ai:error` 只带错误文本，渲染层 `onError` 把一切错误**硬编码**为 `transport_error`，`nextRecoveryLevel` 也就永远看不到"推理/零输出"分类 |
| D2 | `off` 档提前中止/推理吃满时，降档恢复**无档可降**（`nextLowerGateLevel('off') === null`） | 降档是唯一恢复手段；`off` 已是末级 → 直接进终局错误 |

两项叠加的结果就是 G1 里的 4 例用户可见失败：3 例提前中止（空正文）+ 1 例 `length` + 3400/3400 推理。

## 2. 本轮修复

### R1 结构化失败分类透传（修 D1 的根因）

主进程 `classifyFailureOutcome` 早就能区分 `empty_output / reasoning_budget_exhausted / content_filter / network / timeout`，
但这个结论**从未离开主进程**。现在随 `ai:error` 一起下发：

| 文件 | 改动 |
|---|---|
| `shared/ipc-api.ts` | 新增 `AIErrorPayload`（`errorKind?` 可选字段），`ai.onError` 签名改用该类型 |
| `electron/services/ai.ts` | `ai:chat` 的失败分支附带 `errorKind`（复用既有 `classifyFailureOutcome`，与观测口径同源） |
| `electron/preload.ts` | 原样透传 payload |

**向后兼容**：`errorKind` 为可选字段；旧端/旧构建缺失时渲染层保持原行为（见 §4 测试）。

### R2 零输出一次恢复（修 D2 的死路）

`src/store/gateRecovery.ts` 新增纯函数 `resolveEmptyOutputRecovery`：

```text
recoveryUsed                                            → null（一轮最多一次）
errorKind ∉ { empty_output, reasoning_budget_exhausted } → null（传输/审核/超时另有收口）
正文可见字符 > 0（thought 不算正文）                      → null（有正文绝不整条重生成）
reasoning_budget_exhausted 且存在更低档位                 → { level: 下一档, downgrade: true }
其余（off 已是末级 / 未使用门控）                          → { level: 当前档, downgrade: false }  ← 同档重试
```

`src/store/streamController.ts`：

- 把原降档重试内联块抽成 `runRecoveryRetry({ level, downgrade })`（复用同一上下文快照，只重算档位与预算字段，§4.2）；
- `ai:error` 分支：先问 `resolveEmptyOutputRecovery`，命中即重发一次并**不抢占终局**；未命中才走既有 `transport_error` 收口；
- 熔断语义保持干净：**只有降档失败**计入 `noteGateRecoveryFailure`；同档零输出重试失败不计入熔断，也不写 `downgradeRetry` 观测字段（避免被误记成降档）。

**重试上限（§4.3）**：与降档恢复共用 `gateRecoveryUsed` 这一 attempt 位 → 一轮最多 2 次模型调用；不新增开关、不新增轨道、不按实际推理消耗扩大输出（§6.1 禁止项）。

### R3 提前中止观测线改为"可证明的徒劳点"（口径修订）

阶段8 §4.4 原式 `max(gateTokens, requestMaxTokens × 0.85)` 在 G1 实测中被证明会误杀，且与 G1 第 4 条要求互斥。现改为：

```text
estimateReasoningTokens ≥ requestMaxTokens − MIN_USABLE_BODY_TOKENS(256)
```

- `× 0.85` 是无依据魔数；`gateTokens` 是预算承诺而非止损线（接入 P90 后可能大于本式，取 max 会让守卫失效）；
- 新式与 `resolveRequestBudget` 的 `minimumViableOutputTokens` 同源，可单测、可解释；
- 触发时机：预算 > 1707 时晚于旧式（更不易误杀），更小预算下略早（仍是正确的徒劳点）；阈值以 CJK 感知
  估算计量而中文推理估算普遍高于上报值，故实际触发比字面更晚；
- 落点：`electron/services/adapters/types.ts`（`createReasoningRunawayGuard` 去掉 `gateTokens` 入参）+
  `electron/services/adapters/openai.ts`（调用点）+ 阶段8 方案 §4.4 修订说明。

### R4 让 P90 实测样本真正进入预算（§5.4）

G1 实测的失败直接原因是"推理吃满、正文为 0"，而**静态档案余量（3072）低于该端点的真实推理分布**。
W1 的用量档案回读此前只对**无门控**路径生效：`resolveRequestBudget` 在门控在场时直接用 `gate.gateTokens`，
且渲染层 `withReasoningGate` 既无 probe 也不传样本 → 不可信门控永远用静态值。本轮补齐三处：

| 文件 | 改动 |
|---|---|
| `shared/modelOutputProfile.ts` | 不可信门控：`reasoningReserve = max(gateTokens, 保守余量(档案/P90×1.2))`；**可信门控仍严格取承诺值**，不被样本抬高 |
| `shared/reasoningGate.ts` | `ReasoningGateResolveInput.recentReasoningTokens`：用量档案样本与 probe 样本合并参与保守余量估计 |
| `src/store/reasoningGateState.ts` | `withReasoningGate` 带上 `cachedReasoningSamplesFor(...)`（单聊/群聊/方向共用同一入口） |

### R5 全零样本不再把推理余量塌到协议下限（安全下限）

R4 上线后立刻暴露一个真实风险：**样本为 `[0]` 时 P90×1.2 = 0 → 余量 192 → `max_tokens` 从 3400 塌到 520**。
两种解释（真的不推理 / 该桶缺上报数据）代价不对称：`max_tokens` 是**上限而非花费**，多留推理空间不多花钱；
而余量不足会让推理吃满正文。因此共享窗口模型在全零样本时回退档案默认余量：

```ts
if (estimate <= 0) return profile.defaultReasoningReserve   // shared-* 且样本全 0
```

这不只是理论问题——它被**意外做成了 A/B**：因评测器 CLI 把空参数解析成 `[0]`，同一批用例出现
`余量 192 → max_tokens 520 → 6/6 空正文`，而余量 3072（`max_tokens` 3400）时为 `1/18`，
余量 4096（`max_tokens` 4424）时为 `0/12`。详见 §5.2。

## 3. 行为前后对比

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 适配器抛"模型未返回任何内容"（`empty_output`，无正文） | 直接终局错误 | **同档重发一次**；成功则正常收尾，失败则只派发一次最终错误 |
| 适配器抛"推理已占满模型输出硬上限"（`reasoning_budget_exhausted`，无正文） | 直接终局错误 | 有更低档位 → **降档重发**；`off` 已是末级 → **同档重发** |
| `length` + 零正文（done 事件，走降档判定） | 有更低档位则降档；`off` 则终局错误 | 降档逻辑不变；`off` 时由错误/完成路径各自的判定覆盖（错误路径新增同档重试） |
| 已有正文（含半截正文） | 收口保存，绝不整条重生成 | **不变** |
| 用户停止 / 审核拦截 / 传输失败 / 空闲超时 | 各自既有收口 | **不变**（`errorKind` 不在可恢复集合内） |
| 旧端不传 `errorKind` | 按 `transport_error` 收口 | **不变** |
| 会话熔断（连续降档失败 → 从 low 起步） | 只统计降档失败 | **不变**（同档重试不计入） |
| 观测字段 `downgradeRetry` | 仅降档重试写入 | **不变**（同档重试不写） |

## 5. 对 G1 指标的影响（预估，需实机复测）

### 5.1 R1/R2（零输出恢复）

G1 实测 4 例空正文：3 例提前中止（零正文，属 `reasoning_budget_exhausted` 路径）+ 1 例 `length` 零正文。
修复后这 4 例都会获得**一次**额外调用；能否拿到正文取决于模型当次行为，但有两项支撑：

1. 对照样本（G1 报告 §4 F3）：同一夹具首次零正文、复跑拿到 55–111 字符正文 —— 同档重发确实有机会产出正文；
2. 失败不再"零尝试"，最坏情况与修复前相同（一次额外调用换来同一条错误）。

### 5.2 R3/R4/R5 实机复测（2026-09-13 晚，同端点同模型，n=46）

三臂同用例集（`d1,d2,st-suwan-immersive,st-suwan-omniscient` × 3 次重复），另加历史臂对照：

| 臂 | 观测线 | 推理余量 | 用例 | 用户可见失败 | 提前中止 | 中止后空正文 | 推理占比 | P50 / P95 延迟 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 旧线 + 静态（历史，`prod-abort`） | 3481（0.85×4096） | 3072 | 10 | **3（30.0%）** | 2 | 2 | 93.8% | 28.2s / 129.0s |
| **新线 + 静态** | 3840 | 3072 | 12 | **0（0.0%）** | 0 | 0 | 95.9% | 26.0s / 40.1s |
| **新线 + P90** | 3840 | 4096 | 12 | **0（0.0%）** | 0 | 0 | 95.6% | 18.4s / 57.2s |
| 对照（无守卫） | — | 3072 | 12 | 1（8.3%） | — | — | 93.1% | 15.5s / 51.9s |

读法与限度：

- **守卫不再误杀**：新线在 24 例中 0 次提前中止（旧线 10 例 2 次），且全部用例产出了正文（68–129 字符）；
  这符合"观测线后移 → 只在正文放不下时才止损"的设计意图。样本量仍小（n=24 vs n=10），但方向与机制一致。
- **P90 余量未带来回归**：`max_tokens` 从 ~3400 升到 ~4424（+30%），12 例全部产出正文；
  P95 延迟 57.2s 高于静态臂 40.1s，但对照臂本身就有 51.9s，且长尾分布下 n=12 的 P95 不稳定（见 G1 报告 §8）。
- **cap 型失败仍在（与守卫无关）**：对照臂 1/12 出现 `length + 0 正文`（模型把 4096 全花在推理上，52s），
  说明"给足余量"能降低但**不能消除**该端点上的 cap 型空正文——这正是 R1/R2 的同档重试要兜的场景。
- **意外的三档 A/B（R5 的证据）**：同一批 dialogue 用例在不同余量下——
  余量 192（`max_tokens` 520）→ **6/6 空正文**；余量 3072（3400）→ 1/18；余量 4096（4424）→ 0/12。
  这是"余量不足直接制造空正文"的最强证据，也是把全零样本下限写进代码的直接依据。

**结论**：空正文类可见失败在本次小样本复测中为 0/24；但 G1 仍不通过——`< 0.5%` 需要数百样本，
降档恢复成功率与"降档额外 token 占比"依赖应用层灰度，且 R3 修改了第 4 条的判定方式（已同步主计划 §7.7）。

> ### ⚠️ 5.2.1 更正（2026-09-14，n=240 扩样）：0/24 是小样本假象
>
> 同日稍后按同一命令扩到 **n=240**（`--batch dialogue,stream,directions --reps 20 --concurrency 3`）：
> **推理相关空正文 14/240 = 5.8%**，其中 **8 次提前中止全部没有留下正文（8/8）**，且 8 次**集中在同一时间窗**
> （按完成顺序分四段为 `3 / 2 / 9 / 0`）——端点上游推理长度会突发拉长，抽样窗口落在"低推理长度"时段就会看到 0 失败。
>
> 因此上表"守卫不再误杀 / 归零"的读法**只在 n=24 的窗口内成立**，不可作为结论：
> - 观测线在**估算 token** 口径下（CJK 估算普遍高估真实 reasoning 约 1.4×）落在该模型真实推理分布的中段，
>   会周期性误杀"本会产出短正文"的请求；
> - 第 4 条由此判负（8/8 中止无正文）；第 6 条本次无法验证——紧随其后的**同请求体对照臂 96/96 全部 429**：
>   `You've reached your weekly usage limit for your plan. Your limit resets at 2026-09-16T06:36:25.554Z`
>   （北京时间 2026-09-16 14:36）。
> - 方向任务在扩样下依然稳固（53 例成功 0 空正文），W4 修复成立。
>
> 详见 [G1 报告 §5.4](./PC端动态上下文G1灰度取证实机评测报告-2026-09-13.md)；**以该节为准**。

## 7. 交接要点

- 新增判定的唯一入口是 `resolveEmptyOutputRecovery`；后续若要扩到群聊，直接复用该纯函数 + 群聊侧的 `retryWithDowngradedGate`；
- 观测线的唯一入口是 `createReasoningRunawayGuard`（已去掉 `gateTokens` 入参）；**新增适配器提前中止时不要再用 0.85 或 gateTokens**；
- `ai:error.errorKind` 是**可选**协议字段：Android/Bridge 若消费 `ai:error`，可忽略该字段（无破坏性变更）；
- `resolveReasoningReserve` 的"全零样本回退档案默认余量"是**有意的契约变更**（原为回退协议下限 192），
  改动理由与 A/B 证据见 §2.5/§5.2；若将来要恢复旧契约，必须先给出"余量塌到协议下限不会制造空正文"的反证；
- 复测建议：用 G1 报告 §9 的命令重跑 `dialogue,stream` 两臂（本报告 §5.2 的复测用了
  `--only d1-suwan-immersive,d2-suwan-omniscient,st-suwan-immersive,st-suwan-omniscient --reps 3`
  与 `--reasoning-samples 3000,3200,3881` 的 P90 臂），重点看 `empty_body`、`earlyAbort` 与 `attempts` 分布。
