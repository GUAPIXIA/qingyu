**为取消路径做的工具改造**：取消类动作（`embedding.cancelIndex`、`chatTask.cancel`、`ai.cancelChat` 等）标记 `control: true`，**绕过单写者队列**——否则 cancel 会排在被取消的动作之后，永远无法生效。

**过程中的一个真实教训**：我最初用 `observe` 轮询索引进度，结果**观察请求被写队列挡住**（observe 也要排队），误判成“索引太快无法取消”。实测 1500 条索引耗时 **23 秒**；改为固定延迟 + 控制类取消后一次通过。这一点已写进代码注释。

## 3. ② 原生交互后端：实测结论与回退

**做了**：`lib/native-dialog.mjs` —— 进程树展开 + UIAutomation 定位 Win32 通用对话框（`#32770`）+ 填文件名 + 点确认。

**实测能到的程度**：对话框可稳定定位（含“启动 pid 是 cmd 包装进程，需展开进程树”这一坑）；控件可枚举（`class=Edit`/`class=Button`）。

**卡在哪（逐条实测）**：

| 尝试 | 结果 |
|---|---|
| `PropertyCondition(ClassNameProperty, 'Edit')` 查控件 | ❌ 查不到（DirectUI），必须 `TrueCondition` + PowerShell 过滤 |
| 文件名 Edit 的 `ValuePattern` | ❌ `TryGetCurrentPattern` 返回 false（不支持） |
| `SetWindowText` | ⚠️ 显示变了、**对话框内部状态没变** → 文件按默认名落到**用户“下载”目录**（已清理，仅此一次） |
| `SendKeys` 输入 | ❌ 需要对话框在前台，后台进程的 `SetForegroundWindow` 不保证生效 |
| 按钮 `BM_CLICK` | ✅ 能关闭对话框（但文件名不生效时结果仍落默认目录） |

**决定**：停止硬试并**回退为 `needs_interaction`**（方案 §6.3 允许）。理由：继续尝试的代价是**反复往用户文件系统写文件**，这个副作用不可接受；而 `needs_interaction` 是已验证、可恢复、零副作用的正确行为。后端模块保留为后续接入专业桌面自动化库的起点，头部写明了上述全部事实，避免后人重复踩坑。

**若要真正自动化，需要**：能稳定激活前台窗口的桌面自动化库（如带 `AttachThreadInput` 的实现），或**产品侧提供导出目标路径参数**（那样根本不需要对话框）。后者是更干净的方向。

### 8.3 过程中发现并修掉的两个工具缺陷

| 缺陷 | 现象 | 修复 |
|---|---|---|
| **会话卡死在 `restarting`** | 重启失败后 `state` 停在 `restarting`，后续所有动作都被判 `blocked` 且无恢复路径 | `restart()` 失败时置 `error` 并保留错误；`blocked` 消息给出“restart 重试或关闭新建”的提示 |

### 9.1 过程中的四个真实结论（都写进了 README §8.3）

1. **跨进程凭据注入不可行**：Electron safeStorage 的密钥绑定在启动进程的 `userData` 上，外部进程写入的密文产品侧解不开（实测 `Error while decrypting the ciphertext`）。→ 改为**经产品自己的 `settings.saveAPICredential` IPC** 写入隔离档案。
2. **凭据写入做成默认关闭的受控动作**：`requires: ['credential-write']`，只有 `--allow-credential-write` 才放行，否则 `blocked / CREDENTIAL_WRITE_NOT_ALLOWED`；读接口 `settings.getAPICredential` **永久豁免**，外部 Agent 读不到密钥明文。
3. **写入设置与凭据后必须重启应用**：主进程否则仍用启动时的旧快照（实测不重启恒定 401）。
4. **生图模型必须带 `workflow` 且 `enabled: true`**：产品按 `id === activeImageGenModelId && m.enabled` 查找，缺 workflow 报“未配置工作流”。

### 9.2 新增的异步句柄能力（`--no-wait`）

真实取消需要“先拿 taskId 再取消”，而 `awaitTask` 会一直等到终态。为此补上方案 §5.4 要求的异步句柄：

```powershell
pc-agent invoke --action chatTask.start --args-file req.json --no-wait   # → status=accepted + taskId
pc-agent invoke --action chatTask.cancel --args '<taskId>'               # 控制类动作，绕过写队列
pc-agent observe --action chatTask.get --args '<taskId>'                 # → state=cancelled
```

CLI（`--no-wait`）与 MCP（`qingyu_call` 的 `wait:false`）都支持。

### 10.2 小米 MiMo TTS：模型可用，但产品当前**不兼容**（产品集成缺口）

**小米 TTS 本身可用**（直连实测）：`mimo-v2.5-tts` 走 `POST /v1/chat/completions`，音频在 `choices[0].message.audio.data`（base64）：

```jsonc
// 请求
{ "model": "mimo-v2.5-tts",
  "messages": [{ "role": "assistant", "content": "要合成的文本" }],
  "audio": { "format": "mp3", "voice": "mimo_default" } }
// 实测：HTTP 200，1.5s，返回 21432 字节 mp3（magic fff384），usage total_tokens=151
```

**产品的 openai 兼容 TTS 路径用的是另一套接口**（`electron/ipc/tts.ts` → `openaiSpeak`）：

```ts
POST `${baseUrl}/audio/speech`   // OpenAI 风格
body: { model, input, voice, speed, response_format: 'mp3' }
```

小米没有这个端点 → 工具实测 `tts.speak(..., {provider:'openai', baseUrl:'https://api.xiaomimimo.com/v1', model:'mimo-v2.5-tts'})` 返回
`TTS 错误 404: <html>404 Not Found</html>`（可读错误，不是崩溃；`tts.lifecycle` 已把该行为固化为断言，产品哪天支持了会自动变成通过）。

**结论与建议（属产品改动，本工具不改产品）**：要在轻语里用小米 TTS，需要产品侧为 TTS 增加一个适配器：

- 端点：`{baseUrl}/chat/completions`
- 请求体：`messages: [{role:'assistant', content: text}]` + `audio: { format, voice }`
- 取音频：`choices[0].message.audio.data`（base64），`usage` 可用于用量统计
- 音色：`mimo_default`、`冰糖`、`茉莉`、`苏打`、`白桦`、`Mia`、`Chloe`、`Milo`、`Dean`（`voiceclone` 需传样本 base64，`voicedesign` 不支持 voice 字段）
- 参考文档：[小米 MiMo TTS 接口文档](https://mimo.mi.com/static/docs/api/audio/tts.md)

同时 `provider: 'edge'`（微软免费在线语音）与系统语音引擎在轻语里是**可用的**——若只需本机朗读，用 edge 即可，无需小米 TTS。
