## 2. 根因链（均有日志/文件证据）

1. **凭据文件被写入了设置对象（污染源）**
   `data/config/credentials.json`（mtime 14:45:35）里混入了 48 个设置字段——`providers`（对象）、`semanticTrigger`（对象）、
   `fontSizeCustom`（数字）、`connectionProfiles`（空数组）、`schemaVersion` 等——与 6 个 `profile-*` 加密凭据、`bridge-jwt-secret` 混在一起。
   该文件本应是 `Record<string, 密文>`。
2. **`getCredential` 未做类型防御 → `settings:get` 整体失败**
   `electron/services/safeStorage.ts` 的 `getCredential()` 直接 `value.startsWith('plain:')`；
   读取路径 `restoreSecrets()` 会以 `semanticTrigger` 为键取凭据 → 拿到**对象** → `TypeError: value.startsWith is not a function`。
   日志证据（`logs/qingyu.log`）：
   ```text
   [2026-09-13 22:43:39] [ERROR] [ipc] IPC settings:get 异常 | error=value.startsWith is not a function | at getCredential (D:\Code\q...
   [2026-09-13 22:43:39] [ERROR] [App:unhandledRejection] Error invoking remote method 'settings:get': TypeError: ...
   ```
3. **加载失败后仍继续落盘（数据丢失的最后一步）**
   `src/store/useSettingsStore.ts` 的 `loadSettings()` 在 `settings.get()` 抛错时没有捕获：store 停留在
   `settings: getDefaultSettings()`，随后任意一次保存（含退出前的 `flushSettings`）把默认值写入磁盘；
   渲染层的旧 provider 兜底逻辑又为 `ollama` 补了一条**新 id** 的档案（正是观测到的 `52yIu…`）。日志证据：
   ```text
   [2026-09-13 22:43:54] [INFO] [settings] 设置已保存 | activeProfileId=(none) | theme=dark
   [2026-09-13 22:44:12] [INFO] [settings] 设置已保存 | activeProfileId=52yIuCmlswY8sq4YGrdJj | theme=dark
   [2026-09-13 22:44:47] [INFO] [settings] 设置已保存 | activeProfileId=52yIuCmlswY8sq4YGrdJj | theme=dark
   ```
   时间线：22:43:39 `settings:get` 失败 → 22:43:54 默认值落盘 → 22:44:12 兜底 Ollama 档案落盘。
4. **触发条件**：22:44:11 启动了 `release-v2\win-unpacked\轻语.exe`（打包构建）。任何一次"加载设置 + 随后保存"的启动
   都会重现该链路——**与本次会话的评测/命令无关，但应用启动即触发**。

## 4. 顺带发现并修复的凭据泄露（P0）

排查恢复源时发现：`data/tasks` 下的任务快照与事件日志**明文保存了 API Key**。

- 来源：`electron/chat/contextService.ts` 把 `profile.apiKey` 放进 `PreparedContext.model`；
  `electron/chat/orchestrator.ts` 又把 `ctx.model` 原样用于
  ①落盘任务快照（`updateTask` → `data/tasks/**/task-*.json`）、②`task:started` 事件 payload（经 WS 下发给桥接客户端）。
- 影响：本机实测 **84 个任务快照 + 84 个事件日志**含非空明文 `apiKey`（事件日志意味着已配对设备也可能收到）。
- 修复（代码）：
  - 新增 `toPublicModelDescriptor()`（`electron/chat/ports.ts`），只保留 `provider/model/profileId`；
  - `orchestrator.ts` 落盘与外发统一走该函数，`apiKey` 只留在进程内供 `modelPort` 调用；
  - 新增回归用例：伪造含 key 的 context，断言**该次任务落盘的所有文件**都不含 key 与完整 baseUrl。
- 清理（数据）：84 个任务快照 + 84 个事件日志已剔除 `apiKey/baseUrl`；全盘复扫（排除缓存目录）
  **残留含非空 apiKey 的文件数 = 0**。
- **仍需用户操作**：这些密钥曾以明文落盘（且可能经 WS 外发），建议**轮换** commandcode / DeepSeek（及 opencode 若在用）的 API Key，
  并在设置里重新填入（写入后仍是 safeStorage 加密存储）。

## 5. 根因修复（代码，防止再次发生）

| 文件 | 修复 |
|---|---|
| `electron/services/safeStorage.ts` | `readCredentialAll()` 只接受**字符串值**（一步消除污染键并在下次写入时自动清理）；`getCredential()` 再兜一层类型/空值防御。单个畸形条目不再能让 `settings:get` 整体失败 |
| `src/store/useSettingsStore.ts` | 新增 `loadFailed` 状态：`loadSettings()` 捕获 `settings.get()` 异常后**提前返回**（不再走兜底迁移、不再标记 loaded）；`saveSettings()` 在该标记下**拒绝写盘**并给出可操作错误。默认值永不覆盖用户数据 |
| `electron/chat/ports.ts` + `orchestrator.ts` | 落盘/外发剥离凭据（§4） |

回归测试（+5 例，合计 `pnpm test` **253 files / 2823 tests 全绿**）：

- 凭据文件混入对象/数字/数组时：不抛错、正常键仍可读、`restoreSecrets` 整体可用；
- `loadSettings` 失败 → `loadFailed=true`、`loaded=false`，`saveSettings` 与防抖保存都不落盘；加载成功后恢复正常；
- 任务落盘（快照 + 事件）不含 `apiKey`/`baseUrl`。
