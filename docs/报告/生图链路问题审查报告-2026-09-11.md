## 一、高危：生图 API Key 在主进程完全不生效

### 现状

[imageGen.ts L78](file:///d:/Code/qingyu/electron/ipc/imageGen.ts#L78) 用裸 `readJson` 读取生图配置：

```ts
const settings = readJson<Settings>(join(DIRS.config(), 'settings.json'))
// ...
const config = settings.imageGenModels?.find(
  (m) => m.id === settings.activeImageGenModelId && m.enabled,
)
```

### 为什么这是 Bug

H1 修复后（[settings.ts L50-L61](file:///d:/Code/qingyu/electron/ipc/settings.ts#L50-L61)）`stripSecrets` 在**保存时**已把 `imageGenModels[].apiKey` 提取进 safeStorage 并从 `settings.json` 中删除，读取时必须调用 `restoreSecrets()` 回填。此路径没有调用。

补充：该文件 `translatePromptToEnglish` 已专门打了 H-6 补丁显式解密 profile 凭据（[L27-L33](file:///d:/Code/qingyu/electron/ipc/imageGen.ts#L27-L33)），说明作者清楚此机制，但 `imageGenModels` 这条路径被漏掉。

### 后果

- **OpenAI 生图必然失败**：`config.apiKey` 为空 → [openaiGenerate L586-L589](file:///d:/Code/qingyu/electron/services/imageGen.ts#L586-L589) 发出 `Authorization: Bearer `（空 token）→ 401。
- **带鉴权的远程 ComfyUI / SD WebUI 反代**同样拿不到 key：[comfyHeaders](file:///d:/Code/qingyu/electron/services/imageGen.ts#L91-L101) 收到的 `apiKey` 为空，两个鉴权头都不会设置。

### 迷惑性来源

「测试连接」是好的——[testConnection](file:///d:/Code/qingyu/electron/ipc/imageGen.ts#L121-L124) 的 config 由**渲染层传入**，而渲染层经 `settings:get` 已执行 `restoreSecrets`。因此用户会看到"连接成功"，但正式生图稳定 401。

### 修复建议

方案 A（推荐，最小改动）：改用统一的读取入口。

```ts
import { readSettingsFromDisk, restoreSecrets } from './settings'
// ...
const settings = readSettingsFromDisk()
restoreSecrets(settings)
```

方案 B（局部对称于 H-6 的既有写法）：保留裸 `readJson`，仅对该模型显式解密。

```ts
if (!config.apiKey) config.apiKey = getCredential(`imagegen-${config.id}`) ?? ''
```

> 建议采用方案 A：`restoreSecrets` 会一次性回填 profile/tts/imagegen/vision 四类凭据，可同时消除该文件其余潜在遗漏，避免逐个打补丁。另注意本文件顶部已有 `sanitizeApiKey` import，说明作者在意密钥不外泄，但未覆盖"取不到密钥"这一面。

## 三、中危：三处尺寸传入对 OpenAI 非法

### 约束背景

DALL-E 3 官方仅接受 `1024x1024`、`1792x1024`、`1024x1792` 三种尺寸；`512x512` / `256x256` 属于 DALL-E 2 的规格。而 [openaiGenerate](file:///d:/Code/qingyu/electron/services/imageGen.ts#L573-L580) 直接透传、**无任何白名单校验**：

```ts
size: options?.size || config.size || '1024x1024',
```

### 问题点 1：`/imagine` 模式尺寸

[imagine.ts getSizeForMode](file:///d:/Code/qingyu/src/commands/builtin/imagine.ts#L157-L161) 返回 `512x768`（face/character）与 `768x512`（background），而 [L210](file:///d:/Code/qingyu/src/commands/builtin/imagine.ts#L210) 的分支**只对 comfyui 跳过**：

```ts
const sizeOverride = activeImageGen?.provider === 'comfyui' ? undefined : getSizeForMode(mode)
```

→ 当 provider 为 openai 时，`512x768` 会被原样发出 → **400 Bad Request**。即 `/imagine --mode face`、`--mode character`、`--mode background` 对 OpenAI 后端全部失败。

### 问题点 2：角色封面尺寸（必然失败）

[CoverStep COVER_SIZES L17](file:///d:/Code/qingyu/src/components/character-creator/CoverStep.tsx#L17) 为：

```ts
const COVER_SIZES = ['576x768', '768x1024', '512x768', '832x1216']
```

**四个选项对 DALL-E 3 全部非法**。而 [generateCover L569-L572](file:///d:/Code/qingyu/src/store/useCharacterCreatorStore.ts#L569-L572) 无条件传入：

```ts
const result = await window.api.imageGen.generate(coverPrompt, { negativePrompt, size: coverSize })
```

→ OpenAI 生成封面 **100% 失败**，[L579-L581](file:///d:/Code/qingyu/src/store/useCharacterCreatorStore.ts#L579-L581) 的 3:4 裁剪逻辑永远走不到。

### 问题点 3（复核新增）：配置界面自身允许非法尺寸

[ImageGenModelsSection OPENAI_SIZES](file:///d:/Code/qingyu/src/components/api/ImageGenModelsSection.tsx#L25-L28) 包含：

```ts
const OPENAI_SIZES = ['1024x1024', '1792x1024', '1024x1792', '512x512', '256x256']
```

后两项对默认模型 `dall-e-3` 非法（仅 DALL-E 2 可用）。用户可在此选中并在未指定 `options.size` 时透传出去。

### 修复建议

1. **`imagine.ts`**：把 openai 一并纳入跳过，或按 provider 映射合法尺寸。建议改为显式白名单式映射：
   ```ts
   // 仅对接受任意尺寸的后端（sd-webui）应用模式尺寸
   const sizeOverride = activeImageGen?.provider === 'sd-webui' ? getSizeForMode(mode) : undefined
   ```
   （ComfyUI 由工作流决定；OpenAI 由 config.size 决定，二者均不应被模式覆盖。）

2. **`CoverStep.tsx` / `generateCover`**：按 `activeImageGen.provider` 过滤 `COVER_SIZES`——openai 时仅提供 `1024x1024`（后续裁 3:4），或干脆不传 `size` 让其回落到 `config.size`。当前 UI 上"尺寸"与"负面提示词（SD WebUI 专用）"并列，但尺寸未做同类 provider 标注，建议同步补注。

3. **运行时兜底**：在 `openaiGenerate` 内对非法尺寸做校验或映射到最近合法值，避免任何调用方（含未来的）再次踩坑。

> 若后端实际是 OpenAI 兼容代理而非官方端点，部分代理可能放宽尺寸校验——但不应依赖此假设，标准 DALL-E 3 会明确拒绝。

## 四、中危：ComfyUI 若干配置项持久化了但运行时被忽略

### 4.1 `bindings.outputNodeIds` 从不生效

- 类型与 UI 均存在：[shared/types.ts L836](file:///d:/Code/qingyu/shared/types.ts#L836) 定义、[ImageGenModelsSection L185-L198](file:///d:/Code/qingyu/src/components/api/ImageGenModelsSection.tsx#L185-L198) 在出现歧义时收集并保存用户选择的输出节点。
- 但运行时只用提示词绑定：[customComfyWorkflow L284-L285](file:///d:/Code/qingyu/electron/services/imageGen.ts#L284-L285) 仅读取 `positivePromptNodeIds` / `negativePromptNodeIds`，**全文无 `outputNodeIds` 引用**。

后果：用户在工作流有多个输出节点时做出的选择被静默忽略，运行时会收集**全部**输出图片（[comfyuiGenerate L430-L433](file:///d:/Code/qingyu/electron/services/imageGen.ts#L430-L433) 对 `entry.outputs` 全量 `flatMap`）。

修复建议：在 `customComfyWorkflow` 中对非选定输出节点做剔除/禁用（如将 `SaveImage` 改为不参与收集，或仅收集 `outputNodeIds` 对应节点的 images）；若短期不打算支持，则应在 UI 上移除该绑定项，避免"选了不生效"。

### 4.2 内置工作流回退是死路

[ImageGenModelsSection L830-L846](file:///d:/Code/qingyu/src/components/api/ImageGenModelsSection.tsx#L830-L846) 展示了「Checkpoint 文件名（内置工作流）」输入框，文案称"仅内置工作流使用"。但 [handleSave L953](file:///d:/Code/qingyu/src/components/api/ImageGenModelsSection.tsx#L953) 的保存按钮：

```ts
disabled={!form.name.trim() || (isComfyUi && !comfyForm?.workflow?.trim())}
```

要求 ComfyUI 必须有非空 `workflow` → 用户填了 Checkpoint 文件名也**无法保存**，内置工作流（[defaultComfyWorkflow](file:///d:/Code/qingyu/electron/services/imageGen.ts#L103-L158)）成了不可达分支。

修复建议：二选一——① 移除该输入框与 deprecated `model` 字段，明确只支持工作流快照；② 放开保存条件，允许 `workflow` 为空并以 `model` 走内置回退。

### 4.3 图生图工作流可保存但运行时必失败

[comfyWorkflow.ts L978](file:///d:/Code/qingyu/electron/services/comfyWorkflow.ts#L978) 导入时**只拦 video**：

```ts
if (analysis.kind === 'video') throw new Error('当前生图配置不支持视频工作流')
```

而 `image-to-image` 仅产生一条 warning（[L836-L838](file:///d:/Code/qingyu/electron/services/comfyWorkflow.ts#L836-L838)）便放行。但生图链路**无任何输入图片 UI**（IPC `imageGen:generate` 只接收 prompt 与 size/negative/quality），运行时 `LoadImage` 节点必然找不到输入 → 失败。

修复建议：与 video 同等对待，导入时直接拒绝 `image-to-image`（并给出明确文案），而非降级为 warning 后放行。

## 五、低危：清洗函数三行重复、引号没清掉

### 现状

[imageGen.ts L485-L487](file:///d:/Code/qingyu/electron/services/imageGen.ts#L485-L487) 与 [L504-L506](file:///d:/Code/qingyu/electron/services/imageGen.ts#L504-L506) 各连写三行 `.replaceAll`，实测三行**完全相同**（均为 ASCII `U+0022`）：

```
.replaceAll('"', '')   U+0022
.replaceAll('"', '')   U+0022
.replaceAll('"', '')   U+0022
```

原意显然是要清除 `"` `“` `”` 三种引号，实际只清除了直角双引号，**中文引号与弯引号会原样漏进提示词**。

### 附带问题：NFD 规范化会削掉拉丁重音

[L489](file:///d:/Code/qingyu/electron/services/imageGen.ts#L489) 使用 `s.normalize('NFD')`，会把 `é` 等字符拆为 `e` + 组合附加符 `U+0301`，随后被 [L491 的白名单正则](file:///d:/Code/qingyu/electron/services/imageGen.ts#L491)剥离 → 欧洲语言提示词失真（CJK 字符不受影响，因其无分解形式）。

### 修复建议

```ts
// 清除三种引号（直角 + 左右弯引号）
.replaceAll('"', '')
.replaceAll('\u201c', '')
.replaceAll('\u201d', '')

// 用 NFC 保持字符完整；若确需对拉丁文去重音，应显式剥离 \u0300-\u036f
s = s.normalize('NFC')
```

两者都在同一函数内，建议一并处理，并为 `sanitizeSdPrompt` / `sanitizeOpenAiPrompt` 补单测（当前无覆盖，这也是重复三行未被发现的原因）。

## 六、低危：其它交互细节

### 6.1 「生图历史」文案与行为不符（有效）

[QuickSettingsPanel L317-L322](file:///d:/Code/qingyu/src/components/chat/QuickSettingsPanel.tsx#L317-L322)：

```tsx
title="点击复制图片"
onClick={() => navigator.clipboard.writeText(image).catch(...)}
```

实际是把 **base64 data URL 文本**写入剪贴板，而非复制图片；且大图 data URL 可达数百 KB 至 MB 级，`writeText` 可能失败或污染剪贴板。

修复建议：文案改为"复制图片数据（base64）"；若要真正复制图片，需将 data URL 转 Blob 后用 `ClipboardItem` 写入，或经 IPC 走主进程 `clipboard.writeImage`（需在 preload 暴露）。

### 6.2 `getActiveImageGen` 不过滤 `enabled`（有效）

[useSettingsStore L449-L475](file:///d:/Code/qingyu/src/store/useSettingsStore.ts#L449-L475) 仅按 id 查找，**未校验 `m.enabled`**；而 IPC 侧 [imageGen.ts L84-L86](file:///d:/Code/qingyu/electron/ipc/imageGen.ts#L84-L86) 做了 `&& m.enabled` 过滤。

后果：两侧判断不一致。例如 [CoverStep L180](file:///d:/Code/qingyu/src/components/character-creator/CoverStep.tsx#L180) 依据 `getActiveImageGen()` 判定"已配置生图模组"并渲染生成按钮，但点下去实际报"未配置启用的生图模型"。

补充：`enabled` 目前无 UI 可修改（恒为 `true`），因此该问题当前不会触发；但一旦补上开关，或经备份导入含 `enabled: false` 的配置，即会显形。属**潜在缺陷**，建议预先对齐。

修复建议：`getActiveImageGen` 中加入 `&& m.enabled`，与 IPC 侧语义统一。

### 6.3 移动端 `/imagine` 透传声明与实现不符（有效）

[android/README.md L53](file:///d:/Code/qingyu/android/README.md#L53) 声称：

> 生图指令触发即已透传（任何文本按用户消息发送，PC 侧解析 `/imagine`）

实测：`electron/` 目录下**搜不到任何** `imagine` / `parseCommand` / `findCommand`。命令解析仅存在于渲染层 [useChatInputState.ts L294-L313](file:///d:/Code/qingyu/src/components/chat/useChatInputState.ts#L294-L313)；主进程 [orchestrator](file:///d:/Code/qingyu/electron/chat/orchestrator.ts) 仅按普通文本生成回复。

后果：安卓端发送 `/imagine ...` 会被当作普通用户消息，PC 只会返回一条文本回复，**不会生图**。

修复建议：二选一——① 修正 README 措辞，明确"移动端暂不支持生图指令"；② 在主进程命令层实现 `/imagine` 解析（需打通生图服务与消息落盘，工作量较大）。在未实现前，README 的表述会误导联调与验收。

### 6.4 ~~自动生图标记未剥离~~ —— 已作废

原问题：自动生图插入图片后，正文中的 `[image: xxx]` 标记未从 `content` 剥离，会原样显示在气泡里。该问题随自动生图功能整体移除而**自动消失**。
