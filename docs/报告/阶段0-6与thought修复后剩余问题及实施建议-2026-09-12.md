# 阶段 0–6 与 thought 修复后剩余问题及实施建议

> 日期：2026-09-12  
> 基线：[对话输出弹性约束实施报告](./对话输出弹性约束实施报告-2026-09-12.md)  
> 原始评测：[生成效果分批评测报告](./生成效果分批评测报告-2026-09-12.md)  
> 范围：只记录当前仍存在或仍需验证的问题；不包含已移除的族裔功能，也不再把已完成的 thought 修复列为待办。

## 一、结论

阶段 0–6 的主体架构已经成立：动态预算、结构化完成事件、统一收尾器、一次短补尾、群聊与 Bridge 接入、语义分块渲染和灰度回退都已落地。当前没有发现会阻止桌面版正常构建或运行的编译级问题。

剩余问题不是“推翻新方案”，而是少数入口仍没有完全服从同一处理顺序，以及若干此前明确延期的增强项。优先建议先修 S1、S2、S3；它们直接影响截断后的正文完整性和错误展示一致性。

| 编号 | 级别 | 问题 | 当前判断 |
|---|---|---|---|
| S1 | 高 | 桌面单聊的输出正则在 finalizer 之后执行，与群聊/Bridge 顺序不同 | 可重新制造未闭合格式，削弱阶段 3 的收尾保证 |
| S2 | 高 | 群聊收到首个 chunk 后重置的超时处理绕过统一收尾器 | 半截正文可能原样落盘，并把错误文案混进正文 |
| S3 | 中 | 长记忆仍使用固定 6144，群聊长记忆固定 2048 | 推理型端点仍可能吃满预算，导致事实提案缺失 |
| S4 | 中 | 显式“继续生成”仍使用 8 字去重阈值 | 3–7 字的短复读不会被裁掉，各续写入口行为不一致 |
| S5 | 中 | 自动篇幅策略尚未接入本轮用户意图与场景系数 | “简短一点/详细展开”等要求不会同步改变请求预算 |
| S6 | 中 | Android 尚未消费 finish reason 与收尾状态字段 | 移动端不能完整区分正常结束、恢复、截断和取消 |
| S7 | 低 | 群聊 blocks 渲染路径跳过 @提及高亮 | 新消息与旧 Markdown 消息的提及显示不一致 |

| S9 | 低 | 测试环境固定返回同一个消息 ID，并残留临时调试文件 | 全量测试持续打印 ID 冲突和大段 HTML，掩盖真实告警 |
| S10 | 验证项 | thought 语义改变后尚未重新跑真实模型质量评测 | 单元测试证明通道隔离，但还缺生成质量统计更新 |

## 二、问题详情

### S1【高】桌面单聊在收尾之后执行输出正则

#### 现状

- 桌面单聊先在 `streamController` 中调用 `finalizeAssistantOutput`，随后 `useChatStore.onComplete` 才应用 output 正则与停止字符串。
- 群聊和 Bridge 则先应用 output 正则，再进入 finalizer。

这意味着三个入口虽然都“调用了同一个 finalizer”，实际管线顺序仍不相同。

#### 风险

output 正则可以在 finalizer 完成结构检查后再次删除句尾、引号、星号或 `</thought>`。最终落盘内容因此可能重新变成半句或未闭合格式，而收尾状态仍显示为 complete/recovered。

#### 建议

建立唯一的共享顺序：

1. 删除供应商推理残留；
2. 应用 output 正则；
3. 应用停止字符串；
4. 调用 finalizer；
5. 必要时执行一次短补尾；
6. 做续写重叠去重；
7. 落盘并渲染。

不要让各 store 自行决定正则与 finalizer 的先后。可新增一个共享 `finalizeGeneratedReply` 入口，由桌面单聊、重生成、群聊和 Bridge 共同调用。

#### 验收

- 构造一条完整正文，再用 output 正则删除结尾引号或 `</thought>`，最终结果仍应被收尾器恢复或判为不可直接保存。
- 单聊、群聊、Bridge 对同一输入得到完全相同的正文与状态。
- output 正则每条消息只执行一次。

### S2【高】群聊的续期超时处理绕过统一收尾

#### 现状

群聊初始超时处理已经使用 `finalizeAssistantOutput` 和 `generationError`。但收到 chunk 后重新设置的 timeout 回调仍走旧逻辑：

- 直接保存 `clean + "⚠️ 请求超时"`；
- 不检查句子、引号、星号或 thought 是否闭合；
- 把错误说明写进 `content`，而不是独立的 `generationError`；
- 点名/轮询与自由发言各存在一份相同旁路。

#### 风险

最常见的真实超时发生在“已经收到部分正文之后”，恰好会命中这条旧回调。用户可能看到半句正文，刷新后仍保留；错误文本也会进入复制、TTS、上下文和记忆摘要。

#### 建议

- 抽出单一 `handleGroupStreamTimeout`。
- 初始 timeout 与每次 chunk 后的续期 timeout 都只调用该函数。
- partial content 统一经过供应商推理清理、output 正则和 finalizer。
- 错误原因只写 `generationError: "请求超时"`，不得拼进 `content`。
- 群聊 stopStreaming 同样使用 `generationNotice: "已停止生成"`，不要追加正文警告行。

#### 验收

- 点名、轮询、自由发言三种模式分别构造“收到半句后超时”。
- 落盘正文停在最后稳定句界，错误原因不进入正文和下一轮上下文。
- 重新加载后正文与提示状态保持一致。

### S3【中】长记忆预算仍是固定常量

#### 现状

- 单聊长记忆固定使用 6144 output tokens。
- 群聊长记忆固定使用 2048 output tokens。
- 原始第三轮评测已经出现 6144 被推理吃满，事实提案 JSON 中途截断。

本次 thought 修复只会阻止模型推理显示在角色消息中，并不会减少上游实际消耗的 reasoning tokens。

#### 风险

- 单聊可能保住摘要但丢失事实提案。
- 群聊 2048 的余量更小，在同类推理端点上风险更高，目前缺少对应的重复实测。
- 固定常量不会利用阶段 0 已采集的 reasoning P90，也不会随模型能力档案变化。

#### 建议

- 长记忆请求也接入 `resolveRequestBudget` / `modelOutputProfile`。
- 正文预算与推理余量分开计算；推理共享预算模型优先使用近期 P90。
- 在改成动态预算前，单聊可临时提高到 8192；群聊至少与单聊使用同一策略，不建议继续固定 2048。
- `finishReason=length` 且摘要可解析、事实 JSON 不完整时，明确记录“摘要已保存、事实未更新”，不要静默当作完整成功。

#### 验收

- DeepSeek V4 类模型重复 5 次，事实提案解析成功率达到 95% 以上。
- 非推理模型不会因为统一策略无条件请求 8192。
- 观测日志能区分“摘要完整但事实提案缺失”和“整次空响应”。

### S4【中】显式继续生成仍漏掉短复读

#### 现状

`trimContinuationOverlap` 默认阈值仍是 8。聊天输入辅助续写显式传入 4，但消息操作中的“继续生成”没有传阈值，因此仍使用 8。

这会漏掉“楼下的”“今天其实”“门外传来”等 3–7 字的重复接缝。旧评测中的 R8 因此仍未在该入口真正关闭。

#### 建议

- 不建议全局直接降到 3，容易误删“你的/他的”等常见短语。
- 为续写接缝新增专用策略：4 字直接去重；3 字仅在词边界、标点边界或完整短语重复时去重。
- 所有续写入口传入同一策略；自动补尾继续保留更保守的阈值。

#### 验收

- 覆盖 3/4/7/8 字重复以及“你的/他的”等误裁反例。
- 消息继续生成、输入框续写、Bridge 重生成得到相同接缝结果。

### S5【中】自动篇幅没有使用本轮意图和场景变化

#### 现状

`ResponsePolicy` 已预留 `userIntent` 和 `sceneFactor`，但当前上下文构建只传入会话模式、预设提示和最近回复长度。

因此用户在本轮说“简单说”“详细展开”“只回答一句”，模型提示本身虽然能看到这些文字，请求预算与 soft range 却不会同步变化；开场、场景转换、高压短回合也都使用默认系数 1。

#### 建议

- 先实现窄范围、可解释的意图检测，只识别明确词组，不做泛化语义猜测。
- 场景系数只根据确定事件调整，例如首轮/明确场景切换放大，高压即时问答收缩。
- 将检测结果写入阶段 0 观测，便于核对误判。

#### 验收

- “一句话回答”优先于会话的“展开”设置。
- 普通内容不误触发简短或展开。
- 上下文预留与实际请求仍来自同一次预算计算。

### S6【中】Android 未消费结构化完成状态

#### 现状

Bridge 已发送 finish reason，PC 消息也有 `generationNotice`、`generationError` 和 `contentRenderMode`。Android 当前没有对应的消费与展示逻辑。

#### 影响

- 移动端无法明确区分正常完成、自动收束、自动补尾、网络中断和用户取消。
- 同一条消息在 PC 与 Android 上可能只有正文一致，状态提示不一致。
- Android 仍依赖自己的 Markdown/thought 展示路径，没有使用阶段 5 的语义块标记。

#### 建议

- 扩展 Android DTO 和本地缓存字段，兼容缺省值。
- 在消息气泡下方展示与 PC 对齐的中性提示/错误提示。
- 消费 `contentRenderMode=blocks`，或明确记录移动端继续走兼容渲染的降级规则。

#### 验收

- 同一条 recovered、tail_repaired、network_error、cancelled 消息在两端显示同义状态。
- 老版本缓存和旧 PC 返回缺字段时仍能正常解码。

### S7【低】群聊语义块不支持 @提及高亮

#### 现状

群聊旧 Markdown 路径通过 `remarkMentionHighlight` 高亮 @角色名；`contentRenderMode=blocks` 路径直接渲染纯文本段落，没有经过该插件。

#### 建议

将提及识别提取为与 Markdown 无关的纯文本分段函数，供 Markdown 与 blocks 两种渲染路径复用，避免恢复原始 HTML 注入。

### S8【低】legacy 双管线仍待退出

legacy 仍保留旧排版协议、跳过 finalizer、旧 Markdown 渲染与 `normalizeRoleplayDialoguePrefixes`。它是必要的灰度回退，但也使预算、收尾和渲染长期存在两套行为。

建议按原计划，在连续两个正式版本确认 unified 无严重回归后：

1. 先隐藏 legacy UI 入口，保留配置兼容一个版本；
2. 再删除旧提示注入和新消息前缀补齐；
3. 最后保留旧消息 Markdown 只读兼容，不再保留旧生成管线。

### S9【低】测试日志噪声与临时文件

全量 Vitest 已通过，但测试环境全局把 `nanoid()` 固定为 `mock-id`。同一测试创建多条消息时会触发真实的 ID 冲突检测，持续输出“检测到消息 ID 冲突”。这属于测试夹具噪声，不等于生产环境仍在重复生成 ID。

同时工作区仍存在临时调试文件，例如：

- `src/components/chat/__tests__/_tmp_debug.test.tsx`：全量测试时打印整段 HTML；
- `scripts/_tmp_debug.py`；
- `scripts/decrypt-api-key.cjs`：若只是一次性评测辅助，需要决定归档、正式化或移除。

建议把测试 `nanoid` mock 改为递增序列，并清理或移出默认测试集合的临时文件。若正式应用仍出现 ID 冲突，应根据日志中的 characterId/sessionId/msgId 单独追踪，不应通过关闭告警掩盖真实冲突。

### S10【验证项】需要更新真实模型评测

thought 修复改变了提示词和可见输出口径，旧评测中把模型推理误当 `<thought>` 的样本不能继续作为角色心理质量结论。

建议重新执行：

- 单聊：代入式与全局叙事各 5 次；
- 群聊：点名、轮询、自由发言各 5 次；
- 续写：有输入/无输入、4 种变化档位；
- 至少一个共享推理预算模型和一个非推理模型。

新增检查项：

- `<thought>` 是否确实使用当前角色第一人称“我”；
- 是否包含模型计划、规则分析或上下文复述；
- 供应商 reasoning 是否完全不出现在流式 chunk、落盘正文、TTS 和记忆上下文中；
- 全局叙事正文是否保持第三人称，而 thought 仍属于焦点角色。

## 三、建议实施顺序

### 第一批：收尾一致性

1. S1：统一 output 正则、停止字符串和 finalizer 的顺序。
2. S2：合并群聊所有 timeout 回调，错误状态与正文分离。
3. 为两项补单聊/群聊/Bridge 对照测试。

完成标准：任何入口都不能在 finalizer 之后再次破坏正文结构，也不能把超时提示写进正文。

### 第二批：预算与续写质量

1. S3：长记忆接入模型档案与动态推理余量。
2. S4：统一续写接缝去重策略。
3. S5：接入明确用户篇幅意图；场景系数可作为第二步灰度。

完成标准：长记忆事实提案稳定产出，短复读明显下降，明确篇幅要求与实际请求预算一致。

### 第三批：跨端和展示一致性

1. S6：Android 消费完成状态。
2. S7：blocks 路径支持安全的 @提及高亮。

完成标准：PC/Android 对同一消息的正文、状态语义和关键样式一致。

### 第四批：清理与复测

1. S9：清理测试噪声和临时文件。
2. S10：重新跑真实模型评测并更新基线。
3. 满足版本观察期后执行 S8 的 legacy 退场。

## 四、当前验证状态

- 桌面全量 Vitest：228 个测试文件通过、1 个测试文件按配置跳过；2340 项通过、4 项跳过。
- Renderer 与 Electron TypeScript 检查通过。
- thought 相关定向测试通过，覆盖 OpenAI/OpenRouter、Claude、Gemini、Ollama、TTS、单聊/群聊提示与跨 chunk 推理过滤。
- Android 定向测试当前因本机 Gradle 无法建立 loopback connection 而未启动；这是环境级阻塞，尚不能把 Android 部分记为已动态验证。

## 五、不建议顺手混入本轮的问题

- 不重新加入或讨论已移除的族裔配置。
- 不重新设计已经稳定的方向 JSON、预设生成或世界书协议。
- 不用继续增大所有主对话的固定输出上限来掩盖 S1/S2。
- 不因为测试日志嘈杂而删除生产环境的真实 ID 冲突检测。

后续应保持逐批修复：每批先补失败测试，再改共享入口，最后跑全量测试与真实模型小样本复测。
