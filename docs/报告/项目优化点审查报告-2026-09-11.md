## 3. P0：安全缺陷

### P0-1：备份恢复可写出应用数据目录（目录穿越）

**位置**：`electron/services/backup.ts:252-269`（预校验）、`electron/services/backup.ts:297-339`（写入循环）

**状态**：`docs/报告/PC端修改回归测试报告-2026-08-25.md` 已登记为 P0-01，`docs/README.md` 明确标注「⚠️ 仍有效」。经比对 `0.17.0` / `0.17.1` / `0.17.2` 三版 CHANGELOG，**无任何一条提及修复**，代码与报告撰写时一致。

#### 缺陷成因

恢复流程存在两处独立缺陷，且互相放大。

**成因 A — 预校验是空操作。** 第 252-269 行的 `idFromZipPath()` 只取 `basename()` 后调用 `safeId()`，随即把返回值丢弃，唯一的循环体是一句注释：

```ts
const base = basename(zipPath)          // '../../../../pwned.json' -> 'pwned.json'
const id = base.slice(0, -5)            // 'pwned'  ← 非法路径段已被丢弃
if (zipPath.startsWith('characters/')) {
  return safeId(id)                     // 校验的只是 basename，放行
}
```

`safeId()` 本身没有缺陷，但它被喂进去的已经不是原始路径。此外 `chats/`、`groups/` 分支连这个空校验都不存在（第 261 行直接 `return id`）。

**成因 B — 写入路径无根目录边界校验。** 第 303-312 行按前缀分发目标目录，全部使用朴素 `join`：

```ts
} else if (zipPath.startsWith('characters/')) {
  dest = join(DIRS.characters(), zipPath.substring('characters/'.length))
}
```

`characters/../../outside.json` 既能通过 `startsWith('characters/')`，拼接后也会逃出 `DIRS.characters()`。**全仓库 `safePath()` 调用点统计为 0**——该函数已实现于 `electron/utils/pathGuard.ts:23`，单测覆盖了 `..`、绝对路径、`..\win` 三种变体（`electron/utils/__tests__/pathGuard.test.ts:82-88`），但生产代码从未接入。

**成因 C（放大器）— 哈希校验可绕过。** 第 241-245 行：manifest 中查不到哈希的条目仅记 `log.warn` 后继续：

```ts
const expected = manifest.hashes[entry.entryName]
if (!expected) {
  log.warn('备份条目无哈希记录，跳过校验', { entry: entry.entryName })
  continue          // ← 攻击者新增的恶意条目无需伪造哈希
}
```

因此攻击者只需构造一个 ZIP，植入一条 `characters/../../...` 条目即可，无需任何签名或哈希工作。

#### 实测复现

以 Node 还原 `idFromZipPath` 的预校验逻辑与目标路径拼接（仅计算路径，未写入文件系统）：

```
输入条目:  characters/../../../../../../QingYu-pwned.json
预校验结果(未抛错): QingYu-pwned
实际写入路径: C:\Users\QingYu-pwned.json
是否逃出数据目录: true
```

验证脚本：

```js
const { join, normalize, basename } = require('path')
const DIRS_characters = 'C:\\Users\\u\\AppData\\Roaming\\qingyu\\data\\characters'
const safeId = (id) => { if (!/^[a-zA-Z0-9_-]+$/.test(id)) throw new Error('illegal'); return id }

const zipPath = 'characters/../../../../../../QingYu-pwned.json'
const base = basename(zipPath), id = base.slice(0, -5)
const checked = zipPath.startsWith('characters/') ? safeId(id) : id   // 未抛错
console.log('预校验结果(未抛错):', checked)

const dest = join(DIRS_characters, zipPath.substring('characters/'.length))
console.log('实际写入路径:', normalize(dest))
console.log('是否逃出数据目录:', !normalize(dest).startsWith(normalize(DIRS_characters) + require('path').sep))
```

#### 影响面评估（不夸大）

- **触发方式**：需用户主动导入一个他人提供的 `.qingyu` 备份包。`electron/bridge/` 未暴露 restore 端点，**不构成远程任意文件写或 RCE**。
- **实际危害**：本地任意路径写（覆盖用户可写权限内的任意文件）。对一个主打「纯本地存储 / 数据安全」的桌面客户端，属发布级缺陷。
- **修复成本**：低。`safePath()` 已实现且有单测，接入即可。

#### 验收要求

1. 还原循环的每个目标路径统一走 `safePath(rootDir, ...segments)`，拒绝绝对路径、盘符、反斜杠变体、空路径、`.` 与 `..` 段。
2. 对最终 `resolve(dest)` 做根目录边界断言，确保仍在允许的目标根内。
3. 哈希策略收紧：ZIP 中每个非目录条目必须在 manifest 中有哈希记录；manifest 中的哈希条目也必须在 ZIP 中存在。
4. **补齐回归测试**（当前完全缺失，见 P2-1）。

### P0-2：备份宣称不含凭据，但实际仍导出敏感信息

**位置**：`electron/services/backup.ts:33-53`（剥离逻辑）、`electron/services/backup.ts:106-115`

**状态**：同为报告 P0-02，同样未修复。

#### 缺陷成因

`stripSecretsLocal()` 仅遍历 4 个集合：

```ts
const SECRET_COLLECTIONS = [
  { get: (s) => s.connectionProfiles, prefix: 'profile'  },
  { get: (s) => s.ttsModels,          prefix: 'tts'      },
  { get: (s) => s.imageGenModels,     prefix: 'imagegen' },
  { get: (s) => s.visionModels,       prefix: 'vision'   },
]
```

**遗漏两处**：

| 遗漏项 | 说明 |
| --- | --- |
| `settings.semanticTrigger.apiKey` | 语义检索嵌入服务的 Key，未纳入剥离流程 |
| `mcp-servers.json` 的 `env` | 界面明确允许填写 `API_KEY=xxx` 等变量，原样进入备份 |

与此同时 `EXCLUDED_ITEMS`（`backup.ts:33`）与设置页均向用户展示「API Key / 凭据（safeStorage）未包含」——**错误的安全预期比缺陷本身更危险**：用户会放心把备份包发给他人排障。

#### 验收要求

1. 将 `semanticTrigger.apiKey` 纳入 `safeStorage` 与备份剥离流程。
2. MCP `env` 不得原样入包：至少按敏感键名规则（`KEY` / `TOKEN` / `SECRET` / `PASSWORD`）脱敏，更稳妥的做法是把 MCP 凭据单独存入安全存储。
3. 增加 **ZIP 内容断言测试**：在测试凭据写入设置后导出，直接搜索压缩包全部条目，确保不存在明文密钥文本。

## 4. P1：架构层风险

### P1-1：主进程反向依赖渲染层源码

**现状**：`electron/` 生产代码中有 **13 条 import 语句、跨 8 个文件**，引用 **10 个 `src/` 模块**：

| 主进程文件 | 引用的 `src/` 模块 |
| --- | --- |
| `bridge/routes.ts` | `context/contextBuilder`、`components/chat/aiInputHelper`、`utils/messagePostProcess`、`utils/memory`、`utils/memoryWindow`、`store/chatConstants` |
| `bridge/chatService.ts` | `context/contextBuilder`、`utils/regex` |
| `chat/contextService.ts` | `context/contextBuilder` |
| `chat/postProcessor.ts` | `utils/regex` |
| `chat/visionRouter.ts` | `utils/visionModel` |
| `ipc/embedding.ts`、`services/vectorStore.ts` | `utils/vector` |
| `services/adapters/ollama.ts` | `utils/chatTemplates` |

**为何是问题**：

1. **层次倒置**。`src/` 本应是「可替换的 UI 层」，现在修改 UI 目录下的工具函数会连带影响主进程与 Android 桥接的运行时行为。
2. **职责未分离的信号**。主进程引用 `src/components/chat/aiInputHelper`，说明**纯逻辑与 React 组件尚未拆开**——一个名为 component 的文件被主进程依赖，是典型的边界泄漏。
3. **项目已识别该问题，但选择了有风险的规避方式**。`electron/utils/variables.ts` 的文件头注释原文：

   > 变量替换工具（electron 主进程版本）
   > **与 `src/utils/variables.ts` 中的 `replaceVariables` 保持一致。**
   > 此处独立定义，避免 `electron/` 跨层导入 `src/` 代码。

   即：通过**复制粘贴**规避跨层导入。两份实现靠注释约定同步，无任何机制保证一致性——这正是"改一边漏一边"的经典温床。

**修复方向**：将下列纯逻辑模块下沉到 `shared/`（该目录本就为跨端共用而存在，`shared/chat-core/` 已具备容纳能力）：

```
src/context/contextBuilder.ts   -> shared/chat-core/contextBuilder.ts
src/utils/regex.ts              -> shared/chat-core/regex.ts
src/utils/memory*.ts            -> shared/chat-core/memory/
src/utils/vector.ts             -> shared/chat-core/vector.ts
src/utils/chatTemplates.ts      -> shared/chat-core/chatTemplates.ts
src/utils/visionModel.ts        -> shared/chat-core/visionModel.ts
src/utils/variables.ts          -> shared/chat-core/variables.ts（并删除 electron 侧副本）
```

**配套门禁**：在 `eslint.config.js` 增加 `no-restricted-imports`，禁止 `electron/**` 引用 `src/**`，使该类依赖无法回潮。

### P1-2：单聊与安卓/Relay 双生成管线并行

**现状**：同一套业务逻辑存在两条独立调用链。

| 环节 | PC 桌面 | Android / Relay |
| --- | --- | --- |
| 生成实现 | `src/store/streamController.ts`、`chatGeneration.ts`、`memoryManager.ts` | `electron/chat/orchestrator.ts`、`realModel.ts`、`bridge/chatService.ts` |
| 上下文构建 | `src/context/contextBuilder` | 复用（但经反向依赖，见 P1-1） |
| 正则后处理 | `src/utils/regex` | `electron/chat/postProcessor.ts` |
| 长记忆 | `src/store/memoryManager.ts` | `bridge/routes.ts` 内联 + `src/utils/memory` |

**风险表现**：`0.17.2` 的修复条目恰好印证了该风险——「空结果或请求失败会显示可见反馈」「全局旁白不再被用户身份过滤器误删」「续写身份继承原消息，即使之后切换模式也不会串台」，这些修复**横跨两侧实现**。双实现的典型症状正是：改动只落一边、单测全绿、真机表现为「串台」。

**修复方向**：让两侧共用 `electron/chat/orchestrator.ts`（其 ports/adapters 抽象已经具备复用条件），或将共享逻辑沉淀至 `shared/chat-core/`，由两处薄适配层调用。**不建议在发版窗口内动。**

## 5. P2：工程加固

### P2-1：覆盖率门禁形同虚设

**位置**：`vitest.config.ts:25-32`

```ts
thresholds: {
  // 2026-08 实测：lines 18% / functions 44% / branches 70%
  // 阈值调整为可达成且有约束力的水平（原 80/80/75/80 从未通过，形同虚设）
  lines: 15, functions: 35, branches: 65, statements: 15,
}
```

注释坦诚记录了阈值从 80 降到 15 的原因（原值从未通过）。但结果是从一个极端走向另一个极端：**5.6 万行的 `src/` 仅要求 15% 行覆盖率**，几乎无法产生约束力。

**当前测试分布**（源文件数 / 测试文件数）：

| 目录 | 源文件 | 测试文件 |
| --- | ---: | ---: |
| `electron/services` | 49 | 27 |
| `electron/bridge` | 20 | 23 |
| `electron/ipc` | 18 | 19 |
| `electron/chat` | 14 | 19 |
| `electron/relay` | 10 | 4 |
| `electron/mcp` | 4 | 2 |
| `electron/utils` | 5 | 3 |

**最关键的盲区**：`electron/services/__tests__/` 下**不存在任何 backup / restore 相关测试**。这正是 P0-1、P0-2 能存活三个月而无人察觉的直接原因——没有测试遮蔽，改动或回退都不会变红。

**建议**：改为按路径分级阈值，把安全敏感目录单独收紧：

```ts
thresholds: {
  lines: 15, functions: 35, branches: 65, statements: 15,   // 全局现状
  'electron/services/backup.ts': { lines: 70, branches: 60 },
  'electron/utils/pathGuard.ts': { lines: 90, branches: 80 },
  'electron/bridge/auth.ts':     { lines: 70, branches: 60 },
}
```

### P2-2：首屏包体偏大

**实测**：

| 指标 | 数值 |
| --- | --- |
| NSIS 安装包 | 120.5 MB |
| 前端产物总量 | 1.58 MB |
| 首屏主 chunk `index-*.js` | 1.02 MB（占前端产物 65%） |
| 其余页面 chunk | 40–80 KB |

**成因**：`src/App.tsx` 中除 `ChatPage` 外全部页面均已 `lazy()` 拆包（这一点做得很好），但 `ChatPage` 是唯一静态导入的页面，把 `react-markdown + remark-gfm + rehype-highlight + react-virtuoso` 整体带入首屏。

**建议**：将 `MessageBubble`（Markdown 渲染重依赖所在）与虚拟列表拆为独立 chunk，`ChatPage` 内动态导入。

> 安装包 120.5 MB 主要来自 Electron 运行时 + `onnxruntime-node` + `@huggingface/transformers` + `tiktoken`，`package.json` 的 `build.files` 已对 darwin/linux/arm64/web 变体做了排除，可优化空间有限，不建议在此投入。

### P2-3：缺少 CSP

**位置**：`index.html`（仅含 charset / viewport / title / favicon）

XSS 面控制得不错：`MessageBubble.tsx:389`、`GroupChatMessage.tsx:247`、`AnnouncementsPage.tsx:82` 均已显式移除 `rehypeRaw` / `allowDangerousHtml`（注释标注为 BUG-09 修复），且 `electron/main.ts` 已启用 `contextIsolation: true` + `sandbox: true` + `nodeIntegration: false`。

但缺少纵深防御的最后一层。浏览器侧建议补充：

```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
               img-src 'self' data: blob: http: https:; connect-src 'self' http: https: ws: wss:">
```

### P2-4：依赖声明语义错位

`react`、`react-dom`、`zustand`、`react-router-dom`、`react-markdown`、`node-edge-tts` 等**运行时代码**当前声明在 `devDependencies`。

目前因 esbuild / Vite 全量打包而未暴露问题，但 `electron/ipc/tts.ts:334` 使用动态 `import('node-edge-tts')`，且 `electron-build.mjs:35` 已将其列入 `external`：

```js
external: ['electron', '@huggingface/transformers']   // localEmbeddingWorker
```

一旦有人对主进程 bundle 追加 `external: ['node-edge-tts']`，**装机即崩**（生产安装不含 devDependencies）。建议将这些包移入 `dependencies`，并在 `electron-build.mjs` 中显式声明主进程运行时 external 白名单。

## 7. 项目已具备的良好实践（不应改动）

为避免上述问题造成负面印象，以下方面经核查确实做得好，属于**应当在重构中保留**的资产：
