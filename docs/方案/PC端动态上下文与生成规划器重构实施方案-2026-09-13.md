## 1. 执行结论

本次工作不是“再造生成规划器 V2”，而是完成现有规划器的闭环并逐步扩展其职责。

必须按以下顺序执行：

1. 先完成阶段 8：推理门控、运行时探测、流式提前中止、空正文至多一次降级重试和会话熔断。
2. 同批打通生成观测的回读，让现有 `recentReasoningTokens` 真正进入 `resolveRequestBudget`；统计值只帮助无可靠门控的路径估计和止损，不取代服务端门控。
3. 让剧情方向入口停止直接传 `1536`，收编到现有后台任务档案、统一预算和阶段 8 的 `off` 门控。
4. 完成阶段 7.4 的真实样本灰度；在 legacy 退出门槛未满足前，不新增 `generationPlannerV2` 开关，也不删除旧回滚链路。
5. 阶段 8 稳定后，再扩展现有 `ModelOutputProfile` 的能力元数据，并让上下文候选分配器先影子运行、后分层切换。
6. `8192` 通用安全上限在门控和实测完成前保留。是否提高或删除必须通过独立决策门，不属于本方案的预设结论。
7. 动态记忆、世界书与历史分配按“记忆 → 世界书 → 历史压缩”的顺序迁移；每一步都复用同一个输出预留值并可单独验收。
8. 最后迁移 PC 设置与预设。只有 500 次 unified 有效生成、阶段 8 指标和跨端 fixture 同时达标，才允许退出 legacy 和删除兼容代码。

按 W0–W11 的区间求和，预计工作量约 **39–61 工程人日**，另加真实模型灰度所需的自然样本周期。2–3 名实现者并行时，受 W3→W5、W7→W9 等串行关键路径约束，预计 5–8 周；任何排期都不得把“收集 500 次有效生成”伪装成可在单元测试中完成的开发任务。

## 2. 已确认事实与故障边界

### 2.1 真实故障证据

本地 `generation-observations.jsonl` 中 `taskType === 'direction'` 共 15 条：

- 6 条 `bodyVisibleChars = 0`；
- 这 6 条的 `reasoningTokens` 都等于 `requestedMaxTokens = 1536`；
- 这 6 条均以 `terminationCause = provider_length` 结束；
- 即方向任务当前样本中的空正文失败率为 40%。

本地对照评测还显示：

- `max_tokens = 4000` 时，推理消耗 3981，正文仅 50 字符；
- `max_tokens = 8000` 时，推理消耗 8000，正文为 0。

这证明共享窗口模型的推理会随上限弹性增长。单纯把 `1536` 改成 `4096`、`8192` 或更大值，不构成修复。

### 2.2 当前唯一直接绕过统一预算的已知入口

`src/store/dialogueDirectionRunner.ts` 直接使用 `DIALOGUE_DIRECTION_MAX_TOKENS = 1536`，并传 `reasoningMode: 'disabled'`。聚合端若静默忽略关闭推理参数，该请求仍可能让推理吃满全部输出。

Bridge 方向入口 `electron/bridge/dialogueDirections.ts` 使用同一常量，也必须在 PC 单聊修复验证后对齐；不能只修桌面渲染进程而留下 Bridge 漂移。

### 2.3 当前限制的性质必须分清

| 项目 | 当前来源 | 性质 | 本期处置 |
|---|---|---|---|
| `MAX_REQUEST_OUTPUT_TOKENS = 8192` | `shared/modelOutputProfile.ts` | 通用运行安全阀 | 暂保；阶段 8 和能力验证后单独决策 |
| 模型档案 `outputLimit = 8192` | `shared/modelOutputProfile.ts` | 内置能力回退/保守上限 | 改为带来源与置信度的能力值，但不在首批盲目放大 |
| DeepSeek 推理默认 3072、最高 4096 | 同上 | 无门控时的估计与钳制 | 接入实测样本；可靠门控在场时以门控为准 |
| 长记忆 `min(800, budgetBase*0.1)` | `src/context/contextBuilder.ts` | 固定注入上限 | 在上下文分配阶段移除 |
| 世界书 30%、0.4/0.9 分桶 | `src/store/chatConstants.ts` | 固定分配策略 | 影子对比后迁移为统一候选分配 |
| 方向 1536 | `shared/dialogueDirections.ts` | 入口硬编码请求上限 | 第一批收编到统一预算与 `off` 门控 |
| 记忆约 6293 | `resolveRequestBudget(2500)` 的派生结果 | 动态派生值 | 不作为“待删常量” |
| 压缩约 3918 | `resolveRequestBudget(600)` 的派生结果 | 动态派生值 | 不作为“待删常量” |
| 尾部修复约 3418 | `resolveRequestBudget(200)` 的派生结果 | 动态派生值 | 不作为“待删常量” |
| 标题、结构最小长度 | 后台任务档案/解析器 | 有效性下限或软目标 | 可保留；不能混称模型硬上限 |

### 2.4 已知平台债务

Android 暂不接入本期 PC 的门控和动态上下文，因此 Android 主对话在共享推理窗口模型上的空正文风险不会因本期自动消失。验收描述必须写成：

- Android 编译、协议解析和现有行为未被破坏；
- PC 新字段对旧 Android 可选且向后兼容；
- Android 仍有同类生成风险，进入下一期明确待办；
- 不得写成“Android 问题已解决”或“多端已统一”。

### 3.2 部分完成，必须补闭环

1. `resolveReasoningReserve` 已支持 `recentReasoningTokens` 和 P90×1.2，但生产调用点没有传样本。
2. 观测文件只有追加与轮转，没有读取、索引、聚合或 IPC 查询。
3. `reasoningMode: 'disabled'` 只是意图；端点可能拒绝或静默忽略，没有可信度记忆。
4. OpenAI、Claude、Gemini 的推理参数仍有适配器私有策略，语义不统一。
5. 方向任务有结构修复重试，但没有“推理挤占”恢复；两种重试必须共享总次数规则，避免一轮产生无限组合。
6. 上下文已有世界书评分、语义事实、分层记忆与历史裁剪，但各层预算仍由分散比例决定。
7. `generationPipeline` 的 legacy/unified 灰度尚未完成 500 次有效生成退出门槛。

## 4. 不变量与禁止事项

### 4.1 唯一事实来源

- 正文期望：`ResponsePolicy` 或 `BackgroundGenerationProfile`；
- 输出预算：`resolveRequestBudget`；
- 推理约束：阶段 8 的 `resolveReasoningGate`；
- 最终正文处理：`generatedReplyPipeline` / 统一终止协调入口；
- 观测记录：`GenerationObservation`；
- 回滚：现有 `generationPipeline`，以及阶段 8 临时的 `reasoningGateEnabled` kill switch。

不得增加 `GenerationIntentV2`、`OutputPlannerV2`、`generationPlannerV2` 或第二份观测文件。

### 4.2 预算同源

一次请求必须满足：

```text
上下文构建使用的 reservedOutput
  === 最终 ChatParams.maxTokens
  === 观测中的 requestedMaxTokens
```

重试时允许因门控降档重新计算输出预算，但必须复用同一份业务上下文候选快照；不得悄悄改变用户消息、世界书命中或记忆检索结果。

### 4.3 重试上限

- 推理挤占：同一生成轮最多一次自动降档重试；
- 已有正文的 provider length：走既有稳定边界/补尾，不能触发整条重生成；
- 结构修复：方向等后台任务已有一次结构修复时，必须由统一 attempt ledger 决定是否还允许请求；
- 参数被 400 明确拒绝时的“去参重发”是传输层协商，不得无限递归；每个 knob 每个请求至多尝试一次；
- 会话内连续两次推理降档仍失败时熔断，后续从更低档开始，并且提示只展示一次。

建议统一记录：

```ts
interface AttemptLedger {
  logicalRequestId: string
  transportAttempts: number
  reasoningRecoveryAttempts: number
  structureRepairAttempts: number
  tailRepairAttempts: number
}
```

该结构用于观测和约束，不要求替换现有 requestId；每次物理请求仍应有可关联的子 requestId。

### 4.4 数据与隐私

- 默认不保存提示词、角色卡、世界书、回复正文或完整 URL；
- 端点键使用标准化地址的不可逆短哈希，先移除凭据、query 和 fragment；
- renderer 只取得聚合后的样本或分位数，不取得诊断文件路径与原始 JSONL；
- 旧日志读取失败、单行损坏或字段缺失不得阻塞生成；
- `tailSample` 属现有诊断遗留字段，不得被学习闭环读取或展示为模型档案内容。

### 4.5 安全上限

在完成第 10 节决策门前：

- 保留 `MAX_REQUEST_OUTPUT_TOKENS = 8192`；
- 不因模型宣传值自动申请超长输出；
- 不把端点一次成功响应推断成永久物理能力；
- 不把“模型输出上限”和“本轮需要的输出量”混为一谈。

## 5. 目标架构：扩展现有链路，而不是替换

```text
ResponsePolicy / BackgroundGenerationProfile
                    │
                    ├── ModelOutputProfile（现有，逐步补能力来源）
                    ├── UsageProfile（从现有观测日志回读）
                    └── ReasoningGate（阶段 8，服务端约束 + 探测）
                    │
                    ▼
resolveRequestBudget（现有唯一输出预算入口）
                    │
                    ├── requestMaxTokens
                    ├── reasoningReserve / gateTokens
                    └── riskNotice
                    │
                    ▼
ContextBuilder（现有）→ ContextCandidate/Allocator（渐进接入）
                    │
                    ▼
ChatParams + adapter gate mapping
                    │
                    ▼
流式审计 → 阶段 8 恢复 → 阶段 7 finalizer
                    │
                    ▼
GenerationObservation（现有）→ UsageProfile 回灌
```

### 5.1 `ResponsePolicy` 与后台任务档案

主对话继续由 `ResponsePolicy.hardMaxChars` 表达正文保护线。后台任务不强行套用主对话篇幅档位，而由 `BackgroundGenerationProfile` 给出 taskType、期望正文/结构最小空间、默认 gate、允许的修复类型和解析成功判据。

方向任务应声明“短结构化正文、默认 off、允许一次结构修复”，而不是声明“1536 Token”。

### 5.2 `ModelOutputProfile` 的渐进扩展

首批不重命名模块。需要时在现有类型上增加输入/combined limit、token accounting、capability source、confidence 和 updatedAt。若后期认为名称已不准确，可以在所有调用统一后做纯机械重命名；重命名不能和能力语义改造放在同一提交。

能力优先级：用户明确覆盖 > 供应商可验证元数据 > 精确内置规则 > 运行时保守纠正 > fallback。运行时错误只允许降低当前端点的可用能力或置信度，不能污染同名模型的其他端点。

### 5.3 `UsageProfile`：让已采数据参与规划

建议主进程维护只读聚合：

```ts
interface UsageProfileKey {
  provider: string
  endpointFingerprint: string
  model: string
  taskType: string
  reasoningModeOrGate: string
}

interface UsageProfile {
  sampleCount: number
  recentReasoningTokens: number[]
  reasoningP90?: number
  bodyVisibleCharsP95?: number
  reasoningFilledRate: number
  lastUpdatedAt: number
}
```

实现规则：

1. 首次查询时懒加载当前 JSONL；如发生轮转，可读取 `.old`，但总读取量必须有界。
2. 单行 JSON 损坏时跳过并计诊断，不让整个档案失效。
3. 每次新观测写入后同步更新内存索引，避免每轮扫盘。
4. 只返回最近有限个数值样本或聚合分位数；建议每键最多 32 条、全局 LRU 最多 256 个键。
5. 样本不足 5 条时标记低置信度；不足 10 条时沿用当前 `percentile90` 的保守最大值语义。
6. `reasoningTokens === 'unknown'` 不转成 0，也不参与分位数。
7. 成功、推理触顶、参数拒绝分别计数，避免只学习成功样本造成幸存者偏差。

IPC 只暴露聚合查询，例如 `ai:getGenerationUsageProfile`；preload 返回数值结构。发送编排在构建上下文前异步预取并缓存，随后把样本传入现有 `resolveChatRequestPlan` / `resolveRequestBudget`。不得让纯函数内部直接访问文件或 Electron。

### 5.4 推理门控与预算关系

以阶段 8 为准：

```text
可靠 gate：requestMaxTokens = bodyReserve + gateTokens
不可靠/无 gate：requestMaxTokens = bodyReserve + max(档案余量, 近期 P90 估计)
```

- `recentReasoningTokens` 是估计和提前中止阈值，不是推理硬约束；
- 方向任务的正确修复是 `off` 门控 + 静默忽略探测 + 提前中止 + 一次降级恢复，不是把 P90 算得更大。

### 5.5 上下文候选与分配器

```ts
interface ContextCandidate {
  id: string
  kind: 'protocol' | 'character' | 'current-state' | 'memory' |
        'worldbook' | 'history' | 'example' | 'group-state'
  estimatedTokens: number
  mandatory: boolean
  stablePrefix: boolean
  relevance: number
  recency: number
  importance: number
  continuity: number
  dedupeKey?: string
  originalOrder: number
}
```

相同输入必须得到相同顺序与选择；评分相同时按 `originalOrder`、再按稳定 `id` 排序，避免缓存前缀抖动。

分配顺序：

1. 协议、当前用户消息、角色核心与当前场景等 mandatory 块；
2. 最近连续对话和当前群聊参与者状态；
3. 当前状态、相关长期事实与高相关世界书；
4. 示例、低相关记忆、较早原始历史；
5. 若仍超限，先去重，再降低相关块，再用既有摘要替换旧原文；
6. 最后才移除次要设定；持久化记忆永不因本轮分配被删除。

分配器首轮只做影子计算，记录“现有选择 token / 新选择 token / 各类数量 / 是否超预算”，不得记录内容。影子结果稳定后按类别逐步接管，不能一次替换整个 `contextBuilder`。

### 5.6 序列化后最终审计

- 先用现有估算器做候选选择；
- 适配器请求体准备逻辑应可在发送前返回可计数的序列化视图；
- 有供应商 tokenizer 时使用精确计数；没有时使用带 `accountingConfidence: estimated` 的保守估算；
- 最终输入预算必须扣除同源 `requestMaxTokens` 和协议安全余量；
- 审计超限时只回到 `ContextAllocator` 降级一次，不在适配器里私自截消息。

本期验收不能把所有供应商都宣称为“精确 Token”。应分别记录 `exact / provider-reported / estimated`。

## 6. 恢复状态机

### 6.1 推理挤占

严格复用阶段 8：

```text
无正文 + reasoning_gate_exceeded
或 length + 正文 < 20 + reasoning/completion ≥ 0.9
或无 usage 时 length + 正文为空
        │
        ▼
降低一档 gate，复用同一上下文快照，至多重试一次
        │
        ├── 成功：进入阶段 7 finalizer，用户只看到最终消息
        └── 再失败：记录并熔断，展示一次可操作错误
```

不得加入“按实际推理消耗再扩大输出”的恢复步骤。

### 6.2 有正文的长度截断

- 不整条重生成；
- 使用既有稳定句界、结构闭合与一次短补尾；
- 补尾和推理降档触发条件互斥；
- UI 保持同一条消息，落盘仍由阶段 7 latch 保证至多一次。

### 6.3 上下文超限

1. 解析供应商返回的限制信息，只记录结构化数值；
2. 降低当前端点能力置信度；
3. 用同一候选快照重新分配；
4. 自动重试一次；
5. 不删除持久化记忆；
6. 与推理恢复共享 `AttemptLedger`，防止两类恢复交叉放大请求数。

### 6.4 方向任务的双重修复约束

- 推理挤占发生在第一物理请求：允许一次降档重试；若第二次得到合法结构则结束；
- 第二次得到非空但结构不合法：不再进行第三次请求，记录 `structure_invalid_after_reasoning_recovery`；
- 第一请求得到非空但结构非法：允许现有一次结构修复；结构修复请求若再推理挤占，不再额外降档第三次；
- 方向任务每个逻辑请求最多 2 次模型调用。

## 9. 测试与验证矩阵

### 9.1 纯函数与属性不变量

`resolveRequestBudget`：

- 永不超过模型能力、通用安全阀和用户硬上限；
- 可靠 gate 时为正文保留最小空间；
- P90 样本缺失、unknown、异常值稳定回退；
- 增加 `hardMaxChars` 时预算不反向减少，除非命中硬上限；
- 2500/600/200 等结果是公式派生。

`ContextAllocator`：

- 总量不超过预算；
- 可行时 mandatory 全保留；
- 选择确定，输入对象不变；
- 同一 `dedupeKey` 最多一项；
- 增大预算通常保持单调包含；
- NaN、负分、空候选不崩溃。

`UsageProfile`：

- unknown 不转 0；
- 隔离键完整；
- 损坏行不污染其他记录；
- 样本与键数量有界；
- 旧 schema 可读。

### 9.2 状态机

| 场景 | 期望 |
|---|---|
| stop + 完整正文 | 正常收尾，无重试 |
| length + 有稳定正文 | finalizer/补尾，绝不整条重试 |
| length + 空正文 + reasoning 证据 | 降档一次 |
| gate early abort + 空正文 | 降档一次 |
| 第二次仍推理挤占 | 最终错误 + 熔断 |
| 用户 cancel | 不重试、不计失败熔断 |
| timeout/network | 按阶段 7 分类并保留允许保存的正文 |
| content filter | 不重试 |
| 400 拒绝 gate | 去参一次，写 probe |
| 200 接受 off 但仍有 reasoning | disableIgnored + early abort |
| 方向结构非法 | 最多一次结构修复，总调用 ≤ 2 |
| 迟到 done/error | latch 幂等，只落盘一次 |

### 9.3 固定上下文场景

1. 8K 小窗口 + 长角色卡；
2. 64K + 100 轮普通单聊；

5. 多角色群聊；

9. 供应商报告窗口小于内置档案；
10. 用户硬上限低于最小可用输出。

### 9.4 真实模型矩阵

至少包含 DeepSeek 支持门控端点、静默忽略 off 的聚合端、OpenAI 推理模型、Claude 扩展思考、Gemini thinking、非推理模型和 Ollama/本地模型。

## 10. `8192` 安全阀的独立决策门

### 10.1 当前决定

W1–W10 保留 `MAX_REQUEST_OUTPUT_TOKENS = 8192`。本方案不预承诺删除，也不把“模型支持 384K 输出”等价为“应用应允许普通单轮申请 384K”。

### 10.2 允许评估变化的前置条件

1. G1 达标，推理不再依赖扩大输出止损；
2. 能力档案能区分模型输出、combined window 和端点覆盖；
3. 序列化后输入审计可用；
4. 用户硬上限、费用保护与取消生效；
5. 存在明确正文需求被 8192 阻止，而不是推理无界吃满；
6. 超过 8192 的成功样本证明正文收益、成本和延迟可接受；
7. legacy 退出门未被绕过。

ADR 可得出：保留 8192、按任务开放更高有限档、按高置信能力动态设置、或只对显式长篇任务开放。证据不足时默认保留。

## 11. 上线观测与退出标准

### 11.1 指标分组

至少按 provider + endpoint fingerprint + model、task/generation type、gate/knob/probe confidence、generationPipeline、rollout 版本、上下文区间分组。不能只看全局均值。

### 11.2 核心指标

- 推理挤占最终可见失败率；
- early abort 次数与节省时长；
- 降档率、成功率、额外 token 和延迟；
- 正文截断率与补尾成功率；
- 上下文超限与重分配成功率；
- memory/worldbook/history 各类注入 token；
- mandatory 丢失计数（必须为 0）；
- 记忆召回与矛盾人工抽样；
- 首 token / 总耗时 P50、P95；
- 缓存命中率与估算费用；
- 重复落盘、格式破损、跨端失败（必须为 0）。

### 11.3 停止上线条件

出现正文丢失/重复落盘、恢复超次数、取消后重试、协议无法解析、删除持久化记忆、mandatory 丢失、敏感信息进日志，或成本/延迟显著倒退时，立即停止扩大灰度。回滚只切执行逻辑，不清空用户数据或观测。
