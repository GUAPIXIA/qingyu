## 1. 目标与建设范围

让 Codex 或其他 Agent 收到自然语言测试/操作要求后，可以使用标准工具：

1. 发现 PC 可调用的动作、参数、前置条件和执行层级。
2. 启动隔离的真实 Electron，或连接确实具备自动化条件的指定实例。
3. 调用现有 API 或按 UI 操作现有功能，读取状态、等待异步结果。
4. 对真实结果做断言，收集截图、日志、导出文件和持久化证据。
5. 通过 CLI 或 MCP 得到一致的结构化结果，组合完整的测试旅程。

**自然语言 → 外部 Agent → CLI/MCP → 外部驱动 → 现有 PC 功能。** 工具自身不内置 LLM、不把指令转送 PC 聊天模型，也不依赖 PC 普通聊天的 tools 参数。

实施改动限定在 `tools/pc-agent/`、`scripts/check-pc-agent.mjs`、必要的专项测试、依赖登记及文档。`electron/`、`src/`、`shared/` 产品行为和业务协议不因工具建设改变。发现产品缺陷应另列缺陷和证据，修复按单独任务范围执行。

阶段 0 的关键假设**已经有本仓库的实机证据兜底**：`output/playwright/spatial-real-2026-10-03/launcher.cjs` 就是“外部 launcher 设置隔离 `userData` 后加载现有主 bundle”的可用实例，方案不再把它当作未知风险，只需把它整理为不写死角色/端口/输出目录的公共运行器。

## 2. 复用路线

| 现有设施 | 用法 |
|---|---|
| 真实 Electron + 现有 preload/IPC | API 调用和业务状态核验的主路径 |
| Playwright Electron/页面/frame 操作 | 主窗口、表单、消息、嵌入画板和交互流程 |
| `output/playwright/spatial-real-2026-10-03/launcher.cjs` 等真实 GUI 临时驱动 | 阶段 0 的可行性与隔离启动依据；提取生命周期、隔离 userData 和主窗口识别经验，去除写死的角色/端口/输出目录 |
| `electronHarness` | 保留服务级专项打包/启动/日志采集；结果标明服务级，不能冒充完整 UI |
| `browserHarness` | 保留页面/mock 回归；结果标明模拟层 |
| `ipc-api.ts`（28 个命名空间） | 盘点可调用业务接口，工具侧生成目录骨架并建立精确映射和运行时 schema |
| 既有 AI/画板/同步专项 | 包装为可发现的 test suite，不复制其业务逻辑 |
| `check-contracts` / `check-boundaries` / `check-forwarders` 门禁 | 契约漂移检查的既有模式；`check:pc-agent` 照此实现（`check-contracts` 当前已知红，两者结果分别记录） |

不恢复旧 `/api/v1` 伴侣接口，不扩展 `/sync/v1` 为全端控制接口，不重建已删除的 MiMoCode 桥接。

## 3. 两个入口共用一个运行器

```text
外部 Agent
  ├─ 终端：pc-agent CLI（JSON 输入/输出）
  └─ MCP client：独立 pc-agent MCP server（stdio）
          ↓ 同一动作目录、schema、执行与结果协议
本地 Session Host / Driver
  ├─ 生命周期：启动、窗口识别、隔离数据、关闭/重启
  ├─ IPC/API adapter：实际页面调用已暴露 window.api
  ├─ UI adapter：真实点击、输入、选择、frame 与等待
  ├─ 专项 adapter：现有服务/模型/浏览器测试脚本
  └─ 观察/断言/证据：状态读回、日志、截图、产物
          ↓
      轻语现有 Electron / 原产品接口 / 原业务落盘
```

CLI 进程可以多次调用同一自动化会话。由外部 Session Host 持有 Playwright/Electron 句柄，CLI 与 MCP 经共享客户端调用它；默认使用 Windows 本地命名管道。宿主会话 ID、连接令牌和文件权限限定当前测试会话，stdout 不打印凭据。

MCP server 是外部 Agent 注册的独立程序，不配置到轻语自己的 MCP 页面。启动和连接描述由工具包生成；用户不需要在 PC 产品中启用新功能。

### 3.2 依赖与安装归属（v2 定案）

- `tools/pc-agent/` 是带 `package.json` 的**独立包**，加入 `pnpm-workspace.yaml` 的 `packages`，由根 `pnpm install` 统一安装；依赖只写在该包内，**不进根 `dependencies`/`devDependencies`**。
- 依赖收紧到最小集：Electron 自动化所需能力 + `@modelcontextprotocol/sdk`。浏览器渲染回归仍走 `browserHarness`；若工具需要自带浏览器驱动，优先 `playwright-core` + 系统已装浏览器（`channel: 'msedge'`），避免触发浏览器二进制下载；确需下载时按仓库既有 `allowBuilds` 机制显式登记，不做隐式依赖。
- **不得继续从 `spatial-board/package.json` 借 Playwright**（现状见 [browserHarness.mjs](../../scripts/lib/browserHarness.mjs)）。`browserHarness` 自身可维持现状，但 `pc-agent` 必须自持依赖。
- Electron 可执行文件路径、Node 版本要求、平台判定集中在 `platform.mjs` 一处解析；不复制 `scripts/lib/electronHarness.mjs` 里的硬编码路径。
- 根 `package.json` 增加 `pc-agent` 与 `check:pc-agent` 两个入口；`pnpm-workspace.yaml`、`tools/README.md`、`scripts/README.md` 同步登记。

### 3.3 会话所有权、并发与平台（v2 新增）

- **所有权**：一个 session 唯一归属一个 run 根目录、一个隔离 `userData`、一个外部客户端身份。`session.json` 只放可公开字段；令牌、管道名和权限描述放 `runtime/`。
- **单写者**：同一 session 内写动作串行执行（队列 + 每动作超时），读动作可并发；不同 session 默认互不可见。
- **多 Agent**：两个外部 Agent（两个 MCP server 进程）默认各自启动自己的宿主，不共享会话。需要共享时必须显式指定同一 host endpoint 且令牌来自同一 run 目录，且只有其中一个会话可持有写权限；无法判定时返回 `blocked`，不自动合并。
- **陈旧资源**：`runtime/host.lock` 记录 pid、启动时间、session id、管道名。启动前检测“锁存在但进程不存在”“同名陈旧管道”，发现即清理并写入证据，不静默复用。
- **宿主崩溃**：该 run 内的未终态动作标记 `unknown`，要求先读回核对，不自动重放写动作。
- **平台**：首版为 **Windows-only**（命名管道、Electron 可执行文件、系统原生对话框后端）。catalog 与 README 标注 `platform: win32`；其他平台返回 `UNSUPPORTED_PLATFORM`，不做未验证的跨平台宣称。

## 4. 启动、连接与数据隔离

### 4.1 支持配置

| 模式 | 支持原则 |
|---|---|
| `source-isolated` | 源码 + 隔离（**实测形态**）：外部驱动启动仓库 `electron`，以 `--user-data-dir` 或 launcher `setPath` 隔离 userData；工具负责启动 Vite dev server。渲染层是 dev bundle，**不加载发布产物**；会额外产生 `devtools://` 窗口，必须按 `window.api` 可用性排除 |
| `packaged-isolated` | 发布产物 + 隔离（**实测新增**）：运行打包产物并带 `--user-data-dir` + `--remote-debugging-port`，用 CDP 连接。加载 app.asar 内的发布 bundle，`app.getVersion()` 正确；**驱动前必须比对构建身份** |
| `source-service` | 独立 Electron 专项入口，调用原业务；用于服务级集成和现有模型专项 |
| `browser-mock` | 显式模拟回归，不允许作为真实 IPC/持久化验收 |
| `installed` | 与 `packaged-isolated` 同一技术路径，目标为已安装可执行文件。技术前提（`--user-data-dir` 隔离、`--remote-debugging-port` 可连接）已在打包产物上实测成立；接管用户**已打开**的实例仍需显式授权，不可用则返回限制，不修改安装包 |
| `attach` | 仅连接已显式提供调试端点或已有受控驱动句柄的指定实例；产品不提供常驻调试端口，无连接条件则返回 `UNSUPPORTED_ATTACH` |

实测依据见[阶段 0 实施报告](../报告/PC端外部Agent工具阶段0实施报告-2026-10-03.md) §3、§4。

默认不接管用户已打开的正式客户端，也不自动把正式数据复制到测试目录。用户明确要求操作正式实例时，工具会话记录指定实例、允许对象和动作范围；查询与写入按该授权范围执行，不每一步重复问同一项。

若安装版不允许源码级 API 操作，但可通过外部桌面工具验证界面，登记为 `ui_only`，能力目录准确显示。不能为实现任意安装版接管而增加生产常驻调试端口或产品控制接口。

### 4.2 生命周期要求

- 隔离目录、launcher、日志和证据位于本次 run 目录，分别登记所有权。
- **启动前必须清除 `ELECTRON_RUN_AS_NODE`**（实测：本机该变量为 `1`，不清除时 `electron.exe` 退化为纯 Node，Playwright 报 `Process failed to launch!`；`scripts/lib/electronHarness.mjs` 出于同一原因删除它）。
- 启动策略见 §4.3：源码模式依赖 Vite dev server，发布产物必须走打包/安装版，不通过修改 `main.ts` 解决工具假设。
- 区分应用主窗口、DevTools、弹窗和画板 iframe；以 URL、实际 preload 和 `window.api` 可用性综合识别，不依赖 `firstWindow()` 或窗口枚举顺序。
- 重启后重新绑定页面、frame、监听器和 locator；旧对象引用立即失效。
- `session.close` 只关闭本次工具拥有的客户端、宿主和服务；`attach` 默认只断开。
- 清理前校验解析后的绝对路径位于本次 run 根目录。证据默认保留，清理由显式命令按所有权执行。

### 4.3 构建身份与陈旧检测（v2 新增，含阶段 0 实测修正）

- **源码模式不加载发布产物**（实测）：`electron/main.ts` 以 `isDev = !app.isPackaged` 分流，源码启动必然 `loadURL('http://localhost:5173')`，因此 `source-isolated` 的渲染层是 dev bundle，且必须由工具先起 Vite。要验证发布产物只能走 `packaged-isolated`（打包产物 + `--user-data-dir` + CDP）。
- **构建身份不能取自 `app.getVersion()`**（实测）：注入 launcher 时它返回 Electron 版本（实测 `43.4.0`）、`getAppPath()` 落在 run 目录。构建身份必须从产物本身采集：包内 `package.json` 版本、`dist` / `dist-electron`（或 app.asar）的 mtime 与哈希、git commit。
- `doctor` 与 `session start` 输出上述构建身份，并写入 `session.json`；报告必须携带，否则证据不可复现。
- **陈旧即失败**：产物早于 `src/`、`electron/`、`shared/`、`vite.config.ts` 的最新修改时间（排除 `__tests__`）时，返回退出码 3 并给出重建命令，**不静默使用旧构建**；`--allow-stale-build` 可显式覆盖并记录进证据。
- **契约陈旧单独检**：`packaged-isolated` / `installed` 驱动前，比对目标 `window.api` 命名空间集合与当前契约；不一致时报告差异（实测样例：`release-v2` 打包产物缺少 `spatial`，见阶段 0 报告 §4）。
- 一个 run 内构建身份固定，中途不换 bundle。

### 4.4 安全边界（v2 新增，协议层强制）

- **路径**：session 启动前解析 run 根绝对路径；隔离 `userData` 必须位于该 run 根之下。目标路径等于正式 `app.getPath('userData')` 时默认拒绝，只有显式 `--allow-production-data` 且记录授权才继续。
- **动作白名单**：session 创建时登记允许的 action 集合（按模块 + 读写级别）。执行器在 dispatch 前校验；读默认放行，写动作必须显式授权，未授权返回 `blocked` 而不是 `failed`。
- **凭据**：`settings.get` 之类会回填密钥的接口按允许字段过滤，不把完整设置回传 Agent；`runtime/` 下的会话描述、令牌与锁文件在 Windows 上设为仅当前用户可读写，不进入公开 manifest，不入 Git（`output/` 已由 `.gitignore` 忽略）。
- **脱敏范围**：截图、日志、导出文件、任务参数统一脱敏；隔离 `userData` 内的 `logs/qingyu.log` 与界面截图都可能含凭据或隐私内容，收集时按规则处理，并在证据索引标注是否脱敏。
- **权限**：工具以当前用户权限运行，不申请提权；优先本地命名管道/stdio，不新开网络监听端口。

## 5. 动作目录与双入口协议

### 5.1 动作描述

每个动作登记：`id`、中文说明、参数 schema、结果 schema、支持模式、执行层级、目标引用、前置条件、副作用、等待条件、可取消性、断言建议和证据类型。

例如拟建 `chat.session.rename` 映射实际 `window.api.chat.renameSession`，并读回会话确认；`chat.send` 是完整发送功能，需要调用原聊天任务路径或 UI 发送，不能映射成低层 `saveMessage`。

**“完整功能动作”的判据**（v2 补充，避免把低层方法当功能暴露）：动作结束时必须同时满足 —— ① 界面上体现该结果；② 重启后可读回；③ 原任务的异步事件已进入终态。只满足其中一部分的，登记为低层动作并在目录中标明层级，不得作为用户功能的通过依据。

不向外暴露任意 JS、任意 IPC 通道、任意进程命令或直接文件写入作为产品动作。映射实现可以在受控 Playwright 回调中执行可信代码，参数作为结构化值传入，不拼接 Agent 提供的脚本文本。

### 5.2 CLI 草案

```powershell
# 以下命令为拟建接口，不是当前可运行命令。
node tools/pc-agent/cli.mjs doctor --json
node tools/pc-agent/cli.mjs catalog --module chat --json
node tools/pc-agent/cli.mjs session start --profile source-isolated --json
node tools/pc-agent/cli.mjs invoke --session <session-id> --action chat.session.rename --args-file <absolute-json-path> --json
node tools/pc-agent/cli.mjs operation wait --session <session-id> --operation <operation-id> --json
node tools/pc-agent/cli.mjs observe --session <session-id> --target <target-ref> --json
node tools/pc-agent/cli.mjs assert --session <session-id> --spec-file <absolute-json-path> --json
node tools/pc-agent/cli.mjs suite run --session <session-id> --suite chat.basic --json
node tools/pc-agent/cli.mjs evidence --session <session-id> --json
node tools/pc-agent/cli.mjs session close --session <session-id> --json
```

机器模式 stdout 只返回完整 JSON，运行日志走 stderr/证据文件。参数 schema、输出协议与 MCP 相同；不把终端描述文本作为唯一结果。

**stdout 纪律（v2 补充）**：工具自己启动的任何子进程（Electron、Vite、专项脚本）的 stdout/stderr 必须重定向到日志文件，**不得继承 CLI/宿主 stdout**；stdout 只允许出现最终结果 JSON 与协议错误。CLI 与 MCP 两侧都要有对应测试。

### 5.3 MCP 工具草案

| 工具 | 用途 |
|---|---|
| `qingyu_doctor` | 检查构建、依赖、连接条件和支持模式 |
| `qingyu_capabilities` | 返回动作 schema、可用性和执行层级 |
| `qingyu_session` | 启动/连接/重启/断开受控实例 |
| `qingyu_call` | 选择已登记 action 并调用 |
| `qingyu_observe` | 读取允许的业务状态和 UI 状态 |
| `qingyu_operation` | 查询、等待、取消指定异步操作 |
| `qingyu_assert` | 执行有限断言，返回实际值及证据 |
| `qingyu_run_suite` | 运行固定或参数化测试旅程 |
| `qingyu_evidence` | 获取截图、日志和产物索引 |

首版用少量入口加可发现动作目录，避免向 Agent 一次塞入所有底层方法。CLI 和 MCP 输入同一动作时必须获得等价结果，差异只在传输方式；阶段 2 的退出条件包含**自动化比对**两者结果，而不是人工目测。

### 5.4 返回结果与状态机

```json
{
  "schemaVersion": 1,
  "requestId": "req-...",
  "sessionId": "session-...",
  "operationId": "op-...",
  "action": "chat.session.rename",
  "layer": "ipc",
  "status": "succeeded",
  "invoked": true,
  "verified": true,
  "targets": [{ "type": "chatSession", "id": "test-session" }],
  "result": { "title": "QA-改名验证" },
  "evidence": [],
  "error": null
}
```

**动作状态**：`accepted / running / succeeded / failed / rejected / cancelled / blocked / timeout / needs_interaction / unknown`。  
**断言状态**：`pass / fail / blocked`，与动作状态分离定义，不复用同名语义。

约定：

- `requestId` 标识一次协议请求；`operationId` 标识一次可能异步完成的动作。一个 `requestId` 对应一个动作，一个动作在当前实现内只产生一个 `operationId`；若将来出现一对多，必须升 `schemaVersion` 并在目录中登记。
- `rejected` = 参数通过 schema 但被业务拒绝；`failed` = 执行出错；`blocked` = 前置条件/授权/环境不满足；三者不得混用。
- 请求受理不等于成功，方法返回不等于验证通过，取消选择器不等于导出成功。
- 未终态动作在进程中断后不得留在 `running`，必须落为 `unknown` 或 `timeout`。

CLI 退出码约定：0 表示此次请求/查询按协议成功返回，1 表示动作或断言失败，2 表示参数/协议错误，3 表示环境阻塞/不支持（含构建陈旧、平台不支持），4 表示需要用户交互。异步请求返回 `accepted` 时，Agent 仍必须等待或查询最终状态。

### 5.5 catalog 单一真源与防漂移门禁（v2 新增）

- `catalog.generate.mjs` 读取 [IPC 契约](../../shared/ipc-api.ts) 的 `ExposedAPI`，为每个命名空间与导出方法生成骨架条目：字段齐全但 `mode`、`layer`、`assertions`、`evidence` 由人工补全，未补全者标记 `status: unregistered`。
- `catalog.exclusions.json` 记录**不映射**的方法及原因与登记时间，供门禁放行；豁免不是默认值，必须显式添加。
- `scripts/check-pc-agent.mjs`（`pnpm check:pc-agent`）至少校验：
  1. 每个 `ExposedAPI` 成员要么有 action 映射，要么在豁免清单中；
  2. action `id` 唯一，参数/结果 schema 可编译；
  3. catalog 中登记的 `window.api` 路径在 `ipc-api.ts` 中仍存在（无悬空映射）；
  4. `docs/pc-agent/能力矩阵.md` 与 catalog 渲染结果一致（矩阵陈旧即失败）。
- 门禁与既有 `check:gates` 并列执行，结果**分别记录**：`check-contracts` 当前已知红，不得让两者的红绿互相掩盖。
- 手工维护的是 catalog 与豁免清单，能力矩阵是生成产物；出现分歧时以 catalog 为准并重新生成。

## 6. 执行层级与验证原则

| 层级 | 定义 | 不得扩大为 |
|---|---|---|
| `mock` | 受控 host 或 preview API | 真实 IPC/磁盘测试通过 |
| `service` | 专项脚本调用真实服务 | 实际主窗口的用户流程通过 |
| `ipc` | 实际应用页面通过正式 preload 调用 IPC | 按钮、表单、焦点和交互体验通过 |
| `ui` | 真实主窗口操作原控件，再核对业务状态 | 实际模型输出正确，除非还做模型核验 |

是否调用真实模型、外部服务、原生对话框以及是否重启核验，作为独立证据字段记录，不能只用“真实测试”一个标签概括。

### 6.1 读回与断言

- 保存后从原 API 读回；必要时重启客户端再读回，不直接写文件制造结果。
- UI 动作优先使用已有可访问名称、label、角色和稳定结构；未能稳定定位时登记工具限制，不为了方便添加产品按钮/调试入口。
- 前端状态或草稿动作走 UI，检查旧状态、脏编辑和保存时机；不能调用后强制刷新掩盖原 UI 流程故障。
- 状态断言提供等值、包含、数量、存在性、版本变化、会话隔离、产物存在等有限操作，输出 expected/actual 和证据。
- 仅读回磁盘文件不足以证明“操作由此请求完成”；关联请求、目标和原调用结果，防止沿用上次测试产物误报成功。

### 6.2 异步与重复调用

生成、翻译、索引、TTS、画板 AI 和同步须在触发前绑定事件，按 request/task ID 过滤。完成回调后还要核对指定对象或产物；窗口切换不能把结果归到新对象。

副作用动作不自动重试。外部工具的 request ID 记录用于查询和防止重复 dispatch；PC 原接口支持幂等时复用原标识。进程中断且无法证明提交结果时标记 `unknown`，先读回核对，不承诺通用 exactly-once。

取消复用原功能的停止/取消接口；不支持取消的提交明确返回限制。关闭 MCP client 不代表 PC 操作已撤销。

### 6.3 文件和原生交互

API 层需要原生选择器的功能优先通过现有 UI/文件交互完成，不能 monkey-patch 正式 dialog、替换业务 API 后宣称真实界面通过。

标准 web file input、画板 iframe 等由 Playwright 处理；系统原生对话框需要工具包明确支持的桌面自动化后端。后端不可用则返回 `needs_interaction/blocked`，保持任务可恢复。安装版/UI-only 环境不支持的 API 明确降级，不把打开页面算业务完成。

## 8. 授权、数据和证据

会话创建时记录运行对象、隔离目录、允许写入范围、允许测试套件以及用户已授权动作。对本次独立创建的测试对象，可连续执行已明确授权的测试动作；正式用户数据不自动纳入套件。

授权不只是登记，还必须在执行器强制（见 §4.4）：写动作在 dispatch 前对照 session 白名单校验，未授权返回 `blocked` 并记录尝试，不依赖外部 Agent 自觉。

真实模型调用、备份恢复、更新安装、对外发送等按用户任务授权与既有[测试规范](../规范/PC端AI-Agent验证测试规范.md)执行。未提供所需模型或依赖时标记阻塞，继续其他可验证项；仅编写本方案不运行这些动作。

状态接口过滤密钥和非必要个人内容。尤其 `settings.get` 可能回填凭据，工具实现只能在受控回调内按需读取并返回允许字段，不把完整设置回传给 Agent。截图、日志、任务参数和导出证据有统一脱敏与保留规则。

建议输出结构：

```text
output/pc-agent/<run-id>/
  session.json            # 公开实例/版本/模式/构建身份/允许动作
  actions.jsonl           # 输入摘要、状态、实际目标、耗时
  assertions.jsonl        # 预期/实际/层级/结论
  result.json / report.md
  screenshots/ logs/ exports/
  runtime/                # 私有会话描述、令牌、host.lock、launcher、隔离 userData
```

私有连接令牌、凭据和权限描述不进入公开 manifest，不入 Git（`output/` 已在 `.gitignore` 中）。关闭与清理只操作本 run 所有的进程和路径，默认保留测试证据。

## 10. 验收与回退

工具自身验证至少覆盖：错误参数/未知动作、未知 session、越权写动作、正式 userData 路径拒绝、构建陈旧、错误实例、mock 检出、DevTools 误选、iframe 重建、事件先后次序、异步阻塞/取消、选择器取消、失败回执、重复请求、副作用结果未知、CLI 与 MCP 的 stdout 污染、路径清理边界。

测试纳入方式（v2 补充）：

- 纯逻辑（catalog 校验、schema、协议、状态机、路径与授权校验）纳入 `pnpm test`（vitest，无 GUI），作为常规门禁。
- 需要真实 Electron/UI 的测试标记为 GUI 类，默认在本地或专用 Windows 环境按需/定时执行，不进普通 CI 门禁；CI 只跑纯逻辑部分。
- `pnpm check:pc-agent` 与既有 `check:gates` 并列执行，结果分别记录，不与 `check-contracts` 的已知红互相掩盖。
- **接线决定（2026-10-05）**：保持**并列**而非并入 `check:gates`（`check-contracts` 已知红，混链会互相掩盖）；已在 CI 的 “Structure gates” 作业中作为独立步骤运行 `pnpm check:pc-agent`，本地可用 `--require-covered` 收紧。
- **长矩阵约束（2026-10-05 实测）**：同一宿主进程内反复启动 Electron 有上限（本机约 20 次后 `electron.launch` 报 `Process failed to launch!`，退出码 3221225794 = DLL 初始化失败）。因此长矩阵按“每 5 条旅程一个会话、批间重启宿主”执行（见 `verify/matrix.mjs`），且会话在重启失败时进入 `error` 而不是卡在 `restarting`。
- 只读/文档建设阶段不要求执行模型或系统操作；实现阶段不得改产品或测试断言来掩盖失败。工具新增失败必须处理。

真实旅程必须同时从终端和 MCP 完成：创建测试角色及会话、修改并读回、UI 选择目标、执行适当动作、检查持久化、重启恢复、生成结构化报告。全端套件按现有规范覆盖每个模块，AI/外部系统依赖单独记测试环境和实测结果。

停用时移除外部 Agent 的 MCP 配置并关闭工具所拥有的宿主与客户端即可；既有 PC 产品不依赖这套工具继续运行。已对测试数据或授权对象完成的业务操作不会因停用工具自动回滚。
