# PC 端用户体验逻辑优化实施方案

> 日期：2026-09-20  
> 状态：📋 **方案待批准 — 未实施**（v2.1：已吸收首轮四路复核 + 二审三路「必须改」）  
> 依据：[PC 端用户体验逻辑审查报告](../报告/PC端用户体验逻辑审查报告.md)（下称「审查报告」，发现编号 UEX-*）  
> 范围：桌面端 `src/` + `electron/` 用户可感知逻辑 + `shared/` 调度语义；**不含**算法性能（见 [PC 端算法逻辑优化审查报告](../报告/PC端算法逻辑优化审查报告.md)）  
> 目标：打通「失败可见 / 内容不丢 / 危险操作可预期」，并为后续体验打磨留出统一契约

## 1. 结论

| 波次 | 代号 | 主题 | 覆盖 UEX | 建议工期 | 依赖 |

| **中波** | **M** | 危险操作统一 + 表单/草稿生命周期 + 调度语义 | P1 主体（含 P0-12/14） | **9–13 人日** | S1 Toast；**Confirm 底座在 M1a**（勿等 S3） |

> 未进 S 的 P0：**P0-12**→M3、**P0-13**→L2（阻断文案可提前并入 S12）、**P0-14**→M1b。

**推荐落地顺序（用户损失最大先修）**：  
`S1 → S2 → S5/S6/S9/S13/S7/S8（内容不丢）→ S11/S10（卡死/死按钮）→ S3/S4 → S12`。  
M 波在 S1 合入后开工；M1a 可与 S 并行。L 波按模块拆 PR。

**明确不做（本方案边界）**：

- 不改生成提示词、上下文分配、世界书触发算法（算法审查另案）。
- 不引入新 UI 框架 / 不重做视觉体系；Toast/Confirm 复用现有 Tailwind 与 `Modal`。
- 不做 Android 端实现；**但**改 free 拆分 / `maxRounds` / `generationNotice` 语义时，须同步 `shared` fixtures 与 Android golden（如 `group-free-split`）。
- 产品语义债（`maxRounds`、删角色级联、`@` 定发言人）**未拍板不改实现**。
- 顺手架构项（`registerBuiltinCommands` 移出 render、消息虚拟化）可剥离，不作体验验收项。
- 与 [对话输出弹性约束阶段8](./对话输出弹性约束阶段8推理门控与降级闭环方案-2026-09-13.md) 并行时：**错误 / `generationError` / `generationNotice` 以 Phase7 契约为唯一来源**，阶段8 不得改写字段含义。

## 2. 统一契约（先定契约，再改调用点）

### 2.1 全局 Toast 契约

**现状**：`useChatInputState` 局部 `notification`、`PersonasPage` 局部 toast、store `error` 无订阅、`safeSave` 只打日志。

**目标**：**新建** `src/store/useToastStore.ts`（**不要**扩展 `useUIStore`——仓库已有领域 store 惯例）。

```ts
type ToastVariant = 'info' | 'success' | 'warning' | 'error'
interface ToastItem {
  id: string
  variant: ToastVariant
  title: string
  description?: string
  durationMs?: number    // 默认 4000；error 默认 8000 或 sticky
  action?: { label: string; onClick: () => void }
  requestId?: string     // 同 key 去重/替换
}
// push / dismiss / dismissAll
```

**渲染**：`src/components/common/ToastHost.tsx` 挂 `MainLayout`/`App`；**z-index 固定 `z-[40]`**（`Modal` 为 `z-50`）。

**兼容**：`showNotification(msg)` 薄封装为 `toast.push({ variant:'info', title: msg })`，签名不变；**移除**输入区本地 notification 渲染以免双显。`PersonasPage` 局部 toast 暂留，M 波再收编。

**验收**：任意模块可 push；error 长停留可关；同 `requestId` 不堆叠。

### 2.2 危险操作 Confirm 契约

**目标 API**：`message: string | React.ReactNode`；`confirmBusyText?`；`onConfirm` reject → 保持打开 + error 行；成功才 `onClose`；busy 禁双按钮。

**`Modal` 硬前置**：增加 `dismissible?: boolean`（默认 `true`）。`false` 时遮罩、**Esc、X 按钮（`data-modal-close`）均不关闭**。Confirm busy 时传 `dismissible={false}`。默认 `true` 对既有 Modal 调用方零行为变化（M1a 验收含此抽查）。

**文案规范**：必写影响范围/是否可撤销/是否连带；禁止文案范围与实现不符。  
**取消语义**：`onClose` ≠ 业务取消。取消也要继续原操作的场景（世界书「不使用」），必须在调用方续跑待办并清空 pending ref。

**验收**：连点只触发一次；失败可重试且遮罩关不掉；新增危险操作不用 `window.confirm`。

### 2.3 生成任务取消 / 收尾契约（V1 + V2）

1. 最多一个当前生成：`{ engine: 'v1'|'v2', requestId?, activeV2Handle?, sessionId, characterId? }`。  
   **`activeV2Handle = { taskId, unsub, clearPoll }`** — 必须能清订阅与轮询，不能只存 taskId。
2. 用户停止：对应引擎 cancel（v1=`ai.cancelChat`，v2=`chatTask.cancel`）+ **清 unsub/poll** + 保留已见正文 + `generationNotice: '已停止生成'` + 复位 `isStreaming`。**禁止双 cancel**。
3. 迟到事件：用 Phase7 **`createGenerationTerminationLatch` 工厂**为 V2 建 latch；`claim('user_cancel')` 后 chunk/poll 一律不写 UI。**勿把 V1 `activeStream` 塞进 V2**。
4. 终态回写 UI 仅当 session/角色仍匹配；否则只落盘 + `logWarn`。
5. 切换会话若 `isStreaming`：走停止收尾（D4）；群侧 **`abandonActiveStream({ preserve: true })`** 统一入口，禁止裸 `cleanupActiveStream()`。
6. early-return/异常：`isStreaming` 必须复位；`started` = 挂上 `activeStream` 或发出 `ai.chat`/`chatTask.start`。
7. V2 fallback V1 时清空 `activeV2Handle`，再走 V1 cancel。

**验收**：停止后 500ms 可再发、3s 内无新 UI 写入；切会话无串台。建议 1 次主进程 cancel 集成测试。

### 2.4 草稿生命周期契约

1. **发送成功才删草稿**；失败回填（依赖 `sendMessage` 成功/失败信号）。
2. 切换前 flush：debounce **cleanup** 用 ref 持有旧 `{key,text}` 同步 `setItem`。
3. 空草稿不落盘；创建向导保存成功后 `dirty=false`，卸载不再写回。
4. 群草稿 key：`group-draft:{groupId}:{sessionId}`；切换清 `replyTo`。
5. M 波表单 dirty 统一引用本节。
