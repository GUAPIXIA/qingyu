# 全局叙事消息归属与输入续写优化方案

> 状态：阶段 A/B/C 已实施  
> 日期：2026-09-10  
> 适用范围：桌面端单聊、群聊、桥接端与 Android 端  
> 本文用于修正《双叙事模式实施方案》中“全局叙事等于 AI/对方成为旁白”的错误归属。

## 1. 优化目标

本轮优化解决两个已经耦合在一起的问题：

1. **旁白气泡归属错误**：当前实现把全局叙事下的 AI 回复标记为“旁白”，显示在对方一侧。正确语义应是：当我们选择“全局叙事”时，**我们发出的消息**才使用旁白标识与中性气泡；对方仍保持所选角色或群聊成员的身份与气泡。
2. **输入续写方向错误**：全局叙事下的输入框续写目前倾向直接写出完整、细致的剧情段落。正确目标应是生成一段简洁的剧情推动内容，提出新的事件、压力、变化或转折，把具体表演和展开留给对方回复。

本次修正的核心不是换一套颜色，而是把以下概念彻底分开：

- **消息方向**：这条消息属于我们还是对方。
- **显示身份**：用户身份、旁白、具体角色或系统。
- **叙事模式**：我们以角色身份参与，还是从全局层面推动故事。
- **生成来源**：人工输入、输入续写、AI 回复、重生成或气泡续写。

叙事模式不能再单独决定对方气泡的身份。

## 2. 修正后的产品语义

### 2.1 代入角色

- 我们使用当前选中的用户身份参与对话。
- 我方消息显示在右侧，使用用户身份头像、名称与用户气泡。
- 对方消息显示在左侧，使用当前角色或群聊成员的头像、名称与角色气泡。
- 输入续写帮助我们补全一句话、动作或回应，不替对方发言。

### 2.2 全局叙事

- 我们从旁白、导演或世界推动者的角度向故事施加变化。
- 我方消息显示在右侧，但不再伪装成普通用户发言，而是使用“旁白”标识与中性气泡。
- 对方仍是当前角色或群聊成员，继续显示在左侧，不因会话处于全局叙事而自动变成“旁白”。
- 对方可以在内容中描写环境、NPC 或局势变化，但这些仍是对方生成的故事回应，不改变消息归属。
- 输入续写生成的是“下一步剧情推动”，而不是替对方完成整段演出。

可以概括为：

```text
代入角色：我方角色输入  → 对方角色回应
全局叙事：我方旁白推动  → 对方角色/世界回应
```

## 3. 消息显示矩阵

| 会话模式 | 消息来源 | UI 侧 | 显示身份 | 气泡样式 | 是否显示角色焦点 |
|---|---|---:|---|---|---|
| 代入角色 | 我方手动输入 | 右侧 | 当前用户身份 | 用户气泡 | 否 |
| 代入角色 | 输入框续写后发送 | 右侧 | 当前用户身份 | 用户气泡 | 否 |
| 代入角色 | 对方 AI 回复 | 左侧 | 当前角色/群聊成员 | 角色气泡 | 否 |
| 全局叙事 | 我方手动输入 | 右侧 | 旁白 | 中性旁白气泡 | 可选，显示“推动焦点” |
| 全局叙事 | 输入框续写后发送 | 右侧 | 旁白 | 中性旁白气泡 | 可选，显示“推动焦点” |
| 全局叙事 | 对方 AI 回复 | 左侧 | 当前角色/群聊成员 | 角色气泡 | 否 |
| 任意模式 | 系统消息 | 中央/系统区 | 系统 | 系统样式 | 否 |

关键规则：

```ts
// 错误：会话为全局叙事，就把对方回复显示成旁白
message.role === 'assistant' && message.narrativeMode === 'omniscient'

// 第一阶段正确判定：只有我方在全局叙事下发出的消息才是旁白
message.role === 'user' && message.narrativeMode === 'omniscient'
```

群聊同样不能再使用“非用户且为全局模式”作为旁白判定。群聊成员回复必须保留成员归属；只有 `characterId === '__user__'` 且消息快照为全局叙事时，才显示为我方旁白。

## 4. UI 表现

### 4.1 我方旁白气泡

- 位置：保持在右侧，明确属于我们发出的内容。
- 头像：使用地球、镜头或羽毛笔等中性图标。
- 名称：显示“旁白”；可在次级文字中显示当前用户身份，例如“由林默控制”。
- 颜色：使用低饱和度中性色，不使用对方角色色，也不与普通用户暖色气泡混淆。
- 焦点：如确有必要，可显示“推动焦点 · 角色名”，但不能写成对方正在以旁白身份发言。
- 操作：编辑、删除、复制、引用等仍按我方消息权限处理；不提供对方回复专属的重生成或 Swipe。

建议布局：

```text
                         旁白  08:30  ◉
        ┌────────────────────────────┐
        │ 城门外忽然传来急促警钟，   │
        │ 一支陌生队伍正逼近港口。   │
        └────────────────────────────┘

角色头像  艾莉丝  08:30
┌────────────────────────────┐
│ 她停下争论，转身望向窗外…… │
└────────────────────────────┘
```

### 4.2 对方气泡

- 无论当前会话是代入角色还是全局叙事，对方都保留当前角色或实际群聊成员的头像和名称。
- 不再仅凭 `narrativeMode === 'omniscient'` 使用地球图标、“旁白”名称或中性气泡。
- 群聊自由发言若一条回复包含多名角色，应按现有角色分段规则展示；无法可靠拆分时可显示“群像回应”，但不能显示成我方旁白。

## 5. 输入框续写的目标重定义

输入框右侧“续写”属于**我方创作辅助**，结果只回填输入框，用户确认后才发送。两种模式应采用不同任务合同。

### 5.1 代入角色：补全回应

目标：延续当前用户身份的口吻，补全台词、动作或态度。

约束：

- 只生成我方内容。
- 不替对方角色说话或行动。
- 保持既有语气和第一人称/近距离视角。
- 有半句输入时只接续，不复述前文。
- 无输入时生成一条自然、可发送的回应。

### 5.2 全局叙事：生成剧情推动

目标：给故事加入一个明确但简洁的推动因素，而不是直接完成整段剧情。

优先生成以下内容之一：

1. 新事件：外部事件打破当前平衡。
2. 新压力：时间、资源、追兵、误会或环境发生变化。
3. 新信息：出现线索、消息或局势揭示，但不一次解释完全部真相。
4. 新转折：已有计划受到阻碍，迫使角色重新选择。
5. 场景推进：必要时推进少量时间或切换地点，并保留角色反应空间。

输出限制：

- 默认 1–3 句，建议 30–120 个中文字符。
- 描述“发生了什么变化”，不展开完整对白、长篇心理或连续动作细节。
- 不替对方角色写出完整反应，不替玩家作重大决定。
- 不总结世界观，不解释为什么这样续写，不输出“剧情建议：”等前缀。
- 有输入时保持原文抽象层级；原文是简洁事件描述，就继续简洁推动。
- 无输入时优先接续最近尚未解决的矛盾，不随机引入无关事件。

对比示例：

```text
不推荐：
夜色笼罩港口，艾莉丝慢慢站起来，整理衣袖，随后与守卫进行了数轮对话……
（继续详细描写数百字，并替所有角色完成反应）

推荐：
就在双方僵持时，城外忽然响起警钟；一支身份不明的队伍逼近港口，迫使众人暂时改变计划。
```

这里的产品定位应从“全局叙事续写助手”改为“剧情推进助手”。

## 6. 推荐提示词合同

### 6.1 全局叙事且输入框已有内容

```text
你是用户侧的剧情推进助手。请续写用户尚未完成的旁白推动，使其成为一段可直接发送的简洁剧情变化。

要求：
1. 只补充紧接原文之后的部分，不复述原文。
2. 推动局势发生变化，优先加入事件、压力、线索、阻碍或转折。
3. 默认只写 1–3 句，不展开完整场景，不替对方角色完成详细反应。
4. 不替玩家角色作重大选择，不一次解决当前冲突。
5. 不添加角色名前缀、解释或“剧情建议”等标签。
```

### 6.2 全局叙事且输入框为空

```text
你是用户侧的剧情推进助手。根据最近对话中尚未解决的矛盾，生成一段用户可以直接发送的旁白推动。

要求：
1. 用 1–3 句引入一个与当前情节直接相关的新事件、压力、线索、阻碍或转折。
2. 只提出变化并把故事推到下一个反应点，不完成角色的详细表演。
3. 不替玩家角色作重大选择，不一次解决冲突。
4. 不输出分析、解释、标题或角色名前缀。
```

### 6.3 上下文选择

输入续写不应直接复制普通回复的全部生成上下文。建议使用紧凑、稳定的输入：

```text
系统合同
→ 当前模式与我方显示身份
→ 当前角色/群聊概要
→ 最近 4–8 条有效消息
→ 当前未完成输入（如果有）
→ 本次任务指令
```

世界书与长记忆只注入和最近矛盾直接相关的条目，避免模型因背景过多转向长篇世界描写。

## 7. 数据模型优化

### 7.1 第一阶段：最小修正

继续使用现有 `role` 和 `narrativeMode`，但改变持久化与渲染规则：

- 我方消息创建时也保存当前会话的 `narrativeMode` 快照。
- 对方 AI 消息可以继续保存 `narrativeMode`，供重生成、上下文和兼容逻辑使用，但该字段不再直接决定旁白外观。
- 单聊旁白判定改为 `role === 'user' && narrativeMode === 'omniscient'`。
- 群聊旁白判定改为 `characterId === '__user__' && narrativeMode === 'omniscient'`。
- 切换会话模式只影响后续消息，不重绘历史消息。

### 7.2 第二阶段：彻底解耦

建议新增明确的显示身份字段，避免继续让 `role` 同时承担 API 角色、UI 方向和故事身份：

```ts
type MessageSpeakerKind = 'persona' | 'narrator' | 'character' | 'system'
type MessageGenerationKind =
  | 'manual'
  | 'input_continue'
  | 'assistant_reply'
  | 'regenerate'
  | 'message_continue'

interface Message {
  role: 'user' | 'assistant' | 'system' // API/对话方向
  speakerKind?: MessageSpeakerKind      // UI 与故事显示身份
  narrativeMode?: NarrativeMode        // 创建/生成时的模式快照
  generationKind?: MessageGenerationKind
}
```

推荐派生规则：

```text
user + immersive   → speakerKind=persona
user + omniscient  → speakerKind=narrator
assistant          → speakerKind=character（除非某个独立功能明确指定其他身份）
system             → speakerKind=system
```

`speakerKind` 决定头像、名称与颜色；`role`/`characterId` 决定消息方向和操作权限；`narrativeMode` 决定输入辅助和上下文行为。三者不互相替代。

## 8. 生成流程

### 8.1 我方输入续写

```text
点击“续写”
→ 读取当前会话模式
→ 代入模式：生成我方回应补全
→ 全局模式：生成简洁剧情推动
→ 结果只回填输入框
→ 用户编辑/确认并发送
→ 发送时固化 narrativeMode 与 speakerKind
→ 渲染为右侧用户身份或右侧旁白气泡
```

### 8.2 对方正常回复

```text
收到我方消息
→ 使用当前角色/群聊调度生成回应
→ 可依据全局推动扩展环境与事件
→ 固化对方角色身份
→ 始终渲染为左侧角色/成员气泡
```

### 8.3 对方气泡续写、重生成与 Swipe

- 这些操作作用于对方消息，必须继承目标消息的角色身份和消息方向。
- 可以继承目标消息生成时的叙事约束，保证文本连贯，但不能因此切换成我方旁白气泡。
- 如果目标消息属于旧数据且缺少快照，按其 `role` 与 `characterId` 恢复显示身份，不按当前会话模式重绘。

## 9. 现有逻辑的调整点

### 桌面单聊

- `src/components/chat/MessageBubble.tsx`：旁白判定从 assistant 侧改为 user 侧；头像、名称、对齐与操作权限分别依据 `speakerKind`/`role`。
- `src/store/useChatStore.ts`：创建我方消息时固化当前 `narrativeMode`，后续阶段再固化 `speakerKind` 与 `generationKind`。
- `src/components/chat/aiInputHelper.ts`：全局续写提示词从“写下一段全局叙述”改为“生成简洁剧情推动”。
- `src/components/chat/useChatInputState.ts`：回填行为保持不自动发送；空结果必须给出可见提示，不能静默恢复原文。

### 桌面群聊

- `src/components/chat/GroupChatMessage.tsx`：只有我方全局消息显示旁白样式，角色消息保留成员身份。
- `src/store/useGroupChatStore.ts` 与群聊流控制：我方消息固化叙事快照；AI 回复固化实际发言成员或群像回应身份。
- 自由发言的多角色解析继续属于对方回复逻辑，不与旁白身份合并。

### 桥接与 Android

- 消息 DTO 同步 `speakerKind`、`narrativeMode` 与 `generationKind` 可选字段。
- Android 使用相同显示矩阵，不能通过“非用户 + 全局模式”推导旁白。
- 老版本客户端忽略新增字段时仍能依赖 `role` 正常显示，不阻断同步。

## 10. 兼容与迁移策略

不建议批量改写全部历史消息，因为旧消息无法可靠判断当时用户是否真的以旁白身份发送。

建议规则：

1. 新消息完整固化 `narrativeMode`；启用第二阶段后同时固化 `speakerKind`。
2. 旧 `user` 消息缺少模式时按普通用户气泡显示。
3. 旧 `assistant + omniscient` 消息不再自动显示为旁白，恢复为角色气泡。
4. 如果用户确实希望某条历史消息显示为旁白，可在未来提供“设为旁白消息”的单条操作，而不是自动猜测。
5. API 上下文中的 `role` 不因视觉身份而改变，避免破坏模型消息交替与提供商兼容性。

## 11. 测试与验收

### 11.1 单聊显示

1. 代入模式发送消息：右侧用户身份气泡。
2. 全局模式发送消息：右侧旁白标识与中性气泡。
3. 全局模式收到 AI 回复：左侧当前角色气泡，不能显示“旁白”。
4. 切换模式后，历史消息外观不改变。
5. 旧 `assistant + omniscient` 消息恢复角色气泡。

### 11.2 群聊显示

1. 全局模式下我方消息显示右侧旁白气泡。
2. 点名或轮询产生的对方消息显示实际成员身份。
3. 自由发言包含多名角色时保持角色分段，不显示为我方旁白。
4. 桥接端与 Android 的同一消息显示归属一致。

### 11.3 输入续写

1. 代入模式已有半句：只补全我方表达。
2. 代入模式空输入：生成一条我方可发送回应。
3. 全局模式已有输入：只补充紧接其后的简洁剧情变化。
4. 全局模式空输入：围绕最近未解决矛盾生成一个剧情推动。
5. 全局模式结果默认不超过 3 句，不代写对方完整反应。
6. 续写结果只进入输入框，不自动发送；发送后显示为右侧旁白气泡。
7. 模型返回空内容时显示明确错误，并保留原输入。

### 11.4 数据契约

1. 新建消息正确固化模式与显示身份。
2. 非法 `speakerKind` 在 IPC/桥接入口被拒绝或安全回退。
3. 旧消息无新增字段时可以加载。
4. 重生成、Swipe、消息续写不会改变消息方向或显示身份。

## 12. 推荐实施顺序

### 阶段 A：纠正归属（已实施）

1. 我方消息保存 `narrativeMode` 快照。
2. 单聊与群聊的旁白样式移动到我方消息。
3. 对方消息恢复角色/成员身份。
4. 完成桌面端显示与历史兼容测试。

### 阶段 B：纠正输入续写（已实施）

1. 将全局输入续写重写为“剧情推进助手”。
2. 限制默认篇幅和细节层级。
3. 增加空结果可见反馈与真实输入框集成测试。
4. 验证续写后发送得到右侧旁白气泡。

### 阶段 C：跨端与数据解耦（已实施）

1. 引入 `speakerKind` 与 `generationKind`。
2. 同步桥接 DTO 与 Android 数据模型。
3. 统一单聊、群聊、桌面和 Android 的显示派生函数。
4. 增加协议夹具与跨端防漂移测试。

实施结果：

- 共享消息模型已增加可选 `speakerKind` 与 `generationKind`，新消息在持久化边界补齐稳定快照。
- 桌面单聊与群聊统一使用 `resolveMessageSpeakerKind`；合法显式字段优先，旧消息或非法值按方向与模式安全回退。
- 输入框 AI 续写发送时记录 `input_continue`；普通输入、正常回复、重生成与气泡续写分别记录对应来源。
- 桥接单聊/群聊 DTO 已同步三项叙事字段；Android 模型和显示派生规则与桌面保持一致。
- 新增 `message_identity.json` 双端协议夹具，并测试共享副本、旧消息兼容与非法身份回退。

## 13. 最终决策

采用以下不可混淆的规则：

```text
全局叙事描述“我们如何推动故事”，不等于“对方变成旁白”。
旁白标识属于我方全局消息，并显示在右侧。
对方始终保留当前角色或群聊成员身份。
全局输入续写只生成简洁剧情推动，不替对方完成详细剧情。
```
