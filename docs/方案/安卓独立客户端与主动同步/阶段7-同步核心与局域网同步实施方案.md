# 阶段 7：同步核心与局域网同步实施方案

> 状态：⚠️ 待处理  
> 前置：阶段 2、3、4、5；阶段 1 协议未发生未决变化。  
> 目标：实现 TypeScript/Kotlin 行为一致的 Sync Core、冲突中心和用户主动触发的局域网双向同步。

## 1. 同步状态机

客户端状态固定为：

```text
idle
 -> scanning
 -> plan_ready
 -> awaiting_confirmation
 -> transferring
 -> validating
 -> prepared
 -> committing
 -> applying_local
 -> committed
 -> completed

任意非终态 -> cancelling -> cancelled
任意执行态 -> failed(retryable | non_retryable)
```

`scanning/plan` 只读，不修改业务数据和同步游标。双方必须先把待应用批次持久化为 `prepared`；PC 端幂等提交并写入 `commitReceipt` 后，Android 根据该 receipt 原子应用本地 staging。Android 在应用前后崩溃都必须能通过 session 查询恢复。只有本地应用和对端 commit 都已确认后才标记 `completed`；冲突记录的创建属于 apply 结果，但冲突解决由后续本地操作完成。

## 2. 任务拆分

### S7-01 Sync Core 纯逻辑

在 TypeScript 和 Kotlin 中分别实现：

- 版本向量比较、合并和序列化；
- 根据双方 heads/known vector 生成上传、下载、相同、冲突、未知 schema 列表；
- 批次排序：父实体 → 子实体 → 引用更新 → tombstone；
- batch hash、receipt hash 和幂等 key；
- 冲突分类和默认 UI 建议；
- tombstone 确认与可压缩判断；
- capability/schema 协商。
- migration genesis 与相同业务 hash 的伪冲突消解；
- aggregate delete fence、引用图检查和 `DEPENDENCY_CONFLICT` 分类。

两端读取同一 golden，输出规范 JSON 必须逐字节一致。Sync Core 禁止访问网络、磁盘、时钟和随机数；这些均通过输入传入。

### S7-02 同步摘要与高效扫描

- Repository 从 journal/entity_heads 生成摘要，不扫描全部 payload。
- 摘要按 entityType 分区，支持分页和 Merkle/root hash 快速判等。
- 首次同步可发送全量 head，后续使用 peer receipt/known vector 增量。
- 计划中显示实体数量、附件大小、冲突数和不支持 schema；不在 UI 暴露正文预览，除非用户展开某个冲突。
- 对 100 万消息的增量扫描必须有基准，内存有明确上限。

### S7-03 LAN 一次性授权

PC 同步中心增加：

1. 用户点击“允许局域网同步”。
2. PC 生成临时 X25519 密钥对和 256 位一次性 secret，TTL 5 分钟，scope 仅 `sync`。
3. 二维码固定包含协议版本、PC host/port、sessionId、临时公钥、secret、过期时间和指纹。
4. Android 扫码后生成临时密钥，从 ECDH transcript + secret 经 HKDF 派生会话密钥；双方显示由完整 transcript 派生的同一短认证串。
5. PC 用户核对设备名和短认证串后再次确认；拒绝、超时或完成立即吊销并清理临时私钥。

复用 mDNS 只用于发现，不用于授权。不得复用长期 Bridge JWT 作为一次性同步凭据。

### S7-04 PC `/sync/v1` 路由

在 Bridge 服务中挂独立 router：

- 严格匹配方法和路径；
- 独立速率限制、body 限制、并发限制和超时；
- session scope 检查；
- plan/push/pull/blob/commit/abort；
- prepare、session/receipt 状态查询以及 commit 响应丢失恢复；
- 请求日志只记录 requestId、批次大小、状态和耗时；
- 不接入现有 Relay RPC allowlist。

所有 payload 先进入 staging。路由不得直接调用旧文件写函数，只能调用 Sync Application Service 和 Repository。

### S7-05 Android LAN transport

- 扫码、手动地址和已配对 PC 发现；首版同步仍要求每次 PC 显式授权。
- 连接前校验指纹，地址变化时重新确认。
- 分批上传/下载，支持进度、取消和同 batch 重试。
- App 退后台时同步默认暂停或使用明确前台服务；不得静默长期运行。
- Wi-Fi 切换、IP 变化、Android Doze 后可从最后未提交批次安全重试。

### S7-06 冲突中心

至少提供：

- 按数据类型和同步会话筛选；
- 文本字段 diff；复杂对象按字段显示；二进制显示尺寸/hash/缩略图；
- 保留本机、保留对端、复制为新实体、手动合并；
- 批量处理只允许同类型且策略安全的冲突；
- 删除 vs 修改必须单独确认；
- 解决记录保留原版本 hash 和选择，但诊断日志不保存正文。

会话/message 冲突解决需要维护父子引用；复制消息为新 ID 时不能破坏分支/swipe 关系。

### S7-07 同步中心 UI

PC 与 Android 均显示：

- 本地未同步更改数量；
- 最近一次同步目标、时间和结果；
- 局域网/服务器两个手动入口（服务器入口阶段 8 启用）；
- dry-run 计划；
- 进度、取消、失败重试；
- 待解决冲突与已完成 receipt。

不得提供默认开启的“自动同步”。提醒开关只统计本地 backlog。

### S7-08 Tombstone 与设备管理

- 同步 receipt 写入各设备已知向量。
- UI 显示长期未同步设备对清理的影响。
- 退役设备需要二次确认；退役后该设备重新出现必须作为新设备重新授权，旧计数器不能继续写。
- 增加 tombstone dry-run 清理报告，实际压缩放在无同步进行时的维护事务中。

## 3. 故障矩阵

每个场景需自动或可重复集成测试：

| 场景 | 预期 |
|---|---|
| plan 后取消 | 双方业务数据与 cursor 不变 |
| push 批次重复 | 幂等，无重复消息/用量 |
| pull 乱序 | 按 batch sequence 拒绝或缓存，不提前 apply |
| 传输 30% 断网 | 重连后重试未提交批次 |
| apply 中磁盘满 | 回滚 checkpoint，不 commit |
| commit 响应丢失 | 使用同 session/batch 查询 receipt，不能重应用 |
| PC 已 commit、Android 应用前崩溃 | 重启查询 commitReceipt，幂等应用本地 staging |
| Android 已应用、completed 标记前崩溃 | 由本地 applied marker 与 receipt 确认完成，不重复业务写 |
| 同一角色两端编辑 | 建立可见冲突 |
| 一端删除一端编辑 | 不自动复活或删除 |
| 一端删除会话、另一端新增消息 | 建立依赖冲突，不产生可见孤儿消息 |
| Android schema 较旧 | 跳过不支持项并阻止不完整 commit |
| token 超时/重放 | 明确拒绝，不泄露是否存在实体 |
| hash 被篡改 | 整批拒绝并记录安全事件 |

## 4. 性能与安全门禁

- 1 万实体无变化 plan：目标 2 秒内；以阶段 0 设备基线校准。
- 100 万消息、仅 100 条变更：耗时与变更数相关，不重新 hash 全量正文。
- 默认批次不超过 500 条或 4 MiB，以先达到者为准。
- 单 session 同时只允许一个 apply；多个只读 plan 可限量并发。
- fuzz 测试覆盖 envelope、vector、cursor、压缩输入和 QR。
- LAN HTTP 即便运行在私网也要应用层认证、完整性和重放保护。

## 5. 完成定义

在完全不使用服务器的环境中，用户可手动让 PC 与 Android 双向同步全部 P0 数据；故障矩阵无静默丢失；冲突全部可见、可解决；没有后台自动业务同步请求。

## 6. 回滚

关闭 `manualSyncLanEnabled`，吊销未完成 session，保留 journal 和冲突记录。由于 apply 前有 checkpoint，可恢复到最后一次成功 receipt；不得通过删除 journal 假装回滚。
