# 阶段 8：服务器同步与端到端加密实施方案

> 状态：⚠️ 待处理  
> 前置：阶段 7 已通过，Sync Core 与 LAN 协议稳定。  
> 目标：在现有 Relay 基础上新增长期、手动、端到端加密的数据同步服务，且不改变同步合并语义。

## 1. 服务边界

- 开发阶段允许旧 `/relay/v1` 与新增 `/sync/v1` 在隔离环境短暂共存，以便完成迁移测试；首个独立客户端候选版使用的新 Sync Server 部署物不得包含旧伴侣端点。阶段 9 如需服务已发布旧客户端，只能运行冻结且网络/存储隔离的 legacy Relay。
- `/sync/v1` 使用现有空间、设备、Access/Refresh Token 和 RLS 身份基础，但数据库表、配额和路由独立。
- 服务端只验证 envelope 元数据、版本向量、密文大小/hash 和授权，不解密业务 payload。
- 不使用 WebSocket 推送业务变更；客户端只有在用户点击同步时请求服务器。
- 公告服务 `server/` 不承担同步职责。

## 2. 数据库与对象存储

建议表：

```text
sync_space_keys(space_id, key_epoch, created_at, retired_at)       # 只有 epoch/状态，无密钥
sync_device_keys(space_id, device_id, public_key, status)
sync_key_envelopes(space_id, key_epoch, recipient_device_id, envelope)
sync_entity_heads(space_id, entity_type, entity_id, version_hash, version,
                  dot_device, dot_counter_text, schema_version, deleted,
                  key_epoch, cipher_revision, cipher_hash,
                  content_tag, ciphertext, blob_manifest_id, created_at)
sync_changes(space_id, server_seq, entity_type, entity_id, version_hash,
             key_epoch, cipher_revision, cipher_hash, created_at)
sync_device_acks(space_id, device_id, known_vector, server_seq, updated_at)
sync_batches(space_id, device_id, batch_id, request_hash, response, expires_at)
sync_blobs(space_id, blob_id, manifest, size, ref_count, status)
sync_sessions(id, space_id, device_id, state, expires_at)
```

- 所有租户表启用并强制 RLS；查询的 space_id 只来自已验证 token。
- `(space_id, device_id, batch_id)` 唯一保证幂等。
- `sync_entity_heads` 以 `(space_id, entity_type, entity_id, version_hash, key_epoch, cipher_revision)` 唯一；同一业务版本允许轮换出新的密文实例，但只有最高已提交 cipher revision 对客户端可见。并发业务 head 通过不同 version hash 同时保存。
- 大 ciphertext 进入对象存储，数据库只存小实体和 manifest。
- 对象 key 使用随机服务端 ID，不含用户文件名、角色名或实体 ID 明文。
- 垃圾回收先标记、延迟删除，并核对 ref_count 与 committed manifest。

## 3. 任务拆分

### S8-01 E2EE 原语与格式

- 空间密钥：随机 256 位，epoch 从 1 开始。
- 实体：AES-256-GCM，96 位随机 nonce；AAD 包含空间、实体身份、schema、版本 hash、key epoch。
- key derivation：使用 HKDF-SHA-256 从 spaceKey 派生 entity/blob/receipt 子密钥，info 固定并版本化。
- blob：固定上限分块，每块独立 nonce/tag；manifest 自身加密并签完整块列表。
- 客户端生成明文 hash 用于本地校验，但只向服务器发送密文 hash，避免已知内容枚举。
- 为支持同空间内相同内容投影的快速收敛，客户端可发送 `contentTag=HMAC(content-dedupe subkey, entityType/entityId/contentHash)`；服务端只能比较 tag 是否相等，不能据此枚举已知明文。客户端解密后仍须重新计算 contentHash，不能信任 tag 决定业务正确性。
- 密码库 API 失败必须 fail closed；不得回退明文上传。
- 业务 `versionHash`、`keyEpoch` 与 `cipherRevision` 纳入 AAD；重加密只增加 cipher revision，不改变业务版本向量、dot 或 contentHash。

建立 TypeScript/Kotlin 加密互操作 fixture，但 fixture 使用专用固定测试密钥，生产代码必须使用安全随机数。

### S8-02 新设备密钥交付

流程：

1. 新设备生成长期 X25519 与 Ed25519 身份密钥，创建包含 `deviceId/publicKeys/nonce/expiry` 的本地二维码和短认证串，并向服务端登记相同请求。
2. 用户必须用已授权设备扫描二维码，或逐项核对两台设备本地显示的短认证串；仅在服务端列表点击设备名不构成批准。
3. 已授权设备校验登记内容与带外内容一致，通过 ECDH + HKDF 得到封装密钥，加密当前 spaceKey，并用批准设备 Ed25519 密钥签署完整 envelope/transcript。
4. 服务端只保存不透明且带签名的 key envelope，不能替换目标公钥后仍通过客户端校验。
5. 新设备验证批准设备签名、解封并通过 Keystore wrapping key 保存 spaceKey，随后用 challenge 证明可解密。

在完成带外核对和批准设备签名的前提下，服务器管理员不能替换公钥或创建有效 key envelope。恢复时如果没有任何持钥设备，只能使用用户显式导出的加密恢复包；服务端不能“重置密码找回正文”。

恢复包是独立于 Backup V3 的显式导出物：包含格式版本、spaceId/key epoch、随机 salt、KDF 参数和经 AEAD 加密的 spaceKey，不包含业务正文。阶段 0/8 必须冻结跨平台可用的内存硬 KDF（默认评估 Argon2id）、最低参数、口令强度、错误次数限制和恢复后立即轮换流程；PC/Android 必须互相完成导出—恢复 fixture，普通备份不得顺带生成恢复包。

### S8-03 `/sync/v1` API

实现阶段 1 OpenAPI：

- session 创建验证设备状态、协议版本、配额；
- plan 基于 metadata/known vector 计算，不解密 payload；
- push 在事务中校验 batch、版本向量结构、hash、大小和幂等；
- 新本地变更的 `dot.deviceId` 必须等于已认证调用设备，counter 必须单调且不得复用；冲突解决必须携带被支配 head 的证明。重加密批次使用独立权限和 cipher revision，不伪造业务 dot。
- pull 按 server_seq/cursor 返回目标设备未知变更；
- commit 更新 device ack；
- abort 释放 staging；
- blob 使用短时签名上传/下载或服务端流式代理，均绑定 space/device/session/hash/size。

服务端遇到并发 heads 可以同时保存多个版本，不能擅自最后写入胜出。客户端拉取后创建冲突并上传已解决的新 head。

### S8-04 客户端 ServerTransport

PC/Android 共同行为：

- 用户点击后刷新 token、建立 session、plan、确认、push、pull、validate/decrypt、apply、commit。
- 加密在进入 transport 前完成；解密只在本地 staging。
- access token 单飞刷新；refresh 重放链吊销沿用现有安全策略。
- 上传/下载支持分块、进度、取消和指数退避；非 retryable 错误不盲重试。
- 使用服务端时同样不启用业务 WebSocket。

### S8-05 配额与保留

产品必须冻结默认值：实体总量、密文总字节、单 blob、单次同步、设备数。达到配额时：

- plan 明确显示所需与剩余空间；
- push 原子拒绝超额批次，不接受一半；
- 已提交数据不会为腾空间无提示删除；
- tombstone 保留遵循所有活跃设备 ack；
- 用户可查看占用并删除整个空间/退役设备/清理无引用 blob。

### S8-06 密钥轮换

- 设备吊销后创建新 key epoch；新写入只用新 epoch。
- 历史数据后台重加密由持钥客户端在用户显式发起维护时执行，服务器不能独立完成；任务按旧/新 key epoch 和 cipher revision 保存可恢复游标。
- 轮换中允许读取多个 epoch；完成并确认后删除旧 key envelope。
- 中断可恢复；同一实体的新 epoch/cipher revision 替换密文实例，不进入业务 Sync Core，也不得造成业务冲突或新 dot。

### S8-07 运维

- PostgreSQL 迁移幂等，应用角色无 SUPERUSER/BYPASSRLS。
- 对象存储启用服务端加密作为第二层，但不替代 E2EE。
- 备份同时覆盖数据库和对象存储 manifest；恢复到隔离环境做一致性检查。
- 指标：请求、延迟、批次、密文字节、配额、失败码、孤儿 blob；不记录正文、密文内容、token、key envelope。
- 告警：RLS/鉴权异常、hash 错误激增、对象不一致、备份失败、磁盘/连接池压力。

## 4. 安全测试

- A 空间 token 枚举 B 空间 entity/blob/session 一律 404。
- 被吊销设备无法创建 session、拉取、上传或领取新 key envelope。
- batch 重放、cursor 篡改、version counter 倒退、超大 vector、nonce/tag 篡改均拒绝。
- 服务端替换待批准设备公钥、批准签名或 key envelope 后客户端必须拒绝；二维码/SAS 不一致不得继续。
- contentTag 相等但解密后 contentHash 不同必须作为安全错误拒绝，不能自动收敛。
- 恢复包错误口令、参数降级、篡改、跨空间导入和恢复后轮换均有测试。
- 数据库和对象存储快照离线分析不能恢复正文。
- 服务端日志、错误、metrics、备份脚本输出无 token/key/ciphertext。
- 恶意压缩包/JSON 深度/实体数量不会造成内存或 CPU 无界占用。
- 密钥轮换在 0%、50%、commit 后中断均可恢复。

## 5. 集成与灾难演练

- PC 上传 → Android 下载；Android 修改 → 上传 → PC 下载。
- 两端离线并发修改 → 服务器保留双 head → 两端显示同一冲突。
- 服务器在 push/pull/commit 各阶段重启，客户端可安全重试。
- PostgreSQL 恢复 + 对象存储恢复后 receipt/hash 一致。
- 完全丢失服务端时，本地客户端仍独立可用，可创建新空间重新同步。

## 6. 完成定义

服务器作为加密同步中继/存储而非业务权威稳定运行；没有实时业务推送；数据库泄露无法读取用户内容；LAN 和服务器对同一输入产生相同同步/冲突结果。

## 7. 回滚

关闭 `/sync/v1` 新 session 创建，允许只读下载和空间导出一段公告期；客户端可继续纯本地运行或使用局域网同步。不得在未提供导出窗口前删除服务器密文，也不得恢复已删除的旧 Relay RPC 作为回退通道。
