# 安卓独立客户端与主动同步重构总方案

> 状态：⚠️ 待处理  
> 编写日期：2026-09-16  
> 适用基线：PC `0.17.2`、Android `0.3.0 (9)`、Relay `0.1.0`  
> 目标：把 Android 从“依赖 PC 的伴侣端”重构为可独立运行的完整客户端；取消业务数据实时同步，改为用户主动触发的局域网或服务器双向同步。

## 1. 文档用途

本文是整个重构的唯一总纲，负责冻结产品边界、目标架构、数据与同步语义、阶段依赖和最终验收标准。详细任务拆分位于 [`安卓独立客户端与主动同步/`](./安卓独立客户端与主动同步/README.md)。执行 Agent 不得绕过阶段文档直接按本文中的概念自行扩展协议。

本方案不是把 Electron 页面逐页翻译成 Compose。目标是保留 PC 与 Android 各自适合的平台界面，通过语言无关的领域契约、等价业务规则和同一套同步协议实现功能一致。

## 2. 当前基线与问题

### 2.1 已有资产

- PC：Electron + React + TypeScript，完整支持角色、单聊、群聊、世界书、预设、人设、正则、快捷回复、记忆、模型配置、TTS、图片、MCP、备份与用量。
- Android：Kotlin + Compose + Room，已有连接、配对、会话浏览、单聊/群聊消费、消息操作、TTS、公告和用量界面。
- Bridge：PC 暴露 `/api/v1`，承担伴侣端远程操作与流式事件。
- Relay：具备空间/设备隔离、配对、令牌、RPC、短期快照和命令队列。
- `shared/chat-core`：PC 端已抽出较多确定性对话逻辑和契约测试，可作为 Kotlin 等价实现的行为基准。

### 2.2 当前结构不能直接满足目标

1. Android Room 只是最近会话缓存，不是完整用户数据源。
2. Android 的生成请求最终仍由 PC 执行，PC 离线时不能独立聊天。
3. PC 写操作分散于 IPC、Bridge、服务和文件存储，无法可靠生成全域变更日志。
4. Relay 的设计原则是“PC 为权威、服务器仅缓存”，不能保存多端独立修改。
5. 设置同步 v2 是 PC 设置的远程修改，不是通用双向数据同步。
6. 当前 Relay 服务器可读取正文；若升级为长期数据存储，需要客户端加密。

## 3. 目标与非目标

### 3.1 必须达到

- Android 在 PC 关闭、未连接和服务器不可用时，仍可创建角色、配置模型、发起单聊/群聊、管理所有本地内容并查看历史。
- PC 与 Android 都采用本地优先：本地写入立即完成，不等待另一个端或服务器。
- 数据同步只在用户点击“同步”后运行；后台不得周期性上传、下载或合并业务数据。
- 局域网和服务器使用同一个同步核心，仅传输适配器不同。
- 支持新增、修改、删除、附件、断点续传、幂等重试、并发冲突和同步预览。
- 服务器同步采用端到端加密；服务端只处理密文、哈希、版本向量和必要的路由元数据。
- 旧 Android 用户通过一次性迁移保全本机缓存、草稿和未完成发件箱；若原 PC 数据仍可访问，首次同步必须先建立共同迁移基线，再导入完整 PC 数据。新版安装包不提供、不隐藏保留旧伴侣模式或远程聊天入口。
- 所有跨端确定性算法都有同一 fixture 驱动的 TypeScript/Kotlin 一致性测试。

### 3.2 平台等价而非实现相同

| PC 能力 | Android 目标 |
|---|---|
| Windows 系统 TTS / Edge TTS | Android 系统 TTS；网络 TTS 按相同供应商协议实现 |
| 本地文件选择器 | Storage Access Framework |
| MCP stdio 服务器 | 不在手机本机启动；支持远程 HTTP MCP，stdio 配置标记为“仅 PC” |
| PC 本地 ONNX embedding | Android 可用设备上使用移动端运行时；不支持设备显示明确降级，不阻断关键词世界书 |
| ComfyUI/SD WebUI 本机地址 | 允许访问用户配置的网络地址；不假定 `localhost` 指向 PC |
| 桌面多栏布局 | 保持相同业务能力，使用移动端导航与编辑流程 |

### 3.3 明确非目标

- 不在第一轮重写 PC React UI。
- 不要求 PC 与 Android 逐像素一致。
- 不实现持续在线的协同编辑、后台实时推送或自动静默合并。
- 不把 API Key、设备令牌、空间密钥、MCP 敏感环境变量作为普通同步实体。
- 不以 `updatedAt` 单独决定覆盖关系。
- 不用 Relay RPC 模拟“独立 Android”；Android 的 AI 请求直接访问用户配置的模型服务。
- 不保留旧伴侣模式、旧 Bridge 业务 API 或旧 Relay RPC 作为新版运行时回退通道。

## 4. 功能范围与完成口径

### 4.1 P0：独立可用

- 模型连接档案：OpenAI 兼容、Claude、Gemini、Ollama；连接测试、流式生成、取消、重试和用量。
- 单聊：会话、消息、编辑、删除、清空、分支、swipe、重新生成、翻译、续写、方向卡片、引用和导出。
- 角色：创建、编辑、删除、头像/背景、JSON 与 Character Card PNG 导入导出。
- 人设、预设、正则、快捷回复、设置和凭据本地保存。
- 世界书：canonical v2、关键词触发、位置渲染、角色绑定和导入导出。
- 手动局域网与服务器同步核心数据。

### 4.2 P1：完整业务一致

- 群聊三种模式、成员管理、群会话、群记忆。
- 自动/手动记忆、事实记录、上下文预算、历史降级、回复篇幅与推理门控。
- 语义世界书与事实向量；不可用时可解释降级。
- TTS、识图、生图、附件、公告、更新、用量统计。
- 备份 V3：跨平台可恢复，敏感信息默认排除。

### 4.3 P2：平台扩展一致

- 远程 HTTP MCP 与权限确认；PC-only stdio 能力清晰标记。
- 本地 embedding 模型的移动端安装、校验、存储和卸载（仅支持设备）。
- 诊断导出、同步历史、冲突审计和灾难恢复工具。

“完整功能”以能力矩阵逐项验收，不以页面数量或代码行数判断。阶段 0 会生成机器可检查的矩阵；未标记“通过、平台等价或经产品确认不适用”的条目不得宣布完成。

```text
├────────────────┤                              ├──────────────────┤
│ Repository API │                              │ Repository API   │
│ File adapters  │                              │ Room + files     │

                                   │ storage, no content│
                                   └────────────────────┘
```

### 5.1 分层规则

- UI 只能调用 use case/view model，不能直接写文件、Room 或同步表。
- 业务用例只能依赖 Repository 接口，不依赖 Electron IPC、Retrofit 或具体数据库。
- 所有用户数据写入必须经过 Repository，并在同一逻辑事务中生成变更记录。
- Sync Core 只处理规范实体、版本、冲突和批次，不理解 Compose/React 状态。
- Transport 只负责认证、分批、重试和字节传输，不做业务合并。
- 服务端不解析加密 payload，不成为业务规则执行端。

## 6. 规范数据模型

### 6.1 同步实体类型

首版候选实体类型如下；阶段 0 数据域审计可以补充遗漏类型，但必须在阶段 1 冻结前完成，冻结后不得由实现 Agent 临时增删：

```text
settings_public      character          lorebook
preset               persona            regex_rule
quick_reply_set      group              session
message              memory_state       memory_fact
usage_record         mcp_public_config   media_manifest
lorebook_mapping_template               usage_clear_marker
```

本地但不同步：连接密码、API Key、连接档案、设备令牌、空间密钥、缓存、向量索引、下载中的模型、自定义字体文件、日志、窗口/通知偏好。阶段 0 必须为每个本地数据域记录备份策略和平台等价策略，不能用“不参与同步”代替数据清单。

### 6.2 实体信封

```json
{
  "contractVersion": 1,
  "entityType": "character",
  "entityId": "01K...",
  "parentId": null,
  "schemaVersion": 3,
  "version": { "pc_a": "12", "android_b": "4" },
  "dot": { "deviceId": "android_b", "counter": "4" },
  "deleted": false,
  "updatedAt": 1789550000000,
  "contentHash": "sha256:...",
  "payload": {}
}
```

- 新 ID 使用 ULID；保留所有旧 ID，不在迁移时批量改名。
- `version` 是版本向量，用于判断因果关系；时间戳只用于显示和稳定排序。
- 每次本地修改增加当前设备计数，并合并已知版本向量。
- 版本向量 counter 在 JSON 中使用无前导零的 UInt64 十进制字符串；实现不得经过 JavaScript `number`、JVM `Long` 或 SQLite INTEGER 的有损转换。
- 删除写入 tombstone，不直接抹除同步历史。
- `contentHash` 对 canonical JSON 计算，排除 `updatedAt` 等非业务字段。
- 单条 payload 解密后上限 2 MiB；更大的二进制内容必须走 blob。

### 6.3 合并规则

| 数据类型 | 默认策略 |
|---|---|
| 不同 ID | 集合并集 |
| 同一 ID、版本支配 | 使用支配版本 |
| 同一 ID、版本并发 | 创建冲突，不静默覆盖 |
| 同一 ID、版本并发但规范业务哈希相同 | 由同步发起端生成一个支配双方、带新本机 dot 的收敛 head，不要求用户处理伪冲突 |
| message 新增 | 按 ID 合并，展示顺序按逻辑时间与 ID 稳定排序 |
| message 同 ID 编辑 | 并发时冲突；用户可保留一版或复制为新消息 |
| settings_public | 按字段分组显示冲突，不整对象覆盖 |
| 使用量记录 | 事件 ID 去重并集 |
| usage_clear_marker | 保存 `clearedThrough` 版本向量；只清除其因果支配的 usage_record，并发产生的新记录保留；多个 marker 逐设备取最大值 |
| 删除与修改并发 | 冲突；默认不复活、不自动删除 |
| 父实体删除与子实体新增/修改并发 | 创建依赖冲突；在父实体恢复或明确级联删除前，不得产生可见孤儿数据 |
| 派生缓存/向量索引 | 不同步，由目标端重建 |

冲突解决本身是一条新变更，版本向量必须同时支配两个冲突版本。

角色—会话—消息、群组—成员/会话、会话—记忆、消息—引用/swipe、资产—绑定关系属于跨实体不变量。Sync Core 必须使用 aggregate revision 或 delete fence 检测跨 ID 的删除并发；“不同 ID 取并集”不能绕过引用完整性检查。

### 6.4 Tombstone 生命周期

- 默认保留 180 天。
- 只有当所有未退役设备都确认看过该 tombstone，或用户显式退役长期离线设备后，才能压缩。
- 服务端不得仅因数据保留期限删除尚未确认的 tombstone。
- 恢复备份产生新设备身份，不复用备份中的设备计数器。

## 7. 主动同步协议

### 7.1 用户流程

1. 用户打开“同步中心”。
2. 选择“局域网”或“我的服务器”。
3. 客户端执行只读扫描，显示上传、下载、冲突、附件大小和预计结果。
4. 用户确认后执行；无冲突项自动应用，有冲突项进入冲突中心。
5. 成功后保存 receipt、双方已知版本向量和审计摘要。

禁止：启动时自动同步、进入聊天页自动同步、后台定时同步、联网状态变化时自动同步。允许用户显式打开“提醒我有未同步更改”，该功能只显示本地提示，不发起网络请求。

### 7.2 统一会话协议

```text
POST /sync/v1/sessions              创建同步会话并协商版本/能力
POST /sync/v1/sessions/:id/plan     交换摘要，返回 dry-run 计划
POST /sync/v1/sessions/:id/push     分批推送实体信封
POST /sync/v1/sessions/:id/pull     按版本向量拉取批次
POST /sync/v1/sessions/:id/blobs    申请/提交附件传输
POST /sync/v1/sessions/:id/commit   提交 receipt 与确认向量
DELETE /sync/v1/sessions/:id        放弃未提交会话
```

- 同一 `batchId` 重试必须返回同一结果。
- `commit` 前，双方先验证、解密并写入持久化 staging，生成不可变 `preparedReceipt`；提交采用可恢复的 prepare/commit 时序，任一端重启后必须能查询会话并继续前滚或在尚未提交时安全放弃。
- 任一批次失败不能推进同步游标。
- LAN 和服务器响应使用同一错误码、分页和 receipt 结构。
- 协议版本与实体 schema 分开协商。
- `commit` 请求和响应丢失必须通过 session 状态与 `preparedReceipt/commitReceipt` 查询恢复；不得依赖内存状态，也不得在无法确认对端结果时重新应用业务批次。

### 7.3 局域网模式

- PC 继续监听现有 Bridge 端口，但同步使用独立 `/sync/v1` 路由和独立授权 scope。
- 用户在 PC 点击“允许本次同步”，生成 5 分钟一次性会话二维码。
- Android 扫码并主动连接 PC；双向数据都在该 HTTP 会话中传输。
- 首版不要求 Android 常驻 HTTP 服务，因此 LAN 同步由 Android 发起。
- 会话关闭、超时或完成后 token 立即失效。
- 局域网传输仍使用应用层加密与完整性校验，避免受不可信 Wi-Fi 影响。
- 二维码固定携带 PC 临时 X25519 公钥、256 位一次性 secret、过期时间和 TLS/应用公钥指纹；双方从 ECDH transcript 派生会话密钥，并在 PC 二次确认页显示同一短认证串。不得把“直接 secret 或 PAKE”留给执行 Agent 临时选择。

### 7.4 服务器模式

- 复用 Relay 的空间、设备、JWT 轮换和 RLS 基础设施，但新增 `/sync/v1`，不复用 `/relay/v1/bridge/*` RPC。
- PC 和 Android 任一端点击同步时，先上传本地增量，再拉取服务器中自己未见的增量。
- 服务端保存加密实体、版本向量、密文哈希、空间内不可逆的 keyed content tag、附件对象引用和设备确认向量；content tag 只用于相等性判断，客户端解密后仍须校验真实 contentHash。
- 服务端不自动向在线客户端推送；不需要业务 WebSocket。
- 配额、保留策略和空间删除必须覆盖数据库与对象存储。

## 8. 端到端加密与秘密边界

- 每个空间生成 256 位 `spaceKey`，只存在于已授权客户端的系统安全存储。
- payload 使用 AES-256-GCM；每条记录使用随机 nonce，AAD 至少包含 `spaceId/entityType/entityId/schemaVersion/versionHash`。
- blob 分块加密，manifest 记录每块密文哈希和明文总哈希。
- `spaceKey` 不能直接出现在二维码、日志、数据库、崩溃报告或普通备份中。
- 新设备持有长期设备身份密钥（X25519 密钥交换 + Ed25519 签名）。批准时必须由已有设备扫描新设备二维码或人工核对双方本地计算的短认证串，把 `deviceId`、身份公钥、空间和一次性 nonce 绑定后，再加密封装 `spaceKey`；服务端只转交带批准设备签名的密钥信封。
- Android Keystore 不直接假定可导入任意 32 字节空间密钥；使用 Keystore 生成的不可导出 wrapping key 加密保存 `spaceKey`。Android 8 所需 X25519/Ed25519 实现和密码提供方必须在阶段 0 实机验证。
- 设备吊销阻止未来访问，但已下载的历史明文无法远程擦除。若怀疑密钥泄漏，执行空间密钥轮换和后台重加密。
- key epoch/cipher revision 与业务版本向量分离；重加密不得生成业务变更、冲突或新的同步 dot。
- API Key 与设备本地连接档案默认不同步。后续若增加“加密凭据同步”，必须作为单独产品决策和威胁模型，不得混入本方案。

## 9. 兼容、一次性迁移与故障恢复

### 9.1 单轨切换原则

- 新版只运行独立客户端架构，不提供 `companionLegacyEnabled`、旧远程会话页或旧 Relay RPC 回退。
- 旧 Android 第一次启动把 Room 缓存作为一次性迁移来源；不得把不完整缓存直接当权威数据。
- 新版 Android 使用新的主数据库文件；旧缓存先复制为只读快照，再由迁移向导按用户选择导入，不能在用户选择前由 Room 自动升级原缓存库。
- PC 首次启用新架构前创建 Backup V2/V3 快照，并执行只读迁移预检。
- 迁移开始前保存旧数据库/文件的只读快照；迁移成功后旧结构不再被生产代码读取或写入。
- 迁移失败时恢复升级前快照、修复后重试或退出新版，不允许进入旧伴侣运行模式。
- PC 与 Android 从同一旧 PC 数据集迁移时必须共享 `migrationGenesisId` 和规范内容哈希。Android 缓存中的同内容投影不得被赋予独立并发祖先；缺失内容必须列入报告，并在旧网络凭据吊销前通过首次同步补齐或由用户明确放弃。

### 9.2 对外发布条件

满足以下条件后才发布不含旧伴侣模式的独立客户端：

1. P0 能力矩阵全部通过。
2. PC 与 Android 的规范 fixture 100% 一致。
3. LAN/服务器故障矩阵通过，无静默丢数据。
4. 至少完成一次真实旧版本 PC + Android 一次性升级、失败恢复和重新迁移演练。
5. E2EE、跨空间隔离、重放、路径和附件校验完成安全审计。

### 9.3 旧路径删除要求

旧伴侣模式必须在首个独立客户端公开候选版之前从 Android/PC 新安装包和 Sync Server 新部署物中删除，不能以隐藏开关、未链接页面或“紧急回退”形式保留。为已发布旧客户端提供迁移窗口时，只允许运行隔离、冻结、不可被新客户端调用的 legacy Relay 部署；它不得写入新同步存储，也不得成为新版回退通道，并须在稳定版前按公开日期下线。删除范围包括 Android 远程 Repository/连接状态机、PC 旧 Bridge 业务路由与流式 WebSocket、旧 Relay RPC/短期业务缓存/离线命令队列，以及只服务旧模式的 UI、测试和文档。空间、设备认证、RLS、令牌轮换等被 `/sync/v1` 复用的基础设施保留。删除使用独立提交，并以编译期引用清零、路由隔离/最终 404 和依赖扫描作为证据。

## 10. 阶段计划

| 阶段 | 名称 | 核心产物 | 前置 |
|---|---|---|---|
| 0 | 基线冻结与决策门 | 能力矩阵、ADR、fixtures、指标基线 | 无 |
| 1 | 规范契约与仓储边界 | schemas、repository 接口、同步信封 | 0 |
| 2 | PC 写路径收口与变更日志 | PC repository、journal、迁移预检 | 1 |
| 3 | Android 独立数据与模型连接 | 完整 Room、Keystore、模型适配器 | 1 |
| 4 | Android 单聊生成闭环 | 本地生成、上下文、记忆、消息操作 | 1、3；使用阶段 0/1 冻结的 PC 行为 fixture，并跟踪阶段 2 适配变化 |
| 5 | 内容管理功能对齐 | 角色/世界书/预设/人设/正则/快捷回复 | 3、4 |
| 6 | 群聊与平台扩展对齐 | 群聊、媒体、TTS、向量、MCP/生图边界 | 4、5 |
| 7 | 同步核心与局域网同步 | TS/Kotlin Sync Core、LAN transport、冲突中心 | 2、3、4、5 |
| 8 | 服务器同步与 E2EE | `/sync/v1`、密钥信封、对象存储、运维 | 7 |
| 9 | 一次性迁移、旧链路删除与发布 | 升级工具、旧代码/路由清零、全量验证、发布和恢复 | 6、8 |

阶段 2 与阶段 3 可由不同 Agent 并行；阶段 4 只依赖阶段 2 已冻结的契约，不依赖 PC 存储全部完成。阶段 6 和阶段 7 可在阶段 5 数据模型稳定后并行。其他阶段按表中依赖执行。

### 10.1 建议并行工作流

```text
阶段 0 -> 阶段 1 ─┬─> PC 数据线：阶段 2 ──────────┐
                  └─> Android 基础线：阶段 3 -> 4 -> 5 ─┬─> 阶段 6
                                                        └─> 阶段 7 -> 8
                                                阶段 6 + 8 -> 阶段 9
```

- 契约负责人：阶段 0、1，并持续审核 schema/fixture 变化。
- PC 数据负责人：阶段 2，阶段 7 的 PC LAN endpoint。
- Android 负责人：阶段 3—6，阶段 7/8 的客户端 transport。
- 同步/服务负责人：阶段 7 core、阶段 8 server/E2EE。
- QA/安全负责人不应等到阶段 9 才加入；从阶段 0 维护矩阵、故障样例和证据。

工作量用门禁而不是日历承诺管理。按完整 P0/P1、生产级 E2EE 和迁移回滚计算，整体约为 34—50 工程人周；三条开发线并行时，日历周期仍受跨端一致性、实机测试和灰度观察约束。若删减阶段 6 的 P2 能力，必须在阶段 0 矩阵中签字，不能在开发中静默缩减。

### 10.2 Agent 文件所有权建议

- 阶段 1 未完成前，其他 Agent 不修改 `shared/contracts/`。
- PC 数据线主要拥有 `electron/domain/`、Repository adapter 和同步元数据库。
- Android 基础线主要拥有 `android/**/domain`、`database`、`feature`；共享 fixture 变更需契约负责人审核。
- 同步服务线主要拥有 `relay-server/src/sync/` 和新增迁移；阶段 8 不改旧 `/relay/v1` 行为，旧路径统一由阶段 9 删除。
- 对现存高冲突文件（`shared/types.ts`、`electron/bridge/routes.ts`、Android navigation/database）先拆出新模块，再做最小接线，避免多个 Agent 同时大改。

## 11. 跨阶段工程约束

### 11.1 测试金字塔

- schema/fixture：所有语言必须读同一份 `shared/fixtures/cross-platform/` 数据。
- 领域单测：纯函数、迁移、版本比较、冲突分类覆盖边界。
- repository 契约测试：内存实现、PC 文件实现、Room 实现跑同一行为表。
- 协议测试：OpenAPI、错误码、批次幂等、断点续传和旧版本协商。
- 集成测试：PC ↔ Android 模拟器 LAN；PC/Android ↔ 本地 Sync Server。
- 故障注入：断网、重复包、乱序、磁盘满、进程崩溃、令牌过期、密文损坏。
- 安全测试：越权、跨空间、重放、ZIP/路径穿越、日志泄密、恶意超大 payload。
- 实机验收：至少 Android 8、Android 12、Android 14 三档或对应代表设备。

### 11.2 每阶段统一门禁

```powershell
pnpm check
pnpm lint
pnpm test
pnpm --dir relay-server check
pnpm --dir relay-server test
cd android
.\gradlew.bat testDebugUnitTest lintDebug assembleDebug
```

涉及 Room migration、Keystore、网络安全配置或端到端流程的阶段还必须运行受管模拟器或真实设备 instrumentation 测试；阶段 3、7、9 至少执行 `connectedDebugAndroidTest` 或等价 Gradle Managed Device 任务，并在报告中记录 API 等级和镜像版本。

阶段未修改的子项目若因已知环境问题不能执行，报告必须记录命令、失败输出摘要和替代证据，不能写“应该通过”。

### 11.3 Agent 提交规则

- 每个 Agent 只领取一个阶段或阶段内明确编号任务。
- 开工前读取总方案、当前阶段文档、上游阶段报告和 `git status`。
- 不覆盖工作区既有修改；发现同文件冲突时停止该文件并报告。
- 每项任务必须同时提交实现、测试、迁移/兼容处理和文档回写。
- 不允许以 TODO、空实现、仅 UI 假数据或跳过测试标记为完成。
- 阶段报告放在 `docs/报告/`，列出任务 ID、改动、测试证据、遗留和回滚点。
- 阶段完成后更新执行看板；总方案只在架构决策改变时更新。

## 12. 总体验收标准

- PC 与 Android 各自在飞行模式/断开对端时可完成全部适用功能。
- 两端分别修改不同实体后，同步结果为并集；并发修改同一实体时必然可见冲突。
- 任意同步在 30%、70%、commit 前被中断，重试后结果一致且无重复消息。
- 删除不会因长期离线设备重新出现而复活。
- 服务器数据库泄露时不能读取正文、图片或空间密钥。
- 一个空间的令牌、ID 或密文不能访问另一个空间的数据。
- 1 万会话、100 万消息基线下，同步只扫描变更日志，不全表/全目录上传。
- PC 旧数据与 Android 旧缓存均有可验证、可回滚迁移路径。
- 功能矩阵、性能、安全、升级和真实设备验收全部签字后，方可宣布“Android 完整功能版”。

### 12.1 风险登记

| 风险 | 等级 | 触发信号 | 缓解与停线条件 |
|---|---|---|---|
| PC 仍有绕过 Repository 的写入 | P0 | 文件变化但无 journal | 阶段 2 建静态/运行时绕过检测；未清零不得进入阶段 7 |
| TS/Kotlin 业务规则漂移 | P0 | 同 fixture 输出不同 | 共享 golden 门禁；差异必须先改契约或同时修复 |
| 文件正文与 SQLite journal 跨存储半提交 | P0 | 崩溃后 head/hash 不一致 | staging + checkpoint + 启动恢复；故障注入未过不得启用同步 |
| tombstone 被压缩后旧设备复活数据 | P0 | 设备 ack 不完整仍清理 | 180 天 + 全设备确认；退役设备必须重新授权 |
| E2EE 密钥丢失 | P0 | 无持钥设备/恢复包 | 上线前提供加密恢复包与轮换演练；明确服务端不可找回 |
| 服务器能读取或日志泄露用户内容 | P0 | 明文列/正文日志 | 加密互操作、安全扫描和数据库泄露演练不通过即停线 |
| Android 后台限制导致重复请求/计费 | P1 | 恢复后自动重发 | 任务幂等、interrupted 终局；进程恢复默认不重发 |
| 大附件耗尽客户端或服务端空间 | P1 | plan 与实际占用偏差 | 预检、分块、配额原子拒绝、孤儿 GC 和低空间测试 |
| 首次迁移把不完整缓存当权威 | P1 | 缺资产却显示完整 | 旧缓存只读隔离，必须由用户显式导入并显示缺失报告 |
| PC/Android 独立 bootstrap 产生全量伪冲突 | P0 | 首次同步大量同哈希并发版本 | 共同 migration genesis；同哈希合并；旧凭据在首次 receipt 后才吊销 |
| 父实体删除与离线子实体写入形成孤儿 | P0 | tombstone 下出现新消息/绑定 | aggregate delete fence 与依赖冲突；未处理前禁止 commit |
| 功能对齐持续扩张 | P1 | 阶段中新增无矩阵能力 | 只以阶段 0 capabilityId 为范围；新增走变更评审 |

## 13. 关键决策门

以下问题必须在对应阶段冻结；未冻结前不得让实现 Agent 自行选择：

1. 阶段 0：哪些 PC-only 能力采用平台等价，哪些进入 P2。
2. 阶段 1：canonical schema、RFC 8785 数值/字符串规范、十进制字符串 counter、ULID、共同迁移 genesis、aggregate delete fence 和 tombstone 结构。
3. 阶段 2：PC 继续文件存储还是后续迁 SQLite。本方案默认保留文件存储并先收口 Repository，禁止同期大迁移。
4. 阶段 6：Android 本地 embedding 支持的 ABI、模型和最低内存。
5. 阶段 7：LAN 的持久化 prepare/commit 时序、一次性会话密钥派生和重启恢复规则。
6. 阶段 8：恶意服务端威胁模型、带外设备认证、对象存储、空间配额、保留期和密钥轮换运维流程。
7. 阶段 9：旧伴侣路径的完整删除清单、隔离 legacy Relay 迁移窗口和一次性迁移恢复门禁；首个独立版不得携带旧运行模式。
