# 对话输出弹性约束阶段 7：异常链路与跨端收口方案

## 一、结论

阶段 0–6 的总体方向正确，无需回到固定大 Token 上限，也无需推翻动态预算、统一收尾和语义分块架构。

下一步应增加一个阶段 7，解决原方案覆盖不足的六类问题：

1. 所有异常终止路径尚未统一进入最终处理管线；
2. thought 的角色心理语义尚未正式写入架构契约；
3. Android 已能接收生成状态，但语义分块样式还没有闭环；
4. 长记忆等后台生成任务缺少独立于主对话的正式策略；
5. 自动补尾缺少成本、延迟、取消和降级指标；
6. 诊断日志与 legacy 退出缺少明确的数据和版本规则。

阶段 7 的核心目标不是增加更多生成规则，而是建立统一终止入口、明确跨端契约，并让灰度退出有可度量的条件。

## 二、当前基线与边界

### 2.1 已经完成，不在本阶段重复实现

- 正文篇幅与模型 Token 预算已经分离；
- DeepSeek V4 不再无条件固定为 8192；
- output 正则、停止字符串和 finalizer 已建立共享顺序；
- 群聊空闲超时已开始使用统一处理入口；
- 单聊和群聊长记忆已接入动态输出预算；
- 续写已使用专用短接缝去重策略；
- 用户明确篇幅意图与场景系数已接入策略计算；
- 群聊 blocks 路径已补安全的 @提及高亮；
- Android 已增加 `generationNotice`、`generationError`、`contentRenderMode` 字段；
- 测试环境消息 ID 已从固定值改为递增值。

这些成果应保留。阶段 7 只处理其余旁路、跨端展示和运行治理问题。

### 2.2 当前最重要的残留风险

目前正常 `stop`、`length` 和部分 timeout 已能进入共享管线，但普通 `ai:error`、桌面空闲超时等分支仍可能直接保存已经流出的半截文本。

这会造成同一段内容因结束方式不同而得到不同结果：

- 正常触顶时会回退到完整句界；
- 网络错误或桌面超时时可能原样落盘；
- `generationError` 虽与正文分离，但正文自身仍可能以半句、未闭合引号或标签结束。

因此阶段 7 的第一优先级是：**只要允许保存部分正文，就必须先经过同一个最终处理入口。**

## 三、设计原则

### 3.1 单一最终处理所有权

所有可见 AI 正文只能由共享生成结果管线产出。store、Bridge 和界面层不得在管线完成后继续修改正文。

固定顺序如下：

```text
原始流式文本
  ↓
供应商 reasoning / thinking 清理
  ↓
output 正则
  ↓
停止字符串
  ↓
结构完整性检查与稳定边界收束
  ↓
符合条件时最多一次短补尾
  ↓
续写入口执行接缝去重
  ↓
保存正文 + 独立状态字段
```

硬性约束：

- finalizer 之后不得再次执行会改变正文的正则、截断或前缀补齐；
- 错误、超时和停止提示不得拼入 `content`；
- TTS、复制、导出、记忆和下一轮上下文只读取干净正文；
- legacy 可跳过新语义收尾，但不得恢复“错误文案写进正文”的旧行为。

### 3.2 模型结束原因与应用终止原因分离

上游 `finishReason` 只能描述模型或供应商给出的结束原因；空闲超时、用户取消和本地协议错误属于应用层原因，不应全部伪装为 `network_error`。

建议增加应用层终止原因：

```ts
export type GenerationTerminationCause =
  | 'provider_stop'
  | 'provider_length'
  | 'provider_content_filter'
  | 'provider_tool_calls'
  | 'transport_error'
  | 'idle_timeout'
  | 'user_cancel'
  | 'protocol_error'
  | 'unknown'

export interface GenerationTerminalResult {
  rawText: string
  finishReason: AIFinishReason
  terminationCause: GenerationTerminationCause
  errorMessage?: string
  usage?: AICompletion['usage']
}
```

`finishReason` 保持供应商兼容，`terminationCause` 负责产品行为、日志分类和界面提示。两者不得互相覆盖。

## 四、方案一：统一所有异常终止路径

### 4.1 建立终止行为矩阵

| 终止情况 | 有可用正文 | 最终处理 | 自动补尾 | 保存结果 | 用户提示 |
|---|---|---|---|---|---|
| 正常 `stop` | 是 | 完整性检查 | 否 | 完整正文 | 无 |
| `length` | 是 | 稳定边界收束 | 必要时一次 | 完整或恢复正文 | 仅恢复时轻提示 |
| transport error | 是 | 稳定边界收束 | 默认否 | 稳定正文 | 生成中断，已保留完整部分 |
| idle timeout | 是 | 稳定边界收束 | 否 | 稳定正文 | 请求超时，已保留完整部分 |
| user cancel | 是 | 保留用户已经看到的正文 | 否 | 当前可见正文 | 已停止生成 |
| content filter | 任意 | 不做自动补尾 | 否 | 按审核策略决定是否保留 | 明确审核提示 |
| protocol error | 是 | 稳定边界收束 | 否 | 稳定正文 | 响应格式异常 |
| 任意异常 | 否 | 不创建空 AI 消息 | 否 | 不保存正文 | 明确错误与重试入口 |

说明：网络已异常时继续发起补尾成功率低，还会增加等待，因此默认只收束稳定前缀。只有 `provider_length` 允许自动补尾。

### 4.2 新增共享异常收口入口

建议在共享管线之上增加终止协调函数：

```ts
finalizeGenerationTerminalResult({
  terminalResult,
  regexRules,
  characterName,
  legacy,
  allowTailRepair,
}): Promise<GenerationFinalResult>
```

它负责：

1. 根据 `terminationCause` 决定是否允许保存部分正文；
2. 调用现有共享生成结果管线；
3. 生成 `generationNotice` 或 `generationError`；
4. 返回唯一可落盘结果；
5. 保证同一终止事件只处理一次。

桌面单聊、群聊、Bridge、重生成、Swipe 和续写都只消费该函数返回值，不再自己拼装异常正文。

### 4.3 处理超时与迟到事件竞态

超时后供应商仍可能返回最后一个 chunk 或 done 事件。需要用 `requestId + terminalState` 建立一次性状态机：

```text
streaming → finalizing → persisted
    └────→ cancelled
    └────→ failed
```

规则：

- 只有 `streaming` 能进入某个终止分支；
- 进入 `finalizing` 后忽略迟到 chunk、done 和 error；
- 保存成功后进入 `persisted`，同一请求不得再次保存；
- timeout 回调执行前必须先读取完整 accumulated 文本，再清理监听器；
- 所有未执行的 flush timer 必须在终止前同步合并到 accumulated。

这能同时避免重复消息、重复落盘和“超时结果被迟到 done 覆盖”。

### 4.4 验收测试

- 单聊收到半句后触发首次空闲超时；
- 单聊收到多个 chunk 后续期超时；
- 群聊点名、轮询、自由发言分别触发普通 `ai:error`；
- Bridge 在有部分正文时断开；
- timeout 后到达迟到 chunk/done/error；
- stop、length、timeout、transport error 对同一原始文本得到一致的稳定边界；
- 每个 requestId 最多保存一次 AI 消息；
- 错误文案不进入复制、TTS、记忆或下一轮上下文。

## 五、方案二：正式定义 thought 语义

### 5.1 语义契约

`<thought>` 只表示消息所属角色在当前情境中的内心活动，不表示模型的推理过程。

必须满足：

- 使用当前角色第一人称“我”；
- 内容只包含角色能知道、感受到、怀疑或打算的事情；
- 不得出现“模型、用户指令、系统提示、规则、上下文、下一步生成”等元信息；
- 不得复述分析过程或解释为什么这样写；
- 正文使用全局第三人称叙事时，thought 仍属于焦点角色并保持第一人称；
- 群聊中 thought 归属于当前消息的 speaker，不使用群组或旁白作为思考主体；
- 没有必要时不强制输出，每条消息最多一个简短 thought 块。

建议提示词：

```text
【角色内心】
如确有必要，可使用一段 <thought>...</thought> 表示当前角色的内心活动。
其中必须以当前角色第一人称“我”思考，只写角色在情境中能知道、感受或打算的内容。
禁止写模型推理、规则分析、生成计划、上下文复述或任何创作说明。没有必要时省略。
```

### 5.2 reasoning 与 thought 双通道隔离

| 内容 | 来源 | 是否进入消息正文 | 是否显示 | 是否进入 TTS/记忆/下一轮上下文 |
|---|---|---:|---:|---:|
| 供应商 reasoning/thinking | 模型内部推理通道 | 否 | 否 | 否 |
| `<thought>` | 角色可见正文语义 | 是 | thought 样式 | 默认不进入 TTS；可按现有上下文策略保留 |
| 普通正文 | 角色回复 | 是 | 正文样式 | 是 |

清理供应商 reasoning 时不得误删合规的角色 `<thought>`；反过来，也不得把供应商 reasoning 包装成 `<thought>`。

### 5.3 验收测试

- 代入式单聊 thought 使用当前角色第一人称；
- 全局叙事正文为第三人称，thought 仍为焦点角色第一人称；
- 群聊每个角色的 thought 归属正确；
- OpenAI/OpenRouter、Claude、Gemini、Ollama reasoning 均不进入正文；
- 跨 chunk 的 reasoning 标签可以完整清除；
- TTS 不朗读 thought；
- “我需要遵守规则”“接下来生成”等模型分析样本判定为失败。

## 六、方案三：完成 Android 语义分块渲染

### 6.1 当前边界

Android 已能解码并缓存 `generationNotice`、`generationError` 和 `contentRenderMode`，也能展示中性提示和错误提示；但 `contentRenderMode='blocks'` 还没有真正改变正文渲染方式。

### 6.2 推荐方向

第一阶段不新增数据库字段，也不持久化另一份正文。将桌面端确定性分块规则等价移植到 Kotlin：

- `<thought>...</thought>` → thought；
- 纯中文引号段 → dialogue；
- 旧整段 `*动作*` → narration；
- 同行混合内容 → mixed，按普通正文安全显示；
- 空行作为块边界；
- `contentRenderMode` 缺失时继续走旧 Markdown/兼容渲染。

为了防止 TypeScript 和 Kotlin 规则漂移，建立一份共享 JSON fixture，至少覆盖 30 个真实样本。两端测试读取同一批输入与期望块类型。

若后续分块规则变得复杂，再考虑 Bridge 可选下发 `contentBlocks`。当前阶段不建议立即新增第二份持久化内容，以免引入同步和迁移成本。

### 6.3 验收

- PC 与 Android 对同一 fixture 得到相同块数量和类型；
- 对白、动作、thought、混合段、截断恢复内容视觉语义一致；
- 旧缓存消息正常显示；
- 未知 `contentRenderMode` 安全回退，不崩溃；
- 搜索高亮、复制和翻译继续基于原始 `content`。

## 七、方案四：后台生成采用独立策略

### 7.1 区分两类生成任务

| 类型 | 例子 | 主要目标 | 是否使用主对话篇幅策略 |
|---|---|---|---:|
| 用户可见生成 | 单聊、群聊、续写、重生成 | 自然互动、样式完整、可恢复 | 是 |
| 后台结构化生成 | 长记忆、事实提案、历史压缩、标题、方向建议 | 完整结构、可解析、低成本 | 否 |

后台任务不应使用“一个互动回合”提示，也不应直接复用 `brief/balanced/detailed`。应建立 `BackgroundGenerationProfile`：

```ts
interface BackgroundGenerationProfile {
  task: 'memory' | 'compression' | 'title' | 'direction'
  expectedBodyChars: number
  requiresStructuredTail: boolean
  reasoningReservePolicy: 'none' | 'model_profile'
  retryPolicy: 'none' | 'structure_only_once'
}
```

### 7.2 长记忆与事实提案

当前动态预算方向应保留，并补足以下规则：

- 摘要正文和事实 JSON 分别判断完整性；
- `finishReason=length` 时摘要完整但事实提案残缺，只保存摘要并明确记录事实未更新；
- 不把残缺 JSON 当成“无新增事实”；
- 推理型模型使用档案/P90 余量，非推理模型不无条件请求大预算；
- 群聊和单聊使用同一预算算法，只允许任务体量参数不同。

### 7.3 其他后台任务

- 标题：使用小预算，触顶时丢弃结果，不做补尾；
- 历史压缩：有完整摘要边界才保存，原历史不能在压缩失败时丢失；
- 方向建议：结构不完整时最多进行一次“只补结构”的短修复，不重写完整剧情；
- 所有后台任务都记录独立 taskType，不混入主对话篇幅统计。

## 八、方案五：成本、延迟与取消治理

### 8.1 自动补尾限制

- 只有 `provider_length` 且稳定正文不足时允许；
- 每条消息最多一次；
- 不重新发送完整世界书与长历史；
- 补尾期间用户点击停止，立即取消补尾并保留稳定前缀；
- 主请求已经产生明确审核/协议错误时禁止补尾；
- 同一模型连续补尾失败两次后，本次会话暂时关闭自动补尾并提示重新生成。

### 8.2 建议运行指标

| 指标 | 建议目标 |
|---|---:|
| 正常路径额外请求数 | 0 |
| 自动补尾率 | 低于 5% |
| 自动补尾成功率 | 不低于 90% |
| 自动补尾消耗占总 completion tokens | 低于 3% |
| 全体请求 P95 完成延迟相对基线增幅 | 不高于 10% |
| 不可恢复截断率 | 低于 1% |
| 格式破损率 | 0 |

阈值应先通过真实样本建立基线，再作为灰度门槛；样本不足时不得用单次结果判断方案成败。

## 九、方案六：观测隐私与 legacy 退出

### 9.1 诊断日志最小化

默认观测只保存：

- requestId 的不可逆短哈希；
- provider/model/taskType；
- 篇幅模式与预算档；
- 正文可见字符数；
- prompt/completion/reasoning tokens；
- finishReason/terminationCause；
- finalizer 状态、补尾次数和延迟；
- 是否存在结构破损，不保存破损原文。

默认不得把完整提示词、世界书、角色卡和回复正文写入诊断日志。

如确需调试原始文本：

- 由用户显式打开本地调试模式；
- 明确提示可能包含私人对话；
- 文本片段限制长度并对 API Key、邮箱、手机号等做基础脱敏；
- 设置自动过期时间；
- 提供一键清除入口；
- 不上传到远端，除非用户另行明确同意。

### 9.2 legacy 退出门槛

“连续两个版本无回归”改为可衡量条件：

1. unified 覆盖至少 500 次有效生成，并覆盖两个以上供应商；
2. 不可恢复截断率低于 1%；
3. 格式破损率为 0；
4. 重大数据丢失或重复落盘为 0；
5. 自动补尾率和延迟满足第八节指标；
6. PC 与 Android 共享 fixture 全部通过；
7. 真实模型评测确认 thought 不包含模型推理。

退出分三步：

1. 隐藏 legacy 新入口，但保留已有设置可继续回退一个版本；
2. 删除 legacy 生成提示和新消息前缀规范化，保留旧消息只读渲染；
3. 再经过一个版本后移除 legacy 设置字段迁移代码，旧消息兼容渲染长期保留。

任何阶段出现正文丢失、重复落盘或跨端解码失败，应停止退出并恢复上一阶段，不回退用户数据。

## 十、实施顺序

### 阶段 7.1：异常链路统一

1. 增加 `GenerationTerminationCause` 与终止协调函数；
2. 单聊 desktop timeout 接入统一异常收口；
3. 单聊普通 `ai:error` 接入统一异常收口；
4. 群聊点名/轮询/自由发言普通 `ai:error` 接入统一异常收口；
5. Bridge partial error 接入同一入口；
6. 增加终止状态机和迟到事件幂等测试。

完成标准：任何允许保存的部分正文都先通过统一收尾；同一 requestId 最多落盘一次。

### 阶段 7.2：thought 契约与 Android

1. 将 thought 第一人称角色语义写入共享提示与文档；
2. 补角色归属、模型推理隔离和 TTS 测试；
3. Android 实现 `contentRenderMode='blocks'`；
4. 建立 TypeScript/Kotlin 共享 fixture。

完成标准：thought 语义正确，PC 与 Android 对同一消息得到一致的语义块。

### 阶段 7.3：后台任务与运行指标

1. 增加 `BackgroundGenerationProfile`；
2. 长记忆、压缩、标题、方向建议分别接入；
3. 记录 taskType、terminationCause、补尾耗时和额外 Token；
4. 实现补尾取消与连续失败降级。

完成标准：后台结构化任务不再套用主对话篇幅策略，失败状态可解释且不破坏原数据。

### 阶段 7.4：灰度验收与 legacy 退出

1. 跑桌面、Bridge、Android 自动化测试；
2. 跑共享推理预算模型与非推理模型真实评测；
3. 收集至少 500 次有效生成指标；
4. 达标后按第九节顺序退出 legacy。

## 十一、建议修改文件

| 文件/模块 | 修改方向 |
|---|---|
| `shared/types.ts` | 增加应用层终止原因和统一终止结果类型 |
| `src/store/generatedReplyPipeline.ts` | 保持唯一正文处理顺序，增加异常终止协调入口或配套模块 |
| `src/store/streamController.ts` | desktop timeout、普通 error、迟到事件进入同一状态机 |
| `src/store/useChatStore.ts` | 只保存统一终止结果，不再直接保存半截正文 |
| `src/store/groupStreamController.ts` | 普通 error 与 timeout 共用异常收口，不复制保存逻辑 |
| `electron/bridge/chatService.ts` | Bridge partial error 和幂等缓存接入统一终止结果 |
| `shared/responsePolicy.ts` / 上下文提示 | 固化 thought 的角色第一人称契约 |
| `android/.../MessageBubble.kt` | 根据 `contentRenderMode` 使用语义块渲染 |
| `android/.../GroupMessageRow.kt` | 群聊语义块和 thought 归属显示 |
| `shared/fixtures/roleplay-blocks.json`（建议新增） | PC/Android 共用分块样本 |
| 长记忆、压缩、标题、方向模块 | 接入后台任务档案和独立终止策略 |
| 生成观测模块 | 增加 terminationCause、taskType、耗时和补尾成本，默认不记正文 |

## 十二、最终验收清单

- [ ] stop、length、timeout、transport error、cancel、content filter、protocol error 均有明确行为；
- [ ] 所有部分正文进入同一最终处理入口；
- [ ] output 正则和停止字符串每条消息只执行一次；
- [ ] finalizer 后没有其他代码修改正文；
- [ ] 同一 requestId 最多保存一次结果；
- [ ] 错误和提示不进入正文、TTS、复制、记忆和下一轮上下文；
- [ ] thought 是当前角色第一人称心理，不含模型推理；
- [ ] Android 正式消费 `contentRenderMode`，旧消息安全兼容；
- [ ] 长记忆等后台任务使用独立预算和完整性策略；
- [ ] 自动补尾可取消，并满足成本与延迟门槛；
- [ ] 默认诊断日志不保存私人正文；
- [ ] 真实模型评测和跨端 fixture 通过后再退出 legacy。

## 十三、不建议的方向

- 不继续单纯提高所有模型的固定输出上限；
- 不为每种异常分别复制一套收尾代码；
- 不在网络错误后自动完整重生成；
- 不把 timeout、用户取消和供应商错误全部折叠为同一个 finish reason；
- 不把错误提示拼进消息正文；
- 不让 Android 永久忽略 `contentRenderMode`；
- 不把供应商 reasoning 转换成角色 thought；
- 不在默认诊断中长期保存完整角色对话；
- 不为了删除 legacy 而迁移或重写旧消息正文。

阶段 7 完成后，这套方案才算从“主流程可用”收敛到“异常路径一致、跨端一致、可观测且可安全退出旧链路”。
