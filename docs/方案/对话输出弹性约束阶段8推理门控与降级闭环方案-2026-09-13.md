# 对话输出弹性约束阶段 8：推理门控与降级闭环方案

> 日期：2026-09-13

> 范围：主对话（单聊/群聊/Bridge）在共享推理预算模型上的输出约束；适配器参数下发；流式提前中止；空正文降级重试；模型档案运行时探测

## 一、结论

现行"正文预算 + 推理余量"的动态预算（方案 §4.4）方向正确，但它对推理是**被动让位**：只保证"给推理留够空间"，不保证"推理不超过预留"。共享预算模型的推理量由模型自己决定，可以超过任何本地预留；而 `requestMaxTokens` 被 `outputLimit` 与通用安全上限（8192）钳制（**2026-09-17 更新：通用 8192 上限已移除，见 §〇**），无法无限抬高。结果就是本方案要解决的残留失败模式：

```text
reasoningReserve = 3072（或 P90 估计）
模型实际推理  >  requestMaxTokens − 正文所需
→ finish_reason=length，正文 0 字符
→ 适配器抛「推理已占满模型输出硬上限」
→ 用户看到错误，本轮作废
```

新约束方案由四个机制组成，替换"猜余量"：

1. **推理门控（Gate）**：把统一意图翻译成各家 API 的推理控制参数（`thinking:disabled` / `reasoning_effort` / `thinking.budget_tokens` / `thinkingConfig.thinkingBudget` / `thinking_budget`），让推理上限由**服务端强制执行**，而不是本地预留赌概率。门控生效时，预算公式的推理项就是门控值本身，正文空间获得确定性保证。
2. **能力探测与记忆**：门控参数是否被支持、是否被聚合端**静默忽略**，运行时探测并持久化到 (provider+model) 档案；参数被 400 拒绝时按降级表去参重试。不再假设聚合端行为与官方端点一致。
3. **流式提前中止**：推理持续流出而正文迟迟不出现、且已越过门控观测线时，主动 abort 请求，不再无谓等满上限；这是无门控或门控失效模型的唯一止损手段。
4. **空正文降级重试闭环**：正文为空且判定为推理挤占时（无正文损失，不违反"截断不整条重生成"原则），同一轮自动降一档门控重试**至多一次**；仍失败才落入现有错误路径，且带明确原因与操作入口。

目标链路（在现行链路图上只改推理约束一处）：

```text
ResponsePolicy（正文软区间，不变）
        +
ReasoningGate（本轮推理档位：模型档案 × 运行时探测 × 会话记忆）
        ↓
requestMaxTokens = bodyReserve + gateTokens      ← 门控生效时
                 = bodyReserve + 保守余量        ← 无门控模型（配合提前中止）
        ↓
适配器下发性参数（被供应商执行，400 → 降级表去参）
        ↓
流式观测：reasoning 越线且无正文 → 提前 abort
        ↓
length + 空正文 + 推理挤占 → 降档重试一次 → finalizer（复用现有统一收尾）
```

## 二、现状与根因

### 2.1 预留是估计值，推理是开放值

`shared/modelOutputProfile.ts` 的推理余量三档（协议余量 192 / 档案默认 2048–3072 / P90×1.2 上限 2048–4096）（**2026-09-17 更新：现为协议余量 192 / 自动余量 8192 / P90×1.2 上限 32512，见 §〇**）全部是**对模型行为的统计猜测**。共享预算模型的思考长度随上下文复杂度增长（首轮长世界书、多角色群聊、复杂剧情推进时显著变长），没有任何机制阻止它越过预留值——预留被越过时唯一后果就是正文饿死。

### 2.2 P90 滚动估计从未接线

`resolveReasoningReserve` 支持 `recentReasoningTokens` 样本（方案 §4.4 设计的滚动回灌），但 `src/context/contextBuilder.ts:187` 调用 `resolveRequestBudget` 时没有传该字段，全仓库也无其他调用方传入。生产路径永远走档案默认值。上游方案中"连续两次 `length` 时仅提高该模型的推理余量档"同样没有实现（现存的连续失败治理只针对补尾，`streamController.ts:565`）。也就是说，方案设计的自适应闭环实际不存在，余量是静态常数。

### 2.3 关闭参数会被聚合端静默忽略

主对话对 deepseek-v4 已下发 `thinking:{type:'disabled'}`（`openai.ts:36`，由 `streamController.ts:1019` 触发），并且当聚合端**接受参数但不透传**时，本地完全无感知——适配器照常丢弃 `reasoning_content`，但它仍然消耗共享预算。现有 400 回退只覆盖"明确拒绝 thinking"一种情况。

### 2.4 各适配器的门控能力参差且非策略驱动

- Claude（`claude.ts:67`）：`budget_tokens = max(1024, maxTok/3)` 是适配器内的固定比例猜测，与档案、篇幅策略无关；`maxTok` 较小时下限 1024 甚至可能吞掉正文空间。
- Gemini（`gemini.ts`）：**完全没有下发 `thinkingConfig`**，2.5/3 动态思考无约束地挤占 `maxOutputTokens`。
- OpenAI o 系/R1：`reasoning_effort` 硬编码 `'medium'`（`openai.ts:53`），与请求场景无关。
- 未匹配档案的推理模型（新聚合模型为主）：`DEFAULT_OUTPUT_PROFILE` 为 `none`/协议余量 192——任何会思考的未知模型**每一轮都必然触顶**。
- 检测盲区：`isReasoningBudgetExhausted` 依赖 `usage.reasoning_tokens` 上报；聚合端不上报时退化为"模型未返回任何内容"，观测分类为 `unknown`。

### 2.5 失败即终局，没有恢复路径

`openai.ts:134/290` 在空正文时抛 `REASONING_BUDGET_EXHAUSTED_MESSAGE`，走 `ai:error`。这与阶段 7 建立的"终止结果统一收口"不矛盾——但推理挤占是唯一**正文零损失**的触顶场景（没有任何已生成内容需要保留），本应允许一次自动降级重试，而不是直接打扰用户。

## 三、设计目标与非目标

### 3.1 目标

- 共享推理预算模型上，"推理吃光输出、正文为空"的用户可见错误率降到 0.5% 以下。
- 推理预算从"本地猜测"变为"供应商执行的硬约束"（凡端点支持）；不支持门控的端点用提前中止 + 降档重试兜底。
- 失败恢复不打扰用户：空正文自动降档重试一次，成功则用户只感知到一次略慢的生成。
- 门控能力按 (provider+model) 记忆，聚合端静默忽略不污染其他端点。
- 未知模型不再默认"无推理"，首次出现 reasoning 流即自动升级档案。
- 正文预算、统一收尾、补尾、终止状态机等阶段 0–7 成果全部保留，不重复实现。

### 3.2 非目标

- 不通过继续抬高 `outputLimit` 或通用安全上限解决问题（上游方案 §12.1 仍然有效）。
- 不追求消灭所有推理消耗：推理消耗正文空间是共享预算模型的固有属性，目标是**有界且可恢复**。
- 不为"思考得更少"引入新的正文篇幅概念：篇幅仍是 ResponsePolicy 的职责。
- 不要求所有聚合端支持任何门控参数；不支持是常态路径，方案必须优雅退化。
- 不改动 Android/Bridge 协议语义（现有 `finishReason/terminationCause/notice` 字段够用）。

## 四、方案设计

### 4.1 统一推理门控抽象

新增共享模块 `shared/reasoningGate.ts`（纯函数 + 类型），与 `modelOutputProfile` 并列：

```ts
/** 本轮希望供应商执行的推理档位（产品语义，非各家的参数名） */
export type ReasoningGateLevel = 'off' | 'low' | 'standard' | 'full'

/** 端点实际可用的门控方式；探测前为 unknown */
export type ReasoningGateKnob =
  | 'thinking-disable'      // DeepSeek: thinking:{type:'disabled'}
  | 'reasoning-effort'      // OpenAI o系/GPT-5/DeepSeek V4 聚合: reasoning_effort
  | 'thinking-budget'       // Claude: thinking.budget_tokens；Qwen 兼容: thinking_budget
  | 'gemini-thinking-config'// generationConfig.thinkingConfig.thinkingBudget
  | 'none'                  // 无服务端门控：只能本地余量 + 提前中止

/** 某 (provider+model) 的探测结果，持久化于设置存储 */
export interface GateProbe {
  knob: ReasoningGateKnob | 'unknown'
  /** 端点是否接受该 knob 参数（400 拒绝 → false，永久记录） */
  knobAccepted?: boolean
  /** 声称接受但流中仍出现 reasoning_content → disable 被静默忽略 */
  disableIgnored?: boolean
  /** 是否上报 usage.reasoning_tokens */
  reportsReasoningUsage?: boolean
  /** 近期 reasoning token 样本（修复 §2.2：真正接线） */
  recentReasoningTokens: number[]
  updatedAt: number
}
```

档位语义与 token 含义（供预算公式使用）：

| 档位 | 语义 | 建议映射（按 knob） |
|---|---|---|
| `off` | 只要最终正文（辅助任务、降级最后一级、现有 `reasoningMode:'disabled'` 的正式化） | disable / effort=none（若支持）/ thinkingBudget=0 或最小值 |
| `low` | 短思考，够完成一个互动回合的判断 | effort=low / budget≈800–1200 |
| `standard` | 端点默认，不额外干预（首轮、复杂剧情、降级起点之前的默认档） | 不下发或下发默认值 |
| `full` | 用户显式选择"完整思考" | 不下发上限 |

**默认策略**：角色扮演回合默认 `standard`（不干预，保持现有生成质量）；`off` 用于续写、补尾、方向建议、标题、长记忆等已有辅助路径（现有 `reasoningMode:'disabled'` 统一收编为该机制，语义不变、覆盖面扩大）。降级链路是 `standard → low → off`。

**预留产品入口（本期不做 UI，仅类型与解析函数支持）**：会话级"思考强度 自动/省/标准"，与"回复篇幅"并列展示。篇幅是产品意图、门控是资源约束，两者依旧解耦。

### 4.2 预算公式改造

`ModelOutputProfile` 增加 `defaultGate: ReasoningGateLevel` 与 `gateKnobs: ReasoningGateKnob[]`（有序，探测按序尝试）。`resolveRequestBudget` 改为：

```ts
gateTokens = levelToTokens(gateLevel, profile, probe)
// 门控可信（knob 已验证生效）：推理上限被供应商执行，余量即门控值，可信且稳定
// 门控不可信/无门控：gateTokens = max(门控值, 档案保守余量)，仍走 shared-unknown 逻辑
requestMaxTokens = min(profile.outputLimit, MAX_REQUEST_OUTPUT_TOKENS,
                       bodyReserve + gateTokens, userHardCap ?? ∞)
```

关键差异：

- 门控生效时，`gateTokens` 不再需要 P90 猜测——它是承诺值，正文空间 = `requestMaxTokens − gateTokens`，确定非空；
- `recentReasoningTokens` 从 GateProbe 真实接线（本次必须落地，修复 §2.2），用于无门控模型的余量估计与提前中止观测线；
- 无可用门控且无样本的模型：沿用现档案默认值，但**必须配合 4.4 提前中止**，不再假设预留成立；
- `minimumViableOutputTokens` 与 `riskNotice` 机制保留，改为基于 `gateTokens` 计算。

### 4.3 适配器实施与参数降级表

适配器不再各自内嵌推理参数决策，统一消费 `params.reasoningGate: { level, knob }`（由主进程在发请求前用 `resolveReasoningGate(model, preset, probe, taskKind)` 解析）：

| 适配器 | knob → 请求体 |
|---|---|
| openai（DeepSeek 系） | `off`→`thinking:{type:'disabled'}`；`low`→`reasoning_effort:'low'`（V4 聚合端实测支持则用，否则按降级表） |
| openai（o 系/GPT-5） | `off`→尽力 `reasoning_effort:'minimal'`，不支持则跳过该级；`low`→`'low'`；`standard`→不再硬编码 `medium`，改为不下发 |
| openai（Qwen3 兼容） | `thinking_budget:{levelTokens}`、`off`→`enable_thinking:false` |
| claude | `budget_tokens` 由 `resolveReasoningGate` 给出，替换现行 `max(1024, maxTok/3)` 比例猜测，并保证 `≤ requestMaxTokens − 正文最小空间` |
| gemini | 新增 `generationConfig.thinkingConfig`：`off/low`→`thinkingBudget:0/小值`（2.5）或 `thinkingLevel`（3 系）；**补上 §2.4 缺失的控制** |
| ollama | 无统一参数；按 `none` knob 处理 |

**参数降级表（泛化现有 thinking-400 处理）**：请求 400 且错误文本指向被拒字段时，删除该字段重试一次，并把 `knobAccepted:false` 写入 GateProbe——该 (provider+model) 后续不再尝试此 knob，按 `gateKnobs` 顺序退到下一级。现有 `thinkingUnsupported` 逻辑收编进该机制。

**静默忽略探测**：流式响应中出现 `reasoning_content` delta 而本轮请求带 `off` 档 disable → 记 `disableIgnored:true`，本端点后续 `off` 意图落到 `none` knob（提前中止兜底），并把该模型的档案标记降级。

### 4.4 流式提前中止（Abort-on-Reasoning-Runaway）

适配器内流式计数器：`reasoningChars`（被过滤掉的供应商推理文本累积）与 `bodyChars`。中止条件（全部满足）：

- 本轮门控不可信或无门控（`knob:none` 或 `disableIgnored`）；
- `bodyChars === 0` 且 `finishReason` 尚未出现；
- `estimateTokens(reasoningChars) ≥ requestMaxTokens − MIN_USABLE_BODY_TOKENS`。

> **修订（2026-09-13，G1 实机取证后）**：观测线原为 `max(gateTokens, requestMaxTokens × 0.85)`，现改为
> **`requestMaxTokens − MIN_USABLE_BODY_TOKENS`（正文绝对下限，256）**，即"继续下去已不可能留下可用正文"的
> **可证明徒劳点**。理由（[G1 报告](../../报告/PC端动态上下文G1灰度取证实机评测报告-2026-09-13.md)，n=82，CommandCode + deepseek-v4-pro）：
> ① `× 0.85` 是无依据魔数，实测 3/3 次中止全部以空正文结束，而配对对照臂在同一用例上更快地产出了正文；
> ② `gateTokens` 是**预算承诺**而非止损线，接入 P90 余量后它可能大于本式，取 max 会让守卫在"已无正文空间"之后才触发（等于失效）；
> ③ 新式与 `resolveRequestBudget` 的 `minimumViableOutputTokens` 同源，可解释、可单测。
> 触发时机的相对变化：预算 > 1707 时新式晚于旧式（更不易误杀），更小预算下略早（仍是正确的徒劳点）；
> 阈值以 CJK 感知的估算推理 token 计量，而中文推理的估算普遍高于供应商上报值，故实际触发比字面更晚。

中止实现为适配器内部把用户 `signal` 与内部 `AbortController` 合并（复用 `types.ts` 现有 signal 合并工具），返回**专用终局**：`finishReason:'length'` + `terminationCause:'reasoning_gate_exceeded'`（`shared/generationTermination.ts` 新增枚举值），不抛普通 `ai:error`。收益：失败路径等待时间从"写满上限的全部推理延迟"缩短到越过观测线即止。

阈值随观测回灌：有 `recentReasoningTokens` 样本时进入推理余量公式（见 §4.1/主计划 §5.4），不再影响本观测线。

### 4.5 空正文降级重试闭环

接入阶段 7 的终止协调入口（`finalizeGenerationTerminalResult` 的调用侧），新增一条**前置恢复分支**，规则：

| 条件 | 动作 |
|---|---|
| 判定为推理挤占（`reasoning_gate_exceeded`、或 `length` + 可见正文 < 20 字符 + `reasoning_tokens ≥ completion×0.9`、或无 usage 时 `length` + 空正文） | 降一档（`standard→low→off`）重试同一请求，至多一次 |
| 降级重试再次推理挤占 | 落入现有错误路径；文案升级为"该模型推理占满输出预算，已尝试降级仍失败：重试 / 调整思考强度 / 更换模型" |
| 已有可用正文的 `length` | **不触发**本机制，走既有 finalizer 稳定边界收束（阶段 3 行为不变） |
| 用户手动停止 / transport error / content_filter | 不触发 |
| 同一 (provider+model) 本次会话内连续 2 次降级失败 | 会话级熔断：该模型后续请求直接从 `low` 起步，并提示一次 |

约束与成本论证：重试只发生在**正文为空**时，没有任何已生成内容损失，不违反上游方案"不整条重生成"的初衷（该初衷保护的是已有正文与剧情连续性）。重试请求复用同一上下文构建结果（预算字段按新档位重算，历史不重复裁剪），usage 单独记录并归属原生成任务（对齐阶段 7 §8 的补尾治理模式）。

### 4.6 未知模型自动建档

`getModelOutputProfile` 保持 lean 默认，但 `none` 档案的模型一旦出现以下任一信号即运行时升级为 `shared-unknown` 档案并持久化 GateProbe：

- 流中出现 `reasoning_content`/`reasoning` delta；
- `usage.reasoning_tokens > 0`；
- 空正文 `length` 且正文字符 < 20。

升级后的档案按 4.2 参与后续预算计算。这关闭 §2.4 的"新聚合推理模型必然触顶"缺口。

### 4.7 观测与兼容

- `RequestObservability` 增加：`gateLevel`、`gateKnob`、`knobAcceptedThisRequest`、`earlyAbort`、`downgradeRetry`（重试轮标记归属原 requestId 链）；
- `classifyTruncationKind` 在门控信息在场时优先用门控判定 `reasoning_filled`，减少对 `reasoning_tokens` 上报的依赖（缓解 §2.4 检测盲区）；
- 错误文案"推理已占满模型输出硬上限"保留为最终兜底，但只有降级重试也失败后才可见；
- 功能开关 `reasoningGateEnabled`（默认关，灰度）：关闭时完整回退现行余量路径，GateProbe 仍照常记录不影响回退。

## 六、分阶段实施

### 阶段 8.1：门控类型、预算接线与适配器参数

- `reasoningGate` 模块 + 档案扩展 + 预算公式改造；`recentReasoningTokens` 真正传入。
- openai/claude/gemini 下发性参数与参数降级表；移除三处硬编码猜测。
- 验收：同一模型在门控生效端点上，`low` 档 reasoning tokens ≤ 档位值；400 降级一次到位且不吞真实错误。

### 阶段 8.2：提前中止与降级重试闭环（单聊先行）

- 流式计数 + `reasoning_gate_exceeded` 终局；空正文降档重试一次；会话熔断。
- 验收：构造"忽略 disable 的聚合端"流不出现用户可见错误，首轮失败二轮成功；有正文的 `length` 路径行为与阶段 3 完全一致。

### 阶段 8.3：探测持久化与未知模型建档

- GateProbe 存储、静默忽略标记、`none` 档案升级。
- 验收：同一聚合端两次请求只探测一次；未知推理模型第二轮起获得正确预算。

- 灰度门槛见 §八，达标后默认开启。

## 七、测试方案

- **单元**：`resolveReasoningGate` 档位链与 knob 顺序；`levelToTokens` 边界；预算公式在"门控可信/不可信/无门控"三态下的 `requestMaxTokens` 与正文保证；降级表参数删除后重试仅一次。
- **适配器**（现有 fake-fetch 模式）：各 knob 请求体断言；400 "thinking/reasoning_effort/thinkingConfig 不支持" 降级；`reasoning_content` delta 在场时的 disableIgnored 标记；提前中止触发与"用户 cancel 不误伤"竞态。
- **状态机**：`reasoning_gate_exceeded` 与迟到 done/error 幂等（复用阶段 7 latch 测试基架）；每轮至多一次降级重试；熔断计数。
- **集成**：单聊/群聊/Bridge 对同一截断 fixture 得到一致终局；补尾与降级重试共存时每条消息各自至多一次。
- **真实评测**：DeepSeek V4 经"忽略 thinking 的聚合端" + 官方端、Claude、Gemini 2.5、非推理对照，各 5 次 × 首轮/长上下文/多角色三种场景；记录 gateLevel、reasoning tokens、降级重试率、用户可见错误率。

## 八、验收标准

- 主对话"推理挤占"用户可见错误率 < 0.5%（当前为该错误的全部存量）。
- 空正文降级重试成功率 ≥ 90%；重试仅发生在可见正文 < 20 字符时（正文零损失，可静态审计）。
- 门控生效的模型 × 端点组合上，`low` 档请求的 reasoning tokens 不再超过档位值（供应商侧执行证明）。
- 提前中止使必然失败的请求平均节省 ≥ 50% 等待时间（对比写满 8192）。
- 降级重试消耗占总 completion tokens < 3%；P95 成功路径延迟增幅 < 5%。
- 全量 Vitest 通过；新模块分支覆盖率 ≥ 90%；开关可一键回退。

## 九、风险与控制

| 风险 | 控制 |
|---|---|
| 低档门控降低复杂回合的正文质量 | 默认 `standard` 不干预，仅失败后降档且最多停留一档；会话内可手动"完整思考"回 `full` |
| 聚合端把不支持的参数改头换面接受（假接受） | `disableIgnored` 流级探测不依赖 HTTP 状态码；假接受时提前中止仍兜底 |
| 重试引入成本与延迟 | 仅空正文触发、每轮一次、熔断后跳过首轮直降；usage 归链可审计 |
| 与补尾机制叠加造成双重请求 | 两者触发条件互斥（补尾要求有稳定正文，重试要求正文为空），单测锁死 |
| 中止误伤慢启动正文（思考极长后正文才出现） | 观测线设在门控值/P90，非固定小值；`bodyChars>0` 立即解除中止资格 |
| GateProbe 污染（端点临时故障被记为永久不支持） | `knobAccepted:false` 仅由明确 400 字段拒绝写入；网络错误不改探测状态；提供重置入口 |
| 多入口行为漂移 | gate 解析只有一份 shared 纯函数；各入口测试共用 fixture（对齐阶段 7 跨端收束） |

## 十、不推荐方向

- **继续抬高上限**（8192→12288/16384）：推理无界时只是推迟失败，且挤压上下文预留——上游方案 §12.1 的论证对本问题同样成立。
- **对主对话一律关闭推理**：部分端点不支持 `off`（400），且复杂剧情回合依赖思考质量；一律关闭等于用产品意图换稳定性。
- **靠提示词要求模型"少思考"**：模型无法自我约束 reasoning tokens，且指令占 prompt tokens；提示词适合语义边界（正文），不适合资源边界（推理）。
- **把推理余量再调大或改成动态大常数**：回到 §2.1 的猜测式预留原点，失败模式不变。
- **为每个聚合端手工维护参数白名单**：不可枚举、漂移频繁；运行时探测 + 降级表才可收敛。

## 十一、建议的首批实施范围

1. `shared/reasoningGate.ts` + 档案扩展 + 预算公式改造（含 `recentReasoningTokens` 接线）。
2. openai/claude/gemini 三适配器的门控参数下发与统一 400 降级表；移除 `maxTok/3`、硬编码 `'medium'`、gemini 无 thinkingConfig 三处猜测。
3. 单聊链路：`reasoning_gate_exceeded` 终局 + 提前中止 + 空正文降档重试一次 + 会话熔断。
4. GateProbe 持久化与未知模型自动建档。
5. 观测字段进评测脚本，用"忽略 thinking 的聚合端 + DeepSeek V4"复现并验证全链路。

首批完成后，"推理占满硬上限"从用户可见错误降级为自动恢复路径；第二批（8.4）对齐群聊/Bridge 并做灰度门槛验收。
