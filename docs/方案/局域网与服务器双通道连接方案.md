# 轻语局域网与服务器双通道连接方案

> 状态：方案草案，待确认后实施  
> 编写日期：2026-08-31  
> 适用版本：PC 0.16.8、Android 0.2.0 之后  
> 核心目标：保留低延迟局域网直连，同时提供不依赖同一 Wi-Fi、端口开放和防火墙配置的服务器中转连接。

详细开发拆分、协议、数据库和测试门禁见：[局域网与服务器双通道连接实施文档](./局域网与服务器双通道连接实施文档.md)。

## 1. 结论

Android 连接页同时展示两套入口，由用户明确选择：

1. **局域网连接**：沿用现有 `PC IP + 8322 + 配对码/二维码`，数据直接在手机与 PC 之间传输。
2. **服务器连接**：PC 和 Android 都主动连接轻语 Relay 服务器，服务器按独立空间转发并短期缓存数据。

两套方案共享上层会话、消息和角色功能，但底层传输相互独立。第一阶段不做端到端加密；公网链路仍必须使用 HTTPS/WSS，因为登录令牌若以明文传输，任何旁路监听者都可以冒充用户。服务器可以读取中转内容，但普通用户不能枚举、猜测或访问其他用户空间。

PC 是最终数据权威，Relay 缓存只用于断线恢复、离线查看和短时排队，不替代 PC 本地数据库。

## 2. 产品界面

### 2.1 Android 首次连接页

页面固定显示两张卡片，不隐藏任何一种方式：

```text
连接轻语

┌ 局域网连接 ───────────────────┐
│ 同一 Wi-Fi 下速度最快，不经过服务器 │
│ [扫描二维码]  [手动填写]             │
│ 状态：发现 1 台电脑 / 未发现           │
└───────────────────────────────┘

┌ 服务器连接 ───────────────────┐
│ 不要求同一网络，移动数据也可使用       │
│ [扫描中转二维码] [输入连接码]           │
│ 状态：服务器可用 / 维护中               │
└───────────────────────────────┘
```

- 不默认替用户切换通道，用户点击哪张卡就使用哪种连接。
- 已配对后记住选择，下次启动直接恢复该连接。
- 连接管理页允许同时保存多个“局域网 PC”和“服务器空间”。
- 会话页顶部只显示简短状态：`局域网 · 已连接`、`服务器 · 已连接`、`服务器 · 使用缓存`。
- 可在连接详情中手动切换，不在聊天页面堆叠 IP、令牌等技术信息。

### 2.2 PC 手机连接页

PC 端分为两个并列区域：

- **局域网连接**：当前监听地址、端口、局域网二维码、防火墙状态及修复按钮。
- **服务器连接**：Relay 服务状态、当前空间、服务器二维码、已配对设备、缓存用量、断开服务器按钮。

服务器模式首次启用流程：

1. PC 点击“启用服务器连接”。
2. PC 向 Relay 创建一个独立空间，并获得 PC 长期凭据。
3. Relay 返回 5 分钟有效、一次性使用的配对票据。
4. PC 展示二维码和短连接码。
5. Android 扫码或输入连接码，Relay 将 Android 绑定到该空间。
6. PC 弹出设备名称并由用户批准；批准后 Android 获得自己的设备凭据。

## 3. 总体架构

```text
局域网模式
Android ── HTTP/WS ──> PC Bridge :8322 ──> PC 本地业务/数据

服务器模式
Android ── HTTPS/WSS ──┐
                       ├──> QingYu Relay ── WSS ──> PC Relay Agent ──> PC 本地业务/数据
PC      ── WSS ────────┘          │
                                  ├── PostgreSQL：空间、设备、索引、缓存元数据
                                  ├── Redis：在线状态、短期队列、事件序号
                                  └── 对象存储：图片/音频等临时文件
```

### 3.1 服务拆分

现有 `server/` 是公告与版本服务，使用单管理员 JWT 和 SQLite，不承担多用户数据隔离。Relay 应作为独立服务部署，建议目录为：

```text
relay-server/
├── src/http/       # 配对、设备、缓存读取 API
├── src/ws/         # PC/Android 长连接与心跳
├── src/auth/       # 票据、访问令牌、撤销
├── src/tenant/     # 空间隔离与授权策略
├── src/cache/      # 会话/消息缓存与过期清理
└── migrations/     # PostgreSQL 迁移
```

公告服务和 Relay 可以共用同一域名反向代理，但进程、数据库账号和数据目录必须分开：

```text
https://example.com/api/announcements     -> announce-server
https://example.com/relay/v1/*            -> relay-server
wss://example.com/relay/v1/ws             -> relay-server
```

### 3.2 客户端改造边界

- Android 新增 `ConnectionMode.LAN` 与 `ConnectionMode.RELAY`。
- Android Repository/ViewModel 不关心传输模式，通过统一 `QingyuTransport` 调用。
- `LanTransport` 复用现有 Retrofit + OkHttp WebSocket。
- `RelayTransport` 请求 Relay HTTP API并接收 Relay WebSocket 事件。
- PC 新增 `RelayAgent`，主动建立 WSS，不要求公网 IP，也不需要开放入站端口。
- PC 现有 Bridge 路由和业务服务继续复用，避免维护两套聊天逻辑。

建议接口：

```text
QingyuTransport
├── getSessions()
├── getMessages(sessionId, cursor)
├── sendMessage(commandId, sessionId, content)
├── executeAction(commandId, action, payload)
├── observeEvents()
└── connectionState
```

## 4. 用户空间与访问隔离

### 4.1 空间模型

一个 PC 安装实例默认对应一个 `relay_space`。每个空间拥有不可预测的随机 ID，但空间 ID 本身不作为授权凭证。

```text
relay_space
├── space_id             UUID/128 位随机标识
├── owner_pc_id          当前权威 PC
├── status               active / disabled / deleted
├── quota_bytes          空间缓存上限
├── cache_retention_days 缓存保留期
└── created_at / updated_at
```

空间内包含：

- 一个或多个 PC 实例（首版只允许一个权威 PC 在线）。
- 多个已批准 Android 设备。
- 该空间自己的事件序列、待处理命令和缓存记录。
- 独立的对象存储前缀：`spaces/{space_id}/...`。

### 4.2 身份凭据

首版不要求建立完整用户名/邮箱账号体系，使用“空间 + 已配对设备”模型即可：

- PC 首次创建空间后获得 `pc_refresh_token`。
- Android 使用 5 分钟有效的一次性 `pair_ticket` 配对。
- 配对成功后，每台 Android 获得独立 `device_refresh_token`。
- Access Token 有效期建议 15 分钟，Refresh Token 有效期建议 90 天并可自动轮换。
- 服务端只保存 Refresh Token 的不可逆摘要，不保存明文。
- 删除设备、重置空间或修改 `token_version` 后，旧令牌立即失效。

若后续需要换电脑恢复空间，再增加用户账号或离线恢复码；MVP 不应让“可恢复性”拖慢基础中转能力。

### 4.3 必须遵守的隔离规则

防止用户访问其他用户信息依赖服务端授权，不能只依赖隐藏 ID：

1. 每个请求先验证设备令牌，从令牌解析 `space_id`、`device_id` 和权限。
2. 数据库查询的 `space_id` 必须取自已验证身份，禁止信任 URL 或请求体传入的空间 ID。
3. 所有缓存表的主键或唯一索引都包含 `space_id`。
4. PostgreSQL 开启 Row Level Security 作为第二道防线。
5. Redis Key 强制使用 `space:{space_id}:...` 命名空间。
6. 对象存储下载必须签发短时 URL，并校验文件属于当前空间。
7. PC 只能接收绑定到自己空间的命令；Android 只能读取自己被授权空间的数据。
8. 管理后台默认不提供正文检索；运维日志只记录请求 ID、空间 ID 摘要、状态码和耗时。

即使用户知道另一空间的 `space_id`、会话 ID或消息 ID，也会得到 `404`，不返回“存在但无权访问”的差异信息。

## 5. Relay 协议

### 5.1 配对 API

```http
POST /relay/v1/spaces/register-pc
POST /relay/v1/pair-tickets
POST /relay/v1/pair-tickets/{ticket}/claim
POST /relay/v1/pair-requests/{requestId}/approve
POST /relay/v1/pair-requests/{requestId}/reject
POST /relay/v1/tokens/refresh
GET  /relay/v1/devices
DELETE /relay/v1/devices/{deviceId}
```

配对码至少包含 128 位随机熵。若为了手输而使用较短代码，应由服务端限流并让代码 5 分钟、一次性有效，例如 `AB7K-9Q2M`，同时配对时仍需 PC 人工确认。

### 5.2 业务转发 API

为了最大限度复用现有 Android `/api/v1` 语义，Relay 对 Android 暴露：

```http
GET/POST/PATCH/DELETE /relay/v1/bridge/api/v1/*
GET                   /relay/v1/cache/sessions
GET                   /relay/v1/cache/sessions/{id}/messages
GET                   /relay/v1/files/{fileId}
```

Relay 不允许转发任意 URL，只允许固定方法和路由白名单。在线请求封装为 RPC 帧发送给对应 PC：

```json
{
  "type": "rpc:request",
  "requestId": "uuid",
  "commandId": "uuid",
  "method": "POST",
  "path": "/api/v1/sessions/xxx/messages",
  "body": {},
  "deadlineAt": 1788172800000
}
```

PC 返回：

```json
{
  "type": "rpc:response",
  "requestId": "uuid",
  "status": 200,
  "body": {}
}
```

流式生成继续使用事件帧：

```text
ai:chunk -> ai:usage -> ai:done
ai:error
session:updated
cache:snapshot
```

Relay 为每个空间维护单调递增 `event_seq`。Android 重连时携带 `last_event_seq`，服务器补发缺失事件，超出保留窗口则要求客户端重新拉取快照。

### 5.3 幂等和顺序

- Android 为每个写操作生成 `commandId`，重试不得生成新 ID。
- Relay 保存已完成 `commandId` 的结果摘要，默认 24 小时。
- PC 继续复用现有 `requestId` 幂等机制。
- 同一会话的写命令串行投递，不同会话允许并行。
- PC 返回的数据带 `revision`；旧 revision 不得覆盖服务器和 Android 的新缓存。

## 6. 中转与缓存策略

### 6.1 数据权威

- PC 本地数据始终是权威版本。
- Relay 保存可删除、可重建的投影缓存。
- PC 重新上线后，以 PC revision 校准 Relay，不允许 Relay 的旧缓存反向覆盖 PC。

### 6.2 默认缓存范围

| 数据 | 默认策略 | PC 离线时 |
|---|---|---|
| 会话列表 | 最近一次完整快照，7 天 | 可查看 |
| 每个会话消息 | 最近 200 条，7 天 | 只读查看 |
| 角色列表与缩略图 | 最近快照，7 天 | 可查看 |
| 用户发送命令 | 排队 15 分钟 | 显示“等待电脑上线”并可取消 |
| AI 流式内容 | 实时转发，完成后并入消息缓存 | 未完成内容标记中断 |
| 图片/音频 | 对象存储 24 小时，可配置至 7 天 | 在有效期内可查看 |
| 设置和删除等高风险写操作 | PC 在线才执行，不离线排队 | 明确提示需要 PC 在线 |

默认每空间缓存上限建议 500 MB。达到上限后按“临时文件 → 最旧消息投影”的顺序清理，绝不删除 PC 本地数据。

### 6.3 PC 离线体验

- Android 顶部显示 `服务器 · 电脑离线，正在使用缓存`。
- 历史会话可只读浏览。
- 普通消息可选择排队，15 分钟内 PC 上线则自动发送；到期后标记失败并允许手动重试。
- 编辑、删除、切换角色、修改设置等操作不排队，避免延迟执行造成意外。

## 7. 安全基线

本方案不做端到端加密，但以下项目不能省略：

- 公网只开放 HTTPS/WSS，禁用明文 HTTP/WS。
- Access Token 短期有效，Refresh Token 可撤销、轮换，并以安全摘要保存。
- 配对票据一次性、短时有效，配对失败按 IP、票据和设备指纹三维限流。
- 所有 JSON、路径、文件类型和大小在 Relay 与 PC 两侧均校验。
- 单次 RPC body、WS frame、图片和音频分别设置大小上限。
- 设备管理页展示最后上线时间，并支持一键踢下线与撤销。
- 空间停用后立刻关闭所属 WebSocket，并拒绝缓存和文件访问。
- 数据库每日备份；备份文件与生产数据库使用不同凭据和存储位置。
- 管理操作写审计日志，但聊天正文不进入普通日志。

## 8. 数据表建议

```text
relay_spaces(
  id, status, owner_pc_id, quota_bytes, retention_days,
  event_seq, created_at, updated_at
)

relay_devices(
  id, space_id, type, name, fingerprint_hash, token_version,
  approved_at, last_seen_at, revoked_at
)

relay_refresh_tokens(
  id, space_id, device_id, token_hash, expires_at, rotated_at, revoked_at
)

relay_pair_tickets(
  id, space_id, ticket_hash, expires_at, claimed_by, consumed_at
)

relay_commands(
  id, space_id, device_id, session_id, command_type, payload,
  status, expires_at, result_status, created_at, completed_at
)

relay_events(
  space_id, seq, event_type, payload, expires_at, created_at
)

cached_sessions(
  space_id, session_id, revision, payload, updated_at, expires_at
)

cached_messages(
  space_id, session_id, message_id, revision, payload, updated_at, expires_at
)

cached_files(
  space_id, file_id, object_key, mime_type, size_bytes, expires_at
)
```

所有读取和修改语句都必须包含 `space_id`，并为 `(space_id, resource_id)` 建立复合索引。

## 9. 部署建议

首个可用版本建议：

```text
Caddy/Nginx
├── relay-server × 1
├── PostgreSQL 16
├── Redis 7
└── MinIO 或兼容 S3 的对象存储
```

- Relay 服务保持无状态，后续可以横向扩容。
- 多实例时使用 Redis 保存 `pc_id -> relay_node_id` 在线路由，并通过 Pub/Sub 或 Streams 跨节点投递。
- 首版单实例也应使用 PostgreSQL，不建议用 SQLite 承担长连接下的并发写入和多租户隔离。
- 心跳建议 25 秒一次，75 秒未收到 pong 判定离线。
- 服务器健康检查分为 HTTP 存活、数据库、Redis、对象存储和 WebSocket 在线数。

## 10. 分阶段实施

### 阶段 A：传输抽象和双入口 UI

- Android 增加 `LAN/RELAY` 连接类型和两张连接卡片。
- 抽出 `QingyuTransport`，现有局域网功能全部迁移到 `LanTransport`。
- PC 手机连接页拆分为局域网与服务器两个区域。
- 此阶段不改变现有局域网协议。

验收：局域网功能无回归；Relay 尚未启用时有明确“服务器连接暂不可用”状态。

### 阶段 B：Relay 在线转发 MVP

- 新建 Relay 服务、空间、设备和令牌体系。
- PC Relay Agent 主动 WSS 上线。
- Android 完成服务器扫码/连接码配对。
- 支持会话列表、消息历史、发送消息、AI 流式返回和停止生成。
- PC 离线时只提示离线，不做缓存。

验收：PC 在家庭网络、Android 使用移动数据时可以完成一次完整对话；任意跨空间访问均失败。

### 阶段 C：缓存与离线恢复

- 增加 session/message 快照、事件序号和断点续传。
- 增加 15 分钟消息命令队列和取消机制。
- 增加缓存容量、保留期和自动清理任务。

验收：Android 断网后恢复不丢消息、不重复发送；PC 离线时可查看缓存，重新上线后缓存与 PC 一致。

### 阶段 D：文件与生产运维

- 图片、音频走对象存储和短时签名 URL。
- 增加限额、监控、告警、备份、管理端空间封禁和数据清理。
- 完成压力测试与断线风暴测试。

## 11. 测试与验收清单

### 11.1 隔离测试

- A 空间令牌访问 B 空间会话、消息、文件全部返回 404。
- 修改 URL、请求体中的 `space_id/device_id` 不能越权。
- 已撤销设备的 HTTP 与 WS 立即失效。
- 过期或重复使用的配对票据无法绑定设备。
- 对象存储 URL 过期后不可访问，也不能替换文件 ID 获取其他空间文件。

### 11.2 连接测试

- 同一 Wi-Fi 局域网直连。
- Android 移动数据 + PC 家庭宽带的服务器连接。
- PC/Android 任一侧断网、切网、休眠后恢复。
- Relay 重启、Redis 短暂不可用、数据库慢查询时给出明确状态。
- 两套连接均存在时，用户手动切换不串会话、不误用令牌。

### 11.3 数据一致性测试

- 同一 `commandId` 重复提交只产生一条用户消息。
- WS 事件乱序或重复时，Android 最终消息顺序正确。
- PC 离线队列过期后不会在数小时后突然执行。
- Relay 缓存被清空后，可由 PC 重新生成且不丢 PC 数据。

## 12. 建议默认决策

| 决策项 | 建议默认值 |
|---|---|
| 通道选择 | 用户明确选择，记住上次选择 |
| 端到端加密 | 首版不做 |
| 公网传输 | 强制 HTTPS/WSS |
| 空间模型 | 每个 PC 安装实例一个独立空间 |
| Android 配对 | 一次性票据 + PC 人工批准 |
| PC 权威 | 是，Relay 仅保存投影缓存 |
| 消息缓存 | 每会话最近 200 条，保留 7 天 |
| 文件缓存 | 默认 24 小时 |
| 空间配额 | 默认 500 MB |
| 离线写入 | 仅普通消息排队 15 分钟 |
| 数据库 | PostgreSQL |
| 在线状态/队列 | Redis |
| 图片/音频 | S3/MinIO 对象存储 |

## 13. 暂不纳入首版

- 端到端加密及多端密钥恢复。
- 多台 PC 同时写入同一个空间。
- Relay 永久保存完整聊天数据库。
- 用户之间共享空间或公开分享会话。
- 自动在局域网和服务器之间无感切换；首版由用户选择，避免排障时不知道数据实际走哪条链路。

这套边界能够先解决普通用户无法处理 IP、防火墙、NAT 和移动网络连接的问题，同时用服务端强制租户隔离防止跨用户访问，并为后续缓存、自动回退和账号体系保留扩展空间。
