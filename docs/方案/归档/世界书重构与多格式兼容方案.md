## 1. 结论先行

这次不应继续在现有 `normalizeImportedLorebook()` 上追加更多 `if/else`，而应把世界书拆成四个边界清晰的子系统：

1. **统一领域模型**：运行时只认识轻语自己的稳定模型，不直接依赖 SillyTavern、角色卡或其他软件的字段名。
2. **格式适配层**：每种外部格式由独立适配器负责识别、导入、导出和兼容性报告；增加新格式时主要新增适配器和测试样例，不修改核心匹配器。
3. **检索与触发层**：关键词、正则、全文检索、向量检索都是可插拔通道；没有 embeddings 时仍能完整运行。
4. **注入与预算层**：触发结果统一经过分组、概率、递归、预算和位置渲染，不让格式差异渗透到上下文构建代码。

关于“API 调用的 LLM 一般不支持语义索引”：这个判断在实际生态中基本成立。聊天补全接口和 embeddings 接口是两项不同能力，不能假设提供聊天模型的服务一定提供向量模型。因此本方案规定：

* **关键词与本地词法检索是必选基础能力**；

* **向量检索只是可选增强能力**，由独立的 Embedding Provider 提供；

* 项目可以向用户提供**可选下载的本地小型向量模型包**，不要求聊天 API 支持 embeddings，也不要求用户另装 Ollama；

* 没有 embeddings 时，`semanticPreferred` 条目自动降级到本地 BM25/CJK n-gram 检索；

* 只有用户显式设为 `semanticRequired` 的条目才允许在无 embeddings 时停用，并必须在 UI 和调试报告中明确提示；

* 可选使用普通聊天 API 离线生成关键词、别名和摘要，但不能把每轮调用聊天 LLM 当作检索前置条件。

本文解决的是更上游的“如何接收、保留、迁移和执行不同格式”。文中提及的《世界书优化方案》《世界书使用效果提升方案-第二轮》在当前仓库中均不存在，相关匹配与裁剪优化已由本方案阶段 0—7 覆盖。

## 2. 当前实现与主要问题

### 2.1 当前链路

```text
外部 JSON
   │
   ▼
normalizeImportedLorebook
   │  在同一个函数中猜格式、读字段、转换位置并丢弃未知字段
   ▼
Lorebook / LoreEntry
   │
   ├── 关键词 / 正则扫描
   ├── 可选 embeddings 向量检索
   └── 递归、分组、概率、预算
   ▼
contextBuilder / groupChatContext
```

关键现状：

* [`shared/types.ts`](../../shared/types.ts) 的 `LoreEntry` 同时承担存储模型、编辑模型和运行时模型，新增外部格式字段会持续扩大该接口。

* [`electron/services/lorebookImport.ts`](../../electron/services/lorebookImport.ts) 通过字段特征猜测来源，但只返回归一化结果，不返回“识别依据、发生了什么降级、哪些字段未支持”。

* 不同来源的未知字段没有可靠的 namespaced 保留区，同格式导入再导出无法保证往返。

* ST 的多个插入位置当前会在导入时直接折叠为 `at_end`。一旦在导入边界丢失原意，后续即使实现了新注入位置也无法恢复。

* [`electron/ipc/lorebook.ts`](../../electron/ipc/lorebook.ts) 直接保存当前 `Lorebook` 对象，缺少文档 schema 版本和逐版本迁移机制。

* [`src/utils/lorebook.ts`](../../src/utils/lorebook.ts) 已经包含关键词、正则、递归、语义近似、评分、预算和诊断等大量职责，继续扩张会提高回归风险。

* [`electron/services/embedding.ts`](../../electron/services/embedding.ts) 已支持 OpenAI-compatible `/embeddings` 和 Ollama `/api/embed`，但它们是额外能力，不能作为所有用户的默认前提。

* 当前向量索引属于“服务配置后才可使用”的增强通道；纯语义条目在服务不可用时可能成为死条目。

### 2.2 根因

目前的核心问题不是少映射几个字段，而是缺少以下稳定边界：

| 缺失边界             | 直接后果                        |
| ---------------- | --------------------------- |
| 外部格式与内部领域模型边界    | 每支持一个格式都要改核心导入函数和类型         |
| 导入模型与运行时模型边界     | 为兼容外部字段不断污染运行时结构            |
| 检索能力与模型供应商边界     | 聊天 API 无 embeddings 时语义条目失效 |
| 原始字段与已归一化字段边界    | 未识别字段静默丢失，无法可靠导出            |
| schema 版本与数据迁移边界 | 后续字段重构只能继续堆可选字段兼容           |
| 能力映射与降级策略边界      | 不支持的位置、触发器和扩展被静默近似          |

## 3. 目标与非目标

### 3.1 目标

1. 支持轻语原生、SillyTavern World Info、CCv2/CCv3 `character_book`、`lorebook_v3`，并为 Risu、Agnai、NovelAI 等生态格式提供独立适配器。
2. 新格式接入时不修改检索器、预算器和上下文构建器。
3. 同格式往返尽量无损；跨格式导出时明确列出近似、保留但不执行、以及无法表达的字段。
4. 所有持久化世界书都有明确 `schemaVersion`，迁移函数可测试、可回滚、可连续执行。
5. embeddings 完全可选；仅配置聊天 API 的用户也能获得可用且可解释的召回。
6. 单聊、群聊、预览、触发测试器共用同一套核心执行逻辑。
7. 每次触发可解释：命中通道、关键词、分数、降级原因、裁剪原因和最终注入位置均可查询。

### 3.2 非目标

* 不承诺不同软件之间所有私有扩展都能互相执行。

* 不执行导入文件中携带的 JavaScript、STscript、宏脚本或任意插件代码；未知扩展只做不透明保留。

* 不宣称 BM25、n-gram 或聊天模型生成的关键词等价于真正的向量语义检索。

* 第一阶段不做可从网络动态安装的第三方适配器；先建立编译期注册机制，避免引入供应链和脚本执行风险。

* 不要求跨格式导出完全无损；要求的是**同格式可逆、跨格式可解释**。

## 4. 总体架构

```text
文件 / 角色卡内嵌世界书
          │
          ▼
┌──────────────────────────────┐
│ Format Registry              │
│ detect → select adapter      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Import Adapter               │
│ parse / validate / preserve  │
│ 输出 CanonicalDocument       │
│ + CompatibilityReport        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Canonical Store + Migrations │
│ schemaVersion / revision     │
│ foreign fields / source meta │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Runtime Compiler             │
│ 领域文档 → RuntimeLorebook   │
└──────────────┬───────────────┘
               ▼
┌───────────────────────────────────────────────────┐
│ Retrieval Providers                               │
│ keyword │ regex │ local lexical │ optional vector │
└──────────────────────┬────────────────────────────┘
                       ▼
┌──────────────────────────────┐
│ Trigger Engine               │
│ filters / recursion / groups │
│ probability / sticky         │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ Rank + Budget + Injection    │

└──────────────────────────────┘
```

原则是“外部格式止于适配层，内部格式止于编译层”。上下文构建器只能接收已经编译好的注入片段，不能再读取 ST 数字位置或某个软件的私有字段。

## 5. 统一领域模型

### 5.1 顶层文档

建议新建 `CanonicalLorebookDocument`，不要直接在现有 `Lorebook` 上无限追加可选字段。

```ts
interface CanonicalLorebookDocument {
  schema: 'qingyu_lorebook'
  schemaVersion: 2
  id: string
  revision: number
  name: string
  description: string
  enabled: boolean
  defaults: LorebookDefaults
  entries: CanonicalLoreEntry[]
  source?: SourceMetadata
  foreign?: Record<string, JsonValue>
  createdAt: number
  updatedAt: number
}

interface SourceMetadata {
  adapterId: string
  formatVersion?: string
  originalName?: string
  importedAt: number
  contentHash: string
}
```

`foreign` 必须以适配器 ID 命名，例如 `foreign['sillytavern.world-info']`。运行时不能读取这里的字段，它只用于同格式导出、未来迁移和人工诊断。

### 5.2 条目结构

条目分为“内容”“触发策略”“注入策略”“调度策略”“来源信息”五组，避免平铺几十个可选字段。

```ts
interface CanonicalLoreEntry {
  id: string
  sourceId?: string | number
  enabled: boolean
  title?: string
  content: string
  summary?: string

  activation: ActivationPolicy
  insertion: InsertionTarget
  scheduling: SchedulingPolicy

  foreign?: Record<string, JsonValue>
}

interface ActivationPolicy {
  /** 是否需要触发条件；对应外部格式的 constant 语义。 */
  mode: 'constant' | 'conditional'
  /** 预算与裁剪层级，不与触发方式混为一个枚举。 */
  budgetTier: 'protected' | 'standard' | 'supplemental'
  primaryKeys: string[]
  secondaryKeys: string[]
  aliases: string[]
  keyLogic: 'any' | 'all'
  secondaryLogic?: 'and_any' | 'and_all' | 'not_any' | 'not_all'
  caseSensitive: boolean
  wholeWords: boolean
  regex?: { enabled: boolean; flags: string }
  retrieval: 'keyword' | 'semanticPreferred' | 'semanticRequired' | 'hybrid'
}
```

字段映射必须区分三个容易混淆的概念：

* ST `constant=true` → `mode='constant'`，无需关键词或语义命中；

* 非 constant 条目 → `mode='conditional'`；

* ST `selective` 表示二级关键词筛选，应映射到 `secondaryLogic`，不能把它用作 `constant` 的反义枚举；

* 轻语旧字段 `priority='always'` → `constant + protected`，`conditional` → `conditional + standard`，`detail` → `conditional + supplemental`。

这样“是否触发”和“预算不足时先保留谁”可以独立演进，领域名称也不再依赖读者理解旧实现中的 `detail`。

### 5.3 不要提前折叠插入位置

内部模型要能表达已知生态位置，即使当前渲染器暂时只能近似执行。

```ts
type InsertionTarget =
  | { kind: 'prompt'; anchor:
      | 'before_character'
      | 'after_character'
      | 'before_examples'
      | 'after_examples'
      | 'authors_note_top'
      | 'authors_note_bottom'
      | 'prompt_end' }
  | { kind: 'chat'; depth: number; role: 'system' | 'user' | 'assistant' }
  | { kind: 'outlet'; name: string }
  | { kind: 'custom'; source: string; value: JsonValue }
```

当当前上下文协议不支持某个位置时，由 `InsertionRenderer` 在**执行阶段**做近似映射并生成诊断，不能在导入阶段永久改成 `at_end`。

### 5.4 调度策略

把概率、分组、递归和时间效果聚合起来：

```ts
interface SchedulingPolicy {
  order: number
  probability: number
  scanDepth?: number
  recursion: {
    exclude: boolean
    prevent: boolean
    minDepth: number
  }
  groups: Array<{ name: string; weight: number; prioritized: boolean }>
  sticky?: number
  cooldown?: number
  delay?: number
  ignoreBudget: boolean
  characterFilter?: CharacterFilter
  generationTriggers?: GenerationTrigger[]
}
```

### 5.5 运行时模型

`CanonicalLorebookDocument` 用于持久化和编辑；`RuntimeLorebook` 是纯编译产物，可按文档 revision 缓存：

* 已完成默认值填充；

* 已编译安全正则；

* 已生成标准化关键词和别名；

* 已建立词法索引引用；

* 已将格式相关字段隔离；

* 不包含未知 `foreign` 数据。

这样可以避免每轮聊天反复做 schema 兼容和字段兜底。

## 6. 格式适配器体系

### 6.1 适配器契约

```ts
interface LorebookFormatAdapter {
  readonly id: string
  readonly displayName: string
  readonly supportedVersions: string[]
  readonly priority: number

  detect(input: UnknownJson, file: FileMetadata): DetectionResult
  import(input: UnknownJson, context: ImportContext): ImportResult
  export?(document: CanonicalLorebookDocument, context: ExportContext): ExportResult
}

interface DetectionResult {
  score: number       // 0-100
  version?: string
  evidence: string[]
  conflicts: string[]
}

interface ImportResult {
  document: CanonicalLorebookDocument
  report: CompatibilityReport
}
```

规则：

* 识别必须基于多个特征打分，不能只看第一条 entry。

* 最高分低于阈值或前两名分差过小时，不静默猜测；导入预览让用户选择。

* 复杂格式使用独立 TypeScript 适配器；字段差异很小的格式可复用声明式字段映射 helper。

* 不设计一套过度复杂的 JSON 映射 DSL，否则只是把难维护的 TypeScript 变成更难调试的小语言。

### 6.2 注册表

```ts
const lorebookAdapters = defineAdapters([
  nativeV1Adapter,
  nativeV2Adapter,
  sillyTavernWorldInfoAdapter,
  characterBookV2Adapter,
  characterBookV3Adapter,
  lorebookV3Adapter,
  risuLorebookAdapter,
  agnaiMemoryBookAdapter,
  novelAiLorebookAdapter,
])
```

新增格式的标准流程应缩减为：

1. 新增一个 adapter 文件；
2. 在注册表增加一行；
3. 加入最小、完整、异常、往返四类 fixture；
4. 更新能力矩阵。

核心运行时不随之改动。

### 6.3 首批支持范围

| 优先级 | 格式                         |   导入 | 同格式导出 | 说明                                   |
| --- | -------------------------- | ---: | ----: | ------------------------------------ |
| P0  | 轻语当前原生格式                   |   完整 |    完整 | 提供 v1 → v2 迁移                        |
| P0  | SillyTavern World Info     |   完整 |  尽量无损 | 覆盖数字位置、选择逻辑、分组、递归、sticky/cooldown 等  |
| P0  | CCv2/CCv3 `character_book` |   完整 |    完整 | 独立适配器，共用字段 helper                    |
| P0  | `lorebook_v3`              |   完整 |    完整 | 支持 `{spec, data}` 包装和版本校验            |
| P1  | Risu Lorebook              |   完整 |    尽力 | token budget、扩展位置等保留                 |
| P1  | Agnai Memory Book          |   完整 |    尽力 | 建立真实 fixture 后实现                     |
| P1  | NovelAI Lorebook           |   完整 |    尽力 | 作为生态格式，不冒充统一标准                 |
| P2  | 未知 Tavern fork / 通用 JSON   | 映射向导 |     否 | 用户选择 entries、keys、content 等路径并保存映射模板 |

> 阶段 6 完成情况：三个 P1 格式已实现独立 adapter 并通过同格式往返测试（超出"尽力"承诺）；Risu 的 `multiple` 模式以 canonical `keyLogic='all'` 保留；NovelAI/Agnai 无条目级插入位置，导出时对非默认位置显式报告 approximated。P2 映射向导已实现（模板持久化、猜测模板、受限字段搬运），按上表不提供导出。

### 6.4 兼容性报告

每次导入和导出都返回报告：

```ts
type CompatibilityLevel =
  | 'exact'
  | 'converted'
  | 'approximated'
  | 'preserved_only'
  | 'dropped'

interface CompatibilityIssue {
  path: string
  level: CompatibilityLevel
  sourceValue?: JsonValue
  target?: string
  message: string
}
```

UI 汇总示例：

```text
识别格式：SillyTavern World Info（置信度 96）
精确映射：142 项
转换映射：18 项
运行时近似：3 项（AN Top、AN Bottom、Outlet）
仅保留不执行：2 项（未知扩展）
丢弃：0 项
```

任何“导入成功”都不能再等同于“完全兼容”。

### 6.5 未知字段与往返策略

同格式导出采用“原始未知字段作为底稿，规范字段覆盖”的方式：

1. 导入时保留未消费字段到 namespaced `foreign`；
2. 用户编辑后的规范字段拥有最高优先级；
3. 导出到原格式时合并未知字段；
4. 导出到其他格式时未知字段默认不注入目标顶层，只在报告中说明；
5. 不保存整个无限制原始文件快照，避免角色卡或恶意 JSON 造成存储膨胀；设置书级、条目级和总大小上限。

## 7. 无 embeddings 时的检索方案

### 7.1 能力分层

| 通道              | 是否默认可用 | 用途                | 是否是真语义 |
| --------------- | -----: | ----------------- | -----: |
| 精确关键词           |      是 | 高精度显式触发           |      否 |
| 正则              |      是 | 模式和词形触发           |      否 |
| 本地词法检索          |      是 | 无关键词、同义词不足、长世界书召回 |      否 |
| 实体/别名匹配         |      是 | 人名、地名、称号、多语言别称    |      否 |
| embeddings 向量检索 |      否 | 跨表达语义召回           |      是 |
| 聊天 LLM 离线扩词     |      否 | 生成候选关键词、别名、摘要     |   间接增强 |

### 7.2 本地词法索引

增加 `LexicalRetrievalProvider`，不需要远程 API：

* 拉丁文字使用 Unicode 规范化、分词、BM25；

* 中文、日文等无空格文本使用字符 bigram/trigram；

* 标题、主关键词、别名、摘要、正文使用不同字段权重；

* 候选召回后仍执行精确过滤和阈值判断；

* 索引以 `bookId + revision + analyzerVersion` 作为失效键；

* 小书可保存在内存，大书将索引持久化到独立缓存目录；索引可删除并重建，不属于用户主数据。

初期建议实现无原生依赖的倒排索引，避免为 Electron 引入额外原生数据库打包风险。检索接口必须与具体实现解耦，后续可用纯 JavaScript 搜索库或 SQLite FTS 替换而不影响领域模型。

```ts
interface RetrievalProvider {
  id: string
  available(context: RetrievalContext): Promise<Availability>
  ensureIndex(documents: RuntimeLorebook[]): Promise<void>
  search(query: RetrievalQuery): Promise<RetrievalHit[]>
  invalidate(changes: IndexChange[]): Promise<void>
}
```

### 7.3 语义策略的明确含义

| 策略                  | 有 embeddings  | 无 embeddings                  |
| ------------------- | ------------- | ----------------------------- |
| `keyword`           | 关键词/正则        | 关键词/正则                        |
| `semanticPreferred` | 向量为主，词法兜底     | 本地词法检索，并标记 `lexical_fallback` |
| `semanticRequired`  | 仅向量           | 不触发，明确警告                      |
| `hybrid`            | 关键词 + 词法 + 向量 | 关键词 + 词法                      |

外部格式中的 `vectorized=true` 默认映射为 `semanticPreferred`，而不是 `semanticRequired`。这样既保留作者“希望按内容相关性触发”的意图，也不会让只配置聊天 API 的用户得到死条目。

### 7.4 排名融合

不要直接相加 BM25 分数与余弦相似度，因为两者量纲不同。建议采用加权 Reciprocal Rank Fusion（RRF）：

```text
finalScore = Σ channelWeight / (k + rankInChannel)
           + entityBoost
           + recencyBoost
           + budgetTierBoost
```

* 关键词精确命中的通道权重最高；

* 向量和词法负责补召回，不应覆盖明确关键词的强信号；

* 每个通道先独立截取 topK，再融合，控制大书开销；

* 调试信息保留各通道原始 rank 和 score，便于校准。

### 7.5 聊天 API 辅助扩词

对于不提供 embeddings、但可以聊天补全的服务，可提供“建立辅助索引”按钮：

1. 分批让聊天模型从条目中提取实体、别名、同义表达和多语言关键词；
2. 结果先作为建议展示，默认需用户确认；
3. 保存生成来源、模型和时间，不覆盖作者原始关键词；
4. 只在导入、编辑或手动重建时调用，聊天每轮不调用；
5. API 失败不影响世界书正常使用。

现有 `localizeLorebookKeywords` 能力可作为这条管线的起点，但应改造成通用 `KeywordEnrichmentProvider`，避免只服务“英文转中文”单一场景。

### 7.6 查询构建

检索 query 不应简单拼接全部历史：

* 主体：最近一条用户消息；

* 补充：最近 2～4 条消息的实体和名词短语；

* 可选：当前角色名、场景名、群聊发言者；

* 排除：代码块、URL、重复引用和已注入世界书正文；

* 递归触发使用独立 source 标记，防止无限反馈。

## 8. 本地向量模型的安装、更新与卸载

### 8.1 产品定位

本地向量模型是一个**可选能力包**，不是轻语启动、导入世界书或发送消息的依赖。聊天 API 完全不需要知道它的存在：轻语在本地生成世界书条目和当前查询的向量，完成 topK 检索后，只把命中的正文交给聊天 API。

发布形态建议分成三种：

| 形态     | 默认提供 | 适用场景                      |
| ------ | ---: | ------------------------- |
| 基础安装包  |    是 | 不包含模型，体积最小，关键词和词法检索始终可用   |
| 应用内模型包 |    是 | 用户在“模型 → 语义检索”中按需下载、更新或卸载 |
| 离线完整包  |   可选 | 无法访问下载源的用户，附带一个经过签名的默认模型包 |

模型不能打入 `app.asar`，也不能把开发机已经下载的模型带进安装包。模型根目录按运行环境确定：开发环境使用项目目录，便于调试与清理；打包环境使用可执行文件所在的应用安装目录，使模型跟随用户选择的安装位置。索引仍属于用户派生数据，放在 Electron `userData`：

```text
开发环境：<project>/models/embedding/
打包环境：<install-dir>/models/embedding/
  <model-id>/
    <version>/
      manifest.json
      model.onnx
      tokenizer.json
      ...
    current.json

userData/
  indexes/embedding/
    <model-id>/<version>/<book-id>.json
```

模型与索引分开管理：模型是可重新下载的运行依赖，索引是可重新生成的派生缓存，世界书正文才是用户主数据。设置页必须显示实际模型与索引路径；若用户把正式版安装在当前账户不可写的目录，安装模型应明确报权限错误，不得静默改存到其他目录。打包清单显式排除 `<project>/models/**`。

### 8.2 模型目录与清单

应用内置的不是模型文件，而是一个经过签名的模型目录 `ModelCatalog`：

```ts
interface LocalEmbeddingModelManifest {
  schemaVersion: 1
  id: string
  version: string
  displayName: string
  description: string
  languages: string[]
  license: { name: string; url: string }
  runtime: 'onnx'
  architecture: string
  dimensions: number
  maxTokens: number
  dtype: 'q8' | 'q4' | 'fp16' | 'fp32'
  pooling: 'mean' | 'cls'
  normalize: boolean
  queryPrefix?: string
  passagePrefix?: string
  minimumAppVersion: string
  recommendedMemoryMb: number
  installedSize: number
  files: Array<{
    path: string
    size: number
    sha256: string
    urls: string[]
  }>
  catalogSignature: string
}
```

重要约束：

* pooling、归一化、query/passage prefix 必须来自 manifest，不能在代码中按模型名称硬编码；

* 同一个模型的新版本视为不同索引空间，不允许复用旧版本向量；

* manifest 只允许声明数据文件，不能包含安装脚本、动态库路径或任意命令；

* 下载源可有多个镜像，但所有文件必须通过固定 SHA-256 校验；

* UI 必须显示许可证、下载大小、安装后大小、预计内存和支持语言。

### 8.3 模型状态机

安装交互必须由状态机驱动，不能仅使用一个 `installed: boolean`：

```ts
type LocalModelState =
  | 'not_installed'
  | 'queued'
  | 'downloading'
  | 'paused'
  | 'verifying'
  | 'installing'
  | 'testing'
  | 'ready'
  | 'update_available'
  | 'in_use'
  | 'uninstalling'
  | 'uninstall_pending'
  | 'failed'
  | 'corrupted'
  | 'incompatible'
```

状态转移：

```text
not_installed
  → queued → downloading ⇄ paused
  → verifying → installing → testing → ready
                                      └→ failed/corrupted

ready → in_use → ready
ready → update_available → downloading(new version) → testing → atomic switch
ready/failed/corrupted → uninstalling → not_installed
```

应用崩溃或关机后重启，必须从磁盘 staging 状态恢复为“可续传”“重新校验”或“清理残留”，不能永久停在 `installing`。

### 8.4 模型中心页面

“模型 → 语义检索”统一承载检索策略、远程 embeddings 与本地模型管理，模型卡片展示：

```text
多语言语义模型 Small
中文 / English / 日本語 · 量化 Q8
下载 118 MB · 安装后 126 MB · 建议内存 500 MB
许可证：MIT                         [查看]

状态：未安装
[安装]  [导入离线模型包]
```

安装后：

```text
状态：已就绪 · 当前默认
版本：1.2.0 · 向量维度：384
占用：模型 126 MB + 索引 18 MB
已索引：8 本世界书 / 1,423 条

[测试模型] [重建索引] [设为默认] [卸载]
```

页面顶部提供全局策略：

* 默认检索方式：自动 / 本地模型 / 远程 embeddings / 仅词法；

* 后台自动建立索引：开/关；

* 模型更新：仅提醒 / 自动下载但不切换 / 自动更新；默认“仅提醒”；

* 仅空闲时索引：默认开启；

* CPU 使用限制和批次大小：高级设置；

* 模型及索引总磁盘占用，并提供“清理无效索引”。

### 8.5 在线安装流程

用户点击“安装”后按以下步骤执行：

1. **安装确认**：显示模型用途、语言、许可证、下载/安装体积、预计内存、运行位置和隐私说明。
2. **环境预检**：检查应用版本、操作系统架构、可用磁盘、运行时可用性和代理设置。
3. **下载**：下载到唯一 staging 目录，支持断点续传、暂停、继续和取消；显示已下载、总量、速度和预计时间。
4. **校验**：逐文件检查大小和 SHA-256；失败时不进入正式目录。
5. **原子安装**：解压/移动到版本目录，防止半安装状态被识别为 ready。
6. **自检**：用固定测试文本执行一次 embedding，检查维度、有限数值、归一化结果和基本相似度排序。
7. **启用选择**：询问“设为默认并为现有世界书建立索引”或“稍后启用”。
8. **后台索引**：展示书籍数、条目数、进度、暂停和取消；发送消息不等待全量索引完成。

交互要求：

* 关闭模型中心不取消下载或索引，状态移入全局任务中心；

* 点击取消下载只清理 staging，不影响已安装版本；

* 网络错误保留可续传部分，并给出“重试”“更换镜像”“导入离线包”；

* 磁盘不足要在下载前提示，安装中再次检查，避免写满用户磁盘；

* 安装成功但索引失败时，模型状态仍是 ready，索引单独显示失败。

### 8.6 暂停、继续和任务优先级

* 下载任务支持真正的 HTTP Range 续传；服务器不支持 Range 时明确说明会重新下载。

* 索引任务以世界书/批次为 checkpoint，暂停后不重复已完成且内容 hash 相同的条目。

* 用户发送消息时，查询 embedding 优先级高于后台批量建索引。

* 设备处于高负载或省电模式时可以自动暂停后台索引，但不能中断正在发送的消息。

* 同一模型只允许一个安装/更新任务，同一本书同一模型只允许一个索引任务。

### 8.7 模型启用与切换

设为默认模型时执行以下检查：

1. 模型必须处于 ready；
2. 运行一次快速自检；
3. 更新 active model 引用；
4. 将使用其他模型的世界书索引标记为“模型不匹配”，而不是 stale；
5. 提供“立即重建全部”“按需重建”“暂不重建”；
6. 在新索引可用前继续使用关键词/BM25，不使用旧模型的向量。

允许多模型共存，但第一版每轮只使用一个默认本地模型，避免同时加载多个模型造成内存失控。未来需要按语言自动路由时，再通过 `EmbeddingModelRouter` 扩展。

### 8.8 模型更新与回滚

更新必须旁路安装，不能覆盖正在工作的版本：

```text
current v1 可用
  → 下载 v2 到 staging
  → 校验并安装 v2
  → v2 自检
  → 原子切换 current 到 v2
  → 后台重建 v2 索引
  → 用户确认或保留 v1 作为回滚版本
```

规则：

* 小版本也不能假设向量兼容；只要 manifest 的模型版本、维度、pooling、prefix 或权重 hash 变化，就建立新索引命名空间；

* 更新自检失败时自动保留 v1，并将 v2 标为 failed；

* 新版本切换后首次查询异常时提供“一键回滚”；

* 默认保留上一个可用版本，待 v2 索引完成并稳定使用后再提示清理；

* 自动更新只能自动下载和验证，默认不在用户对话中途切换模型；

* 模型目录签名或 hash 校验失败时禁止安装，并显示安全错误而不是普通网络错误。

### 8.9 卸载交互

“卸载”前必须先计算影响范围，确认弹窗不能只有“确定/取消”：

```text
卸载“中文语义模型 Small 1.2.0”？

它当前是默认模型，并被以下数据使用：
- 8 本世界书
- 1,423 条向量
- 模型文件 96 MB
- 相关索引 18 MB

卸载后将自动切换到关键词 + 本地词法检索，聊天仍可正常使用。

(●) 删除模型和相关索引，释放约 114 MB（推荐）
( ) 仅删除模型，保留 18 MB 索引供相同版本重装后复用

[取消] [卸载]
```

执行顺序：

1. 阻止新的查询和索引任务使用该模型；
2. 等待正在执行的单次查询结束，取消后台索引任务；
3. 若是默认模型，先原子切换到远程 embeddings 或词法 fallback；
4. 卸载指定版本，不影响同模型其他版本；
5. 按用户选择删除或保留严格匹配该版本的索引；
6. 清理 staging、锁文件和临时缓存；
7. 更新 UI、健康状态和磁盘统计。

若文件被占用或删除失败：

* 状态标为 `uninstall_pending`，下次应用启动前重试；

* 当前会话不能继续加载该模型；

* 显示未释放的磁盘大小和“重试清理”；

* 不能因为部分删除就把状态显示为“未安装”。

卸载模型不能删除世界书、关键词、摘要或用户手工编辑内容。

### 8.10 离线模型包

定义只包含数据文件的 `.qymodel` 包，用于无网络环境：

```text
model.qymodel
  manifest.json
  signature.json
  files/...
```

导入流程与在线安装共用“预检 → hash/签名校验 → staging → 原子安装 → 自检”，不能因为文件来自本地就跳过安全校验。必须防御 Zip Slip、超大解压比例、重复路径和符号链接。第一版不允许用户导入任意 ONNX 文件；自定义模型应通过开发者模式和显式 manifest 接入。

### 8.11 错误恢复

| 错误          | 用户可见状态             | 恢复方式                  |
| ----------- | ------------------ | --------------------- |
| 网络中断        | 已暂停/等待网络           | 继续下载或换镜像              |
| hash 不匹配    | 校验失败               | 删除损坏文件并重下，不允许忽略       |
| 磁盘不足        | 安装失败，显示所需空间        | 清理缓存后从 checkpoint 继续  |
| 模型自检失败      | 模型不可用              | 重试、回滚或卸载              |
| ONNX 运行时不兼容 | incompatible       | 使用词法 fallback，提供诊断信息  |
| 索引中断        | 模型 ready、索引 paused | 从条目 checkpoint 继续     |
| 索引损坏        | 索引 corrupted       | 删除并重建，不重装模型           |
| 应用崩溃        | 恢复中                | 扫描 staging/lock 并恢复状态 |
| 卸载删除失败      | uninstall\_pending | 重启前/重启后重试清理           |

所有错误都必须分清“模型不可用”和“索引不可用”。前者影响查询向量，后者通常只影响部分书，不能用一个笼统的“语义功能失败”提示。

### 8.12 IPC 与后台任务接口

建议新增独立 API，不把安装逻辑塞进现有 `embedding:indexLorebook`：

```ts
interface LocalModelAPI {
  catalog(): Promise<ModelCatalogItem[]>
  installed(): Promise<InstalledModel[]>
  install(modelId: string, version: string): Promise<TaskRef>
  importPackage(): Promise<TaskRef | null>
  pause(taskId: string): Promise<void>
  resume(taskId: string): Promise<void>
  cancel(taskId: string): Promise<void>
  test(modelId: string, version: string): Promise<ModelTestResult>
  activate(modelId: string, version: string): Promise<ActivationResult>
  rollback(modelId: string): Promise<ActivationResult>
  uninstall(request: UninstallModelRequest): Promise<TaskRef>
  storageUsage(): Promise<ModelStorageUsage>
  cleanup(): Promise<CleanupResult>
  onProgress(listener: (event: ModelTaskProgress) => void): Unsubscribe
}
```

主进程负责下载、校验、文件锁和任务状态；ONNX 推理由 worker 负责；渲染进程只显示状态和发出用户操作。任务状态持久化后，重启应用仍能恢复。

### 8.13 推荐模型策略

第一版最多在官方目录提供两个模型：

* 中文轻量模型：面向中文对话和中文世界书，作为低配置推荐；

* 多语言轻量模型：面向英文世界书、中文对话等跨语言检索，作为可选包。

不要一次提供大量模型让普通用户选择。模型卡片用“中文轻量”“多语言”解释适用场景，模型技术名称放在详细信息中。所有模型都要完成许可证复核、ONNX 数值对拍、量化质量评估和世界书真实 fixture 召回测试后才能进入 catalog。

## 9. 运行时执行管线

统一为以下顺序，单聊、群聊和触发测试器都调用同一个入口：

```text
1. load + migrate
2. compile runtime document
3. eligibility filters
4. build scan corpus / retrieval query
5. keyword + regex + lexical + optional vector candidates
6. trigger verification
7. recursive scan
8. inclusion-group arbitration + probability
9. rank fusion + deduplication
10. book budget + global budget
11. insertion rendering
12. diagnostics + timed-state update
```

建议公开一个纯函数式主入口：

```ts
executeLorebooks(input: LorebookExecutionInput): LorebookExecutionResult
```

所有外部 I/O（读取文件、请求 embeddings、加载索引）在调用前完成，通过 input 注入候选。这样核心规则可用 fixture 做确定性测试，不依赖 Electron IPC 和网络。

### 9.1 注入能力降级

`InsertionRenderer` 根据当前上下文协议返回：

```ts
interface RenderedInsertion {
  messages: Message[]
  diagnostics: InsertionDiagnostic[]
}
```

建议的默认降级仅作为运行时策略：

| 原位置                    | 完整支持时               | 暂不支持时                      |
| ---------------------- | ------------------- | -------------------------- |
| before/after character | 对应 system prompt 锚点 | 不降级                        |
| examples top/bottom    | 示例消息锚点              | 临近示例区 system 片段            |
| AN top/bottom          | Author's Note 锚点    | system 尾部，并报告 approximated |
| chat depth             | 指定深度和 role          | 深度越界时夹到合法范围                |
| outlet                 | 命名 outlet           | system 尾部，并保留 outletName   |

未来实现新锚点时只改 renderer，不需要重新导入旧世界书。

## 10. 存储、迁移与索引生命周期

### 10.1 文档迁移

建议目录：

```text
shared/lorebook/
  domain/v2.ts
  migrations/v1-to-v2.ts
  migrations/index.ts
  runtime/types.ts
```

迁移规则：

* 每个 migration 都是纯函数：`vN document -> vN+1 document`；

* 只允许连续迁移，禁止在读取代码中散落版本判断；

* 读取时迁移到内存，首次保存时写入最新版；

* 批量迁移前制作可恢复备份，并写迁移日志；

* migration 必须幂等或明确拒绝重复输入；

* 保留旧 `Lorebook` → v2 bridge，过渡期不要求一次改完整个 UI。

### 10.2 修订与缓存失效

每次用户修改文档后 `revision + 1`。不同缓存使用自己的复合键：

```text
runtime compiler: bookId + revision + compilerVersion
lexical index:    bookId + revision + analyzerVersion
vector index:     bookId + revision + providerId + model + dimensions
```

不能只比较内容文本；关键词、别名、启用状态、检索策略等变化也会影响索引或执行。

### 10.3 保存一致性

* 主文档先原子写入，再将旧索引标记 stale；

* 索引重建失败不能回滚用户文档；

* stale 索引不能继续冒充有效索引；

* 并发保存按 revision 做乐观冲突检测，避免后写覆盖先写；

* 索引是派生数据，删除世界书时清理，损坏时可安全重建。

## 13. 测试策略

### 13.1 适配器契约测试

所有 adapter 自动运行同一套 contract：

1. `detect` 对自己的 fixture 得分高于其他 adapter；
2. 空对象、数组、恶意深层对象不会崩溃；
3. import 生成合法 v2 文档和兼容性报告；
4. ID 稳定且重复 source ID 不冲突；
5. 未消费字段被保留或明确报告 dropped；
6. 同格式 export → reimport 后规范字段语义等价；
7. 原始输入对象不被修改。

### 13.2 运行时 golden

覆盖：

* 中英文/CJK/ASCII 关键词和边界；

* 正则、非法正则和超长正则；

* primary/secondary 逻辑；

* constant、vectorized、无 keys 条目；

* recursion、group、probability、sticky、cooldown、delay；

* 所有插入位置和 role；

* 单聊/群聊一致性；

* 预算裁剪、摘要和去重；

* 有 embeddings、无 embeddings、索引 stale、模型切换四种状态。

### 13.3 差分与性质测试

* 重构过渡期对同一输入同时运行旧引擎和新引擎，比较触发集合及原因。

* 对倒排候选路径与全量扫描路径做随机对拍，要求无漏召回。

* migration 链执行后再次执行，确保不会继续改变文档。

* 随机打乱对象字段顺序不应改变格式检测和导入结果。

### 13.4 模型生命周期测试

模型管理必须覆盖：

1. 首次安装成功，进度事件顺序正确；
2. 下载中暂停、关闭应用、重启后继续；
3. 服务器不支持 Range 时正确重新下载；
4. hash、签名、文件大小任一错误都拒绝安装；
5. staging 安装中崩溃后不产生伪 ready 状态；
6. 模型自检维度或数值异常时保持旧版本可用；
7. 更新旁路安装、原子切换和一键回滚；
8. 切换模型后拒绝读取旧模型索引；
9. 卸载默认模型时自动切换词法 fallback；
10. “仅卸载模型”和“模型+索引”两种空间结果准确；
11. 卸载文件占用时进入 `uninstall_pending` 并在重启后完成；
12. `.qymodel` 防 Zip Slip、符号链接和解压炸弹；
13. 后台建索引时发送消息，查询任务优先且 UI 不冻结；
14. 模型、索引、staging 和可清理空间统计准确；
15. 卸载、更新或清理永远不删除世界书主数据。

### 13.5 性能门槛

先在阶段 0 记录基线，再确定硬门槛。建议目标：

* 1,000 条世界书条目在索引预热后，**关键词 + 本地词法通道**的单轮检索 p95 不高于 20 ms；该数字不包含 query embedding；

* 向量通道分别记录“query embedding”“向量 topK 搜索”和“融合排序”的 p50/p95，不把 CPU embedding 强行塞入 20 ms 门槛；本地模型的端到端目标应在确定模型、量化方式和基准机器后单独制定；

* 保存单条修改只增量失效相关缓存，不全量重建所有书；

* UI 导入 10,000 条数据时保持可取消，不阻塞渲染线程；

* embeddings 批量重建在 worker/主进程异步执行，不能阻塞保存。

性能数字应在固定测试机和 fixture 上记录，若基线表明目标不现实，再通过 ADR 调整，不能静默删掉门槛。

## 14. UI 与可观测性

### 14.1 导入预览

导入前展示：

* 检测出的格式和版本；

* 条目数、常驻数、关键词条目数、语义偏好条目数；

* 精确/转换/近似/仅保留/丢弃数量；

* 是否需要 embeddings；

* 无 embeddings 时将采用何种 fallback；

* 导入后是否保留原格式导出能力。

### 14.2 世界书健康状态

为每本书显示：

* 文档 schema 版本；

* 来源格式；

* 词法索引状态；

* 向量索引状态和模型；

* 纯语义必需但当前不可用的条目数；

* 非法正则、重复 ID、空内容和降级位置数量。

### 14.3 模型与索引状态

模型中心、世界书页面和聊天调试面板使用同一状态源，但按场景展示不同信息：

* 模型中心：安装、更新、许可证、磁盘、默认模型和任务；

* 世界书页面：该书在当前模型下的 indexed/stale/building/failed 状态；

* 聊天页：本轮实际使用 local vector、remote vector 还是 lexical fallback；

* 全局任务中心：下载、校验、模型更新和批量索引进度。

不得把“模型已安装”显示成“所有世界书已完成语义索引”。

### 14.4 触发调试

单条诊断至少包含：

```text
entryId / bookId
activationSource: keyword | regex | lexical | vector | sticky | always
matchedKeys
lexicalRank / lexicalScore
vectorRank / vectorScore
fusionScore
fallbackReason
```

这样用户能区分“没有命中”“命中了但组内淘汰”“预算裁剪”“位置被近似”和“索引不可用”。

## 15. 安全与健壮性

* 限制导入文件大小、条目数、嵌套深度、单条内容长度和未知扩展保留总量。

* JSON 解析后复制到无原型安全对象，拒绝 `__proto__`、`constructor` 等污染路径。

* 正则限制长度和 flags；复杂正则放 worker 中执行并设置预算，避免 ReDoS 阻塞 UI。

* 不执行外部宏、脚本或扩展代码。

* 路径只使用轻语生成的安全 ID；来源 ID 作为数据保存，不能直接成为文件名。

* embeddings 请求只发送被用户允许的字段；UI 明确说明世界书正文会发送给外部服务。

* 聊天 API 扩词结果视为不可信建议，必须经过 schema 校验，不能把模型输出当脚本执行。

* 本地模型目录必须签名，文件逐项校验 SHA-256；校验失败不允许用户强制跳过。

* 模型包只允许白名单数据文件，不允许运行安装脚本、动态库或 manifest 中的命令。

* 在线下载、离线导入和自动更新必须共用同一套 staging、校验、自检和原子安装管线。

## 16. 风险与控制

| 风险                            | 控制措施                                        |
| ----------------------------- | ------------------------------------------- |
| 统一模型设计过度，后续仍频繁变更              | 只规范跨格式稳定语义；私有字段留在 namespaced `foreign`      |
| 格式误判                          | 多证据评分、歧义阈值、导入预览和手动选择                        |
| “无损”名不副实                      | 同格式 round-trip 测试；跨格式生成逐字段报告                |
| 词法 fallback 误触发               | 独立阈值、topK、精确关键词高权重、调试可见、可按书关闭               |
| 重构改变既有触发行为                    | 新旧引擎差分执行、golden fixture、分阶段切换               |
| 向量服务不可用导致死条目                  | `semanticPreferred` 默认词法降级；仅显式 required 才停用 |
| 原始字段保留造成数据膨胀                  | 分层大小上限、只保留未消费字段、缓存与主数据分离                    |
| 新 adapter 破坏其他格式检测            | adapter contract + 全注册表冲突测试                 |
| Electron 打包受原生索引依赖影响          | 第一版使用无原生依赖实现，检索接口与实现隔离                      |
| ONNX Runtime 增大安装体积或出现 ABI 问题 | 模型按需下载；运行时做目标平台打包测试；失败自动回退词法                |
| 更新后向量空间变化却误用旧索引               | 索引键包含模型版本、权重 hash、维度、pooling 和 prefix       |
| 模型卸载误删用户数据                    | 模型、索引、世界书分目录；删除目标白名单；专项破坏性测试                |
| 下载/解压中断留下半安装状态                | staging + 持久化任务状态 + 原子 current 指针           |
| 多模型同时驻留造成内存过高                 | 第一版只加载一个 active 模型，空闲后释放 worker 会话          |

## 18. 建议的第一批开发任务

建议先做下面六个小而完整的提交，不要一开始同时重写 UI、存储和匹配器：

1. `test(lorebook): 建立多格式 fixture 与现有行为 golden`
2. `refactor(lorebook): 引入 canonical v2 与迁移框架`
3. `refactor(lorebook): 建立 adapter registry 和兼容性报告`
4. `refactor(lorebook): 拆分 P0 格式适配器并接入统一导入`
5. `feat(lorebook): 增加本地词法检索和 semanticPreferred fallback`
6. `feat(embedding): 增加可选本地模型包与完整生命周期管理`

做到第 4 项时，多格式维护性问题已经基本解决；做到第 5 项时，不支持 embeddings 的 API 用户也不会再被排除在“相关性检索”之外；做到第 6 项时，用户可以在不安装第三方服务的情况下获得真正的本地向量检索。之后再迁移运行时主入口和补齐 P1 格式，风险会显著低于一次性大改。
