# 对话方向选择与输入续写长度优化方案

> 状态：阶段 A/B/C 已实施（2026-09-11）  
> 日期：2026-09-11  
> 修订：2026-09-11 第二轮评审修订（方向开关入口、群聊生成钩子、上下文契约、Token 预算、消息失效点、存量测试清单）  
> 适用范围：桌面端单聊、群聊，以及后续的桥接端与 Android 端同步


> 🗄️ **已归档（2026-09-13）**：按「方案完成后一律归档」移入本目录，仅作历史留档，不再更新。归档登记见 [归档 README](./README.md)。

## 1. 背景与问题

当前对话中已有“游戏主持格式”和“输入框 AI 续写”两项能力，但交互语义和生成约束还不够清晰。

### 1.1 游戏主持格式的问题

当前实现通过会话级 `gameMasterMode` 开关，向主回复提示词注入“【判定】”和“【可选行动】”格式。它存在以下问题：

1. 选项混在 AI 正文中，不是真正可点击的交互元素。
2. 用户无法直接选择、编辑或“换一批”。
3. 普通剧情容易出现生硬的游戏系统文案，破坏沉浸感。
4. “世界状态”与“下一步怎么聊”是两个不同职责，当前却被放在同一个设置语义下。
5. 选项作为正文的一部分，容易进入历史上下文，并在后续回复中被模型继续模仿。

### 1.2 输入框续写长度的问题

当前已将“剧情转折强度”和“内容长度”拆分，方向正确，但长度仍然主要依赖 `maxTokens` 上限和“一两句”等模糊提示。这只能限制最长输出，不能让模型稳定落在目标长度。

另一个核心矛盾是：当输入框已有文本时，续写结果会追加在原文之后，模型并不能通过“追加”将已经较长的原文变成“精简”的最终内容。因此，“最终输入框内容长度”并不是适合续写功能的控制语义。

## 2. 优化目标

本轮优化要达成四个目标：

1. 将“游戏主持格式”替换为独立的“下一步方向”交互。
2. AI 正文保持自然叙事，对话方向以气泡外的结构化卡片展示。
3. 用户从 3 个有实质差异的方向中选择 1 个，结果只回填输入框，不自动发送。
4. 将续写长度重定义为“本次新增内容长度”，通过明确字数区间、合理 Token 预算和生成后校验提高稳定性。

## 3. 产品交互方案

### 3.1 对话方向卡片

当 AI 完成一条有效回复后，如果当前会话已开启“下一步方向”，则在该 AI 气泡下方异步生成 3 个选项。

```text
艾莉丝：
“港口已经封锁，任何人都不能通过。”

选择下一步方向
┌ 追问封锁原因 ── 先从守卫口中确认发生了什么
├ 寻找其他入口 ── 暂避正面冲突，调查港口周边
└ 冒险直接闯关 ── 试图突破封锁，接受立即对抗的风险

                                      [换一批]
```

交互规则：

1. 每批固定 3 个选项，降低选择压力。
2. 单击选项后，将对应的可发送文本写入输入框。
3. 不自动发送，用户可继续修改、删除或使用 AI 续写展开。
4. 输入框已有内容时，点击选项默认替换当前草稿；草稿不为空时先显示内联确认条（“将覆盖当前草稿 [替换] [取消]”），不使用阻塞式 `window.confirm`，避免误覆盖。
5. 点击“换一批”仅重新生成该条消息的选项，不重新生成正文。换一批后清空上一次的选择态；若输入框内容来自上一次的点选且未被用户改写过，换一批不自动改写输入框，只更新候选列表，避免用户正在编辑时被打断。
6. 选项加载失败不影响主回复，只隐藏方向区域或显示小型重试按钮。
7. “自由输入”始终存在，选项不得成为必选流程。
8. 点选后方向卡片保持可见，并标记被选中的选项，便于用户对照后改选或换一批；不因点选而折叠整个区域。
9. 方向区域只在“等待用户输入”的状态下渲染；流式生成中、自动接力中不显示。历史消息的方向保留展示，但仅最新一条允许换一批，避免对历史节点重复发起请求。

### 3.2 选项差异性

选项不应使用完全固定的内容类型，但生成时应保持三种不同倾向：

| 倾向 | 目标 | 常见表现 |
|---|---|---|
| 稳妥推进 | 承接当前主线，减少额外风险 | 回应当前问题、执行明确目标、保持现有计划 |
| 探索信息 | 获取线索、深化关系或验证判断 | 追问、观察、调查、交涉、试探 |
| 冒险变化 | 引入更大行动或接受显著风险 | 强行突破、改变计划、公开对抗、转换场景 |

这三种倾向只是生成器的多样性约束，不必在 UI 上直接显示“稳妥／探索／冒险”标签，避免让界面过度游戏化。

### 3.3 与叙事模式的关系

“下一步方向”不再是全局叙事的专属能力，两种叙事模式都可以开启：

- **代入角色**：选项是用户角色可以说的话或可以尝试的行动。
- **全局叙事**：选项是用户作为旁白、导演或世界推动者可以施加的剧情变化。

方向生成必须读取产生它的那条消息的叙事模式快照，不应在用户后续切换模式时改变历史选项的含义。`Message.narrativeMode` 已存在并作为快照持久化，直接复用即可，不要读当前会话的 `narrativeMode`。

方向生成器按快照分两套约束：

- `immersive`：`content` 是用户角色可以说的话或可以尝试的行动，用第一人称或用户视角的口吻写，不得替对方角色发言。
- `omniscient`：`content` 是用户可以施加的旁白推动、导演式调度或世界变化，用第三人称旁白口吻写，不得写成对方角色的第一人称台词。

### 3.4 设置入口

“下一步方向”是对话交互偏好，不是世界状态数据；且世界状态面板只在全局叙事下显示，代入角色叙事不需要该面板。因此本开关不放入世界状态面板，直接落在**对话快捷设置**（QuickSettingsPanel，单聊与群聊共用，两种叙事模式均可访问）：

```text
对话交互
下一步方向                  [开关]
AI 回复后生成 3 个可选方向
```

要点：

1. 开关为**会话级**：单聊写 `ChatSession.dialogueDirectionsEnabled`，群聊写 `GroupSession.dialogueDirectionsEnabled`。
2. 世界状态面板保留“世界状态编辑 + 活跃事实”，仅移除“游戏主持格式”区块及其 prop；面板仍仅在全局叙事下显示。
3. 快捷设置面板通过可选 props 接收当前值与 setter（由 `ChatPage` / `GroupChatPage` 注入），面板本身不直接耦合两个 store。
4. 开关在流式生成期间也允许切换；变更只影响下一次完成的回复，不影响已生成的方向。

## 4. 对话方向生成方案

### 4.1 独立的辅助请求

不建议让主回复在正文末尾同时生成选项。推荐在主回复流结束后，发起一次独立的轻量请求。

优点：

1. 主回复可以继续流式展示，不等待选项生成。
2. 选项失败不会污染正文。
3. 正文不会混入 JSON、XML 或特殊标记。
4. 重新生成选项时无需重新生成主回复。
5. 后续可以使用更快、成本更低的辅助模型。

建议请求参数：

```ts
{
  temperature: 0.6,
  maxTokens: 384,
  reasoningMode: 'disabled',
  stream: false,
}
```

`maxTokens` 取 384：3 组 `label + content` 中文约 200–300 token，JSON 结构与标签包裹再占 60–80 token；取 256 容易在结构尾部被截断，反而把“格式非法→重试”的失败率推高。384 与 256 的成本差异可忽略。

上下文契约（明确边界，避免实现时漂移）：

- **注入**：当前角色或群聊成员的必要设定（`character.description` 级别的精简片段）、当前叙事模式（取自产生方向的**消息** `narrativeMode` 快照）、最近 4–6 条有效对话、产生方向的那条 AI 回复、`memoryCurrentState` 的精简片段。
- **不注入**：世界书全文、preset 完整提示词、向量检索结果。理由：方向生成只回答“接下来可以做什么”，不需要世界观细节；注入世界书会让请求从轻量变为重量，并引入裁剪与压缩逻辑的耦合。
- **不复用主回复的完整上下文构建器**：`contextBuilder` 的产物包含 Assist Prefix、世界书注入与记忆摘要，直接复用会把成本抬到与主回复同级。单聊与群聊各自从消息数组构造精简上下文即可。
- 群聊取成员设定时，只取产生回复的那名角色的设定与参与本轮的成员名单，不逐条注入全部成员角色卡。
- 叙事模式必须按消息快照读取，不得读当前会话设置：用户切换模式后，历史消息上的方向含义不能被改写。

### 4.2 输出合同

推荐输出一组可严格校验的数据：

```ts
interface DialogueDirection {
  id: string
  label: string
  content: string
  tendency: 'safe' | 'explore' | 'risky'
}
```

示例：

```json
[
  {
    "id": "safe",
    "label": "追问封锁原因",
    "content": "先不与守卫冲突，试着追问港口突然封锁的原因。",
    "tendency": "safe"
  },
  {
    "id": "explore",
    "label": "寻找其他入口",
    "content": "暂时离开正门，沿港口外围查看是否存在无人值守的通道。",
    "tendency": "explore"
  },
  {
    "id": "risky",
    "label": "冒险直接闯关",
    "content": "趁守卫注意力被分散时尝试突破封锁，承担立即暴露的风险。",
    "tendency": "risky"
  }
]
```

如果提供商支持 JSON Schema，优先使用结构化输出。为了兼容不同提供商，基础链路可使用单组 `<directions>...</directions>` 标签包裹 JSON，然后复用现有辅助输出的标签提取思路（见 `aiInputHelper.ts` 的 `extractTaggedResult`：标签缺失或重复均判无效，且先 `stripThought`，避免把分析过程当成业务数据）。

校验口径统一使用与续写相同的可计数定义（`Array.from(text.replace(/\s/g, '')).length`），不混用 `String.length`。

### 4.3 服务端校验

只有同时满足以下条件时才允许展示：

1. 必须恰好有 3 个选项。
2. `label` 为 6–14 个可见字符。
3. `content` 为 15–60 个可见字符。
4. `tendency` 三个合法值各出现一次。
5. `id` 三个值互不相同；建议直接由 `tendency` 派生（`safe` / `explore` / `risky`），避免模型自造重复或不稳定的 id。
6. 不含“选项 A”“建议你”“作为 AI”等解释性前缀。
7. 不含系统提示词、隐藏角色动机或玩家尚未知晓的信息。
8. 三项内容不得高度相似。可先用简单文本归一化判重（去空白与标点后比对，再算两两公共前缀/字符集合重叠），不必引入额外向量计算。

校验按“整组同生共死”处理：任一项不合法即整组不展示，不渲染部分选项——只显示 2 个会让“三倾向覆盖”的语义失真。

结构或内容校验失败时自动重试一次（重试时在 system 提示中追加一句“只返回 `<directions>` 包裹的合法 JSON”，并压低温度）；第二次仍失败则放弃展示，静默隐藏方向区域，不应将原始输出直接渲染给用户。

`label` / `content` 的字数上限是**初始值**：如果实测发现模型稳定产出略长的合规选项，应按数据校准区间，而不是放宽到无上限。

### 4.4 生成时机

只在以下条件同时满足时生成方向：

1. 会话已启用下一步方向。
2. 主回复正常完成且存在有效正文。
3. 当前没有执行重生成、Swipe 或删除操作。
4. 对话正在等待用户输入。
5. 群聊自动轮询或自动接力尚未结束时不生成，避免每个中间回复都产生无效选项。

**单聊**：在 `sendMessage` 的 AI 回复完成回调与 `chatGeneration.ts` 的生成收尾处触发；用户消息（`__user__` 角色）与错误/空正文回复不触发。

**群聊**：轮询链的终止点是 `groupStreamController.ts` 的 `checkPollingContinue()`——它在 `rounds.size >= group.maxRounds` 时直接 `return`，当前没有终止回调。实现时必须：

1. 在该终止分支（以及无下一发言者、`currentSpeakerIndex` 越界等提前返回分支）加“轮到用户了”钩子。
2. `mention` / `polling` 模式在 `streamGroupAI` 的 onComplete 内判断本轮是否为最后一轮，是则触发；`free` 模式在 `streamGroupAIFree` 完成后触发。
3. 手动触发的即时接话（`triggerCharacterReply`）与自动接力区分：即时接话完成后即可生成，因为它本身就是等待用户的节点。
4. 钩子必须可重入保护：轮询定时器可能因 `isStreaming` 跳过一轮后重新调度，避免同一条消息重复生成。

**仅对最新一条有效 AI 消息生成**：不追溯历史消息，打开旧会话或切换会话时不批量补生成。方向属于“下一步该做什么”，脱离当时的对话节点后生成没有意义，同时避免一次会话切换打出 N 个辅助请求。

重生成或 Swipe 替换消息正文后，原选项必须立即失效，并为新正文生成新的方向。

编辑消息正文（`editMessage`）同样使该消息的旧方向失效；用户编辑自己的消息不使 AI 消息的方向失效。

## 5. 数据设计

### 5.1 会话设置

将原有字段：

```ts
gameMasterMode?: boolean
```

替换为：

```ts
dialogueDirectionsEnabled?: boolean
```

单聊 `ChatSession` 和群聊 `GroupSession` 使用相同字段，并在桌面端、桥接 DTO 和 Android 数据模型中保持一致。

字段为会话级：每个会话独立开关，新建会话默认关闭，不做角色级默认值（与 `narrativeMode` 的默认值机制区分开）。建议在 `shared/` 中提供一个与 `resolveNarrativeMode` 同形的解析函数，供桌面端、桥接端与 IPC 校验共用，避免三端各自写一套 `?? false` 的降级逻辑。

```ts
export function resolveDialogueDirectionsEnabled(session?: {
  dialogueDirectionsEnabled?: boolean
  gameMasterMode?: boolean
}): boolean {
  return session?.dialogueDirectionsEnabled ?? session?.gameMasterMode ?? false
}
```

### 5.2 消息数据

选项属于生成它的 AI 消息，建议在消息上持久化：

```ts
interface Message {
  // 现有字段……
  dialogueDirections?: DialogueDirection[]
  dialogueDirectionsGeneratedAt?: number
}
```

群聊的 `GroupMessage` 使用相同字段。选项必须跟随消息持久化，不能只保存在 React 或 Zustand 的临时界面状态中，否则切换会话或重启后会丢失。桥接与 Android 的消息 DTO 同步该字段。

### 5.3 旧数据兼容

过渡期解析规则见 §5.1 的 `resolveDialogueDirectionsEnabled`：优先新字段，其次旧字段，最后 `false`。

旧会话如果已开启游戏主持格式，升级后自动启用下一步方向，但主回复不再注入“【判定】”或“【可选行动】”。

新版保存时只写入 `dialogueDirectionsEnabled`。兼容期为一个版本：期间保留 `gameMasterMode` 的读取与 IPC 校验；一个版本后删除 `gameMasterMode` 字段、白名单项、类型校验、各处 DTO 映射与 `buildGameMasterPrompt` 及其测试。

## 6. 续写长度优化

### 6.1 重定义控制语义

将 UI 与提示词中的：

```text
最终输入框内容长度
```

改为：

```text
本次续写长度
```

当输入框已有原文时，长度只统计本次追加的 `<continuation>` 正文。当输入框为空时，生成的完整用户回应就是本次新增内容。

这一定义同时适用于代入角色和全局叙事。

### 6.2 长度档位

建议保留四档，但使用可验收的字数区间：

| 档位 | 新增可见字符 | 结构目标 | `maxTokens` 建议值 |
|---|---:|---|---:|
| 短句 | 20–60 字 | 1–2 句 | 128 |
| 小段 | 80–180 字 | 1 个完整自然段 | 384 |
| 展开 | 220–420 字 | 2–3 个自然段 | 768 |
| 长篇 | 500–900 字 | 4–6 个自然段 | 1536 |

`maxTokens` 只是安全上限，字数区间才是生成目标。预算需为不同模型的中文 Token 切分差异预留空间，不能将字符数直接当作 Token 数。长篇档 900 字配 1536 token 属于紧预算：在 CJK 切分较差（约 1.5–2 token/字）的模型上可能触发截断，实施后需按 §9.2 用实测分布校准，必要时单独上调长篇档预算而不改动其他档。

### 6.3 UI 调整

当前 `ChatInput.tsx` 的 `ContinueSliderControl` 同时渲染了隐形 `input[type=range]` 与四档分段按钮：两者都是四档离散值，滑块只增加一个不可见的热区，键盘与屏幕阅读器路径重复。保留分段按钮，移除隐形滑块与其轨道装饰：

```text
本次续写长度
[短句] [小段] [展开] [长篇]

小段 · 预计新增 80–180 字
```

需要注意的存量耦合：`ChatInput.test.tsx` 通过 `getByLabelText('最终输入框内容长度')` 操作滑块，`ariaLabel` 改为“本次续写长度”后该用例必须同步改写为点击分段按钮。

“剧情转折强度”继续作为独立控制项，但文案可简化为：

```text
剧情变化
[延续] [波澜] [转折] [剧变]
```

两项的职责必须稳定：

- 剧情变化：决定“发生多大的变化”。
- 续写长度：决定“本次增加多少内容”。

### 6.4 提示词合同

长度提示应改成明确的新增范围。例如“小段”：

```text
本次只输出直接接在原文之后的新内容，不要复述原文。
新增正文目标为 80–180 个可见中文字符，形成一个完整自然段。
必须在完整句处结束，不要为了凑字数重复信息。
如果情节已经自然完成，宁可接近下限，也不得增加无关支线。
```

不要再使用“可写多个自然段”等无上限描述作为唯一约束。

### 6.5 生成后校验

在现有 `<continuation>` 提取、中文正文校验和用户视角清洗之后，增加长度校验。

建议统计方式：

```ts
function countVisibleCharacters(text: string): number {
  return Array.from(text.replace(/\s/g, '')).length
}
```

处理规则：

1. 落在目标区间内：直接接受。
2. 低于下限，但已达下限的 80% 且语义完整：允许接受，不为凑字数重试。
3. 低于下限的 80%：发起一次“补足内容”修复请求。
4. 高于上限的 120%：发起一次“压缩内容”修复请求。
5. 介于上限的 100%–120%：若存在接近上限的完整句边界，可在句边界安全收束；否则执行压缩修复。
6. **结尾不完整优先按截断处理**：如果结果以逗号、顿号、连接词、未闭合引号或悬空动作结尾，无论字数是否落在下限的 80% 以上，都按“被截断”处理，走补足修复；不得因字数达标而接受半截正文。截断通常由 `maxTokens` 命中导致，修复请求应同时提示“上次输出可能被截断，请在预算内收尾”。
7. 修复最多一次，避免重复调用。
8. 修复后仍轻微越界，但语义完整时可接受；明显越界则保留原输入并显示可见错误。

“语义完整”的判定不引入模型调用：以结尾是否落在句末标点（。！？…"）或完整行内引号收束为准，作为可测试的保守规则。

不建议对超长结果直接按字符数硬截断，因为容易破坏对白、句子和因果关系。

### 6.6 采样参数

长度不应通过提高温度间接实现。建议将剧情变化四档温度收窄为：

| 档位 | `temperature` |
|---|---:|
| 延续 | 0.45 |
| 波澜 | 0.55 |
| 转折 | 0.65 |
| 剧变 | 0.75 |

过高的温度容易同时增加新支线、新人物和解释性细节，使续写长度更难预测。

## 7. 两项能力的组合流程

```text
AI 正常回复
    ↓
异步生成 3 个下一步方向
    ↓
用户选择其中 1 个
    ↓
对应内容回填输入框
    ↓
用户可修改，或按所选档位继续 AI 续写
    ↓
用户确认后手动发送
```

三个控制项的边界如下：

| 能力 | 回答的问题 |
|---|---|
| 下一步方向 | 接下来可以做什么 |
| 剧情变化 | 这次行动可以带来多大的变化 |
| 续写长度 | 本次要增加多少文字 |

不允许长度档位改变剧情转折程度，也不允许剧情变化档位暗中改变输出长度。

## 9. 测试与验收

### 9.1 对话方向

1. 关闭方向功能时，AI 回复后不发起辅助请求。
2. 开启后，有效 AI 回复下方最多显示 3 个方向。
3. 三个方向分别覆盖稳妥、探索和冒险倾向，内容不高度重复。
4. 点击方向只回填输入框，不自动发送。
5. 有未保存草稿时不得静默覆盖。
6. 换一批不改变主回复。
7. 辅助请求失败不影响主回复的成功状态。

12. AI 正文中不再出现系统强制的“【可选行动】”格式。

### 9.2 续写长度

1. 有原文时只统计本次新增内容，不使用“最终总长度”判定。
2. 空输入时以生成的完整回应作为本次新增内容。
3. 短句档绝大多数结果落在 20–60 字。
4. 小段档绝大多数结果落在 80–180 字。
5. 展开档绝大多数结果落在 220–420 字。
6. 长篇档绝大多数结果落在 500–900 字。
7. 续写结果必须在完整句处结束。
8. 越界修复最多请求一次，不得无限重试。
9. 剧情变化档位不改变长度目标和 `maxTokens`。
10. 长度档位不改变剧情转折指令和温度。
11. 续写失败时保留用户原输入，并显示可见反馈。
12. 代入角色和全局叙事均使用同一长度定义。

## 10. 性能、成本与降级

对话方向会为开启该功能的会话增加一次轻量 AI 请求。建议采取以下控制：

1. 功能默认关闭，由用户按会话启用。
2. 请求不阻塞主回复和输入框。
3. 同一消息不重复生成，除非用户主动点击“换一批”；仅对最新一条有效 AI 消息生成（见 §4.4），切换会话或打开旧会话不批量补生成。
4. 会话切换或消息被删除时取消尚未完成的辅助请求。
5. 输出结构不合法时最多重试一次。
6. 无 API 连接、请求失败或客户端不支持时，静默降级为普通自由输入。

长度修复只在明显越界时发生，不应对每次续写都进行第二次请求。

“换一批”应考虑同一消息上的连续点击：在途请求直接丢弃旧结果，只保留最后一次的响应，避免快速点击把过期结果写回消息。

## 12. 最终决策

采用以下不可混淆的产品语义：

```text
AI 正文只负责自然回应和叙事。
下一步方向是气泡外的独立交互，每次给出 3 个方向供用户选择 1 个。
选择结果只回填输入框，不自动发送。
续写长度只控制本次新增内容，不控制已存在的原文总长度。
字数区间是目标，Token 预算是上限，生成后校验是最终保障。
```

这套方案将“选什么方向”、“剧情变化有多大”和“本次写多少”拆成三个独立维度，既保留用户主权，也能让输入框续写的结果更可预期。

实施前确认的边界决策：

1. 方向开关落在对话快捷设置，世界状态面板保持仅全局叙事显示；以角色视角叙事时不显示该面板。
2. 方向生成不注入世界书与完整 preset，只注入角色设定、叙事模式快照、最近对话与精简世界状态。
3. 方向只对最新一条有效 AI 消息生成；话题切换或模式切换不改写历史方向。
4. 分支会话复制消息时连带方向一并复制，视为可接受行为。

### 阶段 B 回归修复（2026-09-11 实测反馈）

真机使用中“输入框续写”持续提示“续写未返回有效的中文正文”。根因不在解析链路，而在本阶段设定的
`maxTokens`：中文在多数模型上约 1.5–2 token/字，还需容纳 `<continuation>` 标签包裹与模型开场语，
而初版预算（128 / 384 / 768 / 1536）按“字符数≈token 数”估算，均低于下限。输出因此在闭标签前被切断，
`extractTaggedResult` 要求标签对完整，两次尝试都拿不到正文，于是落到“无效中文正文”分支。

修复：

1. 预算改为 256 / 512 / 1024 / 2048，并加不变量断言 `maxTokens ≥ maxChars × 2 + 64`（`continueIntensity.test.ts`），
   防止后续调低档位时再次跌破下限；方向生成预算同步由 384 提到 640（同一类风险，3 组选项 + JSON 结构）。
2. 新增 `classifyContinueFailure`：区分“被截断（有开标签缺闭标签）”“只有思考内容”“无标签”。
   截断时提示改为“续写输出被长度上限截断，请提高「本次续写长度」档位或更换模型”，
   让同类问题下次能直接指向档位，而不是让人去怀疑模型或网络。
3. 原“待核实项”由上述不变量取代：预算是“封顶而非预扣”，给足余量不影响成本。

### 阶段 B 三次修订：实机定位真实成因（2026-09-11）

前两次修订都基于“中文 2 token/字导致输出被切断”的推断，**实机验证后该结论被推翻**。
用真实连接（`deepseek/deepseek-v4.1-flash`，聚合端点）跑探针得到的证据：

| 观测 | 结论 |
|---|---|
| 所有失败请求 `finish_reason=stop` | 输出**从未**因 `maxTokens` 被切断 |
| 显式发送 `thinking:{type:'disabled'}` 后仍返回 `reasoning_content` | 聚合端点**忽略**关闭思考参数 |
| 推理占 167–3479 token，与正文共享同一份输出预算 | 预算偏紧时推理吃光预算、正文为空 |
| 失败样本的正文本身完整通顺（如 583 字完整叙述），仅缺 `<continuation>` 标签 | 标签缺失是主要失败表象，不是内容问题 |

真实成因是三条叠加：**推理与正文共享输出预算** + **端点忽略关闭思考** + **模型频繁不加标签**，
而解析层要求标签对完整，于是把可用正文整段丢弃、报“未返回有效的中文正文”。

据此的修复：

1. `CONTINUE_REQUEST_MAX_TOKENS` 由 4096 提到 **8192**，覆盖“较长推理 + 最大档正文”
   （实测单次完成量最高约 3900 token）；不变量改为
   `≥ maxChars × 2 + 实测最大推理 token + 512`。
2. **标签降级为可选的“信封”**：`parseContinueResult` 完整标签对优先，
   缺失时回退到未闭合标签内容或全文，剥离元说明（“以下是续写：”）后使用；
   无标签路径采用更严的中文占比判据（中文字符不少于英文），
   防止把 `Need final only. 应该继续推进剧情。` 这类混合输出当成正文。
3. 失败归因改为 `empty`（只有思考/空）/ `truncated`（写了没写完）/ `invalid-content`（非中文正文），
   提示分别指向“重试或换模型”“没写完”“无有效正文”。

伴随的职责划分仍然成立：**长度只由提示词的字数指令与生成后校验控制，输出上限只是失控兜底**。

### 阶段 B 二次修订：长度控制与输出上限解耦（已被上一次修订取代，保留供追溯）

第一次修复只是把每档预算调大，仍属“按档位配预算”的思路，只要档位与模型切分方式变化就可能再次踩线。
按实际使用反馈改为职责分离：

1. **长度只由提示词控制**：`CONTINUE_LENGTH_PARAMS` 不再携带 `maxTokens`，只保留 `minChars` / `maxChars` /
   `structure`；提示词明确“篇幅由本指令控制，写 N–M 个可见中文字符”，并新增“一次把目标篇幅写完，
   不要只写开头就收尾，也不要大幅超出上限”。
2. **输出上限降级为统一失控兜底**：新增 `CONTINUE_REQUEST_MAX_TOKENS = 4096`，不再随档位变化。
   它只防止模型跑飞，不参与长度控制；最大档 900 字（约 1800 token）仍有约 2 倍余量。
   之所以保留该参数而不直接省略：`claude` 适配器是 `maxTokens || 4096`、`openai` 始终发送 `max_tokens`，
   省略它会让不同渠道落到各自默认值上，行为不可控。
3. **不变量与判据更新**：`CONTINUE_LENGTH_PARAMS` 断言“不再含 maxTokens”；
   新增“统一上限 ≥ 最大档 maxChars × 2 + 512”的不变量与“上限不随档位变化”的行为断言。
4. **截断提示改为指向模型而非档位**：篇幅既由提示词控制，写不完通常是模型未遵守指令或中途中断，
   因此提示为“续写没有写完，请重试或更换模型；若经常出现可降低「本次续写长度」档位”。
   修复指令也不再复述 token 预算。
