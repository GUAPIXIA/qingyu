## 三、修复方案

### R1　截断策略：主对话保护 + 辅助链路降级（推荐 A+B）

#### A. 新增 `ChatParams.allowTruncatedOutput`

- `shared/types.ts` 的 `ChatParams` 增加可选字段：

  ```ts
  /** 允许在 finish_reason=length 时返回已产出的正文（仅解析器自身可容错的辅助调用）。
   *  缺省 false：主对话等链路的截断仍按错误处理，避免半截内容写入消息。 */
  allowTruncatedOutput?: boolean
  ```

- `electron/services/adapters/openai.ts` 两处截断判定改为条件抛错：
  - 非流式（当前约 `:115`）：`choice?.finish_reason === 'length' && !params.allowTruncatedOutput` 才抛错；
  - 流式（当前约 `:291`）：`finishReason === 'length' && !params.allowTruncatedOutput` 才抛错，否则返回 `normalizeThoughtTags(fullText)`。
  - 条件里**不要**加 `streamedToolCalls.size === 0` 豁免：那会让主对话在「流出了 tool_calls 且 finish_reason=length」时从抛错变成放行，而截断的 arguments 是残缺 JSON，错误会被推迟到 toolLoop 解析时才暴露、更难定位。只按 `allowTruncatedOutput` 门控，主对话（含工具调用）行为零变化。
  - 「零输出防御」（无任何 delta）保持不变：正文为空时仍报错，只是文案沿用现有的长度/空内容分支。
- 主对话不传该字段 → 现有保护不变。IPC 层是整对象透传（`electron/services/ai.ts` 的 `ipcMain.handle('ai:chat', …)`），无需改 preload 与 IPC。

透传链（生图）：

```
src/commands/registry.ts        callAiHelper 选项类型 + allowTruncatedOutput
  → src/components/chat/commandContext.ts    转发到 runAiHelper
  → src/components/chat/aiInputHelper.ts     AiHelperCallOptions → ChatParams
  → src/commands/builtin/imagine.ts          调用处传 allowTruncatedOutput: true
```

长记忆与预设生成各自直接构造 `ChatParams`，单独加一行：

- `src/store/memoryManager.ts` 的 `window.api.ai.chat({...})`（`maxTokens: MEMORY_SUMMARY_OUTPUT_TOKENS` 处）加 `allowTruncatedOutput: true`（`parseMemoryResult` 容忍缺段，截断最多丢当轮【事实提案】）；
- `src/pages/PresetsPage.tsx` 的 AI 生成预设调用（1200 预算）同样加该字段。

#### B. 提高两条紧预算路径的输出上限

| 位置 | 现值 | 建议 | 依据 |
|---|---|---|---|
| `src/commands/builtin/imagine.ts`（`maxTokens: style === 'natural' ? 1200 : 900`） | 1200 / 900 | **2560 / 2048** | 实测生图场景推理峰值 ≈1200，为正文留出 2 倍余量 |
| `src/store/memoryManager.ts` 的 `MEMORY_SUMMARY_OUTPUT_TOKENS` | 4096 | **6144** | 实测推理峰值 3669；该值参与 `resolveMemorySummaryInputBudget` 扣减，小上下文下输入预算减少 2048 token，仍受 `MEMORY_SUMMARY_MIN_INPUT_TOKEN_BUDGET` 保底 |

预算只是上限，不增加正常调用成本；与续写（8192）、方向（1536）的既有做法一致。

#### 备选（最小改动）

只做 B、不做 A：改动约 3 行，但撞上限时仍是硬失败（用户看到"生图失败/长记忆失败"并可重试）。若优先控风险，可采用此方案先上线，A 随后跟进。

#### 测试

- `electron/services/__tests__/ai.test.ts`：非流式与流式各两条——`allowTruncatedOutput` 缺省时 `finish_reason=length` 抛错；置 true 时返回正文（含正文为空仍抛错的用例）。
- 补一条缺省参数下「流式 tool_calls + `finish_reason=length` 仍抛错」的用例，锁定主对话工具调用行为不因本修复改变。
- `src/commands/__tests__/builtin.test.ts`：断言 `/imagine` 调用 `callAiHelper` 时选项含 `allowTruncatedOutput: true` 与新预算。
- `src/store/__tests__/memoryManager.test.ts`：断言总结请求参数含该字段。
- 评测器 `verify` 批次新增断言（见 §五）。

> 同暴露面备注：世界书压缩/扩词（`electron/services/ai.ts` 的 `ai:compressLorebook` / `ai:localizeLorebookKeywords`）走同一适配器，若输出预算偏紧有同样风险。本轮实测未暴露，不进本方案，仅记录待查。

### R2　截断/失败时的消息可见性

1. `shared/types.ts` 的 `Message` 增加可选字段：

   ```ts
   /** 本次生成失败/被截断的原因；有值时气泡展示提示行，历史构建只读 content，不进入上下文。 */
   generationError?: string
   ```

2. `src/store/useChatStore.ts` 的 `onError`（`streamAIResponse` 回调内）：
   - 正文非空 → 用当前内容 + `generationError: errMsg` 覆盖并**保存**该消息（不把错误文案写进 `content`，避免污染后续上下文与复制/导出）；
   - 正文为空 → 保持现有 `⚠️ {errMsg}` 占位逻辑（该分支已可见且会保存）。
3. `src/components/chat/MessageBubble.tsx`：在正文下方渲染提示行（复用"翻译失败"提示的样式与位置，约 `:557`），文案如「⚠️ 生成中断：{generationError}」，旁边沿用已有的"重新生成"按钮。
4. 可选补强：把 `useChatStore.error` 渲染为 `ChatInput` 上方的可关闭提示条。该字段目前被流式失败、重新生图失败等多处写入却无人消费（已核实 StatusBar、ChatInput 等组件均无引用）；补上后与 3 形成"消息级 + 全局"两层反馈。

> 取消路径无影响：手动停止时主进程发 `aiDone` 而非 `aiError`（`electron/services/ai.ts` 约 `:266`），`onError` 不会因用户主动停止而触发，不会把正常中断误标为生成失败。

#### 测试

- `src/store/__tests__/streamController.test.ts` / `useChatStore` 相关：有分片 + 错误 → 消息落盘且带 `generationError`；无分片 + 错误 → 走 `⚠️` 分支。
- `MessageBubble` 断言提示行渲染；`generationError` 不进入 `buildContextMessagesFromData`（可加一条历史构建断言）。
- `generationError` 随 `saveMessage` 持久化，补一条「重载会话后气泡仍显示提示行」的断言。

### R3　生图提示词解析器收紧（`src/commands/builtin/imagine.ts`）

1. `isUsableImagePrompt` 增加拒绝规则：
   - 自我纠错/元信息开头：在现有元词正则基础上补 `let me|i'll|i will|sorry|wait|actually|correct|correction|rewrite|redo`（覆盖 `tag. Let me correct.` 这类）。新词必须并入**锚定行首**的既有正则（`^(?:...)`），不得改成全局匹配——`anatomically correct` 是常见绘画标签，全局匹配会误杀合法提示词；
   - 含任意尖括号标记：`/<\s*\/?\s*[a-z][a-z0-9_-]*\s*>/i`（当前只挡 `<prompt>` 字面量，`<prong>` 会漏过）。
2. `parseImagePromptResult` 增加"取有效段"：候选含多行时，
   - tags 风格从首个匹配 `best quality|masterpiece|highres` 的行开始截取；
   - natural 风格从首个 ≥12 个英文单词的行开始截取；
  丢弃其前的自述/纠错行。截取后先剥掉行首残缺的 `<...>` 片段（如 `<prong>best quality, …` → `best quality, …`），再过 `isUsableImagePrompt`——否则规则 1 的「含任意尖括号标记即拒绝」会把刚截取的段又拒掉，实测样本仍恢复不回来。
3. `finalizeImagePrompt` 对 tags 风格做确定性补齐：结果未以质量前缀开头时自动补 `best quality, masterpiece, highres, `（现在只在评测里告警，不修改）。

#### 测试

把第二轮抓到的原始样本固化为用例：

- 输入 `tag. Let me correct.\n\n<prong>best quality, masterpiece, highres, 1girl, …` → 断言最终提示词以质量前缀开头、不含 `prong`、不含 `Let me`；
- 输入缺前缀的合法 tags 提示词 → 断言被补齐；
- 输入 normal 元信息开头（`we need` 等）→ 仍按"无效"处理并触发重写。

### R5　续写复读兜底（`src/utils/messagePostProcess.ts` + `src/components/chat/useChatInputState.ts`）

前提修正：`trimContinuationOverlap` 现有默认阈值 8 字裁不掉本轮观察到的复读——“今天其实”4 字、“楼道里传来”5 字均低于阈值，直接复用会让下方首个测试用例失败、验收“复读类评审问题为 0”落空。因此先给函数加可选阈值参数：

```ts
// src/utils/messagePostProcess.ts：签名加可选参数，默认值保持 8 不变
export function trimContinuationOverlap(prev: string, next: string, minOverlap = MIN_CONTINUATION_OVERLAP): string
```

在长度修复完成、`cleaned` 最终确定之后、`setContinuedText` 之前插入：

```ts
// 提示词已禁止复读末尾，但模型仍会溢出；用确定性去重兜底。
// 复读样本只有 4–5 字，低于 AI 消息续写路径的 8 字默认阈值，此路径单独放宽到 4。
if (cleaned && hasInput) cleaned = trimContinuationOverlap(originalInput, cleaned, 4)
```

- `src/utils/messagePostProcess.ts` 的 `trimContinuationOverlap`（检测 next 头部与 prev 尾部的最大重叠）加可选参数 `minOverlap`，**默认值保持 8**：`chatGeneration.ts` 的 AI 消息续写路径行为不变，只有用户输入续写路径放宽到 4；
- 拼接语义不变：`setContinuedText(originalInput + cleaned)`；
- 去重后再跑一次 `evaluateContinueLength` 不是必须（去重只削 4 字量级的前缀，不影响档位判定），但建议在 `cleaned` 变更后补充 `isCompleteSentence` 兜底判断，避免剪切把结尾也削掉（当前实现只削前缀，不会影响结尾）。

#### 测试

- 单测：`originalInput='说起来，我今天其实'` + 续写 `'今天其实去了趟老城区的旧货市场…'`（重叠“今天其实”共 4 字）→ `minOverlap=4` 时断言拼接结果无重复短语；
- 单测：重叠 < 4 字时不改动（如 `originalInput='我去看看楼下的'` + `'积水有没有漫上来'`）；
- 单测：不传 `minOverlap` 时默认阈值仍为 8，4 字重叠不裁剪——同步 `messagePostProcess.test.ts`（约 `:353`）既有断言，锁定 AI 消息续写路径行为不变；
- 端到端：`--batch continue --reps 2`，观察评审中“复读”类问题消失。

### R4　前缀后处理跳过已含说话人的行（`src/utils/messagePostProcess.ts`）

`normalizeRoleplayDialoguePrefixes` 的行处理内增加守卫：该行（去空白后）已包含角色名时不补前缀。

```ts
const namePattern = new RegExp(escapeRegExp(characterName.trim()))
if (namePattern.test(trimmed)) return line
```

（模块内已有 `escapeRegExp` 的实现位置请复用或就近新增一个；`aiInputHelper.ts` 中的同名函数为私有实现，不跨模块引用。）

守卫是子串匹配：角色名很短时会误跳过含同名子串的裸对白行（如单字名"晚"遇 `“夜晚真安静。”`）。可接受，用测试固化该行为，不做词边界处理。

## 五、评测器配套改动（`scripts/evaluate-generation.ts`）

在 `verify` 批次（不调模型）新增断言，把本方案的契约固定下来：

1. 扩展现有 `v-adapter-length-error`（就地扩展，不另立覆盖面重叠的新用例）：构造 `finish_reason=length` 的响应——缺省抛错；`allowTruncatedOutput: true` 时返回正文（非流式与流式各一条）；补一条「缺省 + 流出 tool_calls + length 仍抛错」锁定主对话行为。
2. `v-imagine-meta-rejected`：直接调用 `imagineCommand.execute`，`callAiHelper` 返回注入元信息/未知标签的样本（含 `<prong>` 残缺标记与自述行），断言捕获到的提示词干净且带质量前缀。
3. `v-continue-overlap-trim`：对 `trimContinuationOverlap`（`minOverlap=4`）+ 续写解析组合断言去重生效；不传参数时默认 8 字行为不变。
4. `v-dialogue-prefix-guard`：断言含角色名的行不被二次加前缀（含单字角色名子串边界）。

另建议在 `imagine` 批次补一条结构性检查：提示词不得包含 `<...>` 标签或 `let me / i'll / actually` 等元信息词（与 R3 对应）。
