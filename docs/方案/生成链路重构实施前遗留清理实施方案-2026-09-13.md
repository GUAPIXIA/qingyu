## 2. 为什么必须前置：三处真实耦合

这一节是本计划的立项依据。三处耦合都经过代码核对，不是理论风险。

### 2.1 反向依赖 × 主计划 W7–W9

主计划 W7 要"从 `contextBuilder` 提取候选描述"、W8/W9 要继续改造同一文件的记忆、世界书与历史分配。但当前 `electron/` 生产代码反向 import `src/` 共 **17 条、跨 8 个文件**，其中三条直接落在主计划要动的模块上：

- `electron/bridge/chatService.ts:18,23,27,37,40`（contextBuilder、regex、chatConstants、messagePostProcess、generatedReplyPipeline）
- `electron/chat/contextService.ts:9`（contextBuilder）
- `electron/bridge/routes.ts:48-53`（contextBuilder、memory、memoryWindow、chatConstants 等 6 条）

后果：主计划每改一次 `src/context/contextBuilder.ts`，都必须同时对主进程与 Bridge 侧做回归；而 `eslint.config.js` 目前**没有** `no-restricted-imports` 门禁，新增反向依赖不会被拦下。另存在靠注释约定同步的双份实现（`electron/utils/variables.ts:1-5` 自述"独立定义，避免跨层导入"）。

先解耦再改分配逻辑，比边改边解耦便宜得多。

### 2.2 迁移并链 × 主计划 W10

`settings` 当前有**两条互不知晓的迁移链**：

- 主进程版本链：`electron/services/migration.ts:21-26`（`settings: LATEST_VERSION = 2`），`:35-47`（`MIGRATIONS.settings` v0→1、v1→2）；
- 渲染层无版本启动探测链：`src/store/useSettingsStore.ts:91-217`（provider→profiles、tts/imageGen/vision 单字段→数组、authorNote 删除与回写三段）。

主计划 W10 要做 `maxTokens`/`maxContext` 的产品语义迁移。若两条链并存，新迁移该挂在哪条、版本号怎么算、幂等性由谁保证都无法确定。正确顺序是先收敛为单一链（`v2→v3`，renderer 只留兜底读取），主计划再在 `v3→v4` 上做语义迁移。

### 2.3 观测口径 × 主计划 G1/G2

G1/G2 的门槛（推理挤占失败率 < 0.5%、降档恢复成功率 ≥ 90%、P95 延迟增幅 < 5%、500 次有效生成）全部依赖观测口径与基线脚本。而 `scripts/generation-baseline.ts` 目前是**未跟踪脚本**，口径停留在 P50/P90 字符与触顶率，未覆盖 gate、上下文分层维度；S10 报告也指出应用侧观测当时仅有 5 条历史记录、缺 `responseIntent`/`sceneFactor` 字段样本。

这些指标需要自然使用积累，**不能靠单元测试造出来**。主计划自己写明了"任何排期都不得把'收集 500 次有效生成'伪装成可在单元测试中完成的开发任务"——所以口径必须在 W0 前定好并开始积累。

## 4. A 线：安全与发布门槛

这一线不与主计划共享文件，是独立的、可立即开工的一条线。

### 4.1 A1：修复 ZIP 恢复目录穿越（P0-A，双重确认）

**现状（已复核，完全未修）**：

- `electron/services/backup.ts:253-262` `idFromZipPath()` 先取 `basename`，非法路径段已被丢弃，返回值又被调用方丢弃；`chats/`、`groups/` 分支直接 `return id`（`:261`），连空校验都没有。
- 写入侧 5 处前缀分发全部使用朴素 `join`（`:299-316`，写盘 `:329-338`）。`characters/../../outside.json` 既能通过 `startsWith('characters/')`，拼接后也会逃出 `DIRS.characters()`。
- manifest 中无哈希的条目仅 `log.warn` 后 `continue`（`:242-244`），攻击者新增的恶意条目无需伪造哈希。
- 防护函数 `electron/utils/pathGuard.ts:23` `safePath()` 有实现、有单测（`pathGuard.test.ts:80-88`），但**生产调用点为 0**；全仓无任何 backup/restore 测试文件。

**攻击面**：需用户主动导入他人提供的 `.qingyu` 备份包；`electron/bridge/` 未暴露 restore 端点，不构成远程任意文件写或 RCE，但属本地任意路径写——对主打"纯本地存储"的客户端是发布级缺陷。

**改动**：

1. 还原循环每个目标路径统一走 `safePath(rootDir, ...segments)`，拒绝绝对路径、盘符、反斜杠变体、空路径、`.` 与 `..` 段；
2. 对最终 `resolve(dest)` 做根目录边界断言（二次防线，不依赖前置校验）；
3. ZIP 中每个非目录条目必须在 manifest 中有哈希记录，manifest 中的哈希条目也必须在 ZIP 中存在，否则整包拒绝；
4. 删除 `idFromZipPath` 中"重复调用仅为触发校验"的无效写法，或让它真正返回并参与校验。

**验收**：服务级测试覆盖 `characters`、`chats`、`groups`、图片与 Windows 路径变体（含报告实测的 `characters/../../../../../../QingYu-pwned.json`）；断言不产生目录外文件；恶意条目与缺失哈希条目均被拒。

### 4.2 A2：修复备份泄露凭据（P0-B，双重确认）

**现状（已复核，完全未修）**：

- `electron/services/backup.ts:38-43` `SECRET_COLLECTIONS` 只含 `connectionProfiles`/`ttsModels`/`imageGenModels`/`visionModels` 四类，`semanticTrigger.apiKey`（`shared/types.ts:848-862`）未纳入；`electron/ipc/settings.ts:39-45` 是另一份同样遗漏的 `stripSecrets`。
- `backup.ts:91` 将 `mcp-servers.json` 整体入包，无任何 `env` 脱敏；`src/pages/mcp/McpServerFormModal.tsx:107-108` 明确允许填入 `API_KEY=xxx`。
- 同时 `EXCLUDED_ITEMS`（`backup.ts:33`）与 `src/pages/SettingsPage.tsx:319` 仍向用户宣称"未包含：API Key / 凭据"。**错误的安全预期比缺陷本身更危险**——用户会放心把备份包发给他人排障。

**改动**：

1. `semanticTrigger.apiKey` 纳入安全存储与备份剥离流程；
2. MCP `env` 不得原样入包：按敏感键名规则（`KEY`/`TOKEN`/`SECRET`/`PASSWORD`）脱敏，或把 MCP 凭据迁入安全存储；
3. 同步修正 `SettingsPage.tsx` 与 manifest 的用户可见声明，改后与实际行为一致。

**验收**：写入测试凭据后导出，遍历压缩包全部条目，断言不存在明文密钥文本；manifest 与实际内容一致性测试。
