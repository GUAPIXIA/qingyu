# 空间画板与剧情位置系统独立开发方案

> 状态：✅ 独立开发阶段 0–5 已完成，阶段 6 评审材料已提交（待产品冻结范围后进入接入）
>
> 日期：2026-09-29
>
> 当前阶段：PC 接入前评审（只出方案，不写接入代码）
>
> 相关：[PC 接入前评审](./空间画板-PC接入前评审-阶段6.md) · [独立开发报告](../报告/空间画板独立开发报告-阶段0-5.md) · [PC 禁改清单](./空间画板-PC禁改清单-阶段0.md)
>
> 目标：用可视化画板描述区域、地点、层级、距离和角色位置，并以结构化数据驱动剧情中的角色移动；任何不具备图片识别能力的 LLM 也能完整理解。

## 1. 结论

本功能应当被定义为“空间语义编辑器”，而不是一张可绘制的图片。画板负责让用户直观编辑；世界事实由 JSON 数据负责表达。首期只允许用户创建两种空间节点：

1. `region`：矩形区域，用于省、市、县、小区、星球、国家、海域等有范围的空间。
2. `place`：地点图标，用于房屋、空地、商店、车站、遗迹等点状地点。

角色头像不是第三种空间节点，而是由已有角色或用户身份生成的 `actor` 标记。角色标记可由用户拖动，也可由后续剧情适配器提交结构化移动命令。

推荐使用 **React + TypeScript + `@xyflow/react`** 构建独立编辑器。React Flow 原生支持自定义节点、连接线、拖拽、缩放和父子节点；子节点可通过 `parentId` 与 `extent: 'parent'` 跟随父区域并被限制在其范围内，适合矩形区域嵌套。地点图标的内部空间不直接塞进小图标，而是通过“进入内部”打开子画板。官方参考：[Sub Flows](https://reactflow.dev/learn/layouting/sub-flows)、[Custom Nodes](https://reactflow.dev/learn/customization/custom-nodes)、[Custom Edges](https://reactflow.dev/learn/customization/custom-edges)。

本阶段必须保持以下隔离：

- 不给现有 PC 端增加路由、侧栏入口或功能开关。
- 不修改现有 `Character`、`ChatSession`、`ContextBuildData`、IPC 与同步契约。
- 不向轻语正式 `userData/data` 写入任何空间数据。
- 不把独立编辑器加入 PC 正式构建、安装包、备份或移动端同步范围。
- 先完成独立应用、数据契约、交互和模拟剧情移动；通过验收门后再制定接入实施稿。

## 2. 对需求图的正式解释

用户示意图可以拆成五类事实：

| 图中内容 | 正式领域概念 | 示例 |
|---|---|---|
| 大矩形 | `region` 节点 | XX 市、某小区、某星球 |
| 小房屋/地点图标 | `place` 节点 | 用户家、空地、酒馆 |
| 地点内部的 1 楼、2 楼、卧室、厕所 | 地点关联的子画板 | `用户家` → `住宅内部` 画板 |
| 两个相同图形之间的线 | `distance` 关系 | XX 市到 YY 市约 32 km |
| 用户或对话角色头像 | `actor placement` | 用户位于家中卧室，角色 A 位于市外 |

需要区分三种容易混淆的关系：

- **包含关系**：某地点或区域位于另一个区域内。例如“用户家位于 XX 市”。不需要画距离线。
- **内部结构**：某地点具有楼层、房间等内部空间。例如“用户家内部有 1 楼、2 楼、卧室”。通过子画板表达。
- **距离关系**：两个同类节点之间存在用户指定的语义距离。例如“XX 市与 YY 市相距约 32 km”。线条在屏幕上的长度不等于真实距离。

## 3. 产品目标与边界

### 3.1 MVP 目标

1. 新建、重命名、复制、删除画板。
2. 画板中只能创建 `region` 与 `place` 两类空间节点。
3. 用拖拽绘制矩形区域；用点击或拖放创建地点图标。
4. 编辑节点的名称、描述、标签和空间语义。
5. 区域可以嵌套区域或地点；地点可以关联一个子画板来描述内部空间。
6. 仅允许 `region ↔ region`、`place ↔ place` 创建距离线。
7. 距离线支持名称、描述、数值、单位、精度和备注。
8. 从角色托盘拖动用户或角色头像到画板，并显示其当前位置。
9. 用户拖动头像后，结构化位置状态立即更新。
10. 用模拟剧情命令自动移动头像，并保留移动历史。
11. 自动保存草稿，支持撤销、重做、JSON 导入与导出。
12. 生成确定性的 LLM 文本投影，不依赖截图或视觉模型。

### 3.2 本期不做

- 不接入现有 PC 端聊天页、角色页、侧栏或正式设置页。
- 不让 LLM 直接修改 Zustand 状态或画布节点数组。
- 不从自然语言中无条件猜测位置变化；不明确的移动不能静默落库。
- 不实现自由绘画、图片识别、地图瓦片、真实 GIS 经纬度或导航寻路。
- 不允许用户添加第三种空间图形；文字、头像、连接线都不是用户空间节点类型。
- 不实现多人实时协作、云同步或 Android 端。
- 不把画板截图作为存储事实，也不要求模型读取头像或图标像素。
- 不自动把线段像素长度换算成 km、AU 或光年。

### 3.3 后续可扩展但首期预留

- 节点可见性、阵营、危险等级、天气和临时封锁。
- 路线、门、传送、单向通道等非距离关系。
- 战斗站位或房间内更细的网格坐标。
- 多角色群聊位置、雾区和仅用户可见的信息。
- 世界书条目、角色卡和会话模板绑定。
- PC 与 Android 同步。

## 4. 核心设计原则

### 4.1 数据是唯一事实来源

画板渲染结果可以随主题、缩放和组件版本变化，但同一份 JSON 必须表达相同世界。所有关键事实都要有稳定字段：

- 节点 ID、类型、名称与描述；
- 父节点或子画板关系；
- 角色所在画板、锚点与相对位置；
- 距离两端、数值、单位和精度；
- 变更版本、来源和时间。

截图只可用于测试取证或分享预览，不参与运行时判断。

### 4.2 布局坐标不等于世界语义

节点在画板中的 `x/y/width/height` 只用于排版。LLM 理解空间时优先读取：

1. 父子包含路径；
2. 角色锚定节点；
3. 用户填写的相对方位；
4. 显式距离关系；
5. 最后才是画布布局坐标推导出的粗略方向。

因此，用户把两个城市画得很近，并不自动代表两城距离很短。只有距离关系中的值才是距离事实。

### 4.3 定义与运行状态分离

同一张世界地图可以被多个会话复用，但不同剧情中的角色位置不同。必须分成：

- `WorldDefinition`：画板、区域、地点和距离，属于相对稳定的世界定义。
- `WorldRuntimeState`：某个会话中的角色位置与移动历史，属于剧情状态。

不得把当前角色位置写进静态节点，也不得为每次移动复制整张地图。

### 4.4 所有变更都通过命令进入核心

手动拖拽、撤销重做、剧情自动移动和导入迁移，最终都转换为同一套 `SpatialCommand`，再由纯函数 reducer 校验并生成新状态。UI 和 LLM 不能绕过命令层直接写数据。

### 4.5 不确定时保持原位

“角色望向城外”“想回家”“谈到了卧室”都不等于已经移动。自动移动只接受明确的动作完成事实。无法唯一定位时：

- `off`：忽略自动移动；
- `suggest`：生成待确认建议；
- `auto`：仅对高置信且目标 ID 唯一的命令自动应用。

默认使用 `suggest`，而不是 `auto`。

## 5. 空间层级模型

### 5.1 画板、节点和子画板

每个 `board` 是独立坐标空间。根画板可表示世界、国家或星系；节点可按需进入更细一级。

```text
世界定义
└── 根画板：大陆
    ├── 区域：XX 市
    │   ├── 地点：用户家 ──> 子画板：用户家内部
    │   │                   ├── 区域：1 楼
    │   │                   │   ├── 地点：卧室
    │   │                   │   └── 地点：厕所
    │   │                   └── 区域：2 楼
    │   └── 地点：中央广场
    └── 区域：YY 市
```

同一画板内：

- `region` 可作为父节点，包含其他区域或地点。
- `place` 不能用自身小图标作为可见容器；需要内部结构时创建 `childBoardId`。
- `region` 也可关联子画板，用于从省级画板进入城市细节。
- 一个节点最多关联一个直接子画板；更深层级继续递归。

### 5.2 节点类型

```ts
type SpatialNodeKind = 'region' | 'place'

interface SpatialNodeBase {
  id: string
  boardId: string
  kind: SpatialNodeKind
  name: string
  description: string
  tags: string[]
  parentNodeId: string | null
  childBoardId: string | null
  createdAt: number
  updatedAt: number
}

interface RegionNode extends SpatialNodeBase {
  kind: 'region'
  geometry: {
    x: number
    y: number
    width: number
    height: number
  }
  regionCategory: 'administrative' | 'settlement' | 'building-area' | 'natural' | 'celestial' | 'custom'
  categoryLabel?: string
}

interface PlaceNode extends SpatialNodeBase {
  kind: 'place'
  geometry: {
    x: number
    y: number
  }
  placeCategory: 'building' | 'open-space' | 'facility' | 'landmark' | 'celestial-object' | 'custom'
  categoryLabel?: string
  iconKey: string
}

type SpatialNode = RegionNode | PlaceNode
```

`geometry` 直接使用 React Flow 的画布坐标（flow units），与窗口像素和当前缩放无关。坐标允许为负数或超出初始参考视区，因此画布没有固定边界；导入时只拒绝非有限数值及非正区域宽高。

### 5.3 画板类型

```ts
interface SpatialBoard {
  id: string
  name: string
  description: string
  parentEntryNodeId: string | null
  coordinateConvention: {
    north: 'up'
    origin: 'top-left'
    units: 'canvas'
  }
  viewportHint?: {
    x: number
    y: number
    zoom: number
  }
}
```

`viewportHint` 只保存用户上次查看位置，不属于世界事实，LLM 投影时忽略。

## 6. 距离关系设计

### 6.1 约束

首期仅允许：

- `region` 到 `region`；
- `place` 到 `place`；
- 两端必须位于同一画板；
- 不能连接自身；
- 默认同一对节点只能有一条距离关系；
- 关系默认为无方向，交换起终点不产生新关系。

跨类型或跨画板距离在 MVP 中拒绝，并给出明确提示。包含关系不使用距离线。

### 6.2 数据结构

```ts
type DistanceUnit = 'm' | 'km' | 'au' | 'ly' | 'custom'

interface DistanceRelation {
  id: string
  kind: 'distance'
  boardId: string
  sourceNodeId: string
  targetNodeId: string
  name: string
  description: string
  measurement: {
    value: number | null
    unit: DistanceUnit
    customUnit?: string
    displayText: string
    certainty: 'exact' | 'estimated' | 'unknown'
  }
  travelNotes?: string
  createdAt: number
  updatedAt: number
}
```

`value + unit` 供计算与排序，`displayText` 保留“约两天马程”“视天气而定”等叙事表达。二者冲突时数据校验应提醒用户，不自行覆盖。

## 7. 角色头像与剧情位置

### 7.1 Actor 不是第三种空间图形

```ts
type ActorKind = 'persona' | 'character'

interface SpatialActor {
  id: string
  kind: ActorKind
  externalRef: {
    type: 'qingyu-persona' | 'qingyu-character' | 'standalone'
    id: string
  }
  displayName: string
  description?: string
  avatarAssetRef?: string
}
```

`avatarAssetRef` 只用于 UI 装饰。LLM 依赖 `id`、`displayName` 和 `description`，即使图片缺失仍能理解全部信息。

### 7.2 位置结构

```ts
interface ActorPlacement {
  actorId: string
  boardId: string
  anchor: {
    kind: 'board' | 'node'
    nodeId?: string
  }
  position: {
    x: number
    y: number
  }
  semanticPosition: {
    containmentPath: string[]
    relativeToNodeId?: string
    relativeDirection?: 'north' | 'north-east' | 'east' | 'south-east' | 'south' | 'south-west' | 'west' | 'north-west' | 'center' | 'inside' | 'nearby'
    precision: 'exact' | 'approximate' | 'inside-only' | 'unknown'
    note?: string
  }
  revision: number
  updatedAt: number
  updatedBy: 'user' | 'story' | 'import' | 'system'
}
```

拖动角色头像时：

1. 命中地点图标：锚定该地点，语义为 `inside` 或 `nearby`，由落点区域和用户选择确定。
2. 命中矩形区域：锚定区域，并保存当前画布坐标。
3. 命中空白画板：锚定画板，只保存粗略位置。
4. 拖到子画板入口：弹出“进入内部”操作，不靠像素碰撞自动跨画板。
5. 拖动完成才提交命令；拖动过程只更新临时预览，避免每帧写历史。

### 7.3 祖先画板上的显示

角色位于“用户家内部 → 1 楼 → 卧室”时：

- 在当前内部画板显示头像的准确位置；
- 在城市画板的“用户家”图标显示小型人数徽标或角色缩略标记；
- LLM 获得完整包含路径；
- 不为祖先画板复制多个角色位置记录。

## 8. 世界定义、运行状态与事件日志

### 8.1 顶层文档

```ts
interface SpatialWorldDocumentV1 {

  name: string

```

### 8.2 命令协议

```ts
type SpatialCommand =
  | { type: 'create_node'; payload: SpatialNode }
  | { type: 'update_node'; nodeId: string; patch: SpatialNodePatch }
  | { type: 'delete_node'; nodeId: string; strategy: 'reject-if-not-empty' | 'cascade' }
  | { type: 'create_distance'; payload: DistanceRelation }
  | { type: 'update_distance'; relationId: string; patch: DistanceRelationPatch }
  | { type: 'delete_distance'; relationId: string }
  | { type: 'place_actor'; actorId: string; placement: ActorPlacementInput }
  | { type: 'move_actor'; actorId: string; from?: PlacementGuard; to: ActorPlacementInput; reason?: string }
  | { type: 'remove_actor_from_board'; actorId: string }
```

所有运行时命令携带 `expectedRevision`。版本不一致时返回冲突，不覆盖较新的用户拖动结果。

### 8.3 事件日志

```ts
interface SpatialEvent {
  id: string
  runtimeId: string
  revision: number
  commandType: SpatialCommand['type']
  actorId?: string
  before?: ActorPlacement | null
  after?: ActorPlacement | null
  source: 'user' | 'story' | 'import' | 'system'
  reason?: string
  messageId?: string
  createdAt: number
}
```

事件日志用于审计、剧情回看和故障恢复。MVP 不要求完全事件溯源：当前状态仍直接存储，事件只是追加的变更记录。为控制体积，可保留最近 500 条，超出后生成快照并归档旧事件。

## 9. LLM 可理解的数据投影

### 9.1 两种输出

系统同时提供：

1. **完整 JSON**：用于保存、导入、迁移、工具调用和测试。
2. **紧凑文本投影**：用于普通聊天模型上下文，避免把全部布局细节塞入提示词。

文本投影必须由确定性函数从 JSON 生成，不让另一个 LLM先总结地图。

### 9.2 完整 JSON 示例

```json
{
  "schemaVersion": 1,
  "id": "world_demo",
  "name": "示例世界",
  "rootBoardId": "board_world",

      "name": "世界",
      "parentEntryNodeId": null,
      "coordinateConvention": { "north": "up", "origin": "top-left", "units": "canvas" }

    {
      "id": "board_home",
      "name": "用户家内部",

      "boardId": "board_world",

      "tags": ["城市"],

```

正式 schema 中仍须包含 `createdAt/updatedAt` 等必填字段；示例为阅读方便省略部分字段。

### 9.3 紧凑文本示例

```text
[空间状态 v1]
世界：示例世界（world_demo）
当前视角：世界 > XX 市 > 用户家 > 1 楼

区域：
- XX 市 [region_city_x]：用户家所在的城市。

地点：
- 用户家 [place_home]，位于 XX 市，拥有内部画板：用户家内部。

角色位置：
- 用户 [actor_user]：用户家 > 1 楼 > 卧室；精度=inside-only。
- 林雪 [actor_lin_xue]：YY 市；精度=approximate。

已知距离：
- XX 市 [region_city_x] ↔ YY 市 [region_city_y]：约 32 km；估算。
```

默认只投影以下内容：

- 当前角色所在路径及其直接兄弟节点；
- 当前场景中的其他角色；
- 与当前节点直接相关的距离；
- 最近一次位置变化；
- 用户或剧情明确查询时再展开完整地图。

这样可控制 token 用量，并避免布局坐标干扰叙事。

## 10. 剧情驱动自动移动

### 10.1 核心与模型解耦

空间核心只接收 `SpatialCommand[]`，不知道命令来自哪家模型。未来接入层按模型能力选择：

1. 支持工具调用：模型调用 `move_actor` 工具。
2. 支持可靠结构化输出：在正文外返回 JSON sidecar。
3. 普通文本模型：回复完成后用独立提取请求生成 JSON；失败不影响正文。
4. 无法可靠结构化：仅提供手动拖动和移动建议。

不可让模型返回 React Flow 的 `nodes/edges`。剧情命令应优先给语义锚点；确需布局落点时可给画布坐标，但不能使用受窗口和缩放影响的屏幕像素。

### 10.2 模型命令示例

```json
{
  "schemaVersion": 1,
  "expectedRevision": 17,
  "commands": [
    {
      "type": "move_actor",
      "actorId": "actor_lin_xue",
      "from": { "nodeId": "place_square" },
      "to": {
        "boardId": "board_home",
        "anchor": { "kind": "node", "nodeId": "place_bedroom" },
        "semanticPosition": {
          "precision": "inside-only",
          "relativeDirection": "inside",
          "note": "角色已跟随用户进入卧室"
        }
      },
      "reason": "assistant_message_explicit_arrival"
    }
  ]
}
```

### 10.3 校验顺序

1. JSON schema 正确。
2. `worldId/runtimeId/revision` 匹配。
3. actor、board、node ID 存在。
4. 目标节点属于目标画板。
5. 包含路径可从世界定义重新计算，不能信任模型自行提交的路径。
6. 来源消息确实完成移动，而不是计划、回忆、否定或假设。
7. 策略允许自动应用；否则进入待确认队列。
8. reducer 原子提交状态和事件。

### 10.4 自动移动策略

| 模式 | 行为 | 建议用途 |
|---|---|---|
| `off` | 不解析、不移动 | 用户完全手动管理 |
| `suggest` | 解析后显示“是否移动到卧室” | MVP 默认，最安全 |
| `auto` | 高置信命令直接执行，失败保持原位 | 稳定后可选 |

以下情况一律不自动执行：

- 目标名称对应多个节点；
- 目标不存在；
- 模型想创建新地图节点；
- 使用“可能、准备、想要、如果”等未完成语气；
- 目标与当前世界定义冲突；
- revision 已变化；
- 同一回复包含互相冲突的移动结果。

## 11. 独立编辑器交互设计

### 11.1 页面布局

```text
┌──────────────────────────────────────────────────────────────────┐
│ 世界名 | 面包屑：世界 / XX市 / 用户家 | 撤销 重做 导入 导出 保存 │
├──────────────┬───────────────────────────────────┬───────────────┤
│ 工具与角色托盘 │                                   │ 属性检查器      │
│              │              画板                  │ 名称            │
│ ▭ 矩形区域    │                                   │ 描述            │
│ ◉ 地点        │                                   │ 类型/标签       │
│ ─ 距离模式    │                                   │ 距离/单位       │
│              │                                   │ 子画板          │
│ 用户头像      │                                   │ 位置历史        │
│ 角色头像      │                                   │                 │
├──────────────┴───────────────────────────────────┴───────────────┤
│ 状态：已保存 | 当前层级 | 选中对象 | 缩放比例 | 校验问题数量       │
└──────────────────────────────────────────────────────────────────┘
```

左侧只有两个空间创建工具；“距离模式”和角色托盘是操作工具，不违反“两种用户可添加图标”的产品约束。

### 11.2 基本操作

- 选择“矩形区域”后在画板拖出矩形，松开后立即填写名称。
- 选择“地点”后单击空白处创建，或从工具栏拖到目标区域。
- 拖动节点进入矩形区域时高亮候选父区域；松开后更新 `parentNodeId`。
- 将有子节点的区域拖出父区域时先确认是否变更包含关系。
- 双击有 `childBoardId` 的节点进入子画板；顶部面包屑返回上级。
- 选中地点后点击“创建内部画板”，再在内部使用同样的两类节点。
- 进入“距离模式”后依次点击两个同类节点，随后打开距离编辑框。
- 不同类型的第二个节点显示禁用提示，不创建半成品关系。
- 从角色托盘拖入头像；画板已存在该角色时改为移动，而不是重复添加。
- `Delete` 删除选中项，`Ctrl+Z/Ctrl+Y` 撤销重做，`Space + 拖动` 平移画布。

### 11.3 属性检查器

区域：

- 名称（必填）；
- 描述；
- 区域分类与自定义分类；
- 标签；
- 父区域；
- 子画板入口；
- 几何数值和“适应内容”。

地点：

- 名称（必填）；
- 描述；
- 地点分类；
- 图标主题 `iconKey`；
- 所属区域；
- 内部画板；
- 标签。

距离：

- 关系名称；
- 描述；
- 数值；
- 单位；
- 精确/估算/未知；
- 显示文本；
- 旅行备注。

角色：

- 当前完整路径；
- 相对方位与精度；
- 位置备注；
- 最近移动来源与原因；
- 移除出画板。

### 11.4 删除规则

- 删除有子节点或子画板的节点时，默认拒绝并展示影响范围。
- 用户明确选择“级联删除”后才删除后代、相关距离和入口关系。
- 删除 actor 定义与“从当前画板移除”分开，避免误删角色。
- 删除画板前检查入口节点与角色位置。
- 所有删除都必须可撤销；导出保存后仍依赖事件/备份恢复，不承诺跨会话无限撤销。

## 12. 独立开发架构

### 12.1 目录建议

本阶段在仓库中建立独立根目录，推荐名称：

```text
spatial-board/
├── package.json                 # 独立依赖和脚本
├── index.html
├── vite.config.ts               # 独立端口，例如 5188
├── tsconfig.json
├── src/
│   ├── app/                     # 页面组合与路由
│   ├── core/                    # 纯 TypeScript 领域核心
│   │   ├── model.ts
│   │   ├── commands.ts
│   │   ├── reducer.ts
│   │   ├── validation.ts
│   │   ├── hierarchy.ts
│   │   ├── projection.ts
│   │   └── migrations.ts
│   ├── canvas/                  # React Flow 适配
│   ├── components/
│   ├── store/                   # 独立 Zustand store
│   ├── persistence/             # IndexedDB / file adapter
│   └── story-adapter/           # 模拟剧情命令，首期不连接正式 AI
├── schemas/
│   ├── spatial-world-v1.schema.json
│   ├── spatial-runtime-v1.schema.json
│   └── spatial-command-v1.schema.json
├── fixtures/
│   ├── city-home.json
│   ├── planet-system.json
│   └── invalid/
└── tests/
```

不得从该目录反向 import `src/`、`electron/` 或渲染层 store。可以复制必要的主题色，但不要直接依赖 PC 内部组件。

### 12.2 分层

```text
React Flow UI
    │ 只发出意图
    ▼
独立 Zustand Store
    │ 生成 SpatialCommand
    ▼
Spatial Core：校验 → reducer → projection
    │
    ├── Browser Repository：独立开发期 IndexedDB 草稿
    ├── JSON Import/Export：可移植文件
    └── Story Adapter：模拟或解析剧情命令
```

核心层必须不依赖 React、React Flow、Electron、DOM 或文件系统，未来可以直接被 PC 主进程、渲染进程和测试复用。

### 12.3 技术选型

| 能力 | 选择 | 原因 |
|---|---|---|
| UI | React + TypeScript | 与 PC 技术栈一致，后续迁移成本低 |
| 画板 | `@xyflow/react` | 自定义节点/边、缩放、拖动、父子节点与可视区优化成熟 |
| 状态 | Zustand | 与现有项目一致，但使用独立 store |
| 校验 | JSON Schema + Ajv | 导入文件、模型命令和迁移均可运行时校验 |
| ID | `nanoid` | 无需中央序列，现有项目已使用 |
| 单测 | Vitest + Testing Library | 与现有工具链一致 |
| E2E | Playwright | 验证真实拖拽、缩放、连接和导入导出 |
| 草稿存储 | IndexedDB adapter | 浏览器独立运行，不接触 Electron 正式数据 |

React Flow 自带的是交互与渲染能力，不是领域模型。禁止直接把其原生 `Node[]/Edge[]` 当成持久化格式；必须通过 canvas adapter 在 React Flow 类型与领域类型之间转换。

### 12.4 仓储接口

```ts
interface SpatialRepository {
  loadWorld(worldId: string): Promise<SpatialWorldDocumentV1 | null>
  saveWorld(world: SpatialWorldDocumentV1, expectedUpdatedAt?: number): Promise<void>
  loadRuntime(runtimeId: string): Promise<SpatialRuntimeStateV1 | null>
  saveRuntime(state: SpatialRuntimeStateV1, expectedRevision: number): Promise<void>
  listWorlds(): Promise<Array<{ id: string; name: string; updatedAt: number }>>
  deleteWorld(worldId: string): Promise<void>
}
```

独立期实现 `IndexedDbSpatialRepository` 与 `InMemorySpatialRepository`。未来 PC 接入时新增 Electron repository，而不是改写核心和 UI 行为。

## 13. 保存、导入、导出与迁移

### 13.1 保存策略

- UI 修改先进入内存状态。
- 500 ms 无新操作后自动保存草稿。
- 窗口失焦或关闭前尝试刷新待保存操作。
- 顶部持续显示“已保存 / 保存中 / 保存失败”。
- 保存失败不得清空内存状态；提供重试和导出 JSON。
- 世界定义与剧情状态分别保存，避免移动角色导致整张大地图反复写入。

### 13.2 导出包

MVP 可先导出两个 JSON：

```text
my-world.world.json
my-world.runtime.json
```

后续需要打包图标或自定义头像时再引入 ZIP manifest。内置图标只保存 `iconKey`，不复制图片。

### 13.3 导入校验

- 最大文件大小建议 5 MiB；超限明确拒绝。
- 最大画板数 200、节点数 5,000、关系数 10,000、层级深度 20。
- 所有 ID 必须唯一且符合长度限制。
- 拒绝循环父子关系、悬空引用、跨画板父节点和非法距离端点。
- 文本字段设长度上限并按纯文本渲染，禁止把描述作为 HTML 注入。
- 先完整校验到临时内存，通过后再替换当前草稿。
- 导入旧版本时先迁移到新版本，再执行完整校验。

### 13.4 版本策略

- 顶层 `schemaVersion` 为整数。
- 只提供逐版本迁移：`v1 -> v2 -> v3`，不写任意版本直达逻辑。
- 未知高版本只读预览或拒绝，不降级覆盖原文件。
- 为每个版本保留 canonical fixture 和迁移 golden test。

## 14. 撤销、重做与并发

- 撤销栈保存领域命令及其逆命令，不保存每次鼠标移动帧。
- 节点拖动、缩放从 pointer down 到 pointer up 合并为一个历史操作。
- 编辑描述的连续输入按 800 ms 合并。
- 自动剧情命令作为单独事务，可整体撤销。
- 导入整个世界前创建快照；导入视为一个可撤销操作。
- 每次运行状态写入使用 `revision` 乐观并发控制。
- 当剧情提取正在运行而用户手动拖动角色时，旧 `expectedRevision` 的剧情命令应失败并转成待确认建议。

## 15. 校验规则清单

### 15.1 世界定义

- 根画板存在且只有一个。
- board 的 `parentEntryNodeId` 与 node 的 `childBoardId` 双向一致。
- `parentNodeId` 只能指向同一画板内的 `region`。
- 任意节点不能成为自己的祖先。
- 节点名称去除首尾空白后不能为空。
- 同一父级允许同名但显示警告；ID 永远不能重复。
- region 的坐标与宽高必须有限，宽高必须大于最小值。
- place 坐标必须是有限画布坐标，可为负数或超出初始参考视区。
- 子节点几何必须位于父 region 范围内，或由修复操作显式重新定位。

### 15.2 距离

- 两端存在、同画板、同类型且不同 ID。
- 数值若存在必须有限且不小于 0。
- `custom` 单位必须有 `customUnit`。
- 无数值时 `displayText` 必填。
- 同一无向节点对不重复。

### 15.3 角色位置

- 一个 runtime 中每个 actor 最多一个当前位置。
- node 锚点必须属于 placement 的 board。
- `containmentPath` 不接受外部输入，提交时由核心重算。
- 角色进入子画板后祖先入口必须可追溯。
- 删除被角色占用的节点前必须迁移角色或明确级联移出。

## 16. 性能与可用性目标

MVP 验收基线：

- 单画板 300 个节点、500 条距离线时拖动保持可用，交互目标约 30 FPS 以上。
- 世界总计 5,000 节点时导入、校验和生成文本投影不阻塞超过 1 秒；达不到时移入 Worker。
- 开启 React Flow 的可视元素渲染优化，只渲染视口内节点。
- 拖动期间不触发磁盘写入、全量 schema 校验或 LLM 投影。
- 节点组件使用稳定 selector，属性面板修改一个节点不应让全部节点重渲染。
- 画板支持 25%–200% 缩放、适应内容、小地图开关和“定位当前角色”。

可用性：

- 所有图标按钮带文字或 tooltip。
- 选中状态不能只靠颜色。
- 区域和地点有固定外形差异。
- 提供键盘删除、撤销、重做、复制和缩放。
- 属性表单有明确错误提示，不在保存时才一次性报错。
- 深层画板始终显示面包屑，避免用户不知道当前位置。

## 17. 测试方案

### 17.1 领域单元测试

1. 创建、更新、移动、删除节点。
2. 父子包含与循环检测。
3. 地点子画板双向引用。
4. 同类距离允许、跨类型距离拒绝。
5. 距离去重和无向规范化。
6. actor 放置、移动、跨画板与祖先投影。
7. revision 冲突。
8. 命令原子性：一批命令中任一失败则整批不提交。
9. undo/redo 逆命令。
10. 文本投影稳定性与 token 裁剪顺序。
11. v1 JSON schema 正反例。
12. 导入限制、悬空引用、循环与恶意深度。

### 17.2 组件测试

- 创建两类节点后属性面板同步。
- 拖地点进入区域并更新父节点。
- 不同类型连接时显示禁用原因。
- 创建并编辑距离标签。
- 从角色托盘拖动头像并更新语义位置。
- 子画板面包屑进入和返回。
- 保存失败提示和导出兜底。

### 17.3 E2E 关键旅程

1. 新建世界 → 画 XX 市/YY 市 → 创建距离 → 导出 → 清空 → 导入后完全一致。
2. 在 XX 市创建用户家 → 创建内部画板 → 添加 1 楼/2 楼/卧室 → 将用户头像拖入卧室。
3. 提交模拟剧情命令 → 角色头像移动 → 事件日志记录 → 撤销恢复。
4. 用户手动移动后提交旧 revision 剧情命令 → 命令被拒绝并进入建议。
5. 导入循环层级、悬空 actor、跨类型距离 → 文件被拒绝且当前数据不变。

### 17.4 Golden fixtures

至少维护：

- 城市—住宅—楼层—房间；
- 星系—星球—基地；
- 多角色分处不同层级；
- 估算距离和自定义单位；
- 20 层最大合法深度；
- 每类非法引用样本。

## 18. 分阶段实施计划

### 阶段 0：冻结契约与独立边界（1–2 人日）

交付：

- 目录与依赖边界检查；

### 阶段 1：纯领域核心（3–5 人日）

- 层级、距离和 actor 校验；

- undo/redo 核心；

### 阶段 3：子画板与角色位置（4–6 人日）

- 语义位置编辑；
- 移动历史；

### 阶段 4：剧情命令模拟与安全应用（4–6 人日）

- `off/suggest/auto` 策略；
- revision 冲突；
- 批量命令原子应用；

退出标准：关键旅程 3、4 可重复通过；不连接真实 LLM 也能验证全部状态机。

### 阶段 5：质量收口（3–5 人日）

交付：

- E2E、性能基线、键盘与可访问性；
- 大文件/深层级/恶意 JSON 限制；
- 崩溃恢复和保存失败兜底；
- 独立开发报告与已知限制。

退出标准：全部 P0/P1 缺陷关闭，数据往返不丢字段，5 个关键旅程通过。

### 阶段 6：PC 接入前评审（2–3 人日，只产出方案）

此阶段仍不接入 PC，仅提交评审材料：

- 数据域归属；
- IPC 和 repository 设计；
- 备份与同步影响；
- 上下文 token 预算；
- 角色/身份引用策略；

独立功能完整交付约 20–34 人日。单人开发建议按 5–7 周安排，先在第 2 周得到可操作画板，在第 4 周得到可验证的剧情移动闭环。

## 19. 未来接入轻语 PC 端的接口点

### 19.1 建议数据目录

```text
└── runtimes/<sessionId>.json
```

世界定义可以跨会话复用；runtime 按会话隔离。实际接入时必须使用现有原子写入与数据域仓储，不由渲染层直接访问文件系统。

### 19.2 建议可选字段

```ts
interface ChatSession {
  spatialWorldId?: string | null
  spatialRuntimeId?: string | null
}

interface ContextBuildData {
  spatial?: {
    worldId: string
    runtimeId: string
    compactContext: string
    revision: number
  }
}
```

字段保持可选，旧角色和旧会话行为不变。不得把整个 5,000 节点地图无条件塞进每轮上下文。

### 19.3 上下文接入

- 空间上下文由 `projection.ts` 生成，进入统一 context builder。
- 当前路径和角色位置属于“当前状态”，优先级高于一般世界书背景。
- 完整地图按查询或相关性按需展开。
- 模型移动命令在正文落盘后独立处理；移动失败不得撤销已经生成的对话正文。
- `messageId` 写入 SpatialEvent，支持从位置变化回溯到剧情消息。

### 19.4 备份、同步与删除

- PC 接入时空间数据必须成为明确的新数据域。
- 备份清单、恢复事务、同步 schema、冲突策略和删除墓碑必须同时设计。
- 未完成 Android 契约前不加入移动端同步白名单。
- 删除角色时不能直接删除世界；只处理 actor 外部引用并提供修复提示。
- 删除会话时 runtime 是否随会话删除必须由产品决策冻结，默认放入可恢复回收区。

## 20. 风险与应对

| 风险 | 后果 | 应对 |
|---|---|---|
| 把 React Flow 节点直接当领域数据 | 库升级或 UI 变化破坏文件兼容 | 单独领域模型 + adapter |
| 像素距离被误解为真实距离 | LLM 得出错误空间结论 | 明确 distance 关系才是真实距离 |
| 地点内部内容塞进小图标 | 交互拥挤、层级不可读 | 地点关联子画板 |
| 自动解析剧情过度移动 | 位置与正文冲突 | 默认 suggest，高置信/唯一目标才 auto |
| LLM 用名称而非 ID 修改 | 同名地点误移动 | 上下文携带 ID，命令只接受 ID |
| 大地图全量注入 | token 爆炸 | 确定性相关子图投影 |
| 删除父节点造成悬空引用 | 数据损坏 | 拒绝或显式级联事务 |
| 剧情移动覆盖用户拖动 | 用户修改丢失 | revision 乐观锁 |
| 独立原型与 PC 代码耦合 | 未上线功能污染正式包 | 独立入口、依赖、store、repository |
| 头像文件失效 | UI 缺图且模型误识别 | actor 语义不依赖图片，提供占位头像 |

## 21. 验收标准

### 21.1 功能验收

- 用户只能创建矩形区域和地点两类空间节点。
- 能复现需求图中的城市、用户家、另一城市、距离和用户头像。
- 用户家能进入独立内部画板并创建楼层、卧室、厕所。
- 只允许同类节点创建距离。
- 任意节点和距离均可命名、描述并完整导出。
- 角色头像可拖动，模拟剧情命令可自动移动。
- 子画板中的角色能在祖先画板正确显示汇总状态。

### 21.2 数据验收

- 清空浏览器后从导出 JSON 导入，世界定义与剧情状态一致。
- 缺失全部头像图片时，JSON 和文本投影仍能完整说明空间状态。
- JSON 中没有依赖截图识别才能理解的事实。
- 所有引用通过 schema 与领域校验，无悬空 ID 和循环层级。
- 相同数据重复生成紧凑文本得到字节级一致结果。

### 21.3 隔离验收

- 现有 `src/App.tsx`、`Sidebar.tsx` 没有新入口。
- 现有 PC `package.json` 正式 build 不构建独立应用。
- 现有 Electron IPC、preload 与正式数据目录无空间功能改动。
- PC 端 `pnpm check`、`pnpm test`、`pnpm build` 行为不因独立应用而改变。
- 独立应用可以单独启动、测试和构建。

### 21.4 进入 PC 接入阶段的门槛

以下条件全部满足才允许写接入代码：

1. 数据契约冻结并拥有迁移测试。
2. 五个 E2E 旅程稳定通过。
3. 300 节点/500 边性能基线通过。
4. 自动移动默认建议模式无静默错误。
5. 独立 JSON 往返无字段丢失。
6. 完成 PC 数据域、备份、同步和上下文预算评审。
7. 明确第一版是仅单聊、同时支持群聊，还是只提供手动画板；不得在实现中临时决定。

## 22. 推荐的第一批开发任务

按可验证价值排序：

1. 写 `spatial-world-v1.schema.json`、`spatial-runtime-v1.schema.json`、`spatial-command-v1.schema.json`。
2. 用纯 JSON 完整表达需求示意图，作为第一个 golden fixture。
3. 完成 hierarchy、distance、placement 三个校验器。
4. 完成 command reducer 和 revision 冲突测试。
5. 完成紧凑文本投影，先证明无视觉模型也能理解。
6. 再搭建 React Flow 独立画板，避免 UI 反过来绑架数据模型。
7. 最后实现剧情命令模拟器；真实 LLM 接入留到 PC 接入评审之后。

这一路径可以最早发现数据模型问题，也确保即使视觉编辑器重做，已验证的世界数据和剧情位置核心仍可复用。
