# 角色卡三视图图生图扩展规划与实施方案

> 状态：规划稿
>
> 日期：2026-09-12
>
> 目标版本：PC 端 MVP，ComfyUI 优先
>
> 修订说明：Qwen 2511 作为首个验收模板，底层改为可扩展的图片入口适配器，以兼容其他图生图工作流。
>
> 评审修订（2026-09-12）：明确 MVP 仅启用 `none`/`front-only` 转换；三视图保留原始扩展名落盘；生图设置禁止进入移动端同步白名单；补充 `--ref` 与角色卡策略优先级；补充 GGUF 前置检查。

## 1. 结论

在现有 `/imagine` 文生图链路上增加一条“角色参考图生图”分支：角色卡可以绑定正面、侧面、背面三张视觉参考图；生成含该角色的图片时，应用自动选择专用的 ComfyUI 图生图工作流，把三张参考图与原有文字提示词一起提交。没有三视图、生成环境空镜或用户主动关闭参考图时，继续走当前文生图流程。

首个官方适配与验收工作流采用 **Qwen-Image-Edit-2511 + `TextEncodeQwenImageEditPlus`**。该原生节点提供 `image1`、`image2`、`image3` 三个独立输入，天然对应正面、侧面、背面；不需要先把三张图片拼成一张联系表，也不需要在应用内训练角色 LoRA。

底层能力不绑定 Qwen、模型名称或固定节点 ID。应用保存的是“角色视图 → 工作流图片入口 → 注入策略”的声明式绑定；标准 `LoadImage`、IP-Adapter、InstantID、PuLID、FLUX Kontext 等工作流只要能暴露可写图片入口，均可通过内置适配器或后续扩展的节点适配器接入。

```text
角色卡三视图 ──┐
               ├─> 角色参考工作流 ─> ComfyUI ─> 新场景角色图
剧情/用户提示词 ┘

无三视图 / 环境空镜 / --ref off
               └─> 现有文生图工作流 ─> 原有生成结果
```

## 2. 产品目标与边界

### 2.1 本期目标

1. 每张角色卡可分别上传、预览、更换和删除正面、侧面、背面参考图。
2. 三视图以角色资产保存，不把大体积 base64 写入角色 JSON。
3. ComfyUI 配置可以区分“普通文生图”和“角色参考图生图”两种用途。
4. 图生图工作流导入后可识别并绑定图片资产入口，而不是硬编码 Qwen 或固定节点 ID。
5. `/imagine` 保留原有提示词生成能力，并在满足条件时自动带入当前角色的三视图。
6. 参考图上传、工作流执行和输出下载均复用现有 ComfyUI 地址与鉴权配置。
7. 原有角色、角色卡导入导出、文生图配置和不含人物的生成行为保持兼容。
8. 首版支持基于标准 `LoadImage` 的三入口和仅正面单入口；底层契约同时为工作流内批次、联系表和自定义节点适配预留扩展点。

### 2.2 本期不做

- 不训练角色 LoRA，也不引入训练任务管理。
- 不做人脸替换、视频生成、群聊多角色同画面。
- 不让用户在每次 `/imagine` 时临时选择任意本地文件。
- 不把三张原图塞进标准 SillyTavern PNG/JSON 角色卡；标准格式没有可靠的多图资产约定。
- MVP 不自动识别一张“三视图联系表”并裁成三张。后续可增加带裁剪确认的一键拆分，不能直接按三等分静默裁切。
- MVP 不承诺“任意自定义节点零配置可用”。无法从 API 工作流和 `/object_info` 判断文件字段语义的节点，必须增加显式适配器。
- MVP 不实现 `contact-sheet-horizontal` 合成。该转换只进类型契约（阶段 B），实际启用在第二阶段，随主进程图像处理能力一并交付。

## 3. 现状与缺口

当前代码已经完成了较好的 ComfyUI 工作流基础设施，但运行通道仍是纯文字：

| 现状 | 对本功能的影响 |
|---|---|
| `Character` 只有 `avatar` 与 `cover` 图片字段 | 没有正面、侧面、背面资产模型 |
| 头像和封面已采用文件落盘，角色 JSON 不存 base64（`chatBackground` 是现存例外，仍以 base64 data URL 存于角色 JSON，属既有债务） | 三视图应沿用文件落盘策略，不得效仿 `chatBackground` |
| `ImageGenOptions` 只包含负面词、尺寸、质量 | 渲染层无法声明要使用哪个角色的参考图 |
| `customComfyWorkflow` 只注入提示词、种子和参数覆盖 | 不会把图片上传至 ComfyUI，也不会改写 `LoadImage` |
| 分析器能把含 `LoadImage` 的工作流识别为 `image-to-image` | 已具备发现入口的基础，但没有图片角色绑定，也不识别其他资产入口节点 |
| `compatible` 只允许 `text-to-image` | 图生图工作流目前永远不能成为可执行生图配置 |
| 设置中只有一个 `activeImageGenModelId` | 普通文生图与角色图生图无法并存并自动切换 |
| `/imagine` 已能依据角色卡和对话生成场景提示词 | 可复用，但 Qwen 应改用自然语言提示词并加入参考图语义 |

## 4. 核心设计决策

### 4.1 三张独立图片是角色资产标准，工作流输入可转换

固定语义顺序：

| 角色视图 | Qwen 2511 默认输入 | 语义 |
|---|---|---|
| `front` | `image1` / Picture 1 | 正面身份、脸部、服装正面 |
| `side` | `image2` / Picture 2 | 90° 侧面轮廓、发型和服装侧面 |
| `back` | `image3` / Picture 3 | 背面发型、服装背面和整体比例 |

参考图建议满足：同一角色、同一套基础服装、相近光线和纯净背景；单人、全身、无遮挡、无文字水印。三张视图必须由用户明确放入对应槽位，程序不根据文件名或图像内容猜测方向。

就绪条件由所选布局决定：`three-direct` 与 `contact-sheet` 要求 **3/3 完整**，`front-only` 只要求正面图。三图模式不得在缺少侧面时把背面压缩到第二输入，以免 Picture 编号与提示词含义错位。

三张独立原图是角色卡侧的数据标准，但工作流侧不强制必须有三个直连插槽。适配器可以按模板能力选择：三图直连、只取正面、由工作流内的批次节点合并，或在上传前生成一张临时联系表。转换产物只服务于本次生成，不反向覆盖角色卡原始三视图。

MVP 只实现并启用 `none` 与 `front-only` 两种转换，两者都是纯文件拷贝，不需要主进程解码或重编码图片。`contact-sheet-horizontal` 属第二阶段：类型契约在阶段 B 定型，但 MVP 的绑定校验必须把选择该转换的配置判为“暂不支持”并拒绝保存，避免提交无法执行的转换。第二阶段实施前需先为主进程选型图像处理依赖（如 `sharp` 或 `@napi-rs/canvas`），这是联系表裁剪与合成的前置条件。

### 4.2 工作流仍是唯一事实来源

沿用当前 ComfyUI 设计：模型、采样器、尺寸、LoRA 和所有生成参数仍由导入的工作流快照决定。应用只负责四类运行时数据：

1. 正面提示词；
2. 负面提示词；
3. 随机种子；
4. 角色参考图片入口及其适配策略。

应用不内置一套不可见的 Qwen 工作流，也不依据模型名重写 Steps、CFG 或采样器。模板差异通过声明式绑定和适配器解决，不在生图主流程中堆叠模型名称判断。

### 4.3 普通文生图与角色图生图分开配置

新增独立的活动配置 `activeCharacterImageGenModelId`，保留现有 `activeImageGenModelId` 作为普通文生图配置。原因是两种工作流输入契约不同，强行共用一个“活动模型”会让环境空镜、没有参考图的旧角色和角色参考图互相冲突。

建议给 ComfyUI 配置新增用途字段：

```ts
type ImageGenPurpose = 'text-to-image' | 'character-reference'

interface ComfyImageGenConfig {
  // 现有字段省略
  purpose: ImageGenPurpose
  referencePromptProfile?: 'qwen-three-view' | 'identity-reference' | 'none'
}
```

迁移时，旧 ComfyUI 配置全部写成 `text-to-image`，行为不变。`activeCharacterImageGenModelId` 默认不存在，不自动复制旧配置。

新增生图字段（`purpose`、`referencePromptProfile`、`activeCharacterImageGenModelId`、参考绑定等）禁止加入移动端同步白名单 `MobileSafeSettings`。当前白名单不含任何生图配置（v3/v4 已移除 `imageGenSize`、`imageGenAutoEnabled`），本功能必须维持该边界；若未来需要向移动端同步生图设置，必须连同 Android 端 `SettingsSync` 契约与 fixtures 一并修订，不允许单方面扩白名单。

### 4.4 不静默牺牲角色一致性

角色参考策略建议支持三个值：

```ts
type CharacterReferencePolicy = 'auto' | 'required' | 'off'
```

| 策略 | 行为 |
|---|---|
| `auto` | 当前布局所需参考资产齐全且参考工作流可用时走图生图，否则走普通文生图 |
| `required` | 缺图、缺工作流或上传失败时直接给出可操作错误，不降级 |
| `off` | 始终忽略三视图，走普通文生图 |

角色卡默认 `auto`。一旦参考工作流已经开始执行，失败时不得再静默改走文生图，否则用户会误以为失败结果使用了三视图。

## 5. 数据与文件设计

### 5.1 共享类型

```ts
export type CharacterReferenceView = 'front' | 'side' | 'back'

export interface CharacterReferenceAssetMeta {
  mimeType: 'image/png' | 'image/jpeg' | 'image/webp'
  bytes: number
  sha256: string
  updatedAt: number
}

export interface CharacterVisualReferences {
  schemaVersion: 1
  policy: 'auto' | 'required' | 'off'
  views: Partial<Record<CharacterReferenceView, CharacterReferenceAssetMeta>>
}

export interface Character {
  // 现有字段省略
  visualReferences?: CharacterVisualReferences
}
```

`views` 只保存可验证的元数据，不保存绝对路径和 base64。是否完整由 `front && side && back` 动态计算，不额外保存容易失真的 `complete` 布尔值。

### 5.2 磁盘文件

沿用当前角色目录，使用可预测的平铺文件名：

```text
<characters>/
├── <characterId>.json
├── <characterId>_cover.webp
├── <characterId>_ref_front.<ext>
├── <characterId>_ref_side.<ext>
└── <characterId>_ref_back.<ext>
```

实现要求：

- 接受 PNG、JPEG、WebP，单张上限建议 10 MiB。
- 根据文件魔数判断 MIME，不信任扩展名或 data URL 声明。
- 沿用头像/封面的落盘策略：解码 data URL 后按原始字节写盘，不做转码或压缩；扩展名跟随真实 MIME（`.png`/`.jpg`/`.jpeg`/`.webp`），不固定为 `.webp`。因此 MVP 不需要任何主进程图像处理能力。
- 替换某个槽位前清理该槽位的旧扩展名文件，防止读取到旧图。
- 文件写入成功后再更新角色 JSON；JSON 更新失败时回滚新文件或返回明确错误。
- 删除角色时同步删除三个槽位的所有支持格式。
- 备份功能按现有整目录策略自然包含三视图。

### 5.3 预览协议

扩展当前 `tavern://character/<id>/<kind>`：

```text
tavern://character/<id>/ref-front?v=<updatedAt>
tavern://character/<id>/ref-side?v=<updatedAt>
tavern://character/<id>/ref-back?v=<updatedAt>
```

`src/utils/asset.ts` 的 `kind` 联合类型同步增加三个值。主进程继续校验角色 ID 和有限的 kind 白名单，不接受任意相对路径。

### 5.4 标准角色卡导入导出

- PNG/JSON 标准导出默认不嵌入三视图原图，也不输出指向本机文件的路径。
- 导入普通角色卡时 `visualReferences` 默认为空。
- 如需可迁移的完整角色资产，后续新增“轻语角色包”ZIP，内含角色卡 JSON、头像、封面、三视图和 manifest；不要私自扩展标准 PNG 后假定其他客户端会保留。

## 6. IPC 与服务契约

### 6.1 角色参考图管理

在 `CharacterAPI` 增加：

```ts
setVisualReference(
  characterId: string,
  view: CharacterReferenceView,
  dataUrl: string,
): Promise<{ success: boolean; meta?: CharacterReferenceAssetMeta; error?: string }>

removeVisualReference(
  characterId: string,
  view: CharacterReferenceView,
): Promise<{ success: boolean; error?: string }>

setVisualReferencePolicy(
  characterId: string,
  policy: CharacterReferencePolicy,
): Promise<{ success: boolean; error?: string }>
```

每个入口都必须执行 `safeId`、视图枚举校验、大小校验和图片魔数校验，并复用角色级文件锁。渲染层只传受限枚举与图片数据，不传可写文件路径。

### 6.2 生图请求

保持现有调用兼容，在 `ImageGenOptions` 增加受限的角色引用描述：

```ts
interface CharacterReferenceRequest {
  characterId: string
  policy?: CharacterReferencePolicy
}

interface ImageGenOptions {
  // 现有字段省略
  characterReference?: CharacterReferenceRequest
}
```

不从渲染层传三张 base64。主进程根据已验证的 `characterId` 从角色资产目录读取，既减少 IPC 体积，也避免调用方伪造三个不受管理的图片来源。

## 7. ComfyUI 工作流分析与绑定

### 7.1 分析结果扩展

当前 `kind` 只能说明工作流是否依赖图片，不能说明它如何接收参考资产。建议新增能力与资产入口描述，而不是继续扩大 `compatible` 的单一含义：

```ts
interface ComfyWorkflowCapabilities {
  textToImage: boolean
  characterReference: boolean
  acceptedReferenceLayouts: Array<'three-direct' | 'front-only' | 'contact-sheet'>
}

type ComfyReferenceAdapterKind =
  | 'comfy-load-image'
  | 'filename-widget'
  | 'url-widget'

type ComfyReferenceTransform =
  | 'none'
  | 'front-only'
  | 'contact-sheet-horizontal'

interface ComfyWorkflowAssetIngress {
  nodeId: string
  inputName: string
  adapterKind: ComfyReferenceAdapterKind | null
  title?: string
  reachable: boolean
  supported: boolean
}

interface ComfyWorkflowAnalysis {
  // 现有字段省略
  capabilities: ComfyWorkflowCapabilities
  assetIngresses: ComfyWorkflowAssetIngress[]
}
```

`characterReference` 的最低判定条件：

1. 有可达图片输出；
2. 有可达正面提示词入口；
3. 当前绑定需要的资产入口全部可达，并存在受支持的适配器；
4. front、side、back 三个来源已经按所选布局完成无歧义映射；
5. 所选布局满足模板的数量要求；
6. 不存在缺失模型和未知节点阻断项。

分析器按以下顺序发现入口：

1. 优先识别内置 `LoadImage`、`LoadImageMask` 等已知文件加载节点；
2. 通过 `/object_info` 查找能通向下游 `IMAGE` 输入的候选资产节点；
3. 查询节点适配器注册表，判断哪个字段接收上传后的文件名或 URL；
4. 找不到适配器时只展示为“未支持候选”，不猜测字段并修改工作流。

注意：普通节点的 `IMAGE` 插槽在 API JSON 中通常接收的是上游节点引用，而不是图片文件名。轻语不能简单把字符串写进任意 `IMAGE` 输入；必须定位产生该 IMAGE 的资产入口节点，或由专用适配器按该节点协议注入。

### 7.2 自动与手动绑定

标准三入口工作流作者可给三个资产入口节点设置标题标记：

```text
[QINGYU:front] 角色正面
[QINGYU:side] 角色侧面
[QINGYU:back] 角色背面
```

分析器优先读取精确标记；没有标记时，即使刚好有三个候选入口，也只列为候选，由设置界面让用户分别选择“正面入口 / 侧面入口 / 背面入口”。不要依赖 JSON 对象顺序自动分配语义。

保存后的配置建议增加：

```ts
interface ComfyReferenceTarget {
  nodeId: string
  inputName: string
  adapterKind: ComfyReferenceAdapterKind
}

interface ComfyReferenceBinding {
  sources: CharacterReferenceView[]
  target: ComfyReferenceTarget
  transform: ComfyReferenceTransform
}

interface ComfyWorkflowBindings {
  // 现有字段省略
  referenceImages?: ComfyReferenceBinding[]
}
```

典型绑定：

```ts
// Qwen 2511 三入口
[
  { sources: ['front'], target: { nodeId: '10', inputName: 'image', adapterKind: 'comfy-load-image' }, transform: 'none' },
  { sources: ['side'],  target: { nodeId: '11', inputName: 'image', adapterKind: 'comfy-load-image' }, transform: 'none' },
  { sources: ['back'],  target: { nodeId: '12', inputName: 'image', adapterKind: 'comfy-load-image' }, transform: 'none' },
]

// 只接受一张参考图的身份节点
[
  { sources: ['front'], target: { nodeId: '20', inputName: 'image', adapterKind: 'comfy-load-image' }, transform: 'front-only' },
]

// 只接受一张综合参考图的模板
[
  { sources: ['front', 'side', 'back'], target: { nodeId: '30', inputName: 'image', adapterKind: 'comfy-load-image' }, transform: 'contact-sheet-horizontal' },
]
```

若同一来源被意外绑定多次、目标节点不可达、字段与适配器不匹配、三图直连模式的多个来源指向同一文件字段，或 MVP 下选择了尚未启用的 `contact-sheet-horizontal` 转换，禁止保存为角色参考工作流。

### 7.3 设置界面

导入图生图工作流后显示：

- 用途：`普通文生图` / `角色三视图`；
- 参考图布局：`三图独立` / `仅正面` / `横向联系表`；
- 与布局对应的图片入口下拉框和适配器类型；
- 正面提示词入口与输出入口；
- 模型依赖、动态参数和现有警告；
- `设为角色参考工作流` 操作。

`requires-image-input` 对角色参考用途不再是错误，而是预期条件；缺少或歧义图片绑定才是阻断项。

高级 JSON 区只负责查看工作流快照，不要求用户手写绑定 JSON。无法自动识别的模板应在可视化表单中完成来源、目标和转换方式选择。

### 7.4 模板兼容分级

| 兼容级别 | 典型模板 | 接入方式 | MVP |
|---|---|---|---|
| A：标准三入口 | Qwen Image Edit 多图、三个 `LoadImage` 进入多参考节点 | front/side/back 分别注入三个入口 | 完整支持 |
| B：标准单入口 | InstantID、PuLID、单参考 FLUX Kontext | 默认只取正面；后续可改用联系表 | 支持仅正面 |
| B：工作流内批次 | 多个 `LoadImage` 经 Image Batch 接 IP-Adapter | 仍绑定上游各 `LoadImage`，批次由工作流负责 | 可支持 |
| C：单入口综合参考 | 只允许一张图但能理解联系表的编辑模型 | 应用生成临时横向联系表后注入 | 第二阶段 |
| C：自定义文件节点 | 自定义 loader、路径 widget | 为节点声明文件字段和返回格式的适配器 | 按需增加 |
| D：URL/API 节点 | 只接收 URL、云端专用节点 | 上传后生成服务可访问 URL，需专用鉴权与生命周期策略 | 非 MVP |
| 不支持 | 图片封装在不可展开节点且无可写入口 | 无法安全注入 | 拒绝保存并说明原因 |

身份方法的默认建议：

- Qwen Image Edit / FLUX 多参考：优先使用三图独立输入；
- InstantID：正面图作为身份入口，三视图不能提升其单脸关键点协议时不强塞另外两张；
- IP-Adapter：模板若已有三路 loader + batch 链则使用三图，否则先以正面图建立兼容基线；
- PuLID：正面图作为主要身份输入，其他视图仅在模板本身提供多参考协议时启用；
- FLUX Kontext：按模板支持的参考图数量选择三图独立或正面单图。

### 7.5 节点适配器注册表

新增集中式注册表（建议 `electron/services/comfyReferenceAdapters.ts`），不要把特殊节点判断散落在 `imageGen.ts`：

```ts
interface ComfyReferenceAdapter {
  kind: ComfyReferenceAdapterKind
  supports(node: ComfyNode, objectInfo?: Record<string, unknown>): boolean
  validate(target: ComfyReferenceTarget, node: ComfyNode): string[]
  inject(node: ComfyNode, uploaded: ComfyUploadedAsset): void
}
```

首版只注册 `comfy-load-image`。后续适配一个自定义节点时，只新增适配器及测试，不修改角色卡结构、`/imagine` 分流或 ComfyUI 队列主流程。

## 8. ComfyUI 运行时实施

### 8.1 准备并上传参考资产

在独立服务（建议 `electron/services/comfyImageInputs.ts`）实现：

1. 读取并验证当前绑定所需的角色参考文件；
2. 按绑定执行 `none`、`front-only` 或 `contact-sheet-horizontal` 转换；
3. 以 `multipart/form-data` 调用 ComfyUI `POST /upload/image`；
4. 使用现有 `Authorization` 与 `X-API-Key` 头；
5. 上传到受控子目录，例如 `qingyu-character-references`；
6. 文件名使用 `characterId + source/transform + sha256`，同一资产多次使用时名称稳定；
7. 返回 ComfyUI 接受的 `name/subfolder/type`，交给目标节点的适配器转换并注入。

首版每次生成都执行幂等上传，以正确处理 ComfyUI 重启、输入目录被清理或远程节点切换。后续确认服务端文件存在性后再增加缓存，不能只依赖进程内“已上传”标记。

互不依赖的上传可以并行；任意一个必需资产失败时不得提交 `/prompt`，错误需指出具体视图或转换产物。

### 8.2 工作流注入顺序

建议将当前构建过程调整为：

```text
解析并深拷贝工作流
  -> 替换兼容占位符
  -> 注入正/负提示词
  -> 随机化基础采样阶段种子
  -> 应用用户保存的参数 overrides
  -> 执行参考图布局转换与上传
  -> 由适配器最后注入运行时图片资产
  -> 提交 /prompt
```

图片注入必须在 `overrides` 之后，且设置界面不得把已经绑定的目标字段暴露为普通参数。这样保存的工作流文件名或恶意覆盖项不能顶掉本次角色资产。

### 8.3 参考工作流节点约定

推荐的 Qwen-Image-Edit-2511 工作流骨架：

```text
LoadImage [QINGYU:front] ─┐
LoadImage [QINGYU:side]  ─┼─> TextEncodeQwenImageEditPlus [QINGYU:positive]
LoadImage [QINGYU:back]  ─┘                     │
                                                  ├─> KSampler -> VAE Decode -> SaveImage [QINGYU:output]
UNETLoader -> LoraLoaderModelOnly -> Model patch ─┘
CLIPLoader + VAELoader ───────────────────────────┘
```

连接规则：正面接 `image1`，侧面接 `image2`，背面接 `image3`。Lightning 4-step LoRA 使用 `LoraLoaderModelOnly`；具体 Steps、CFG、Sampler、Scheduler、Denoise 仍取工作流自身配置，不在轻语代码中硬编码。

这是首个验收模板，不是运行时特判。Qwen、IP-Adapter、InstantID、PuLID 或 FLUX 工作流最终都通过相同的 `referenceImages` 绑定和适配器接口进入队列流程。

## 9. 提示词策略

### 9.1 提示词包装也按模板配置

当前提示词风格判断只把 OpenAI、Z-Image 和 FLUX 归为自然语言。需把 Qwen Image/Edit 工作流也归入 `natural`，避免把复杂的多参考编辑指令降成标签堆叠。

图片入口适配和提示词包装是两个独立维度。配置保存 `referencePromptProfile`：

| Profile | 用途 |
|---|---|
| `qwen-three-view` | 使用 Picture 1/2/3 语义的 Qwen 多图编辑模板 |
| `identity-reference` | InstantID、IP-Adapter、PuLID 等不需要在文本中点名图片编号的身份模板 |
| `none` | 工作流或自定义节点自行处理参考说明，轻语只传原场景提示词 |

自动推荐可以参考工作流节点类型，但最终值在设置页可见、可改，并随工作流配置保存。不能仅凭配置名称包含 “qwen” 或 “flux” 就在运行时硬编码行为。

### 9.2 Qwen 三视图组合模板

`qwen-three-view` 在最终场景提示词外包一层稳定的参考说明：

```text
Pictures 1, 2, and 3 show the same character from the front, side, and back.
Use them together as the authoritative identity and design reference.
Create a new image for this scene: {scenePrompt}
Preserve the character's facial identity, hairstyle, body proportions, and outfit design
unless the scene explicitly requires a change. Do not copy the reference background,
pose, text, or layout. Show only one clear instance of this character.
```

职责分离：

- 三视图是脸、发型、体型和基础服装设计的最高优先级事实；
- 最新对话仍是地点、动作、表情、镜头、时间和临时服装状态的最高优先级事实；
- 用户直接提供 `/imagine 描述` 时，也必须经过同一参考说明包装；
- `--mode background` 永远不传三视图，防止模型强行把角色画进空镜。

`identity-reference` 不使用 Picture 编号，只追加“保持参考身份、场景按文本变化”的中性约束，避免 InstantID、IP-Adapter 或 PuLID 模板收到并不存在的第二、第三图片描述。`none` 完全不包装。

### 9.3 命令控制

为 `/imagine` 增加可选参数：

```text
/imagine --ref auto ...      # 默认
/imagine --ref required ...  # 必须使用三视图，否则报错
/imagine --ref off ...       # 本次忽略三视图
```

优先级为：本次命令参数 > 角色卡 `policy`。`--mode background` 生成环境空镜时本就不含角色，不视为违反 `required`，直接走普通文生图且不报错；`required` 只对含角色的生成生效。

若不希望扩大命令表面，MVP 可以只实现 `auto/off`，角色卡中的 `policy` 决定默认行为。

## 13. 验收标准

- 角色编辑器能稳定保存并再次打开三张参考图，应用重启后不丢失。
- `three-direct` 布局下三视图完整、参考工作流可用、策略为 `auto` 时，含角色的 `/imagine` 使用三张输入图。
- `qwen-three-view` Profile 中 `Picture 1/2/3` 永远分别代表正面/侧面/背面。
- Qwen 之外的标准单入口模板可选择“仅正面”运行，不需要修改代码。
- 工作流内已有图片批次链时，可绑定其上游资产入口，不要求轻语理解下游身份节点实现。
- 非 Qwen 模板不会收到错误的 Picture 1/2/3 提示词包装。
- 环境空镜不上传参考图、不意外生成人物。
- 旧角色与旧配置无需迁移操作即可继续文生图。
- 参考图片不会以 base64 出现在角色 JSON、设置 JSON、日志或错误文本。
- 工作流导入后模型缺失、节点缺失、图片入口歧义都在提交前被发现。
- 任一参考图上传失败时不会排队一个缺图的生成任务。
- 标准角色卡导出不会携带本机路径或失效资产引用。

## 14. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 多参考图仍可能改变脸或服装 | 使用 Qwen 2511 多图节点；固定语义顺序；参考提示明确“身份权威、场景可变” |
| 三视图风格或服装不一致 | 上传区给出质量提示；后续增加三图一致性检查，不在 MVP 自动修图 |
| ComfyUI 工作流节点 ID 改变 | 以导入快照和绑定校验为准；编辑时重新分析，不硬编码官方模板 ID |
| 把任意 `IMAGE` 输入误当作文件字段 | 只允许已注册适配器写入资产入口；未知节点只展示候选，不修改工作流 |
| 自定义节点图片协议差异 | 使用集中式适配器注册表；缺少适配器时在提交前拒绝并提示节点类型 |
| 远程 ComfyUI 无法访问本机图片 | 一律通过 `/upload/image`，不传本机文件路径 |
| ComfyUI 输入目录积累 | 以内容哈希命名避免每次产生新文件；后续增加受控清理，不直接递归删除用户 input 目录 |
| 参考图 payload 或日志泄漏 | IPC 限大小；日志只记角色 ID、视图、字节数和短哈希，不记 base64 与绝对路径 |
| 8GB 显存不足以运行 Qwen 2511 | 上线前以量化/GGUF 工作流或远程 ComfyUI 实测；应用功能不绑定 BF16 主模型；GGUF 依赖 ComfyUI-GGUF 自定义节点，需纳入前置检查 |
| 新增生图设置泄漏进移动端同步快照 | 生图字段禁止加入 `MobileSafeSettings` 白名单；如需同步必须连同 Android `SettingsSync` 契约一并修订 |
| 主进程缺少图像处理库导致联系表转换无法落地 | MVP 只启用纯拷贝转换（`none`/`front-only`）；第二阶段实施前先选型并验证 `sharp` 或 `@napi-rs/canvas` |
| 群聊出现多个角色 | MVP 明确禁止自动套用；后续需独立设计多角色参考与构图契约 |

官方 ComfyUI 打包的 Qwen 2511 BF16 主模型约 40.9GB，FP8 mixed 版本约 20.5GB。对当前 8GB VRAM + 16GB RAM 机器，两者都不能视为顺畅可用的默认方案。实施代码前应先选定并手工跑通一个适配当前硬件的量化/GGUF 工作流，或使用显存更高的远程 ComfyUI；轻语只消费经验证的 API 工作流，不应在代码中假定 BF16 可运行。GGUF/量化路线依赖 ComfyUI-GGUF 等自定义节点：实施前需确认其已安装且加载节点出现在 `/object_info` 中，分析器应把已确认存在的加载节点记为已知节点，避免被“未知节点阻断”规则误拦。

## 16. 推荐提交拆分

1. `feat(character): add file-backed visual reference assets`
2. `feat(comfy): analyze and bind character reference image inputs`
3. `feat(comfy): upload and inject character reference images`
4. `feat(ui): manage character front side back references`
5. `feat(imagine): route character generation through reference workflow`
6. `test(imagegen): cover three-view routing and failure boundaries`

每个提交都应能独立通过 `pnpm check` 和相关 Vitest；阶段 C 与 D 合并后再执行真实 ComfyUI 冒烟测试。
