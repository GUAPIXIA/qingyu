# ADR-011：阶段 2 采用「单仓储 + 逐域瓶颈收口」而非每域一个 adapter 类

> 日期：2026-09-17
> 状态：已采纳
> 相关：阶段 2 实施方案 S2-01/S2-04；ADR-003（PC 暂保留文件存储）；ADR-002（语言无关 schema 与双实现）

## 背景

阶段 2 实施方案 S2-01 原计划拆出多个 adapter 类：

```text
FileBackedEntityRepository / ChatRepository / GroupRepository / MediaRepository / SettingsRepository
```

实际实施前的代码勘察（阶段 0 `data-domain-inventory` §3–§4）显示：PC 端 12 个同步域的写入口并不各自独立，而是集中在少数「瓶颈函数」上，例如

| 域 | 真实瓶颈 |
|---|---|
| session | `ipc/chat.saveSessions`（20+ 调用点）、`ipc/group.saveSessions` |
| message | `ipc/chat.writeMessages` / `appendMessage`（15+ 调用点） |
| group | `ipc/group.saveGroups` / `saveSessions` / `writeMessages` / `appendMessage`（30+ 调用点） |
| character | `services/charCard.saveCharacter`（5 个导入/保存入口） |
| 其余 | 单文件数组或一实体一文件，1–4 个写点 |

即 `MediaRepository`/`SettingsRepository` 在 PC 侧没有独立的物理存储边界，`ChatRepository` 与 `GroupRepository` 共用同一套「数组文件 + JSONL」形态但路径由父实体决定。若为对称而拆类，将引入大量仅做转发的空壳 adapter，而真正的收口点仍是那些瓶颈函数。

## 决策

1. 保留**一个**实现类 `electron/domain/pcRepository.ts` 的 `PcDomainRepository`，承载事务与 journal；不新建按域的 adapter 类。
2. 收口以「**逐域最低层瓶颈函数**」为单位：把瓶颈函数改为调用
   `writeThroughDomain` / `deleteThroughDomain` / `commitThroughDomain`，使全部上层调用点自动被覆盖。
3. 用**语言无关的 repository 契约行为表**替代「每个 adapter 跑同一套件」的约束目标：
   `shared/contracts/fixtures/repository/behavior-table.json` +
   `shared/contracts/repositoryContract.ts` 执行器，
   当前由「进程内内存实现」与「PC 文件实现」共同满足；
   阶段 3 的 Room 实现按同一张表实现等价 runner。
4. 单文件容器（会话数组、JSONL 消息）使用**多实体单事务**：`commitWithJournal({ puts, deletes, files })`
   在一个文件事务内原子提交全部 head 与 change_log。

## 后果

- **收益**：收口证据可自动化（`scripts/check-write-bypass.mjs --strict`，调用点级 AST），
  改动集中、可回滚；不存在为对称而生的空壳层。
- **代价**：与实施方案字面上的「每域一个 adapter」不一致；域与仓储的映射关系写在
  各瓶颈函数与 `data-domain-inventory` §7，而不是靠类型系统表达。
- **约束**：新增同步域时必须同时
  (a) 在 `featureFlag.ts` 增加 domain key，
  (b) 在 `bootstrapScanners.ts` 增加扫描器，
  (c) 在 `remoteMaterializers.ts` 增加 materializer，
  (d) 在 `scripts/check-write-bypass.mjs` 的 `SYNC_DOMAIN_FILES` 中登记其文件，
  否则检测器会以 `UNCLASSIFIED` 报违规。
- 若后续确需按域拆类（例如 Android Kotlin 侧或 media blob 独立存储），
  以本 ADR 的契约行为表为基准迁移，不改变对外可观测语义。
