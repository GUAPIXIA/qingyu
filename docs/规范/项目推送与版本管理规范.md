## 1. 总则

### 1.1 目的

统一两端（桌面 Electron、Server）的版本号管理、分支策略、提交规范与推送门禁，确保：

- `main` 分支永远可发布
- 每次推送前通过全量门禁（类型检查 / Lint / 测试 / 安全审计）
- 版本号、Tag、CHANGELOG 三者一致
- 敏感文件不进入版本库

两份规范按职责维护，公共规则只在本文件定义，桌面端发版操作只在更新与上传规范定义：

| 内容 | 维护位置 |
|---|---|
| 版本来源、递增规则与脚本 | 本文件 §1.2、§2 |
| 子模块、分支、提交、推送门禁与 CI | 本文件 §1.3、§3～§5、§12 |
| CHANGELOG 格式、Tag 管理 | 本文件 §7、§10 |
| 桌面端构建、Release、服务器和公告同步、升级验收及发布故障处理 | [项目更新与上传规范](./项目更新与上传规范.md) |

### 1.2 各端版本权威来源

| 端 | 权威文件 | 版本脚本入口 |
|---|---|---|
| 桌面端 | [package.json](../../package.json) 的 `version` | `node scripts/version.mjs` |
| 服务端 | [server/app/package.json](../../server/app/package.json) 的 `version` | `npm version --no-git-tag-version`（在 `server/app/` 下执行，见 §6.4） |

> 桌面端与服务端各自独立版本线，服务端独立 SemVer。当前版本直接读取权威文件，不在本规范维护数值快照。（Android 独立版本线与 `--sync-android` 已随安卓端兼容移除退场。）

### 1.3 仓库拓扑与子模块推送规则（2026-10-02 核对；2026-10-14 更新）

| 仓库 | 挂载点 | 说明 |
|---|---|---|
| `GUAPIXIA/qingyu` | `./` | PC 主仓；含 `server/` 公告／版本服务端子项目 |
| `GUAPIXIA/qingyu-shared` | `shared/` | 共享核心（chat-core、契约、fixture）；**唯一挂载点** |

- **推送顺序**：shared 有变更时，先在 `shared/` 提交并推送到 `qingyu-shared`；再在 PC 主仓提交 gitlink 指针。只更新主仓指针而未推送 shared 源码提交视为未完成。
- **克隆与 CI** 一律递归初始化：`git submodule update --init --recursive`；CI 已在 checkout 步骤声明 `submodules: recursive` 并校验缺失。
- 子模块 URL 为相对路径（`../qingyu-shared`），要求两个仓库同级部署。
- `android/` 子模块、第二挂载点 `android/shared/` 与 `GUAPIXIA/qingyu-android` 已于 2026-10-14 随「移除安卓端兼容」退出 main；安卓端改为在其独立仓自行维护与发布，PC 仓不再为其门禁、版本一致性或 APK 产物负责。详见[仓库拓扑：PC 仓 + shared 子模块](../架构/仓库拓扑-PC与Shared双仓-2026-10-14.md)。

## 2. 版本号规则

### 2.1 SemVer 变体

```
主版本.次版本.修订号[-预发布.序号]

0.12.0              正式版
0.12.0-alpha.1      内部联调
0.12.0-beta.1       公测
0.12.0-rc.1         候选
1.0.4               Server（独立 SemVer）
```

| 段 | 含义 | 递增时机 |
|---|---|---|
| 主版本 | 不兼容的大架构变更 | 如 `0.16.0 → 1.0.0` |
| 次版本 | 架构升级 / 批量新功能 | 如 `0.11 → 0.12`（统一 ChatOrchestrator） |
| 修订号 | 热修 / Bug 修复 / 安全修复 | 如 `0.12.0 → 0.12.1` |
| 预发布 | 开发阶段标记 | `alpha` 内部 → `beta` 公测 → `rc` 候选 → 正式 |

### 2.2 版本递增决策

| 变更类型 | 递增 | 示例 |
|---|---|---|
| Bug 修复、安全热修 | `patch` | `0.12.0 → 0.12.1` |
| 新功能、架构升级 | `minor` | `0.12.0 → 0.13.0` |
| 不兼容变更 | `major` | `0.12.0 → 1.0.0` |
| 预发布迭代 | `prerelease --pre <phase>` | `0.13.0-alpha.1 → 0.13.0-alpha.2` |
| 预发布转正 | `release` | `0.13.0-rc.1 → 0.13.0` |

> `main` 分支的 `package.json#version` 始终指向**当前开发版本**。Tag 才标记正式发布点。

### 2.3 版本脚本

[scripts/version.mjs](../../scripts/version.mjs) 是桌面端版本号的唯一入口：

```bash
# 查看当前版本与最近 Tag
node scripts/version.mjs status

# 递增修订号
node scripts/version.mjs patch

# 递增次版本
node scripts/version.mjs minor

# 不兼容的大版本
node scripts/version.mjs major

# 预发布迭代（默认 alpha，可指定 beta/rc）
node scripts/version.mjs prerelease --pre beta

# 预发布转正式
node scripts/version.mjs release

# 直接设定版本号（需校验格式）
node scripts/version.mjs set 0.13.0-beta.1
```

也可通过 `package.json` scripts 别名调用：

```bash
pnpm version:status
pnpm version:patch
pnpm version:minor
pnpm version:prerelease
pnpm version:release
```

桌面端递增命令默认只写入 `package.json#version`，CHANGELOG 需按 §7 整理；shared 有变更时按 §1.3 先推送子模块源码提交，再更新主仓 gitlink 指针。

## 3. 分支模型

```
origin/main          唯一保护分支，永远可发布；允许在门禁通过后直推（与发版操作一致）
├─ feat/*            功能分支（从 main 切出）
├─ fix/*             修复分支
├─ chore/*            工程治理 / 依赖升级 / 文档
└─ release/vX.Y.Z    热修或预发布分支（从对应 Tag 切出，合回 main 后删除）
```

### 3.1 规则

| 规则 | 说明 |
|---|---|
| 允许直推 main | 门禁（check/lint/test）通过后可直推；复杂变更仍建议 PR |
| 功能分支命名 | `feat/<简述>` 或 `fix/<issue号>-<简述>` |
| 分支生命周期 | 合入 main 后立即删除 |
| 热修分支 | 从最近正式 Tag 切 `release/vX.Y.Z`，修复合回 main 并打新 Tag |
| 禁止 rebase 已推送的公共分支 | 保持 merge commit，保留完整历史 |

## 4. 提交规范

### 4.1 Commit Message 格式

```
<type>(<scope>): <subject>

<body 可选>
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `security` | 安全修复 |
| `refactor` | 重构（无行为变更） |
| `perf` | 性能优化 |
| `test` | 测试补充 |
| `docs` | 文档 |
| `chore` | 工程 / 依赖 / 配置 |
| `release` | 发版提交（升版本 + CHANGELOG） |

scope 示例：`bridge` / `chat` / `mcp` / `server` / `settings` / `character`。

示例：

```
feat(chat): 持久任务恢复与事件补播
security(bridge): JWT 密钥明文落盘收敛
release: v0.12.1 - 修复群聊保存竞态
```

### 4.2 提交粒度

- 一个提交做一件事，避免大杂烩。
- 功能与修复代码先按各自类型提交；发版提交包含版本号、CHANGELOG、必要的 README/索引版本同步，以及实际发生变化的 lockfile 或子模块指针。
- 所有提交使用显式路径暂存，提交前检查 `git diff --cached --stat`，提交后检查 `git show --stat HEAD`；工作区有并行改动时不得使用 `git add -A`。
- 敏感文件（`.env` / `*.pem` / `*.key` / `*.keystore` / `*.apk`）**永不提交**，见 [§8](#8-安全与敏感文件管理)。

## 5. 推送前门禁

### 5.1 本地门禁（每次 push 前必须全绿）

```powershell
Set-Location D:\Code\qingyu

# 1. TypeScript 类型检查（双 tsconfig）
pnpm check

# 2. ESLint（0 errors）
pnpm lint

# 3. 全量单元测试
pnpm test
# 若需覆盖率门禁：
# pnpm test:coverage

# 4. 服务端测试（如改动了 server/）
Set-Location server/app; npm test; Set-Location ../..

# 5. 工作区检查
git status          # 确认无敏感文件
git diff --stat     # 确认变更范围符合预期
git log --oneline -5
```

### 5.2 CI 自动门禁

[.github/workflows/ci.yml](../../.github/workflows/ci.yml) 是 CI 配置来源，各 Job 职责统一见 §12；推送后确认适用的 CI 检查通过。工作流定义不等于远端分支保护设置，是否阻止合入以仓库实际保护规则为准。

### CI 触发关系（2026-09-13 整理，消除双流水线歧义）

| 事件 | 触发的 workflow | 产出 |
|---|---|---|
| push `main` | CI（test / lint / build-windows 等） | 校验 + Windows artifact，**不创建 Release** |
| push `v*` Tag | `release.yml` | 校验 Tag 与 package.json 一致 → 构建 → **自动创建 GitHub Release** 并上传 exe/blockmap/latest.yml |
| push `server-v*` Tag | 按需 | 服务端发布标记（不触发桌面 Release） |

发版操作权威见 [项目更新与上传规范](./项目更新与上传规范.md)。

## 6. 发布入口与分支准备

### 6.1 桌面端正式发布

完整操作按 [项目更新与上传规范](./项目更新与上传规范.md) §三～§七执行，本节不维护第二套打包、Tag 推送或 Release 上传命令。

默认只发布 PC。涉及 shared 变更时按 §1.3 先提交并推送子模块源码提交，再更新主仓指针；不得在主仓直接暂存子模块内部文件。发布提交范围按 §4.2，正式发布后禁止替换同版本安装包。

### 6.2 预发布分支（alpha / beta / rc）

```powershell
# 从 main 切预发布分支
git checkout main
git pull origin main
git checkout -b release/v0.13.0

# 在此分支按 §2.3 管理 alpha / beta / rc 版本
# 各轮变更按 §4 / §7 提交与记录，按 §5 验证
# 正式转正并提交后合回 main
git checkout main
git merge --no-ff release/v0.13.0
```

每次迭代均按 §7 整理 CHANGELOG、按 §4 提交并通过 §5 门禁。上述命令只说明版本与分支准备，不是可连续执行的发版脚本。

公开预发布前需明确测试渠道、Release 的 Pre-release 标记和更新清单；`v*` 预发布 Tag 也会触发 `release.yml`，须按更新与上传规范 §四.3 处理 CI 与手工资产的关系。正式转正后执行 §6.1，发布完成再删除分支；正式版成为 Latest 的要求不直接套用于预发布。

### 6.3 热修分支

```powershell
# 从最近正式 Tag 切热修分支
git checkout -b release/v0.12.1 v0.12.0

# 修复代码...
# 按 §4 用显式路径暂存修复文件
git commit -m "fix: <描述>"

# 合回 main
git checkout main
git merge --no-ff release/v0.12.1
```

合回后通过 §5 门禁，再按 §6.1 发布新的、未使用过的修订版本；若 main 已有更高版本，以实际版本线确定目标，不能照抄示例降版。发布完成后删除热修分支，不替换已发布版本的资产。

### 6.4 服务端独立发布

服务端版本号独立于桌面端，在 `server/app/` 下管理：

```powershell
Set-Location D:\Code\qingyu\server\app

# 升版本
npm version patch --no-git-tag-version    # 只改服务端版本文件，避免生成桌面端 v* Tag

Set-Location ../..

# 更新 server/CHANGELOG.md
# 完成 §5 门禁；显式暂存实际改动的版本文件与日志
git add server/app/package.json server/CHANGELOG.md
# server/app/package-lock.json 如有变化，也显式暂存
git commit -m "release(server): v1.0.5 - <摘要>"

# Tag 用 server- 前缀区分
git tag -a server-v1.0.5 -m "server v1.0.5"

git push origin main
git push origin server-v1.0.5
```

> 服务端 Tag 使用 `server-v*` 前缀，与桌面端 `v*` 区分。

## 7. CHANGELOG 规范

### 7.1 格式（Keep a Changelog）

文件：[CHANGELOG.md](../../CHANGELOG.md)

```markdown
## [Unreleased]

开发中的变更放在此处，发版时移入正式条目。

## [0.12.1] - 2026-08-21

### 修复
- 修复群聊保存竞态导致消息丢失的问题。

### 安全
- Bridge JWT 密钥轮换机制完善。

## [0.12.0] - 2026-08-20

### 新增
- 统一 ChatOrchestrator 单一执行内核。

### 变更
- `api/v2` 冻结，`v1` 兼容两个小版本。
```

### 7.2 规则

| 规则 | 说明 |
|---|---|
| 每次发版必须有条目 | 未发布内容放 `## [Unreleased]` 下 |
| 分类标签 | `### 新增` / `### 修复` / `### 安全` / `### 变更` / `### 性能` / `### 废弃` |
| 安全修复单列 | 在 `### 安全` 下单独说明 |
| 条目用过去时 | 描述已完成的事实，非计划 |
| 版本号与 Tag 对应 | `[0.12.1]` 对应 Tag `v0.12.1` |
| 日期格式 | `YYYY-MM-DD` |
| 发布归档 | 将本次 `[Unreleased]` 内容移入正式版本章节，并保留空的 `[Unreleased]` |
| 面向用户 | 描述可感知的变化，不罗列无意义的文件名；`[Unreleased]` 为空时按上次 Tag 以来的提交整理 |

### 7.3 各端 CHANGELOG 关系

- 桌面端变更写入根 `CHANGELOG.md`。
- 服务端变更写入 `server/CHANGELOG.md`（独立）。

## 8. 安全与敏感文件管理

### 8.1 永不提交的文件

[.gitignore](../../.gitignore) 已覆盖：

| 类别 | 模式 |
|---|---|
| 环境配置 | `.env` / `.env.*`（`.env.example` 例外） |
| 密钥证书 | `*.pem` / `*.key` / `*.keystore` / `*.jks` |
| 构建产物 | `dist/` / `dist-electron/` / `release-v2/` / `**/build/` / `*.apk` / `*.aab` |
| 缓存 | `node_modules/` / `.cache/` / `coverage/` / `.gradle/` |
| 本地工具 | `.trae/` / `.reasonix/` / `.qoder/` / `.codebuddy/` / `.workbuddy/` |
| 审查产物 | `lint*.json` / `.poc-tmp/` / `piolium/` |

### 8.2 推送前检查

```powershell
# 确认无敏感文件被跟踪
git status --porcelain | findstr /i "\.env \.pem \.key \.keystore \.apk token \.db"

# 如果输出非空，立即停止：
git reset HEAD <file>        # 从暂存区移除
echo <file> >> .gitignore    # 补充忽略
```

### 8.3 敏感配置管理

- API Key / 密码等通过 Electron `safeStorage` 加密存储，不入库。
- 服务端 `JWT_SECRET` / `ADMIN_PASSWORD` 通过 `.env` 环境变量注入，仓库仅留 `.env.example`。
- 如误提交了敏感文件：`git filter-branch` 或 BFG 清理历史，并**立即轮换泄露的凭据**。

## 9. 源码回退与发布故障入口

### 9.1 源码回退

```powershell
# 回退造成问题的代码提交，保留公共分支历史
```

源码回退不能使已安装的客户端自动降级。需要热修时按 §6.3 准备分支，发布、撤下问题版本和双源文件恢复统一按 [项目更新与上传规范](./项目更新与上传规范.md) §八执行；不要通过回退版本号或重打已公开 Tag 替换原版本。

## 10. Tag 管理规范

### 10.1 Tag 命名

| 端 | 格式 | 示例 |
|---|---|---|
| 桌面端 | `vX.Y.Z[-prerelease.seq]` | `v0.12.0` / `v0.13.0-beta.1` |
| 服务端 | `server-vX.Y.Z` | `server-v1.0.5` |

### 10.2 Tag 操作

```powershell
# 查看本地所有 Tag（按版本排序）
git tag --list | Sort-Object -Descending

# 推送单个 Tag
git push origin v0.12.1

# 删除本地误打的 Tag
git tag -d v0.12.1

# 删除远端误推的 Tag
git push origin --delete v0.12.1
```

> 日常推送只推目标分支，不带 `--follow-tags` 或 `--tags`。桌面端发版先推分支并确认远端检查，再显式推本次 Tag，具体顺序见 [项目更新与上传规范](./项目更新与上传规范.md) §三.5～§三.6。删除 Tag 命令仅用于尚未对外发布的误打标记；已公开版本的 Tag 和资产不得重写。


## 12. CI 流水线详解

### 12.1 触发条件

| 事件 | 触发的 Job |
|---|---|
| push → main | relay-lint-and-unit + test + lint + gates + build-windows + audit |
| PR → main | test + lint + gates + audit |

### 12.2 各 Job 职责

以下按当前工作区的 `ci.yml` 整理，实际执行以工作流为准。

**test**（`ubuntu-latest`）：
1. `pnpm install --frozen-lockfile`
2. `pnpm check` — TypeScript 双配置编译（`tsconfig.json` + `tsconfig.electron.json`）
3. `pnpm test:coverage` — vitest 全量测试 + 覆盖率门禁（`vitest.config.ts#thresholds`）
4. `node electron-build.mjs` — Electron 主进程 esbuild 编译验证
5. `pnpm audit --audit-level=critical` — critical 漏洞硬门禁

**lint**（`ubuntu-latest`）：
- `pnpm lint` — ESLint，0 errors 硬门禁

**gates**（`ubuntu-latest`）：
- `pnpm check:gates`、`pnpm check:spatial-core`、`pnpm check:pc-agent`、`pnpm check:contracts` — 结构边界、核心纯度、动作目录与契约漂移门禁。

**build-windows**（`windows-latest`，仅 main push）：
- `node scripts/version.mjs status` — 构建前校验各端内部版本一致性。
- `pnpm electron:build` — electron-builder NSIS 安装包
- 上传 artifact `qingyu-win-x64`（`release-v2/*.exe`）

**audit**（`ubuntu-latest`）：
- `pnpm audit --audit-level high` — 当前未设置 `continue-on-error`，命令失败会导致该 Job 失败。

### 12.3 覆盖率门禁

`vitest.config.ts` 的 `thresholds` 定义各模块覆盖率下限。覆盖率下降会直接导致 CI 红灯。新增代码需同步补测，保持阈值。
