# 轻语项目更新与上传规范

> 适用范围：轻语 Windows 桌面端的日常更新、GitHub Release 发布、官方服务器安装包同步及公告后台版本维护。
> 发布目标版本**始终以根目录 `package.json#version` 为准**（2026-10-05 核对为 `0.20.0`）。禁止覆盖或重复发布已对外发布的版本号。
> 用户一句「发版 `<x.y.z>`」即可开工：触发方式、默认决策与用户参与项见 §三.0，执行步骤见 §三，发布格式见 §四，验收清单见 §七。

## 一、更新体系与版本来源

客户端检查更新时会同时检查官方服务器和 GitHub，两者互不替代：

| 数据 | 唯一来源 | 用途 | 是否每次发布都要更新 |
|---|---|---|---|
| 当前安装版本 | 根目录 `package.json` 的 `version` | 安装包版本、应用内“当前版本” | 是 |
| GitHub 最新版本 | GitHub Release 中的 `latest.yml` | 版本展示、自动下载、重启安装 | 是 |
| 服务器最新版本 | `https://cjbtj.xyz/qingyu/update/latest.yml` | 版本展示、国内服务器手动下载 | 同步服务器下载时是 |
| 公告版本 | 管理后台 `/api/version` 的 PC 版本号 | 左上角新版提示 | 建议同步 |
| 安卓版本 | 管理后台安卓版本字段 | 安卓端更新 | 仅发布安卓版本时 |

重要规则：

1. 桌面端版本号只以根目录 `package.json` 为发布基准。
2. Git Tag 必须是 `v` 加 `package.json` 版本，例如 `package.json` 为 `0.15.2`，Tag 必须为 `v0.15.2`。
3. GitHub 自动更新只使用 GitHub Release，不使用公告后台下载地址。
4. 服务器手动下载只使用服务器 `latest.yml` 中的安装包路径。
5. 公告后台 PC 版本仍有必要维护，但它只控制左上角新版提示；点击提示会进入“设置 → 软件更新”。
6. 同一个版本一旦对外发布，不得替换安装包内容。修复后必须提升版本号重新发布。

## 二、版本号规则

采用语义化版本：`主版本.次版本.修订版本`。

| 场景 | 示例 | 命令 |
|---|---|---|
| Bug 修复、体验优化 | `0.15.1 → 0.15.2` | `pnpm version:patch` |
| 新增较完整功能 | `0.15.2 → 0.16.0` | `pnpm version:minor` |
| 不兼容的大版本 | `0.16.0 → 1.0.0` | `node scripts/version.mjs major` |
| 测试版本 | `0.16.0-beta.1` | `pnpm version:prerelease -- --pre beta` |
| 指定版本 | `0.15.2` | `node scripts/version.mjs set <x.y.z>` |

发布前检查：

```powershell
pnpm version:status
(Get-Content package.json -Raw | ConvertFrom-Json).version
```

不要直接在多个文件里搜索替换版本号。桌面端使用 `scripts/version.mjs` 修改根目录 `package.json`；安卓版本只有在确定需要联动发布时才使用 `--sync-android`。

## 三、标准发布流程

### 0. 触发方式与默认决策

用户只需一句话即可开工，执行方按下面的默认决策一路做到 §七 检查清单全部勾选，不逐项询问：

```text
发版 <x.y.z>
```

可选限定词写在同一句话里：`走 CI`、`不同步公告后台`、`跳过服务器同步`、`不动安卓`、`只做本地包`。

| 决策项 | 默认值（未指定时按此执行） | 依据 |
|---|---|---|
| 递增类型 | 依据 `[Unreleased]` 内容：含「新增」→ `minor`；仅「修复/变更」→ `patch`；两种都讲不通时**问一次** | §二 |
| 版本号 | 用户给定；未给定则按上一条递增 | §二 |
| 发布路径 | **手工构建 + 手工发布**（本地产物同时是 GitHub 与服务器产物） | §四.3 路径 1 |
| 发布说明 | 由 `pnpm release:notes` 生成，禁止手写 | §四.1 |
| 便携包 | 生成并上传（仅 GitHub） | §四.2 |
| 服务器同步 | 执行，三个文件，`latest.yml` 最后 | §五 |
| 公告后台 | 拿到口令就更新，否则记为待办并告知用户 | §六 |
| 安卓 / shared 联动 | 不联动；若 `shared/` 有未推送提交，先推 shared 再更新两处指针 | 推送规范 §1.3 |
| CHANGELOG 内容 | `[Unreleased]` 为空时，按上次 Tag 以来的提交整理，只写用户可感知的变化 | §三.3 |

**必须由用户完成的三件事**（其余步骤执行方负责到底）：

1. **夸克网盘包**：沿用长期分享链接 `https://pan.quark.cn/s/a9853284d260`；若本次重新上传导致链接变化，由用户提供新链接（执行方无法上传网盘）。
2. **公告后台 PC 版本**（§六）：需要管理员口令，它只存在于服务器 `.env`。用户可在 `/admin` 自行修改，或临时提供口令由执行方调用接口。
3. **真机升级确认**：旧版本客户端走完「检查更新 → 下载 → 重启安装」。执行方可驱动到下载完成，重启安装由用户确认。

执行纪律：

1. **显式路径提交**：工作区常有并行改动，只提交本次发布实际改动的路径，绝不 `git add -A`；提交后 `git show --stat` 复核文件清单。
2. **门禁失败不放行**：偶发失败（如渲染层个别用例）先在隔离下复跑，确认与本次改动无关才可放行，并在汇报中写明。
3. **不覆盖已发布版本**：同版本号不得替换资产，修复必须升修订号。
4. **CI 覆盖**：推 Tag 必然触发 `release.yml`（`gh release create` 自动建 Tag 同样触发），手工发布路径必须在发布步骤前取消该次运行，否则资产被 CI 产物覆盖、与服务器文件不再一致。
5. **凭据**：SSH 私钥、服务器 `.env`、管理员口令一律不入库、不写文档、不回显。

### 1. 发布前准备

确认所有目标改动已经完成，并检查工作区：

```powershell
git status --short
git diff --check
```

发布提交中不得混入以下内容：

- `.env`、Token、密码、SSH 私钥、服务器数据库；
- `dist/`、`dist-electron/`、`release-v2/` 等本地构建产物；
- 与本次版本无关的调试文件或个人配置。

### 2. 更新版本号

下一次修订版示例（版本号以实际为准）：

```powershell
pnpm version:patch
```

执行后应显示当前版本 → 下一版本。如果目标版本不是自动递增结果，使用：

```powershell
node scripts/version.mjs set <x.y.z>
```

### 3. 更新 CHANGELOG

将根目录 `CHANGELOG.md` 中 `[Unreleased]` 的内容归档为正式版本，并重新保留一个空的 `[Unreleased]` 区域：

```markdown
## [Unreleased]

## [0.15.2] - 2026-08-26

### 新增

- ...

### 变更

- ...

### 修复

- ...
```

更新日志应描述用户能感知的变化，不记录无意义的文件名罗列。

### 4. 执行发布门禁

```powershell
pnpm install --frozen-lockfile
pnpm check
pnpm lint
pnpm test
pnpm electron:build
```

全部命令通过后，再检查本地安装包：

```powershell
Get-ChildItem release-v2\QingYu-Setup-*.exe, release-v2\*.blockmap, release-v2\latest.yml
Get-Content release-v2\latest.yml
```

必须确认：

- `latest.yml` 的 `version` 等于 `package.json` 版本；
- `path` 和 `files.url` 指向本次安装包文件名；
- `.exe`、`.blockmap`、`latest.yml` 三个文件齐全；
- 在测试机上至少完成一次安装、启动和“检查更新”验证。

打包通过后，再按 §四.2 生成便携包、按 §四.1 生成发布说明（`pnpm release:notes`），两者都是发版必需产物。

如果打包阶段出现 `EPERM ... win-unpacked`，先关闭正在运行的轻语程序和占用 `release-v2` 的资源管理器窗口，确认无进程占用后再清理旧构建目录并重试。不得带着失败的构建结果继续发版。

electron-builder 首次打包需要下载 `winCodeSign` / `nsis` 等二进制。若卡在 `github.com:443` 超时（2026-10-05 实测 `ETIMEDOUT 20.205.243.166:443`），改用镜像重试即可，不影响产物内容：

```powershell
$env:ELECTRON_BUILDER_BINARIES_MIRROR='https://npmmirror.com/mirrors/electron-builder-binaries/'
pnpm electron:build
```

### 5. 提交源代码

先检查即将提交的文件，再用**显式路径**创建发布提交（工作区常有并行改动，`git add -A` 会把别人的改动卷进发布提交）：

```powershell
git diff --stat
git status --short
git add package.json CHANGELOG.md README.md docs/<本次改动的文档> src/<本次改动的源码>
git commit -m "release: v<x.y.z> - <摘要>"
git push origin main
git show --stat HEAD   # 复核提交里只有本次发布的文件
```

推送前再次确认没有密钥和本地构建产物进入提交。

### 6. 创建并推送 Tag

建议先让 `main` 推送及远端检查通过，再创建 Tag：

```powershell
git tag -a v<x.y.z> -m "轻语 v<x.y.z>"
git push origin v<x.y.z>
```

推送 `v*` Tag 后，`.github/workflows/release.yml` 会自动：

1. 校验 Tag 与 `package.json` 版本一致；
2. 执行类型检查、Lint 和全量测试；
3. 构建 Windows NSIS 安装包；
4. 创建 GitHub Release；
5. 上传安装包、`.blockmap` 和 `latest.yml`。

正常情况下不要在本地使用 `electron-builder --publish always`，也不要手动上传一个与 CI 构建内容不同的同版本安装包。

## 四、GitHub Release 格式与验收

### 1. 名称与说明格式

| 项 | 约定 |
|---|---|
| Tag | `v<x.y.z>`，与根目录 `package.json#version` 完全一致（禁止其他前缀或补零写法） |
| Release 标题 | `轻语v<x.y.z>`（**无空格**，沿用历史发布格式） |
| Draft / Pre-release | 均不勾选；正式版必须直接对外可见，且成为 Latest |

Release 说明（正文）固定为**「网盘链接块 + 更新日志」两段**，首行不留任何临时说明：

```text
夸克网盘链接
https://pan.quark.cn/s/a9853284d260

# 更新日志

## [<x.y.z>] - <YYYY-MM-DD>

<该版本在 CHANGELOG.md 中的章节原文>
```

要求：

1. 网盘链接块固定两行：第一行文字 `夸克网盘链接`，第二行链接本身，其后空一行；
2. 标题行用一级标题 `# 更新日志`，版本章节用二级标题 `## [<x.y.z>] - <日期>`，**与 `CHANGELOG.md` 对应章节逐字一致**（直接从仓库复制，不手写、不改写）；
3. 正文只包含上述两段，不写「本次为 PC 端版本」「官方服务器同步下载」之类的临时说明；服务器下载地址由客户端自行读取（见 §一），不需要写进 Release 说明。

生成方式（禁止手抄）：

```powershell
pnpm release:notes                                  # 生成 release-v2/release-notes-<x.y.z>.md
node scripts/release-notes.mjs <x.y.z> --stdout     # 只打印
node scripts/release-notes.mjs <x.y.z> --check <已有说明文件>   # 校验已有正文与仓库章节一致
```

`scripts/release-notes.mjs` 直接从 `CHANGELOG.md` 提取对应版本章节，版本与 `package.json` 不一致时直接报错（预览可加 `--allow-mismatch`）；`--check` 只忽略 CRLF 与末尾空行，其余字符差异一律报错。

修改说明正文（不触碰资产）：

```powershell
gh release edit v<x.y.z> --repo GUAPIXIA/qingyu --notes-file <说明文件路径>
```

### 2. 资产清单

```text
QingYu-Setup-<x.y.z>.exe
QingYu-Setup-<x.y.z>.exe.blockmap
latest.yml
win-unpacked-<x.y.z>.zip      # 免安装便携包
```

便携包由 `release-v2/win-unpacked/` 直接压缩产生（用 electron-builder 自带的 7za，避免 `Compress-Archive` 处理大目录过慢）：

```powershell
$7za = Get-ChildItem "$env:LOCALAPPDATA\electron-builder\Cache\7zip@*\*\bin\7za.exe" | Select-Object -First 1
& $7za.FullName a -tzip -mx=5 "release-v2/win-unpacked-<x.y.z>.zip" "release-v2/win-unpacked/*"
```

**注意**：CI（`release.yml`）只发布 exe / blockmap / latest.yml 三个资产，**不产出便携包**。若本次走 CI 路径又要保留四个资产的格式，需在 CI 完成后用本地同一提交构建的便携包补传：

```powershell
gh release upload v<x.y.z> "release-v2/win-unpacked-<x.y.z>.zip" --repo GUAPIXIA/qingyu --clobber
```

此时便携包与安装包来自两次不同构建（安装包以 CI 为准），必须在发版汇报中说明；要求四个资产完全同源时使用 §四.3 的手工路径。

### 3. 手工发布与 CI 的关系（2026-10-05 实测）

推送 `v*` Tag 会触发 `.github/workflows/release.yml`，其 Windows 作业执行 `electron-builder --win nsis --publish always`，会**用 CI 构建的产物覆盖 Release 上的同名资产**。另实测：用 `gh release create` 让 API 创建 Tag，**同样会触发该 push 事件**（`Spatial Board` 等按路径匹配的工作流也会一并触发）。

因此当本次发布采用**手工上传本地构建产物**（例如为保持 GitHub 与服务器文件完全一致）时，三条路任选其一，选完都必须按 §五 复核 sha256：

1. 在 CI 跑到发布步骤前**取消该次运行**（Release 资产保持手工上传的内容）；
2. 让 CI 正常完成，随后**用 CI 产物重新同步服务器**（最终发布的是 CI 构建版本）；
3. 让 CI 只做校验、不发布（需改工作流，属流程变更，需单独评审）。

手工发布命令：

```powershell
gh release create v<x.y.z> --repo GUAPIXIA/qingyu --title "轻语v<x.y.z>" --notes-file <说明文件> `
  "release-v2/QingYu-Setup-<x.y.z>.exe" `
  "release-v2/QingYu-Setup-<x.y.z>.exe.blockmap" `
  "release-v2/latest.yml" `
  "release-v2/win-unpacked-<x.y.z>.zip"
```

### 4. 验收

发布完成后（CI 或手工），在项目 Releases 页面确认本次版本包含上述四个文件，然后执行：

1. Tag、Release 标题、`latest.yml` 和安装包文件名版本一致；
2. Release 不是 Draft；正式版不应误标为 Pre-release；
3. 安装包可以正常下载和安装；
4. 旧版本客户端在“设置 → 软件更新”中能显示 GitHub 最新版本；
5. 点击“下载更新”后能下载，并能通过“重启安装”完成升级。

正文是否与仓库一致，用脚本核对（不要肉眼比对）：

```powershell
cmd /c "gh release view v<x.y.z> --repo GUAPIXIA/qingyu --json body --jq .body > release-v2/body-from-github.md"
node scripts/release-notes.mjs <x.y.z> --check release-v2/body-from-github.md
```

GitHub 发布失败时，先修复失败原因。若 Tag 尚未形成公开 Release，可在确认安全后重新运行工作流；若错误版本已公开，不要覆盖，提升修订版本重新发布。

以上是 Release 侧的验收项；完整发版清单见 §七，两处如有出入以 §七 为准。

## 五、官方服务器上传规范

服务器源用于国内手动下载。应从已经验收通过的 GitHub Release 获取产物，确保 GitHub 与服务器上的同版本文件完全一致。

### 1. 待上传文件

```text
QingYu-Setup-<x.y.z>.exe
QingYu-Setup-<x.y.z>.exe.blockmap
latest.yml
```

服务器默认持久化目录为：

```text
server/app/data/updates/
```

Docker 部署通过 `./app/data:/app/data` 挂载；如果配置了 `UPDATES_DIR`，以实际环境变量目录为准。

本项目当前部署（2026-10-05 核对，部署变更时同步本表）：

| 项 | 值 |
|---|---|
| 主机 / 用户 | `47.92.7.207`，用户 `admin`（SSH 私钥在本地 `~/.ssh/id_ed25519`，**凭据一律不入库**） |
| 正式目录 | `/opt/tavern-announce/data/updates/`（属 root，移动需 `sudo`） |
| 容器 | `tavern-announce`，挂载 `/opt/tavern-announce/data → /app/data`，监听 `127.0.0.1:3000` |
| 对外地址 | `https://cjbtj.xyz/qingyu/update/`（Nginx 剥 `/qingyu` 前缀转发到 3000） |
| `UPDATES_DIR` | 未设置，以挂载目录为准 |
| 文件权限 | `644`（上传后 `ls -l` 确认） |

历史版本的安装包与 blockmap 保留在同目录（客户端按文件名下载，不读取目录列表），因此不需要清理旧版本文件。

### 2. 上传顺序

必须遵守以下顺序：

1. 上传 `.exe`；
2. 上传 `.blockmap`；
3. 校验文件大小或 SHA-256；
4. 最后上传并替换 `latest.yml`。

`latest.yml` 是客户端看到新版的开关。先替换它会导致客户端发现新版本时安装包尚不存在。

推荐先传入服务器临时目录，再移动到正式目录：

```powershell
scp release-v2/QingYu-Setup-<x.y.z>.exe release-v2/QingYu-Setup-<x.y.z>.exe.blockmap release-v2/latest.yml 47.92.7.207:/tmp/qingyu-update/
```

在服务器上确认临时目录文件正确后，先移动安装包和 blockmap，最后原子替换清单（替换前先备份现有 `latest.yml`）：

```bash
ssh 47.92.7.207 "sudo cp /opt/tavern-announce/data/updates/latest.yml /tmp/qingyu-update/latest.yml.prev; \
  sudo mv /tmp/qingyu-update/QingYu-Setup-<x.y.z>.exe /opt/tavern-announce/data/updates/ && \
  sudo mv /tmp/qingyu-update/QingYu-Setup-<x.y.z>.exe.blockmap /opt/tavern-announce/data/updates/ && \
  sudo chmod 644 /opt/tavern-announce/data/updates/QingYu-Setup-<x.y.z>.* && \
  sudo mv /tmp/qingyu-update/latest.yml /opt/tavern-announce/data/updates/latest.yml && \
  ls -l /opt/tavern-announce/data/updates/ | tail -4"
```

禁止把服务器密码、私钥或管理 Token 写入仓库文档和脚本。自动化部署应使用 GitHub Actions Secrets 或服务器侧受限凭据。

### 3. 服务器验收

```powershell
Invoke-WebRequest https://cjbtj.xyz/qingyu/update/latest.yml -UseBasicParsing | Select-Object -ExpandProperty Content
Invoke-WebRequest https://cjbtj.xyz/qingyu/update/QingYu-Setup-<x.y.z>.exe -Method Head -UseBasicParsing
```

验收要求：

- `latest.yml` 返回 HTTP 200，且内容为本次版本；
- 安装包和 blockmap 均可访问；
- `latest.yml` 响应不被长期缓存；
- 软件设置页分别显示正确的“服务器最新版本”和“GitHub 最新版本”；
- 服务器下载按钮指向官方域名下的本次安装包。

**三处 sha256 一致**是服务器同步的硬性验收项（本地构建产物 = GitHub Release 资产 = 服务器文件）：

```powershell
(Get-FileHash release-v2/QingYu-Setup-<x.y.z>.exe -Algorithm SHA256).Hash
gh release download v<x.y.z> --repo GUAPIXIA/qingyu --pattern "QingYu-Setup-<x.y.z>.exe" --dir release-v2/verify --clobber
(Get-FileHash release-v2/verify/QingYu-Setup-<x.y.z>.exe -Algorithm SHA256).Hash
ssh 47.92.7.207 "sha256sum /opt/tavern-announce/data/updates/QingYu-Setup-<x.y.z>.exe"
```

三个哈希必须完全相同；只要有一个不同，就说明本次发布的三处资产不是同一份构建，必须查明来源后重新对齐（禁止“看起来都对”就放行）。

## 六、公告后台维护规范

完成 GitHub 发布和服务器同步后，再更新公告后台 PC 版本：

| 字段 | 建议值 |
|---|---|
| 最新版本号 | 与 `package.json` 一致，不带前缀 `v` |
| 更新日志 | 本次面向用户的简短摘要 |
| 下载地址 | GitHub Releases 页面或官方备用下载页 |

公告后台 PC 版本号不会参与设置页的双源版本判断，也不会决定自动更新地址，但它会控制左上角的版本提示，因此建议每次正式发布后同步。若暂时不希望左上角提示新版，可以延后修改此字段。

安卓版本号、安卓更新日志和 APK 地址是独立字段。没有发布安卓版本时不要跟随桌面端修改。

维护方式二选一：

1. **浏览器**：访问 `https://cjbtj.xyz/qingyu/admin`，登录后修改（推荐，无需处理口令）。
2. **接口**：`POST /api/auth/login` 取 JWT，再 `PUT /api/version`。`PUT` 是**部分更新**——只提交 `version` / `changelog` / `downloadUrl` 三个字段不会动到安卓字段：

```powershell
# 口令只从环境变量读取，禁止写进命令行历史、脚本或文档
$login = @{ username = 'admin'; password = $env:QINGYU_ADMIN_PASSWORD } | ConvertTo-Json
$token = (Invoke-RestMethod -Method Post -Uri https://cjbtj.xyz/qingyu/api/auth/login `
  -ContentType 'application/json' -Body $login).token
Invoke-RestMethod -Method Put -Uri https://cjbtj.xyz/qingyu/api/version `
  -Headers @{ Authorization = "Bearer $token" } -ContentType 'application/json' `
  -Body (@{ version = '<x.y.z>'; changelog = '<面向用户的简短摘要>'; downloadUrl = 'https://github.com/GUAPIXIA/qingyu/releases/latest' } | ConvertTo-Json)
```

约束（服务端已校验）：`version` 必须是 `x.y.z`（不带 `v` 前缀）；`changelog` 为字符串且 ≤ 50000 字符；`downloadUrl` 必须是 `http(s)://` 链接且 ≤ 2048 字符。连续 5 次登录失败会锁定该 IP 15 分钟。

`ADMIN_PASSWORD` 只存在于服务器 `.env`。执行方不得擅自读取、猜测或索取该口令：能拿到时按上面第 2 条执行，拿不到时把公告后台记为待办并明确告知用户（属 §三.0 的用户参与项）。

## 八、回滚与故障处理

### GitHub 版本有严重问题

不要覆盖同版本文件。立即：

1. 将有问题的 Release 标记为 Pre-release 或从公开入口撤下；
2. 修复问题；
3. 提升修订版本，例如 `0.15.2 → 0.15.3`；
4. 重新走完整发布流程。

已安装的新版本不能仅靠把 `latest.yml` 改回旧版本自动降级。

### 服务器源有问题

如果只是服务器文件损坏，而 GitHub 正常，可临时将服务器 `latest.yml` 移出公开目录，使客户端显示服务器源获取失败；GitHub 检查与自动更新仍可继续使用。修复并验证安装包后，再最后恢复正确的 `latest.yml`。

### 两个来源版本不一致

客户端会分别显示两个版本，这是允许的短暂发布状态。发布顺序建议为：

```text
GitHub Release 验收通过
        ↓
同步官方服务器文件
        ↓
更新公告后台版本
```

不要让服务器 `latest.yml` 宣告一个尚未上传安装包的版本，也不要让公告后台长期高于两个真实下载源。
