## 目标

在不明显增加生成延迟的前提下，提高长期设定、人物关系、事件状态的准确率，并降低重复摘要带来的信息漂移与上下文成本。

当前实现已经具备会话隔离、原子写入、版本校验、编辑后失效、自动总结游标与并发锁等正确性基础。后续优化应聚焦于摘要增量化、上下文分层、事实可维护性与质量评测。

## 总体架构

将对话上下文拆分为四层，各层职责不重叠：

| 层级 | 内容 | 注入策略 | 预算建议 |
| --- | --- | --- | --- |
| 当前状态 | 场景、时间、地点、进行中的任务、即时情绪 | 每轮优先注入，内容短且必须最新 | 5%（上限 240 token，`fitLayeredMemoryBudget` 已实现） |
| 长期事实 | 身份、关系、偏好、承诺、物品归属、稳定设定 | 按相关度、重要性和最近性检索后注入 | 10%（经排序后 Top-N，事实优先于时间线） |
| 时间线摘要 | 已发生的重要事件、转折和因果 | 在需要回顾历史时按预算注入 | 10% |
| 最近原文 | 最近若干轮真实对话 | 始终保留，保证语气与局部上下文连续 | 剩余预算（不低于 60%） |

原则：同一信息只应有一个权威来源。例如，当前地点属于“当前状态”，不要同时在长期事实和时间线摘要中反复出现。

> **动态预算：** 预算占比随 `maxContext` 缩放，同时设绝对上限（state≤240token、fact≤40%剩余、timeline 剩余回补），避免 128k 上下文下单类膨胀。已在 `memory.ts:fitLayeredMemoryBudget` 落地，`contextBuilder.ts` 接入后生效。

## 阶段一：增量摘要与 Token 窗口

> **状态：✅ 已落地**（`memoryWindow.ts:buildMemorySummaryWindow` + `memoryManager.ts:runMemorySummary`），本节保留为实现规格。

### 方案

以 `memoryLastMessageId` 作为真实摘要游标：

1. 找到游标之后尚未总结的消息。
2. 额外携带游标之前最近 2 条消息（`OVERLAP_COUNT=2`，占预算≤25%），作为语义衔接上下文。
3. 按 Token 预算（`MEMORY_SUMMARY_INPUT_TOKEN_BUDGET=6000`）截取待总结内容，而非固定按消息数量截取；首条 pending 即使超限也完整保留，避免游标卡死。
4. 总结完成后一次性更新摘要、事实、游标、版本号、向量版本与更新时间。

### 伪代码（已对齐当前实现）

```ts
const pending = messagesAfter(memoryLastMessageId)
const overlap = messagesBefore(memoryLastMessageId).slice(-OVERLAP_COUNT)
// overlap 预算≤25%，过长旧消息直接略过，避免挤掉新增内容
// selected 始终是 pending 的前缀，首条超长必保留
const { selected, processedThroughMessageId } = buildMemorySummaryWindow(
  messages, memoryLastMessageId, formatMessage, estimateTokens,
)
const result = await summarize({ previousMemory, previousFacts, input: selected })
await updateSession({
  memory: result.summary,
  memoryFacts: result.facts,
  memoryLastMessageId: processedThroughMessageId ?? memoryLastMessageId,
  memoryVersion: previousVersion + 1,
  factsVectors: [],
  factsVectorVersion: 0,
})
```

> **正确性要点：** `buildMemorySummaryWindow` 必须返回 `selected+processedThroughMessageId`，游标推进到 `processedThroughMessageId`，而不是 `pending.at(-1)?.id`。否则预算截断后未送入摘要的消息会被永久跳过，造成记忆空洞。

### 验收标准

- 同一批已总结消息不会再次成为主要摘要输入。
- 长消息不会因固定“消息条数”造成输入预算明显超限。
- 自动与手动总结均能正确推进游标。
- 摘要、事实、游标及版本号始终同时提交（原子写入）。

### 阶段一完成后：立即建立评测基线

> 评测不能等到阶段六才介入。阶段一完成后就应建立最小回归集，否则后续优化是否有效无从判断。

## 阶段三：事实检索排序与预算分配（字符串事实阶段）

> **依赖说明：** 本阶段在字符串事实的基础上做相关度排序与预算裁剪，不依赖结构化事实。结构化事实（阶段四）的 `importance`、`status` 等字段是对本阶段评分的增强，而非前置条件。
> **状态：⚠️ 部分完成**（`scoreAndRankFacts`/`selectFactsByBudget` 已落地，`fitLayeredMemoryBudget:489` 写死 `null` 未透传 `semanticScores`）

### 检索评分（字符串事实版）

对每条候选事实（纯文本）计算综合分数：

```text
score = semanticSimilarity × 0.70
      + recencyScore × 0.30
```

其中：

- `semanticSimilarity`：当前对话与事实的向量相似度；
- `recencyScore`：根据事实最后一次被更新的时间衰减（`updatedAt` 归一化）。

> 本阶段不含 `importanceScore`，因为字符串事实没有重要性字段。阶段四迁移到结构化事实后，评分公式升级为三因子加权：`0.5*semantic + 0.3*recency + 0.2*importance(归一化)`。

### 预算规则

- 优先按评分从高到低选择事实。
- 单条事实超过剩余预算时跳过并继续尝试后续内容，而不是停止整个选择过程。
- 向量不可用或版本不一致时，使用降级方案，不直接全量注入。
- 对每轮实际注入内容记录 Token、来源和评分，便于调试与调参。

### 降级方案细化

向量索引不可用时的降级行为：

| 项目 | 规则 |
| --- | --- |
| 降级触发 | `factsVectorVersion !== memoryVersion`、索引文件缺失、相似度查询异常 |
| 降级排序 | 按 `importance` 降序 + `updatedAt` 降序（字符串阶段则按 `updatedAt` 降序） |
| 降级上限 | 复用预算裁剪（而非固定 Top-10），避免撑爆上下文 |
| 日志标记 | 上下文构建日志标记 `retrievalMode: 'fallback'` |
| 用户通知 | 连续降级超过 3 轮时，在对话页显示“记忆检索降级，建议检查向量索引”提示（设置页可关闭） |

### 验收标准

- 不相关事实不会长期占用上下文。
- 单条超长事实不会阻止短而重要的事实进入上下文。
- 向量索引失效时，仍可获得稳定且可解释的降级结果。
- 降级模式在日志中可追溯。

## 阶段四：结构化事实、来源追踪与冲突处理

> **状态：✅ 已落地核心**（`FactProposal` + 服务端键匹配 + 退避），本节为规格沉淀。
> **依赖说明：** 本阶段在阶段三（字符串事实检索）稳定后实施。结构化事实的 `importance`、`status` 字段是对检索评分的增强，而非检索的前置条件。

### 数据结构

将事实由纯文本迁移为可维护的记录：

```ts
type MemoryFact = {
  id: string
  subject: string
  predicate: string
  value: string
  status: 'active' | 'inactive' | 'superseded'
  importance: 1 | 2 | 3 | 4 | 5
  confidence: number
  sourceMessageIds: string[]
  updatedAt: number
  scope?: string      // 多角色/多分支隔离
  entityId?: string   // 角色卡 ID 优先匹配
}
```

示例：

```json
{
  "subject": "林夏",
  "predicate": "与用户的关系",
  "value": "恋人",
  "status": "active",
  "importance": 5,
  "confidence": 0.9,
  "sourceMessageIds": ["msg_123"],
  "updatedAt": 1723968000000
}
```

### 变更模型

摘要模型不应每次返回整份事实清单，也不应要求模型输出事实 ID（模型容易引用错误或编造 ID）。模型只需输出语义变更描述，由服务端按规范化键匹配后决定 add/update/deactivate：

```ts
/** 模型输出：语义描述，不含 ID */
type FactProposal = {
  subject: string        // 主体（如"林夏"）
  predicate: string      // 属性（如"与用户的关系"）
  value: string          // 新值（如"恋人"）
  changeType: 'set' | 'clear'   // set=新增/更新，clear=失效
  scope?: string         // 作用域（如"本会话"），避免同名角色冲突
  entityId?: string      // 角色卡 ID（多角色场景区分同名）
}

/** 服务端应用：按 subject + predicate + scope 规范化键匹配后生成 */
type FactChange =
  | { action: 'add'; fact: MemoryFact }
  | { action: 'update'; id: string; patch: Partial<MemoryFact> }
  | { action: 'deactivate'; id: string; reason?: string }
```

**ID 生成与匹配规则（已实现于 `memory.ts:factKey`）：**
1. 服务端收到 `FactProposal` 后，按 `subject + predicate + scope + entityId` 组成规范化键（小写+trim）查找现有事实。
2. 键不存在 -> `add`，ID 由服务端生成（`fact-${timestamp}-${index}`）。
3. 键已存在且 `changeType = 'set'` -> `update`，旧值设为 `superseded` 并归档到 `memoryFactHistory`。
4. 键已存在且 `changeType = 'clear'` -> `deactivate`，设为 `inactive` 并归档。
5. 模型不接触 ID，避免引用错误。

冲突处理规则：

1. 相同 `subject + predicate` 出现新值时，比较更新时间、来源与置信度。
2. “已结束、已归还、已失效、已死亡”等事件将旧事实设为 `inactive`，而不是直接删除。
3. 高重要性事实发生变化时，保留旧值的来源，便于调试和解释。
4. 输出不符合结构时，保留旧事实并记录解析失败，不执行破坏性覆盖。

### 解析失败降级与重试（已实现）

当摘要模型输出不符合 `FactProposal` 结构时，不应激进地停止记忆积累，而应分层降级：

| 连续失败次数 | 处理方式 | 记忆状态 |
| --- | --- | --- |
| 1-2 次 | 结构化事实更新暂停，长摘要继续以旧文本格式生成 | 摘要正常推进，事实暂不更新 |
| 3-4 次 | 按指数退避重试（间隔 2 倍递增：`retryAfterVersion = nextVersion + 2^(n-2)`） | 摘要继续，事实继续暂停 |
| 5 次以上 | 结构化事实持续暂停，长摘要仍以旧格式运行 | 摘要不中断，事实暂停 |

**关键原则（已落地）：**
- **长摘要不中断：** 即使结构化事实解析失败，长摘要仍继续生成和推进游标（`memory.ts:parseMemoryResult` 保留旧事实）。
- **指数退避重试：** `memoryFactRetryAfterVersion` 控制下次尝试版本，避免每轮重试。
- **日志而非弹窗：** `logWarn('memory', ...)` 记录；设置页可显示“记忆事实更新暂停”状态。
- **恢复机制：** 下次成功解析后自动重置 `memoryFactParseFailureCount=0`。

### 迁移策略

1. 先兼容读取旧的字符串事实（`isMemoryFact` 区分）。
2. 新生成的事实使用结构化格式（`legacyFactToRecord` 稳定 hash）。
3. 在会话下次总结时逐步迁移旧数据（`normalizeFact`）。
4. 完成迁移后，移除字符串事实写入，但保留导出兼容层。

## 阶段五：编辑、重生成与分支

> **状态：✅ 已落地轻量版** — 游标感知失效 + 乐观锁（`chatUtils.ts:88` / `checkpoint.test.ts:6`），重度增量重算延期

当前编辑或删除消息后清空派生记忆的做法正确且安全。后续可升级为检查点重算：

1. 记录最早发生变化的消息 ID。
2. 找到其之前最近的有效摘要检查点（`memoryVersion` 快照）。
3. 保留检查点之前未受影响的摘要与事实。
4. 从检查点开始重新生成后续摘要、事实和向量。
5. 重生成或切换分支时创建独立记忆版本，避免不同分支污染。

## 移动端影响与同步策略

安卓端 `ChatViewModel.loadSessionInfo` 会读取 `memory` / `memoryFacts`，需配合本方案做同步适配：

| 阶段 | 移动端影响 | 适配方式 |
| --- | --- | --- |
| 阶段一 | 桥接路由 `/sessions/:id/memory/summarize` 必须同步采用增量游标 + Token 截断逻辑（安卓端可通过桥接接口触发手动总结） | 桥接层 `chatService.ts` / `routes.ts` 同步修改；安卓 UI 本身不改 |
| 阶段二 | 无（上下文构建在 PC 端） | 无需改动 |
| 阶段三 | `memoryFacts` 由字符串数组变为 `MemoryFact[]` | 安卓端 `MemoryDto` 类型更新 + 兼容旧格式读取 |
| 阶段四 | 无（检索在 PC 端） | 无需改动 |
| 阶段五 | 编辑后记忆失效信号需同步 | WS `session:updated` 事件携带 `memoryVersion` 变更标记 + `409 TASK_CONFLICT` 复用 `SessionLock` |

### 结构化事实下发格式

桥接层 `/sessions/:id/memory` 端点返回格式升级：

```json
{
  "memoryEnabled": true,
  "memoryMode": "auto",
  "autoMemoryInterval": 10,
  "messageCount": 42,
  "memory": "摘要文本...",
  "memoryFacts": [
    {
      "id": "fact_1",
      "subject": "林夏",
      "predicate": "与用户的关系",
      "value": "恋人",
      "status": "active",
      "importance": 5,
      "confidence": 0.9
    }
  ],
  "memoryVersion": 3,
  "factsVectorVersion": 2
}
```

> **字段对齐：** 保留现有 `memoryVersion`（记忆内容版本）和 `factsVectorVersion`（向量是否与事实版本匹配），不引入 `memoryFactsVersion` 避免双版本概念混淆。

安卓端兼容策略：
- 读取时检查 `memoryFacts[0]` 是否为字符串（旧格式）或对象（新格式）；
- 旧格式按纯文本展示，新格式按 `subject: value` 展示；
- 不在安卓端做事实冲突处理（全部由 PC 端负责）。
