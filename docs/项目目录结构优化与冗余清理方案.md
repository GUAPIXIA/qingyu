# 轻语项目目录结构优化与冗余清理方案

> 生成日期：2026-08-20  
> 当前工作区：`D:\Code\qingyu`  
> 文档性质：目录治理与清理实施方案  
> 原则：先保护代码与历史，再合并分叉，最后清理和重构

## 1. 背景与目标

当前工作区同时包含桌面端、Android 伴侣端、公告服务端、构建产物、依赖缓存、安全审计产物及运维敏感文件。目录中存在多个 Git 仓库和多份已经分叉的源码，直接删除所谓“重复目录”可能造成代码或提交历史丢失。

本方案的目标是：

1. 建立唯一、清晰的项目根目录和 Git 仓库边界。
2. 合并 Android 与 Server 的分叉版本，确保没有代码丢失。
3. 清理依赖、缓存、安装包和临时验证产物。
4. 将敏感配置移出代码工作区，并完善忽略和扫描机制。
5. 逐步将桌面端源码从“按技术类型组织”调整为“按业务功能组织”。
6. 保证清理后的项目可以从全新克隆环境完成安装、测试和构建。

## 2. 当前目录盘点

### 2.1 Git 仓库边界

`D:\Code\qingyu` 本身不是 Git 仓库，当前存在三个独立仓库：

| 仓库 | 路径 | 当前状态 |
|---|---|---|
| 主仓库 | `酒馆/` | `main` 领先 `origin/main` 13 个提交，另有 4 个未提交修改 |
| Android 独立仓库 | `android/` | 工作区干净，但没有配置远端 |
| Server 独立仓库 | `server/` | 工作区干净，但没有配置远端 |

主仓库 `酒馆/` 内又包含一份 `android/` 和一份 `server/`，因此当前形成了两套 Android 和两套 Server 源码。

### 2.2 副本差异

顶层 Android 与主仓库内 Android 并不相同：

- 顶层 Android 有 128 个非生成文件，主仓库内有 104 个。
- 顶层 Android 独有 24 个源码或测试文件。
- 97 个同路径文件内容不同。
- 顶层 Android 包含更新的稳定性、安全、网络生命周期、草稿、分享、搜索、通知和无障碍相关提交。

顶层 Server 与主仓库内 Server 同样存在分叉：

- 顶层 Server 独有本地 `.env`。
- 20 个同路径文件内容不同。
- 差异覆盖安全修复、测试、管理后台、Docker 和文档等内容。

因此，顶层 `android/` 和 `server/` 不能作为普通冗余目录直接删除，必须先完成代码和历史合并。

### 2.3 空间占用

当前主要空间占用如下：

依赖、构建产物、缓存和临时验证内容合计约 1.8 GB，均可以在满足前置条件后清理或重新生成。

### 2.4 敏感和待确认内容

以下内容已被顶层 `.gitignore` 标注为敏感文件：

- `token.txt`
- `conn_pb.bin`
- `服务器备忘.md`
- `server/.env`

其他待确认内容：

- `.poc-tmp/`：包含安全验证 APK，应先确认审计留档需求。
- `piolium/`：安全审计结果，应决定脱敏入库或移至仓库外归档。

## 3. 推荐目标结构

近期建议采用低风险结构，不立即引入复杂的 `apps/packages` Monorepo：

```text
qingyu/                         # 唯一 Git 根目录
├─ .github/                     # CI/CD 工作流
├─ docs/
│  ├─ architecture/             # 架构和设计文档
│  ├─ audits/                   # 脱敏后的审计报告
│  ├─ operations/               # 不含凭据的部署说明
│  └─ assets/
│     └─ screenshots/           # README 和发布截图
├─ src/                         # Electron 渲染进程
├─ electron/                    # Electron 主进程
├─ shared/                      # 跨进程类型与 IPC 契约
├─ android/                     # 唯一 Android 工程
├─ server/                      # 唯一公告服务
├─ scripts/                     # 构建、版本和清理脚本
├─ tests/                       # 跨模块或金丝雀测试
├─ artifacts/                   # 本地构建制品，整体忽略
├─ package.json
├─ pnpm-lock.yaml
├─ pnpm-workspace.yaml
├─ README.md
└─ .gitignore
```

最终应让 `D:\Code\qingyu` 本身成为唯一 Git 根目录，移除当前外层工作区与 `酒馆/` 主仓库之间的多余嵌套。

## 4. 实施阶段

### 阶段一：冻结并保护现有成果

目标：任何后续操作都可恢复。

1. 暂停在三个仓库中并行开发。
2. 为主仓库当前 4 个未提交修改创建独立提交，或暂存到明确命名的 stash。
3. 将主仓库领先远端的 13 个提交推送到远端；如果暂时不能推送，则创建 Git bundle。
4. 分别为顶层 Android 和 Server 创建备份分支、标签及 Git bundle。
5. 将 bundle 保存到项目工作区之外，并验证 bundle 可以列出引用。
6. 记录三个仓库当前 HEAD、分支和工作区状态，作为迁移基线。

建议的备份命名：

```text
qingyu-main-before-layout-20260820.bundle
qingyu-android-before-merge-20260820.bundle
qingyu-server-before-merge-20260820.bundle
```

完成标准：

- 三个仓库的全部提交均存在远端或可验证的离线 bundle 中。
- 主仓库未提交修改已经被安全保存。
- 可以明确指出发生问题时的恢复路径。

### 阶段二：合并 Android 分叉

目标：将顶层 Android 的最新功能和历史纳入主仓库 `酒馆/android/`。

1. 从主仓库创建专用集成分支，例如 `chore/consolidate-android`。
2. 将顶层 Android 仓库作为本地 remote 或 Git subtree 源接入。
3. 合并顶层 Android 的提交，避免直接用文件覆盖方式替换目录。
4. 重点解决以下类型冲突：
   - Gradle 配置和版本号。
   - `AndroidManifest.xml` 与网络安全配置。
   - Room 数据库实体和迁移。
   - 网络、WebSocket、重试和生命周期管理。
   - ViewModel、导航及 UI 状态。
   - 单元测试和安全回归测试。
5. 对合并结果执行完整构建和测试。

验证命令：

```powershell
Set-Location android
.\gradlew.bat testDebugUnitTest
.\gradlew.bat assembleDebug
```

完成标准：

- 顶层 Android 独有的 24 个文件均已纳入或有明确的不纳入说明。
- 97 个差异文件均完成审查。
- Android 单元测试和 Debug APK 构建通过。
- 版本号、CHANGELOG 和 README 一致。

### 阶段三：合并 Server 分叉

目标：将顶层 Server 的安全修复、测试和后台改动纳入主仓库 `酒馆/server/`。

1. 从主仓库创建专用集成分支，例如 `chore/consolidate-server`。
2. 将顶层 Server 仓库作为本地 remote 或 Git subtree 源接入。
3. 合并代码和提交历史，不复制真实 `.env`。
4. 重点审查以下差异：
   - 认证和 JWT 中间件。
   - 输入清理和 XSS 修复。
   - CORS、Helmet 和安全响应头。
   - 公告、版本及认证路由。
   - 管理后台静态页面。
   - Docker Compose、Dockerfile 和 `.npmrc`。
   - Vitest 测试及安全回归用例。
5. 执行单元测试和容器构建验证。

验证命令：

```powershell
Set-Location server\app
npm ci
npm test

Set-Location ..
docker compose build
```

完成标准：

- 20 个差异文件均完成审查。
- 真实 `.env` 没有进入主仓库。
- Server 测试和 Docker 构建通过。
- 版本号、CHANGELOG 和 README 一致。

### 阶段四：执行三端回归验证

在删除任何独立仓库前执行以下验证：

```powershell
# 桌面端
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build

# Android
Set-Location android
.\gradlew.bat testDebugUnitTest
.\gradlew.bat assembleDebug

# Server
Set-Location ..\server\app
npm ci
npm test
```

补充验证：

1. 对顶层 Android 与合并后的主仓库 Android 进行文件清单和哈希比较。
2. 对顶层 Server 与合并后的主仓库 Server 进行相同检查。
3. 对未纳入的文件逐一记录理由。
4. 验证桌面端与 Android 的共享协议、版本号和接口契约保持一致。

### 阶段五：清理冗余目录和生成内容

只有在阶段一至四全部完成后，才删除顶层独立源码副本。

#### 5.1 可直接重新生成的内容

建议清理：

```text
酒馆/node_modules/
酒馆/release-v2/
酒馆/.cache/
酒馆/dist/
酒馆/dist-electron/
android/.gradle/
android/.kotlin/
android/.idea/
android/build/
android/app/build/
server/app/node_modules/
```

清理前应先执行 Git 忽略文件预览：

```powershell
git clean -ndX
```

不要在未经逐项审查时执行：

```powershell
git clean -fdx
```

建议后续增加安全的 `scripts/clean.ps1`，将清理范围写成明确目录列表，并提供：

- `clean:build`：只清理构建产物。
- `clean:cache`：清理缓存。
- `clean:deps`：清理依赖。
- `clean:all`：组合执行，默认先显示预览。

#### 5.2 审计和临时产物

| 内容 | 建议处理方式 |
|---|---|
| `.poc-tmp/installed-companion.apk` | 若审计完成，转移到仓库外归档后删除 |
| `piolium/` | 脱敏后移到 `docs/audits/`，或整体移出仓库 |
| `.trae/` | 确认不再依赖后删除或归档 |
| 顶层 `docs/` | 与主仓库文档合并，按主题分类 |
| `png/` | 移至 `docs/assets/screenshots/` 并进行无损或轻量压缩 |
| `a.txt` | 确认没有脚本引用后删除 |
| `nul` | 检查内容及来源后删除，并修复生成该文件的命令或脚本 |

### 阶段六：建立唯一仓库根目录

推荐使用“新建干净副本并切换”的方式，不建议直接拖动 `.git` 和大量文件。

1. 在阶段二、三合并完成后，确保主仓库分支已提交并备份。
2. 将原工作区重命名为临时迁移备份，例如 `qingyu-migration-backup`。
3. 从合并后的主仓库克隆或复制出干净的 `D:\Code\qingyu`。
4. 仅迁移确认需要保留且不敏感的顶层文档。
5. 不迁移旧的依赖、构建产物、缓存和真实凭据。
6. 在新路径中重新安装依赖并执行三端验证。
7. 保留迁移备份一段观察期，确认稳定后再做最终归档或清理。

完成后，整个工作区只能存在一个 `.git/`。

## 5. 敏感内容治理

### 5.1 移出工作区

以下内容应移入密码管理器、受权限保护的运维目录或加密存储：

```text

conn_pb.bin
服务器备忘.md

```

仓库内只保留：

- `.env.example`

如果凭据曾经上传、共享或进入云盘备份，应立即轮换；仅删除本地文件不能消除泄露风险。

## 6. 桌面端源码结构优化

当前 `src/` 主要按技术类型组织：

```text
src/
├─ components/
├─ pages/
├─ store/
├─ utils/
├─ hooks/
└─ context/
```

随着功能增加，同一业务的页面、组件、store、工具和测试分散在多个目录中。建议逐步调整为功能优先结构：

```text
src/
├─ app/
│  ├─ App.tsx
│  ├─ router/
│  ├─ providers/
│  └─ layout/
├─ features/
│  ├─ chat/
│  │  ├─ components/
│  │  ├─ state/
│  │  ├─ services/
│  │  ├─ utils/
│  │  └─ __tests__/
│  ├─ group-chat/
│  ├─ characters/
│  ├─ character-creator/
│  ├─ lorebook/
│  ├─ presets/
│  ├─ personas/
│  ├─ quick-replies/
│  ├─ settings/
│  ├─ mcp/
│  ├─ announcements/
│  └─ usage/
└─ shared/
   ├─ components/
   ├─ hooks/
   ├─ lib/
   ├─ styles/
   └─ test/
```

### 6.1 迁移顺序

建议按以下顺序逐个功能迁移：

1. `settings`：边界明确，适合作为目录规范样板。
2. `announcements`、`usage`：依赖相对较少。
3. `characters`、`lorebook`、`presets`。
4. `chat` 和 `group-chat`：文件最多、依赖最复杂，最后处理。

### 6.2 依赖规则

建议建立以下约束：

```text
app -> features -> shared
```

- `shared` 不允许依赖任何具体 feature。
- feature 之间默认不能直接导入内部文件。
- 跨 feature 能力通过公开入口或 app 层编排。
- 页面、组件、状态、服务和测试尽量在功能目录内聚。
- 通用工具只有被多个 feature 使用后才进入 `shared`。
- 禁止把暂时不知道放在哪里的代码全部放进 `utils`。

### 6.3 渐进式迁移策略

1. 一次只迁移一个功能。
2. 为旧路径保留临时兼容导出，避免一次修改所有 import。
3. 每次迁移前后执行类型检查和测试。
4. 迁移完成后再删除兼容导出。
5. 每个迁移提交只包含目录调整和必要的 import 修改，避免同时重写业务逻辑。

## 7. Electron 主进程结构优化

当前 Electron 代码按 `bridge`、`chat`、`ipc`、`services`、`mcp` 等技术模块组织，总体可用，但 IPC handler 和业务服务之间应进一步明确边界。

推荐结构：

```text
electron/
├─ app/
│  ├─ main.ts
│  ├─ preload.ts
│  └─ lifecycle/
├─ features/
│  ├─ chat/
│  ├─ characters/
│  ├─ lorebook/
│  ├─ image-generation/
│  ├─ tts/
│  ├─ mcp/
│  └─ companion-bridge/
├─ infrastructure/
│  ├─ storage/
│  ├─ logging/
│  ├─ security/
│  ├─ ai-adapters/
│  └─ networking/
├─ ipc/
│  ├─ handlers/
│  └─ register.ts
└─ shared/
```

调整原则：

- IPC handler 只负责参数校验、权限检查、调用业务服务和返回结果。
- 文件系统、加密、网络、数据库和模型适配器归入 infrastructure。
- 主进程和渲染进程共享的类型继续放在根 `shared/`，避免双份定义。
- `electron/chat` 与 `src/store` 中的聊天流程需要明确职责，避免两套状态机逐渐分叉。

## 8. 文档和制品规范

### 8.1 文档分类

```text
docs/
├─ architecture/      # 架构、协议、数据流
├─ decisions/         # ADR 架构决策记录
├─ development/       # 本地开发、测试、发布流程
├─ operations/        # 脱敏部署说明
├─ audits/            # 脱敏安全和质量报告
└─ assets/            # 文档使用的图片
```

文档中不得包含：

- 真实域名后台密码。
- JWT secret、API token、私钥。
- 可直接使用的生产连接字符串。
- 个人账号和服务器登录凭据。

### 8.2 构建制品

建议将桌面构建输出从 `release-v2/` 统一到：

```text
artifacts/
├─ desktop/
├─ android/
└─ server/
```

`artifacts/` 整体不进入 Git。正式安装包、APK 和镜像应由 CI 上传到 GitHub Release、容器仓库或专用制品库。

## 9. 建议拆分的实施提交

为降低审查和回滚成本，建议拆成以下提交或 PR：

1. `chore(repo): backup and document repository baseline`
2. `chore(android): consolidate standalone Android repository`
3. `chore(server): consolidate standalone announcement server`
4. `chore(repo): remove duplicate repositories and generated artifacts`
5. `chore(repo): flatten canonical repository root`
6. `chore(repo): harden gitignore and secret scanning`
7. `docs: reorganize project documentation and screenshots`
8. `refactor(settings): migrate settings to feature structure`
9. 后续逐功能迁移的独立提交或 PR

不要把代码合并、目录平铺、缓存删除和业务重构放入同一个巨大提交。

## 10. 风险与回退方案

| 风险 | 预防措施 | 回退方式 |
|---|---|---|
| 删除了顶层独有代码 | 合并前做哈希差异清单和 Git bundle | 从 bundle 恢复仓库或分支 |
| 主仓库未提交修改丢失 | 先提交或 stash，并记录状态 | 恢复提交或 stash |
| Android 合并后数据库不兼容 | 审查 Room schema 和 migration，运行升级测试 | 回退 Android 集成提交 |
| Server 安全修复被旧代码覆盖 | 逐文件审查安全相关差异和回归测试 | 回退 Server 集成提交 |
| 平铺目录导致构建路径失效 | 使用全新干净副本验证，不直接覆盖旧目录 | 切回迁移备份目录 |
| 删除依赖后无法重装 | 保留锁文件并验证 registry 配置 | 从缓存恢复或重新安装 |
| 凭据仍存在历史或备份中 | 扫描历史并轮换凭据 | 吊销旧凭据并签发新凭据 |
