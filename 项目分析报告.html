2.2 资源泄漏

高 已修复 TTS stdout 监听器累积泄漏 electron/ipc/tts.ts:102-107, 158
初始化时添加的监听器 resolve 后未移除；每次 sendCommand 又添加新监听器。长时间运行后，stdout 上可能挂载数十个监听器，每次输出都触发所有监听器，内存与 CPU 泄漏。
已修复：ensureProcess() 中 init 监听器命名为 onInitData，resolve 和超时路径均调用 psProcess?.stdout?.off('data', onInitData) 移除。

已修复：4 个适配器均已用 try { while(true){...} } finally { try { reader.releaseLock() } catch {} } 包裹。
中 已修复 MCP 客户端监听器未清理 electron/mcp/client.ts:62-87, 155-167

三、架构评估

3.1 整体架构

项目采用 Electron + React 标准三层架构：

  • 渲染进程（src/）：React 18 + Zustand 5 + react-router-dom 7（HashRouter），UI 用 Tailwind CSS 3，虚拟滚动用 react-virtuoso
  • 主进程（electron/）：14 个 IPC 模块 + 服务层（AI 适配器、存储、生图、TTS、MCP）
  • 服务端（server/）：可选独立部署的公告系统，Express + better-sqlite3 + JWT
  • 共享层（shared/）：types.ts 类型定义 + ipc-api.ts IPC 契约

整体分层清晰，技术栈选型合理。但存在以下架构问题：

与 useChatStore.streamAIResponse（:225 调用 cleanupActiveStream()）不同，streamGroupAI 和 streamGroupAIFree 在创建新流前未清理旧的 activeStream。模块级 activeStream 变量被覆盖（:734/:863），但旧流的 unbindChunk/unbindDone/unbindError 函数丢失，IPC 监听器永远不会被移除。如果两次流式请求重叠（如超时触发后新的 sendPollingRound 开始），第一个流的监听器永久泄漏。
修复方案：在 streamGroupAI（:603）和 streamGroupAIFree（:785）开头添加 cleanupActiveStream()，与 useChatStore 保持一致。
严重 未修复 群聊 translateMessage 使用 stream:false 但注册流式监听器 src/store/useGroupChatStore.ts:265-313
IPC 调用（:293）发送 stream: false，但代码注册了 onChunk/onDone/onError 流式监听器。对于非流式响应：onChunk 永远不会触发，result 保持为空字符串；onDone 触发时 result 为空，finalResult = result || null 返回 null。翻译功能完全静默失败，用户看到加载动画后什么都没有。
修复方案：改为 stream: true，或处理非流式响应路径（从 chat() Promise 返回值读取结果）。
严重 未修复 file:readImageBase64 安全验证被绕过（validatedPaths 从未检查） electron/ipc/file.ts:13,27,42-46
validatedPaths Set 在 selectImage 时填充（:27），但 readImageBase64 中从未调用 .has() 检查。唯一验证是文件扩展名（:42），任何渲染进程可读取磁盘上任意 .png/.jpg/.jpeg/.gif/.webp 文件（路径穿越漏洞）。即使文件不是真正的图片（如将敏感数据重命名为 secret.png），也能被读取为 base64 回传。
修复方案：在 readImageBase64 中添加 if (!validatedPaths.has(filePath)) throw new Error('Path not validated')，或改用白名单机制。
严重 未修复 translatePromptToEnglish 读取加密凭据作为明文使用 electron/ipc/imageGen.ts:25-33
translatePromptToEnglish 直接 readJson 读取 credentials.json，该文件存储的是 Buffer.from(encrypted).toString('base64')——base64 编码的密文。代码将密文作为 API Key 放入 Authorization: Bearer 头，导致中译英功能完全失效（始终返回 401）。应使用 getCredential() 从 services/safeStorage.ts 解密。
修复方案：改用 import { getCredential } from '../services/safeStorage'，调用 getCredential(profile.id) 获取解密后的密钥。
严重 未修复 服务端无全局错误处理——DB 异常泄漏堆栈 server/app/server.js（全局）
缺少 Express 错误中间件（4 参数 (err, req, res, next)）和 process.on('uncaughtException')/process.on('unhandledRejection') 处理。better-sqlite3 是同步的，任何 DB 异常（损坏、I/O 错误、磁盘满）都会抛出。在开发模式（NODE_ENV 未设置）下，Express 默认错误处理器会将完整堆栈和内部文件路径发送给客户端。匿名用户可触发此行为获取服务器目录结构。
修复方案：添加 Express 错误中间件（返回 500 + 简短错误消息）；添加 process.on('uncaughtException') 日志记录 + 优雅退出；设置 NODE_ENV=production。
严重 未修复 req.body 未校验——POST/PUT 缺少 Content-Type 直接崩溃 server/app/routes/announcements.js:72, auth.js:61, version.js:32
当请求不带 Content-Type: application/json 头时，express.json() 不解析 body，req.body 为 undefined。所有路由处理器直接解构 req.body 导致 TypeError: Cannot destructure property of undefined。攻击者可绕过 /api/auth/login 的限流（崩溃发生在凭据检查之前）。开发模式下错误详情泄漏给匿名用户。
修复方案：添加 body 存在性校验中间件：if (!req.body) return res.status(400).json({ error: 'Invalid content type' })；或在每个路由开头添加 guard。

8.2 高危级（HIGH）— 尽快修复

高 未修复 sendMessage onComplete 竞态——允许并发状态变更 src/store/useChatStore.ts:296,774-838
streamAIResponse 中 isStreaming 在 :296 设为 false，然后 :298 调用 onComplete(fullContent)。onComplete 执行多个异步操作（正则应用、消息保存、记忆摘要、图片生成）。由于 isStreaming 已为 false，用户可发送新消息，新消息的 sendMessage 与旧 onComplete 交叉执行，导致：消息双重保存、get().messages 读取过时状态、重复记忆摘要。
修复方案：添加 per-request 锁（类似 loadRequestId），或延迟设置 isStreaming: false 直到 onComplete 完全完成。
高 未修复 deleteCurrentSession 状态不一致——listSessions 失败后 src/store/useChatStore.ts:484-497
deleteSession 成功后调用 listSessions，若后者抛异常，会话已从磁盘删除但 store 状态仍引用已删除会话。UI 显示过时数据，后续对已删除会话的操作全部失败。
修复方案：用 try/catch 包裹 listSessions，失败时从当前 sessions 数组过滤掉已删除的会话。
高 未修复 useChatStore.translateMessage IPC 监听器泄漏 src/store/useChatStore.ts:1024-1119
translateMessage 注册 onChunk/onDone/onError IPC 监听器，仅在 onDone/onError 触发或 .catch() 时清理。如果：(1) 用户在翻译进行中切换页面；(2) 快速点击多条消息的翻译；(3) 后端从未发出 done/error 事件——监听器永久累积，每个泄漏的监听器保持对 set()/get()/result 的闭包引用，阻止 GC。
修复方案：用模块级 Map（以 messageId 为键）存储 unbind 函数，新翻译开始前清理旧的；添加超时兜底。
高 未修复 服务端分页参数无界——可被匿名用户 DoS server/app/routes/announcements.js:9-11,26-28
pageSize 无上界：?pageSize=999999999 强制 DB 返回数亿行到内存，同步阻塞事件循环。pageSize=-1 是 truthy 值，LIMIT -1 在 SQLite 中返回全表。page 无边界，负值产生大负 offset（SQLite 静默从头返回）。任何匿名用户可轻松触发 DoS。
修复方案：添加 const pageSize = Math.min(Math.max(parseInt(req.query.pageSize) || 20, 1), 100)；page 类似处理。
高 未修复 服务端缺少 trust proxy——限流器失效或可绕过 server/app/server.js + routes/auth.js:54
Docker 部署暴露端口 3000，反向代理后所有请求 req.ip 显示代理 IP。per-IP 限流器变为全局限流（一人失败登录锁定所有人），或若 trust proxy 配置不当，X-Forwarded-For 可伪造绕过限流。
修复方案：根据部署环境设置 app.set('trust proxy', 1) 或 app.set('trust proxy', 'loopback')。
高 未修复 CSP 全局禁用——XSS 可窃取 admin JWT server/app/server.js:14
helmet({ contentSecurityPolicy: false }) 对整个应用禁用 CSP，包括 API 端点和管理后台。管理后台将 JWT 存储在 localStorage，任何 XSS 漏洞（如公告内容中的恶意 Markdown）可直接窃取 admin 会话。CSP 应仅对 /admin 静态文件有条件启用。
修复方案：将 CSP 中间件限定到 /admin 路径，或使用 contentSecurityPolicy: { directives: { ... } } 配置白名单。
高 未修复 公告内容存储型 XSS server/app/routes/announcements.js:72-92
title/content/summary 字段原样存入 SQLite，零过滤。管理后台用 escapeHtml() 渲染列表，但客户端（AI 角色扮演客户端）几乎肯定以 HTML 渲染 Markdown 内容。任何脚本标签、事件处理器或 data URI 会在客户端上下文中执行。管理员账号被攻破后可攻击所有用户。
修复方案：服务端用 sanitize-html 过滤存储内容；或客户端移除 rehypeRaw 改用纯 Markdown 渲染。
高 未修复 Electron 主进程无 uncaughtException/unhandledRejection 处理 electron/main.ts（缺失）
整个 Electron 主进程零 process.on('uncaughtException') 或 process.on('unhandledRejection') 处理器。代码库充满异步操作（MCP 子进程、网络请求、文件 I/O），任何未处理的 rejection 或非 IPC 异步上下文中的抛出错误将静默崩溃主进程，无恢复、无日志、无用户通知。
修复方案：在 main.ts 顶部添加：process.on('uncaughtException', (err) => { logger.fatal('Uncaught exception', err); app.exit(1) }) 和 process.on('unhandledRejection', (reason) => { logger.error('Unhandled rejection', reason) })。
高 未修复 before-quit 处理器可能留下僵尸 MCP 进程 electron/main.ts:130-138
before-quit 处理器无条件调用 event.preventDefault()，等待 MCP 关闭最多 3 秒，然后 app.exit(0)。若 shutdownAll() 超时，MCP 子进程仍在后台运行成为孤儿。app.exit(0) 跳过 will-quit/window-all-closed 等事件，依赖这些事件的清理代码不会执行。
修复方案：超时后对未响应的进程发送 SIGKILL（而非仅 SIGTERM）；使用 app.quit() 替代 app.exit(0) 以触发完整关闭流程。
高 未修复 announcement:httpGet 无 SSRF 防护 electron/ipc/announcement.ts:40-55,110-112
httpGet 向任意 URL 发起 HTTP 请求，setServerUrl（:110）接受任意字符串无校验。恶意 URL 如 http://169.254.169.254/latest/meta-data/ 可查询云元数据，http://127.0.0.1:6379/ 可与本地服务交互。项目已有 isSafeUrl() 函数（utils/pathGuard.ts:49）但从未被调用。
修复方案：在 httpGet 和 setServerUrl 中调用 isSafeUrl(url) 校验。
高 未修复 MCP stdout 缓冲区无大小限制——内存耗尽 electron/mcp/client.ts:61-73
buffer 变量在 setupStdioHandlers 中累积所有 stdout 数据，仅在换行符处裁剪。若 MCP 服务端输出不含换行符（如发送二进制数据或超长单行 JSON），缓冲区将无限增长，最终耗尽 Node.js 内存导致主进程崩溃。
修复方案：添加 if (buffer.length > 1024 * 1024) { buffer = ''; return; } 上限守卫。
高 未修复 McpManager 单例初始化与目录创建竞态 electron/mcp/manager.ts:10,16-18
mcpManager 单例在模块导入时创建（:152），构造函数立即调用 readJson(CONFIG_FILE)。但 CONFIG_FILE 依赖 DIRS.config()（即 app.getPath('userData')），而 main.ts 中 ensureDataDir() 在导入之后才运行（:69）。首次启动时配置目录不存在，readJson 返回 null（静默处理）。但若存在文件系统错误或权限问题，构造函数可能在 logger 初始化前抛出未处理崩溃。
修复方案：将 mcpManager 改为延迟初始化（lazy singleton），在 ensureDataDir() 之后创建。

8.3 中等级（MEDIUM）— 排期修复

中 未修复 群聊 round 计算可能产生 NaN src/store/useGroupChatStore.ts:345-347
若消息的 round 字段为 undefined（数据迁移场景），Math.max(undefined, 0) 返回 NaN，currentRound 变为 NaN。NaN 传播到 GroupMessage.round，在 checkPollingContinue（:979）中 rounds.size >= group.maxRounds 永远不满足（NaN rounds 永远不等于阈值），导致轮询永不停止。
修复方案：添加 fallback：Math.max(...state.messages.map(m => m.round ?? 0), 0) + 1。
中 未修复 loadMessages 问候消息可能保存到错误会话 src/store/useChatStore.ts:631-679
loadMessages 中 sessionId 是局部变量，异步 listSessions 后使用。在 listSessions 和后续 listMessages 之间，另一个操作（如 switchSession）可能改变 currentSessionId。currentLoadId 检查（:652）丢弃过时结果，但 sessionId 局部变量用于 saveMessage（:673），可能将问候消息保存到错误会话。
修复方案：currentLoadId 检查通过后，重新从 state 读取 currentSessionId 并验证与局部 sessionId 匹配。
中 未修复 群聊轮询定时器页面导航后不清理 src/store/useGroupChatStore.ts:996-1001
pollingTimer 是模块级变量，在 stopStreaming()/deleteGroup()/selectGroup() 中清理，但不在组件卸载时清理。用户在自动轮询模式下导航到其他页面，定时器继续触发 sendPollingRound 在后台流式输出 AI 响应。虽然 zustand store 正确更新，但 UI 不显示流式状态，用户返回时可能看到意外消息。
修复方案：在组件级 useEffect cleanup 中清理 pollingTimer。
中 未修复 translateMessage onDone 保存时可能丢失 tokenUsage src/store/useChatStore.ts:1072-1075
翻译 onDone 回调中 set() 后调用 get().messages.find() 保存消息。若在翻译 set() 和 get() 之间有另一个 set()（如 onUsage），消息可能有额外字段。虽然 zustand get() 返回最新状态，但多次 set() 的交叉可能导致数据不一致。
修复方案：在 set() 回调参数中直接构建要保存的消息对象，而非后续 get() 读取。
中 未修复 useCharacterStore.importPng 监听器可能双重触发 src/store/useCharacterStore.ts:142-161
importPng 在 finally 中用 setTimeout(() => { unbind(); set({ importProgress: null }) }, 2000) 延迟清理。若用户快速触发两次 importPng，两个 onImportProgress 监听器同时挂载。第一个的 unbind 在 2 秒后调用，但第二个监听器仍活跃，导致双重状态更新。

中 未修复 GroupChatPage useEffect 缺少 characters 依赖 src/pages/GroupChatPage.tsx:70-80
开场白选择器的 useEffect 使用 characters（来自 useCharacterStore）但未将其加入依赖数组。若 characters 异步加载（App.tsx:27 的 loadCharacters 是 async），effect 不会在 characters 加载完成后重新运行，可能错过开场白选择器触发。
